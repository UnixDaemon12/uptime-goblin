# Contributing

Contributions are accepted under the project's [AGPL-3.0 license](LICENSE). No formal support channel or release schedule is promised.

The [engineering quality and security policy](docs/engineering-quality.md) applies to every Uptime Goblin repository, branch and worktree. Security, accurate documentation, complete changelogs and readable code are requirements throughout development. Automated checks and independent review are both required; neither proves that all defects are absent.

## Work locally

Use Node.js 24+ and npm. Install with `npm ci --ignore-scripts`; start with `npm start`. Keep all real configuration in the ignored data directory, and use only generic identities in committed fixtures.

During development, run focused checks to find problems early: Prettier (`npm run format`; CI runs `format:check`), `npm run check` (`node --check` over `deploy/manifest.txt` and its imports, plus `bash -n` on the installer), the SQL and import lints, every suite (`npm test`; browser, Docker, systemd and upgrade tests skip when unavailable, and the audit log capacity measurement unless asked for) and the production dependency audit:

```sh
npm run format
npm run check
npm run lint:sql
npm run lint:imports
npm test
npm audit --omit=dev
```

`npm run lint:sql` and `npm run lint:imports` check the server modules' SQL and import rules; `npm run check` and the CI test jobs do not run them, and the gate below runs them only once its `candidate-policy` and `platform-manifest` checks have passed: the commit and release gates then, but the CI security scan never for a 1.5 commit, because on a CI runner `platform-manifest` cannot pass (the gate approvals and reviewed baselines it needs are kept only in a local repository), so CI runs neither lint; run both yourself. `TEST_REQUIRE=browser,fixtures,docker,systemd` makes those suites fail instead of skipping when their dependency is missing, `git` does the same for the tests that run Git (the documentation, security gate, commit guard, finalization, SonarQube and packaging tests, and the 1.4.3 web app update test), which skip with the reason `git is not installed (TEST_REQUIRE=git makes this fail)` where there is no Git, such as the git-less `node:24-bookworm-slim` container (Git is a development tool and stays out of the shipped image), while a `git` that is present but broken, or a repository it cannot read, fails them whatever `TEST_REQUIRE` says (as it fails the upgrade suite's release tag reads; the release tags and development milestones come from the private history input that `TEST_HISTORY` names, never from the checkout, and a missing input or tag skips the 1.4.3 build, 1.4.2 fixture, export, upgrade, installer and sign-in tests and the 1.4.3 web app test unless `TEST_REQUIRE` lists `history`, while the notification policy test drops its 1.4.3 check whatever `TEST_REQUIRE` says; see [the private historical qualification](docs/engineering-quality.md#the-private-historical-qualification)), and `capacity` adds the 250,000-entry audit log measurement (`test/audit/capacity.test.mjs`), which otherwise always skips, and holds the 30-day chart from history summaries to a p95 within 10 ms (`test/series/summaries.test.mjs`, whose 5-times-faster-than-the-readings check runs in every run): before a release, run `TEST_REQUIRE=browser,fixtures,systemd,docker,capacity,git npm test`; the focused scripts are `test:fast`, `test:browser`, `test:upgrade`, `test:installer` and `test:docker`. CI runs them as separate jobs on Ubuntu/Node 24, with the production dependency audit. An audit finding requires review; a clean audit is not a security guarantee. Inspect skipped or unavailable cases explicitly: focused checks and an `npm test` run with skips do not satisfy the commit or release gate.

Every container a test starts gets finite `--memory`, `--cpus` and `--pids-limit`, right after `docker run` or `docker create` and nowhere else before the image, since Docker keeps the last value given (a Compose service: `mem_limit`, `cpus` and `pids_limit`); `test/docker-limits.test.mjs`, part of `test:fast`, fails on a Docker call without them, or with one given again. Start docker from a test module by name, with an argument array, calling `spawnSync` and the like or a `(...args)` wrapper, and name every program a test spawns in a literal (or review it there). That test reads every file below `test/`: any other file (a shell stand-in, whatever its name, mode or first line) fails it on a line that mentions docker, however it is quoted or escaped, unless the line is reviewed there; so does, in a test module, docker named by a path anywhere, or docker in a literal the module hands to another program or to code it runs (`sh -c`, `env`, `node -e`, `eval`), unless that literal is reviewed. What it cannot read (a Compose file, a command line read from a file or built at run time) meets the guard `test/setup.mjs` puts first on `PATH` (`test/helpers/docker-guard.mjs`), which refuses a container or a Compose service without the limits before Docker sees it, wherever docker runs by name on that `PATH`; neither check sees such a line run docker by a path, or on a `PATH` the test sets without the guard. Every test file fails where the guard cannot run (a `TMPDIR` mounted `noexec`). A test does not assume what filesystem the temporary directory is on (in a container it can be a FUSE or virtiofs bind mount), and waits for the event it needs, not for a fixed time; on a fake clock it also fixes any random wait (the delivery service's `rng: () => 1`). A test that checks a memory, CPU or cgroup figure passes the value in instead of reading the machine running it. Where Git is missing (the Node 24 container), the upgrade tests take tagged releases from `TEST_TAG_TREES`, exported on a host with Git by `test/upgrade/export-tag.mjs` (its header shows the run); the upgrade tests that need Git itself (the two that run that export, and the fixture test that compares against the `v1.4.2` tag) skip there, or fail when `TEST_REQUIRE` includes `history`, not `git`; the tests named above for `git` skip there too, and fail only when it includes `git`.

The documents follow the same rule. A `docker run` or `docker create` in the code of a Markdown file outside `test/` (a fenced block or inline code), or in a command line of the comments of the Compose files and `.env.example` (`#` and three blanks), gives finite `--memory`, `--cpus` and `--pids-limit` right after the subcommand, `--pull=never` before the image, and no more than 1 GiB, 2 CPUs and 256 processes unless the test lists why; a Compose command that makes a container reads only `compose.yaml`, `compose.secret.yaml` and `compose.override.yaml`, which keep each service's `mem_limit`, `cpus` and `pids_limit` finite. `test/docs-install-changelog.test.mjs` fails otherwise (B39).

A test that can run on one platform only (Linux, macOS, or the T8 driver's container) gets no platform check or skip of its own: list it in `test/platform-manifest.json` (a stable id, its exact file and test name, its platforms, runtimes, prerequisites and the runs that must execute it) and register it with `platformTest()`, or a subtest with `platformSubtest()`, from `test/helpers/platform.mjs`. It is then registered only on its platform and absent elsewhere, never skipped, and a missing prerequisite there fails it. A test that asserts one thing on Linux and another on macOS becomes one platform subtest per platform. `node scripts/check-platform-coverage.mjs` checks a run's TAP and records against the manifest: absence is never a pass. Removing an entry, or narrowing its file, name, platforms, runtimes, prerequisites or runs (or a run's pinned image), loses coverage and needs a reviewed disposition, and deleting the manifest is refused, also after a commit made without the commit guard ([coverage accounting](docs/engineering-quality.md#coverage-accounting-on-15)). Browser tests start Chrome through `test/helpers/cdp.mjs`, which gives Chrome a home folder inside its throwaway profile. On macOS with Chrome 154 that was measured to keep every file Chrome writes, its crash database included, in the profile; on Linux the same settings should do so through Chrome's `HOME` and `XDG_*` folders, which is not measured yet. A new tool or test must not write into your home folder either.

A new runtime file under `lib/` or `public/` must be listed in `deploy/manifest.txt`: the installer, Docker image and packaging install exactly that list, and `npm run check` fails on an unlisted import. After editing `public/`, restart Uptime Goblin, because it reads the web app once at startup.

## Change expectations

- Agree file ownership and preserve unfinished work. Use small, cohesive changes with clear names and explicit failure behavior. Explain important invariants and tradeoffs, and avoid unrelated formatting or abstraction.
- Preserve unavailable values as missing, never fabricate a zero to fill a chart.
- Treat pause, cancellation, configuration edits and per-source history as lifecycle behavior that must remain consistent.
- Keep collectors read-only apart from session authentication. Add no service control actions, automatic discovery or credential scraping.
- Normalize numeric measurements on the server. Never return raw source responses, passwords, API tokens, cookies, session IDs or client/media identities.
- Use bounded HTTP requests, verified TLS and redirect rejection. Validate inputs without echoing secrets in errors.
- For a new integration, supply a sanitized representative fixture, positive and failure cases, permission requirements, metric units, and a documented compatibility limit. Describe which versions were actually tested live, if any.
- Test behavior and failure modes, not only lines of implementation. Include meaningful regression and positive controls for security fixes, concurrency, cancellation and recovery. Mail tests must inject a fake transport and never send messages.
- Never listen on 4317, Uptime Goblin's default port, in a test: an Uptime Goblin run with its defaults, or another test's, may hold it. Start Uptime Goblin with `port: 0` (`createApp`, `startOrbit`) or a `PORT` from `freePortSync()` (`test/helpers/net.mjs`), and test a first native install with `makeFreshHost` (`test/installer/helpers.mjs`). `test/setup.mjs` fails a test that listens on 4317, and the installer tests' stand-in for Uptime Goblin refuses that port.
- Keep dependencies exact and update the lockfile deliberately. Use lifecycle scripts only after explicit review.
- Check the documentation impact of every commit using the [change mapping](docs/engineering-quality.md#documentation-and-changelog-ownership), update the affected guides and the Unreleased changelog, and record documents checked unchanged. Use `example.com` domains and fictional identities throughout docs. Separate implemented behavior from plans, release approval and deployment.

A useful change description explains the problem, resulting behavior, checks performed and remaining limitations. Avoid unrelated formatting or dependency upgrades.

## Before every commit

```sh
node scripts/security-gate.mjs commit
```

Validate an immutable snapshot of the complete staged candidate, including documentation and tests, and obtain independent review of that same tree. Start the gate with `node` as shown, not with `npm run security:commit`: npm would put the worktree's `node_modules/.bin` first on `PATH` and pass an `.npmrc`'s `node-options` to the gate itself ([why](docs/engineering-quality.md#every-commit)). The [evidence requirements](docs/engineering-quality.md#evidence-tied-to-the-candidate) bind the tree and file manifest to commands, runtime/tool versions, logs, findings and exact pass/fail/skip counts. On 1.5 the gate also runs the two lint commands, `node scripts/sql-lint.mjs` and `node scripts/import-graph.mjs` (which `package.json`, in the canonical form Prettier writes for it, must name as `lint:sql` and `lint:imports`), and its full test runs set `TEST_REQUIRE=browser,fixtures,systemd,docker,capacity,git`. In the platform contract's draft, not yet reviewed, the gate removes every inherited `TEST_*`, `UPDATE_GOLDEN` and `NODE_TEST_CONTEXT` before any stage, checks each full test run against `test/platform-manifest.json`, and a candidate with that manifest also needs a companion run on the other platform (`node scripts/security-gate.mjs platform <run-id>`), named after the run when you finalize it; the run, the review and the finalization are bound to the candidate's complete parent vector, so conclude a merge with `git merge --no-commit` and then `git commit`, as the commit guard refuses an automatic merge ([details](docs/engineering-quality.md#the-gates-side-of-the-platform-contract)). The gate refuses an `.npmrc` in the snapshot, tracked or left by an earlier stage, and a `node_modules/.bin` entry there that would replace a command an npm stage starts, or a `node_modules/.bin` it cannot list (the shell still runs commands from an execute-only one); it runs each npm stage with empty user and global npm configuration, so no setting in your own `.npmrc` (a registry or proxy among them) applies there. The commit guard refuses a candidate that removes or renames either lint script once a parent of the commit or the history behind it defines it, judged by what npm reads in the candidate's `package.json` whatever its layout (a deleted or unparseable one defines neither): doing that on purpose needs a reviewed update of the installed guard ([1.5 adoption](docs/engineering-quality.md#evidence-tied-to-the-candidate)). Whatever candidate code the gate starts runs with your privileges, and nothing contains it: today that is the two lint sources (once `candidate-policy` and `platform-manifest` pass), and the candidate's dependencies, scripts and tests once their authorities exist and they are no longer withheld. So review every change the gate would run, not only the gate and the lint sources. Test the supported and development runtimes as required by the matrix, and run a platform-only test on its platform: a local skip stays a skip. Confirm that the eventual commit has the validated tree and parents. The installed guard refuses `git commit --amend`, which would give the commit other parents than those approved: make a new commit instead. Until the qualified golden-tool manifest binds an Actionlint pin, every gate run is pending and exits 1, naming the missing pin and the evidence it needs; no other Actionlint stands in for it, a local golden-tool record included, and no finalization is a pass, a maintenance one included. A commit or release run of the draft does not start its two image builds either: until the record of what a build may use before it runs is defined and reviewed, both builds and the checks of the built image stay pending. Nor does it start its full test runs, whose Docker tests build images with no such record, its npm install and audit stages (no qualified host listener; the registry is no fallback), the Semgrep image (not approved), `docker version` or the T8 image inspect (no reviewed rules for those Docker commands): each is recorded pending with why, and the CI security scan builds no image either. Before any of it, the gate starts no candidate code at all unless `candidate-policy` and `platform-manifest` both passed in that run ([details](docs/engineering-quality.md#the-gates-side-of-the-platform-contract)).

After the run, follow the [exact-finding review and finalization procedure](docs/engineering-quality.md#review-and-finalize-a-completed-commit-run). The commit guard checks the retained raw reports, tests and supporting evidence; an acknowledgement or scanner exit alone is not approval. On 1.5 the finalized run must also carry each lint stage the guard requires of the candidate, and the 1.5 finalizer requires both.

This full gate applies to every commit, including documentation-only changes and merges. A missing entry point, unavailable scanner, skipped required integration, failed job or missing evidence blocks completion. Do not use a focused run, a production-only dependency audit or an older successful result as a substitute. Any edit after validation requires the candidate gate to run again. See the policy's [adoption status](docs/engineering-quality.md#evidence-tied-to-the-candidate) before assuming a branch implements every stage.

## Before sharing

Follow the [source-only packaging guide](docs/security.md#preparing-a-source-only-upload) and the [history publication policy](docs/engineering-quality.md#safe-history-for-github). A redacted Uptime Goblin export still contains infrastructure details and is not a public fixture. Preserve complete commits, tags and attribution; scan all history reachable from the branches and tags intended for GitHub, including files later deleted. Never rewrite history, delete tags or force-push automatically to resolve a finding. `.gitignore` does not remove already tracked or historical content.

Run `npm run package` only after the source/docs are ready, then review the generated source tree and hash manifest. Review the exact file list and diff. Before publishing a package, run:

```sh
node scripts/security-gate.mjs release
```

The [final release checklist](docs/engineering-quality.md#final-release-validation) requires a fresh full gate, independent review, an audit of all documentation and exact-artifact validation, including the built container, vulnerability/secret scans, SBOMs, signatures and provenance. Keep unresolved findings and unavailable checks visible; they are not passing results. Packaging, testing and release approval do not authorize a public push or production deployment.
