# Security and privacy

[Back to Uptime Goblin](../README.md) · [Security reporting](../SECURITY.md) · [Installation](installation.md)

## Trust boundary

Uptime Goblin is a trusted-administrator application. Its login grants the ability to configure endpoints reachable from the server and use stored credentials. It has no separate viewer/admin roles, per-source access control, MFA enrollment, built-in TLS server or managed secret vault. Host allowlisting and request-origin checks do not make public exposure appropriate. Admins are accountable through the [audit log](#audit-log): Uptime Goblin records every sign-in and every configuration and security change, with who made it and from where, and **Check integrity** shows whether the record was edited since.

Use a unique Uptime Goblin password and private HTTPS access. Keep the listener/proxy path restricted. Browsers sign in on Uptime Goblin's page and then carry a session cookie, which is as good as the password while it lasts; Uptime Goblin issues it only over HTTPS through a trusted proxy or to a browser on the Uptime Goblin computer itself, unless you allow plain HTTP with `GOBLIN_INSECURE_HTTP_SESSIONS=1`, which sends the password at each sign-in, as well as the cookie, over the network in clear ([signing in](authentication.md#https-cookies-and-plain-http)). Legacy HTTP Basic for scripts protects no password against network inspection unless the connection itself is encrypted, so on the plain-HTTP (`http`) transport Uptime Goblin accepts it only under that same opt-in, `GOBLIN_INSECURE_HTTP_SESSIONS=1` (otherwise 403 `https_required`, before the password is checked). The exception is a proxy on the Uptime Goblin computer that sends no forwarding headers and keeps a loopback Host: Uptime Goblin takes its requests for the Uptime Goblin computer's own (the `loopback` transport), so Basic through it is accepted with no opt-in and no warning in the log, also from clients that reach the proxy over plain HTTP. Make such a proxy send `X-Forwarded-For` and `X-Forwarded-Proto` and name it in `GOBLIN_TRUST_PROXY` ([legacy Basic](authentication.md#scripts-and-legacy-basic)). Nothing turns that opt-in on for you where the network can see it. The [native installer](installation.md#native-debian-or-ubuntu-lxc) stops an install that would listen on the network without a trusted proxy until systemd would give Uptime Goblin a yes or no (in `/etc/uptime-goblin.env`, a drop-in or its own environment) or you run it with `--allow-insecure-http`, and it stops every install whose `/etc/uptime-goblin.env` holds the line that earlier 1.5 pre-release installers added by themselves until you decide ([plain HTTP and the installer](authentication.md#https-cookies-and-plain-http)). Docker Compose turns it on by itself only while it publishes Uptime Goblin's port on the Docker host's loopback (its default): published on another address, with neither `GOBLIN_TRUST_PROXY` nor `GOBLIN_INSECURE_HTTP_SESSIONS` in `.env`, Uptime Goblin refuses to start (exit status 78) until you choose ([Docker Compose](installation.md#docker-compose)). While it is on and Uptime Goblin is reachable from the network, the log warns at every start and every signed-in page shows the plain-HTTP banner. While it is on and Uptime Goblin listens (or Compose publishes it) on loopback only, the log warns at every start too when `GOBLIN_TRUST_PROXY` names a proxy or `GOBLIN_ALLOWED_HOSTS` a host that is not loopback: a proxy there that relays sign-ins over plain HTTP is accepted under the same opt-in. Uptime Goblin always requires the admin password, also on loopback: it refuses to start without `auth.json` or `GOBLIN_PASSWORD`, and without a credential every request but the sign-in page, its files, the sign-in itself and `/health` gets 401 ([a password is always required](authentication.md#a-password-is-always-required)).

### Failed sign-in throttling

Every password check, including the bootstrap `GOBLIN_PASSWORD`, runs the salted scrypt hash, so guesses cost real work. The first five failed attempts from a client are free. Each failure after that locks the client out (even with the correct password) for 1 second, doubling with every further failure up to 15 minutes. IPv4 clients are counted per address and IPv6 clients per /64 network, because one client normally controls a whole /64. On a home or office network, though, every IPv6 device usually takes its address from the router's one /64, and those devices are then one client: they share one lockout (one device's failures lock out the others' sign-ins and scripts), one place in the list of addresses trusted during a guessing attack (below: a correct password from one of them makes them all trusted), and, when they connect to Uptime Goblin directly, one allowance of open connections (`GOBLIN_MAX_CONNECTIONS_PER_CLIENT`, 32 by default). A reverse proxy that `GOBLIN_TRUST_PROXY` names does not separate them for the lockout or the trusted list, since Uptime Goblin counts each client by the address the proxy forwards, an IPv6 one by its /64 too. To keep them apart, reach Uptime Goblin over IPv4, where each address is a client of its own; for the connections alone, reaching Uptime Goblin through a proxy that `GOBLIN_TRUST_PROXY` names (it has no such allowance) or raising `GOBLIN_MAX_CONNECTIONS_PER_CLIENT` is enough. If 50 or more failed password checks happen across all clients together within 10 minutes (an attacker spreading guesses over many addresses), Uptime Goblin then accepts sign-in attempts, and password changes (which check the current password), only from addresses that used the correct password within the last 30 days; everyone else gets 429 without a password check. Only a correct password makes an address trusted (a sign-in, a password change, or a script's Basic); a session cookie used from an address keeps that address trusted if a password already made it so, and never makes a new one trusted, so a stolen or lost device's cookie gives its addresses no way around the pause, before or after it is signed out. Those refusals are not counted. The pause ends as soon as fewer than 50 failures remain in the rolling 10-minute window; further failures from trusted addresses can extend it. A restart clears both this failure window and the list of known addresses. Parallel guesses get no more checks than sequential ones: checks already running count toward a client's free attempts. At most two password checks run at once and a few more wait briefly in line. A client's own parallel attempts refused as busy count as failures, so they cannot be used as free guesses; a refusal because other clients filled the line does not count against the client that was turned away, since no password of its own was checked. An attacker with very many addresses can still slow down new sign-ins; trusted addresses remain subject to their own per-client lockouts. The global pause never applies to a sign-in from the Uptime Goblin computer itself (the `loopback` transport: no proxy and no forwarding headers, for example through `ssh -L`), which remains your way in during an attack; the per-client lockout still applies to it, under a key of its own (`loopback`, not an address), so no forwarded header can lock it, and neither can the clients of a proxy that `GOBLIN_TRUST_PROXY` names and that sends forwarding headers: one that does not name its clients in `X-Forwarded-For` makes them share the proxy's address instead (and the log says so once an hour). A reverse proxy on the same host that follows the documented recipe sends forwarding headers and is named by `GOBLIN_TRUST_PROXY=loopback`, so its clients are never `loopback`; the `loopback` transport also needs a loopback Host (`localhost`, `127.x.x.x`, `[::1]`), so a proxy that sends no forwarding headers but forwards the browser's host name is `http` for that name, and a browser sign-in through one that keeps `Host: 127.0.0.1` from a page at another address is refused. **Unless `GOBLIN_TRUST_PROXY` names it (`loopback`), every request that connects to Uptime Goblin from a loopback address (127.0.0.0/8 or `::1`) counts against the `loopback` key**, whatever its Host or forwarding headers say: Uptime Goblin believes nothing such a proxy says about its clients, so through a proxy on the Uptime Goblin host that connects to Uptime Goblin at a loopback address and that `GOBLIN_TRUST_PROXY` does not name, a remote client can lock out the ssh tunnel. It cannot get a second lockout, and so more guesses, by asking for another Host or adding a forwarding header. (A proxy on the Uptime Goblin host that connects to Uptime Goblin's own network address, with `HOST=0.0.0.0`, arrives from that address and is counted by it, like a proxy on another host.) A correct password with the `loopback` key (through the tunnel, from a script on the host or through such a proxy) also clears the failures counted against it, those of a remote client behind such a proxy included. The global pause always holds those requests, except the ones that are the `loopback` transport, whatever password any request with that key proved: off the `loopback` transport, the `loopback` key never counts as an address that used the correct password. **A proxy on the Uptime Goblin host that sends no forwarding headers at all goes further**, trusted or not: Uptime Goblin cannot tell its requests that keep a loopback Host from the host's own, whatever page address (`Origin`) they carry, so they are the `loopback` transport, with the `loopback` key, and the global pause does not hold them. With `GOBLIN_TRUST_PROXY=loopback` such a proxy is trusted: the key of its other requests comes from the forwarding headers it passes on, as for any trusted proxy, and a proxy that sends none of its own passes on whatever the client wrote. The log names such a proxy once it relays a request under a Host that is not a loopback one, or one from a page at a `GOBLIN_ALLOWED_HOSTS` name ("A reverse proxy on this computer sends Uptime Goblin requests without any forwarding header…"); one that relays only requests that keep a loopback Host and come from no such page (a script's Basic or `Bearer` request, say) is never named. Make every proxy on the host send `X-Forwarded-For` and `X-Forwarded-Proto`, and name it in `GOBLIN_TRUST_PROXY`. A restart clears a lockout, after which the tunnel signs in again.

Requests with a session cookie are never throttle-checked and never counted, so browsers already signed in keep working during a lockout or a guessing attack. A browser request (one carrying `Sec-Fetch-Site` or `X-Goblin-Client`) never has its `Authorization` header checked or counted: a browser that still remembers 1.4.x's Basic login cannot lock anyone out where it sends those headers, over HTTPS and on the Uptime Goblin computer itself. To a plain-HTTP address on the network (not `localhost`, `127.x` or `[::1]`) browsers send no `Sec-Fetch-Site`, so while legacy Basic is on, a request the browser makes there on its own (a typed address, a link, an image, another site's included) is checked like a script's wherever Uptime Goblin accepts Basic over plain HTTP, and a wrong remembered password counts: with the plain-HTTP opt-in (`GOBLIN_INSECURE_HTTP_SESSIONS=1`, or Docker Compose's default on a loopback port), and through a proxy on the Uptime Goblin host that sends no forwarding headers and keeps a loopback Host, where it counts against the ssh tunnel's lockout (`loopback`) ([legacy Basic](authentication.md#scripts-and-legacy-basic)). Per-address rate limiting at the proxy only trims bursts from one address; against many addresses, restrict who can reach Uptime Goblin at all (a VPN, an allowlist or client certificates).

Every sign-in on Uptime Goblin's page and every password change checks the password in full, and a correct one clears that client's count. On the sign-in page a wrong password always counts, the one you just replaced included: after a change, a browser or phone whose password manager still fills in the old password gets the same lockout as any other client (five free failures, then 1 second, doubling up to 15 minutes), so update saved logins first. Those failures also count toward the global 50 in 10 minutes. Scripts using legacy Basic are handled as in 1.4.x: once a script's password has been checked, Uptime Goblin remembers it, so its later requests are not full checks and do not clear the count, and for a day after a change (until Uptime Goblin restarts) a script's old password is refused without counting, so a forgotten integration cannot lock you out. After an hour without failures the count is forgotten, and a restart clears all counts.

Behind a reverse proxy every request arrives from the proxy's address, so without further configuration one attacker's failures would lock out everyone. Set `GOBLIN_TRUST_PROXY` to tell Uptime Goblin which peer is your proxy: `loopback` (or `1`) for a proxy on the same host, or a comma-separated list of proxy addresses or CIDR ranges. Uptime Goblin then uses the last `X-Forwarded-For` entry, but only on connections that come from those addresses; anyone else is keyed by their own address (anything that connects from a loopback address as `loopback`, see above) and cannot choose a key. The proxy must set `X-Forwarded-For` (see the [nginx example](installation.md#https-trust-and-network-access)).

An authenticated administrator can change the shared login password under **Configure → Account**. The current password is required, so someone using an unattended signed-in browser cannot change it; the browser holds only the session cookie, never the password. Guard the password and lock your computer. The login name remains `admin`. A successful change signs out every other session and invalidates the old password for Basic scripts; this browser's session is replaced by a new one. There is no unauthenticated password-reset endpoint.

## Sign-in sessions

- **Cookies.** Over HTTPS the cookie is `__Host-goblin_session` with `Secure; HttpOnly; SameSite=Strict; Path=/`; on the `loopback` transport and with `GOBLIN_INSECURE_HTTP_SESSIONS=1` it is `goblin_session` without `Secure`. A request reads only the cookie of its own transport, so a cookie set over plain HTTP (by another site on the same host, whose cookies are not isolated by port) cannot take the place of the secure one. Each session also records the transport it signed in over and is accepted only as that transport's cookie: a session secret that crossed the network over plain HTTP is never accepted as `__Host-goblin_session`, and a start with `GOBLIN_INSECURE_HTTP_SESSIONS` off deletes every session signed in over plain HTTP. Two cookies of the transport's name refuse the request (`multiple_credentials`), so a cookie tossed in from a parent domain cannot fixate a session. Such a cookie (set by another port of the same host, a site on a parent domain, or anyone who can inject a response over plain HTTP) cannot keep a session alive either: signing in, signing out and the HTTPS end of a plain-HTTP session look up every cookie value of Uptime Goblin's names the request carries (up to 256, more than a browser sends), not only a single one, and a sign-out sent with two cookies of the transport's name still ends every session among them and expires Uptime Goblin's own cookie. The other site's cookie stays (Uptime Goblin cannot know its domain or path), so the sign-out answers 200 with code `multiple_credentials` and the sign-in page says to remove this site's cookies. "Keep me signed in" adds `Max-Age`; without it the cookie lasts until the browser ends its session, which a browser that reopens your previous tabs may not do when it closes.
- **Other ports.** Browsers do not separate cookies by port. Uptime Goblin's cookie is sent to every service at the same host name, whatever its port (`__Host-goblin_session` to every HTTPS port, `goblin_session` to every port, over HTTP and HTTPS), and the server of any of them can read it from the request and act as you until the session ends (`HttpOnly` hides it only from page scripts, and `SameSite=Strict` does not help: another port of the same host is the same site). Give Uptime Goblin a host name of its own. At `http://localhost` (Docker Compose's default, the ssh tunnel), every local web app you open in the same browser receives Uptime Goblin's cookie: use a separate browser profile for Uptime Goblin, or sign out when you are done.
- **Transport.** Uptime Goblin decides HTTPS only from `X-Forwarded-Proto` (or `Forwarded: proto=`) sent by a proxy named in `GOBLIN_TRUST_PROXY`; the `Host` header never decides. The browser's `Origin` can only make Uptime Goblin refuse a sign-in (`proxy_proto_mismatch`), never weaken a cookie.
- **Secrets.** The session secret is 32 random bytes; `control.sqlite` stores only its SHA-256 and a public id (`s_…`) that the sessions list shows. A session never contains the password, and no log line, API answer or snapshot contains a cookie value.
- **Lifetimes.** 12 hours without use for every session; at most 7 days, or 30 days with "Keep me signed in". Automatic dashboard refreshes do not count as use (on a page opened with `?kiosk=1`, no read does), and a session is written to at most once a minute. A [wall display](authentication.md#wall-displays) signed in with a display code is the exception: it can only read the dashboard, every request it makes counts, and it ends after 7 days without one, and after 30 days at most (`GOBLIN_DISPLAY_IDLE_DAYS`, `GOBLIN_DISPLAY_SESSION_DAYS`). The idle limit ends a session nobody uses. Whether a request is use is up to the request (Uptime Goblin's page marks its automatic refreshes `X-Goblin-Activity: background`), so a cookie that someone else keeps using does not go idle: it stays valid until its 7- or 30-day limit. End it with **Sign out** in the sessions list, **Sign out other devices**, or a password change ([a stolen session](#sign-in-sessions), below). Sign-in rotates the session: a new id and secret every time, and every session cookie the browser presented is ended, however many it sent.
- **Revocation.** Signing out, **Sign out** in the sessions list, **Sign out other devices**, a password change, an imported password, a snapshot restore and a restored backup of the data directory ([below](#state-and-backups)) delete the sessions at once (signing in or out over HTTPS also ends every plain-HTTP session the same browser still presents, whose secret crossed the network in clear, even beside another cookie of the same name: someone who captured that cookie over plain HTTP can also inject more); a request already waiting (for example a save queued behind another) is refused before it runs or is answered from a stored reply. When the delete cannot be written (a full or failing disk) the session is refused at once all the same, but only by the running Uptime Goblin: the answer says the sign-out was not recorded (503 `storage_full`, or 500), and trying again deletes it. A browser signing itself out keeps its cookie until Uptime Goblin has recorded the sign-out, because that cookie is the only way the browser can name its session: the cookie no longer signs in, but pressing **Sign out** again with it deletes the session (and, over HTTPS, the plain-HTTP session it ended too), and so does signing in again from that browser. **Sign out other devices** also deletes every session signed out that way. Uptime Goblin retries hourly and once more when it stops, and if the rows are still there at the stop the log says "Uptime Goblin could not remove N signed-out sessions from control.sqlite (…), so they are accepted again after Uptime Goblin starts", with what to do.
- **A stolen session.** A session can end only sessions that signed in no later than it did (a script's Basic, which proves the password with every request, ends any). A cookie taken from a lost device, by malware, or on the network over plain HTTP proves only that its holder has the cookie, so it cannot end a newer sign-in, however often it sends **Sign out other devices**; otherwise it could end each of your sign-ins before you could sign it out or change the password. Nor does it go idle while its holder keeps using it: it lasts until its 7- or 30-day limit (lifetimes, above). The way out never needs the Uptime Goblin host: sign in again (a sign-in comes after every session there is, even if the clock was set back), then use **Sign out other devices**, and change the password if the cookie's holder could also know it. Without the password the cookie's holder can neither sign in again nor change it. Until you sign in again it can still end your older sessions; signing in again answers that too. Once it is signed out it ends nothing more: a **Sign out other devices** it sent that Uptime Goblin was still reading ends only the sessions it had already signed out, and one whose request Uptime Goblin had not acted on yet (still waiting for its body, say) ends none.
- **Cross-site requests.** Every change made with a session cookie, and every sign-in, needs `X-Goblin-Request: 1`, a JSON body and an `Origin` whose host equals the request's `Host` or is one of the `GOBLIN_ALLOWED_HOSTS` names; `Sec-Fetch-Site` must be `same-origin` when present. Any request with a session cookie whose `Sec-Fetch-Site` is `same-site` or `cross-site` (an image or script another app under the same parent domain, or another port of `localhost`, makes the browser load) is refused with 403 `cross_origin` before the session is read: it neither answers nor counts as use, so such a page cannot keep an idle session signed in. A typed address or bookmark (`none`) is allowed. Browsers send `Sec-Fetch-Site` only over HTTPS and to `localhost`, `127.x` and `[::1]`, so sessions at a plain-HTTP address on the network (`GOBLIN_INSECURE_HTTP_SESSIONS=1`) lack this check. The configuration and audit exports need `X-Goblin-Request: 1` and, when sent, an `Origin` naming the request's `Host`, with a session cookie or Basic, on every transport (403 `cross_origin`, before the export is built or its audit entry written): wherever the browser sends no `Sec-Fetch-Site` (at a plain-HTTP address on the network, not `localhost`, `127.x` or `[::1]`: Uptime Goblin's own, or that of a proxy on the Uptime Goblin host that sends no forwarding headers and keeps a loopback Host, which is the `loopback` transport; and over HTTPS from a browser too old to send it) a load that another site's page starts and that carries the browser's remembered 1.4.x Basic login looks like a script's, and the custom header is what another site's page cannot send. Uptime Goblin never sends `Access-Control-*` headers.
- **One credential per request.** A request presenting two credentials (for example a session cookie and a script's `Authorization`) is refused, never decided by order. A browser's `Authorization` header does not count (see above).
- **Answers without sign-in** are JSON with a `code` (such as `signin_required` or `session_expired`). Only requests without browser headers (neither `Sec-Fetch-Site` nor `X-Goblin-Client`) get `WWW-Authenticate: Basic`, while legacy Basic is on, and not on the plain-HTTP (`http`) transport without the plain-HTTP opt-in (`GOBLIN_INSECURE_HTTP_SESSIONS=1`, or Docker Compose's default on a loopback port), where Basic is refused. So a browser is never asked for Basic where it sends `Sec-Fetch-Site`: over HTTPS, and to `localhost`, `127.x` and `[::1]` (on the Uptime Goblin computer itself, and at `http://localhost:4317`, where Docker Compose's default publishes the port). To a plain-HTTP address on the network (not `localhost`, `127.x` or `[::1]`) it sends none, so one that opens an API address there while it is not signed in gets the challenge and may show its own Basic prompt wherever Uptime Goblin accepts Basic there: with the plain-HTTP opt-in, and through a proxy on the Uptime Goblin host that sends no forwarding headers and keeps a loopback Host (the `loopback` transport, with no opt-in and no warning in the log: make such a proxy send `X-Forwarded-For` and `X-Forwarded-Proto` and name it in `GOBLIN_TRUST_PROXY`). Scripts such as `wget` need that challenge before they send Basic.

## Public health check and version headers

`/health` answers without signing in so that Docker, the installer and external monitors can check Uptime Goblin without a password. It reveals nothing about your lab: the answer is `{"status":"ok"}` (or 503 `{"status":"stopping"}` during a stop), with no version, source names, states or counts. It still requires an allowed Host, like every other request. `?instance=<value>` adds only `"instance": "match"` or `"mismatch"`: the value is compared with the per-start nonce in the private `run/status.json` in constant time and never echoed, so the answer proves which process is serving without disclosing the nonce.

Every answer given after the Host allowlist, refusals and the sign-in page included, carries `X-Goblin-Build`, which open pages use to notice an update; `/health` and refused hosts do not. The build is therefore visible before sign-in, as it already was in the page's `<meta name="orbit-build">`: the sign-in page must load without signing in, and hiding the build would gain nothing. Only signed-in answers carry `X-Goblin-Version`. Restricting who can reach Uptime Goblin at all (a VPN, an allowlist or client certificates) remains the stronger protection.

## Credentials and integrations

- Keep API keys/passwords in Uptime Goblin's private settings, never in destination URLs, source names, screenshots, fixture files or shared logs.
- Destination links refuse credential-like query parameters and fragment parameters, also beside empty or valueless fields, after a route (`#/home&access_token=…`) and in a text directive (`#intro:~:text=…&access_token=…`). Startup removes parameters with such names from older saved links without logging them, even if their values are harmless. Ordinary SPA routes and anchors stay allowed, and a route's own query (`#/callback?x=1&access_token=…`) is the application's: it is not checked. This check cannot find every secret in an arbitrary URL.
- Use dedicated accounts/tokens and the narrowest supported resource/read permissions. A read-only collector can still hold an excessively privileged credential.
- Protect powerful media API keys where a service offers no read-only key. Restrict network access as a separate control.
- Do not expose an unrestricted Docker socket/API. Use a restricted inventory proxy; Uptime Goblin needs no Docker daemon socket mount.
- Rotate a leaked credential at its issuer and replace it in Uptime Goblin. Removing a file from the current checkout does not erase previously published history, logs or archives.

Configuration and database directories use restrictive modes, and the native/Docker runtime is nonroot. Stored source and SMTP secrets are plaintext on disk protected by filesystem access (in 1.5 only the webhook's private signing key is sealed, below); backups require the same care and preferably encryption. Anyone with appropriate host/data access can read them. Configuration and password saves create a fresh, exclusively opened temporary file with mode 600 before replacing `config.json` or `auth.json`; an occupied temporary path is left untouched. Invalid JSON stops startup with a parse error that includes only safe numeric line and column information when available, never configuration text or credential fragments.

A sudden crash during a save may leave a mode-600 `config.json.<UUID>.tmp` or `auth.json.<UUID>.tmp` file in the private data directory. These can contain credentials or a password hash; protect them like configuration and backups. The next start of Uptime Goblin 1.5 or later removes them (and `created-by.json.<UUID>.tmp`) while it holds `goblin.lock`, before anything is saved, and logs only their names: such a save never completed and nothing reads the file. Orbit 1.4.x leaves them; under 1.4.x, do not bulk-delete these files without checking whether another process still owns them.

Everything Uptime Goblin reads back from its data directory is treated as input: a hand edit, a restored backup or a damaged disk decides what is there. `config.json` must be UTF-8 (other bytes refuse the start instead of becoming U+FFFD inside a value such as a password); a member name given twice, or `__proto__`, is logged by its place (never its value), the last value is used and the file is saved without it. A FIFO, socket or directory in place of a file Uptime Goblin reads at start (`config.json`, `auth.json`, the key files, `control.sqlite`, `history.sqlite`, `goblin.lock`, a restore's journal) or beside a database (its `-journal`, `-wal` or `-shm` file, which SQLite opens by name), and a symbolic link to nothing or a loop of links in place of a database, `goblin.lock` or `snapshots/`, refuses the start (exit status 78) instead of holding it or creating a new database through the link; such a `snapshots/`, or anything else there that is not a directory, makes `goblin-admin snapshots`, `snapshot`, `migrate --apply` and `restore-snapshot` refuse with the start's message (exit status 78, nothing written but `goblin.lock`), and `goblin-admin status` report it (`Snapshots: PROBLEM: …`) instead of no snapshots or an interrupted restore; `goblin-admin check-data` refuses (exit status 78), as the start does, a `history.sqlite` (or its `-journal`, `-wal` or `-shm`) that is not a regular file or a link to one, instead of reporting no history database and no drift; `goblin-admin restore-snapshot` refuses, changing nothing but `goblin.lock`, when a file it would set aside is not a regular file; `goblin-admin snapshot`, and the snapshot a migrating start or `goblin-admin migrate --apply` takes, refuse (exit status 78) before any of the snapshot is written when a file they copy is not a regular file or a link to one: a FIFO, a directory, a loop of links or a symbolic link to nothing (read as absent, a link to nothing was recorded so, and restoring that snapshot once the volume was mounted again moved the live file out of the data directory), also when every file of the data directory is such a link (`migrate --apply` took that directory for an empty one and migrated it without a snapshot); `history.sqlite` left out with `--no-history` is recorded as left out, so a restore keeps it; a snapshot manifest that is not a regular file of at most 1 MiB lists that snapshot as invalid. Of a restore's journal, only the names of the four files a restore replaces are read: any other name in it is ignored. Text from saved data that reaches the log or `goblin-admin` output (a time zone being repaired, a fence or migration row, `run/status.json`, snapshot folder and file names, the file names of a snapshot `restore-snapshot` keeps apart, the keyring's key ids and purposes in `key status` and `key rotate`, table, trigger and view names, and SQLite's reason for a damaged database, which quotes the database's own table and column names, in a start's failure, `snapshots --verify`, `restore-snapshot` and any `goblin-admin` command's failure) is printed without control characters and cut to one line. The JSON that `goblin-admin --json` prints holds no control character, line or paragraph separator or text-direction embedding, override or isolate as it is: a line feed, carriage return, tab, backspace or form feed is written `\n`, `\r`, `\t`, `\b` or `\f`, and any other of them as a `\u` escape. In it, a key id or purpose, a fence's name and release, a migration id, a snapshot, file, table, trigger or view name, SQLite's reason for a database `restore-snapshot` moved aside, and the key id of a journal line `verify-audit` could not check are values of their own and whole, so parsing the JSON gives them back as saved; the `run/status.json` fields in `status --json`, and the sentences that quote such text (`problems` in `check-data` and `snapshots --verify`, `refusal` in `status` and `migrate --plan`), are cut and without those characters, as in the text output; and a command that fails says why in text, with `--json` too. `goblin-admin status`, the healthcheck and the installer never read `run/status.json` through a symbolic link, a linked `run/` directory included, and `status` shows only the fields Uptime Goblin writes there. A trigger or a view in `control.sqlite` or `history.sqlite`, which Uptime Goblin never creates, refuses the start (exit status 78, `schema_planted`; a trigger would run inside Uptime Goblin's own writes), and a snapshot holding one is not restored; so does any other entry of their catalog that is not a table or an index as SQLite writes one (SQLite runs a trigger whose entry spells its type `TRIGGER`, or `trigger` followed by a NUL, like any other), and `goblin-admin check-data` reports each (exit status 1). A notification or reading that `control.sqlite` or `history.sqlite` holds damaged is skipped (a notification is marked failed with "could not read") instead of stopping delivery or the dashboard. A start sets `config.json` to mode 600 when others could read it (not through a symbolic link, whose target is yours to choose) and warns when other users can enter the data directory.

The Uptime Goblin login password saved under **Configure → Account** is different: private `auth.json` contains a versioned, salted scrypt hash, not the password, and `control.sqlite` holds the same hash. It is written atomically with mode 600 and overrides the environment bootstrap password. An invalid saved authentication file stops startup instead of silently falling back. The bootstrap `GOBLIN_PASSWORD` remains in the private deployment environment, so protect that file too. Configuration exports never include the authentication hash. Password recovery requires host-level operator access and a stopped-service backup; see [recovery instructions](troubleshooting.md#forgotten-uptime-goblin-password).

Saved source credentials are never sent to a different server without being re-entered: changing a source's collection address to another scheme, host or port requires typing the credential again (or clearing it) in the same save or connection test. Paths on the same origin may change freely.

Public settings and export remove service `apiKey`/`password` and SMTP `password`, replacing secrets with configured flags. They still expose usernames, sender/recipient addresses, endpoints, labels and topology. Redacted does not mean anonymous. Review the actual export before sharing; do not publish it as an example configuration.

## Encryption key and sealed secrets

Uptime Goblin seals the secrets it keeps in `control.sqlite` with data keys, which are themselves wrapped by one encryption key (see [the encryption key](installation.md#encryption-key) for its sources). In 1.5 the sealed secrets are the webhook's private signing key and the [ntfy and Gotify](notifications.md#tokens-and-passwords-are-write-only) tokens and password; source and SMTP credentials are not sealed yet.

- **Custody.** Keep the key outside the data directory (the native installer's `/etc/uptime-goblin/secret.key`, root:uptime-goblin 0440, or a Compose secret) and back it up apart from the data: whoever holds both holds the secrets. A `secret.key` that Uptime Goblin generated in the data directory travels with every copy of it, and each start warns so; so does a key file inside the data directory that `GOBLIN_SECRET_KEY_FILE` names (or that a Compose secret is mounted from), and Uptime Goblin then says to copy the key out of it first, never to delete the file it still reads. A systemd credential belongs in a file only root can read (`LoadCredential=`, as in `/etc/credstore`) or encrypted in a file (`LoadCredentialEncrypted=`); the `goblin-admin` key commands then run in a transient service that loads the same file ([with a systemd credential](installation.md#goblin-admin)), never with the file made readable by `uptime-goblin`. `SetCredentialEncrypted=` works for Uptime Goblin too, but has no file for that way: encrypt the key to a file instead. `SetCredential=orbit-secret-key:<key>` keeps the key in plain text in a drop-in that every local account can read (`systemctl edit` writes mode 0644), so the installer warns about it, as it does about `GOBLIN_SECRET_KEY` in `/etc/uptime-goblin.env`. The key is never logged, shown or sent: only its 16-character fingerprint (the installer names a `SetCredential=` line only by its setting, `SetCredential=orbit-secret-key:…`).
- **The environment.** `GOBLIN_SECRET_KEY`, `GOBLIN_SECRET_KEY_PREVIOUS` and `GOBLIN_PASSWORD` are removed from Uptime Goblin's environment as soon as they are read, so programs Uptime Goblin starts never inherit them. `/proc/<pid>/environ` still shows the environment Uptime Goblin started with, to root and to the user Uptime Goblin runs as, and `docker inspect` shows a container's: use `GOBLIN_SECRET_KEY_FILE` (or a systemd credential or Compose secret) instead. A key file keeps the key out of those two views, not from the account Uptime Goblin runs as: natively that is the `uptime-goblin` account, which opens the key itself; under Docker Compose without user-namespace remapping it is host uid 1000 with gid 1000, and while Uptime Goblin runs any process of that uid and gid can read the Compose secret through `/proc/<pid>/root`, as it can read `GOBLIN_PASSWORD` through `/proc/<pid>/environ`, and read and change Uptime Goblin's data volume through `/proc/<pid>/root/var/lib/uptime-goblin` (`/app/data` before 1.5), so keep uid 1000 no one's on such a host, or use Docker's `userns-remap` ([the encryption key](installation.md#encryption-key)).
- **Memory.** The key, the data keys and the secrets they open are in Uptime Goblin's memory while it runs. `compose.yaml` and the systemd unit forbid swapping Uptime Goblin's memory and core dumps of it (`memswap_limit` equal to `mem_limit` and `ulimits: core: 0`; `MemorySwapMax=0` and `LimitCORE=0`), though a kernel without swap accounting has no swap limit to set, and Docker and systemd then start Uptime Goblin without one. A supervised Uptime Goblin on Linux warns at every start when core dumps are allowed after all, and, where it can read the swap limit of its cgroup (cgroup v2 with swap accounting), when swap is ("Uptime Goblin's memory can be written to disk: …", a drop-in, an override file or a changed `compose.yaml`). On a host with swap where it cannot read that limit (a kernel without swap accounting, a memory controller the container's host does not delegate, cgroup v1 or a hybrid layout) it says at every start that it cannot tell ("Uptime Goblin cannot tell whether its memory can be swapped out: …"); on a cgroup v1 or hybrid host it cannot verify its memory, CPU and process limits either, and refuses to start unless `GOBLIN_ALLOW_UNLIMITED` names them ([resource limits](installation.md#resource-limits)). The host's other processes are not Uptime Goblin's to control: on a host with swap, use encrypted swap, and keep the host's crash dumps private.
- **A lost key** loses only what it sealed: `goblin-admin key reset --confirm-lost-key` makes a new keyring, and in 1.5 Uptime Goblin then makes a new webhook signing key, whose public key receivers need: the webhook holds its notifications until an admin presses **Resume** ([lost encryption key](troubleshooting.md#lost-encryption-key)).

**The webhook signing key** is an Ed25519 key pair Uptime Goblin generates. The private key is sealed with the key and never leaves Uptime Goblin: no page, API answer, export, log line, audit entry or error holds it. Receivers verify with the public key, which is not a secret: **Configure → Notifications → Show public key** shows it to any signed-in admin, and its API (`GET /api/notifications/webhook/public-key`, with the right to read notifications) to a script with the admin password while [legacy Basic](authentication.md#scripts-and-legacy-basic) is on. Reading it is neither limited nor recorded; a receiver that has it can verify requests but cannot sign one. **Replace signing key** makes a new key pair; the previous private key keeps signing for 24 hours. Uptime Goblin keeps only one previous key, so a second **Replace signing key** within those 24 hours stops the older one signing at once (the page says so first). Replace it whenever the private key may have been exposed: the encryption key together with a copy of the data directory ([a leaked key](#a-leaked-key)). Pre-release builds of 1.5 signed with an HMAC secret that any admin could show; this release never signs with such a secret: its first start replaces it with a new key pair, or, without a webhook, removes it. A key pair made in place of such a secret, or of a key that no longer opens, never signs beside it: the webhook holds its notifications until an admin gives receivers the new public key and presses **Resume** ([a new signing key waits for Resume](notifications.md#a-new-signing-key-waits-for-resume)). This release keeps the private keys in settings fields those builds never open, and every start of it saves those settings in a form the builds can read but not change, so such a build started on data this release has run on shows no signing secret, cannot make one and sends webhooks unsigned: do not start the data with such a build. Pre-release builds that already signed with Ed25519 kept the private key in the HMAC secret's field, until a start of this release moves it out; an HMAC build started on their data before that took the key for its HMAC secret, signed with its text and showed it under **Show signing secret**. If one has, press **Replace signing key** twice, as in step 2 of [a leaked key](#a-leaked-key), and give receivers the new public key.

**Signatures** are Ed25519 over the delivery id, the time and the exact body (`<X-Goblin-Delivery>.<t>.<body>`), so a captured request can be replayed neither later (receivers reject a `t` more than 5 minutes off) nor under another delivery id to get past a receiver that drops repeats ([verifying signatures](notifications.md#verifying-signatures)).

### A leaked key

If the encryption key may have leaked, alone or with a copy of the data directory (a backup, a snapshot, a copied Docker volume, which without `compose.secret.yaml` holds the key too):

1. Stop Uptime Goblin, put a new key in place and run `goblin-admin key rotate` with the old key as the previous one; [changing the key](installation.md#changing-the-key) has the lines for each install. It wraps every data key with the new key and makes new data keys, so audit entries written from then on are signed with a new audit key. In 1.5 it seals nothing again: until you replace it, the webhook signing key is the one the old key opens.
2. Start Uptime Goblin. With a webhook set, press **Replace signing key** under **Configure → Notifications** twice: after the first press the old key keeps signing for 24 hours, and the second press stops it at once. Then give receivers the new public key and have them drop the old one.
3. After a copy of the data directory leaked, change the admin password too (which signs every other session out): the copy holds its hash. In 1.5 `config.json` holds the source and SMTP passwords and API keys in plain text, so change those at their services as well.
4. Backups and snapshots made before the change, the leaked copy included, still open with the old key, and `key rotate` keeps the old data keys (retired) to open older values. Delete the backups and [snapshots](installation.md#snapshots) you do not need, keep the others as carefully as a key, and delete the old key file once no backup you keep needs it.

A copy of the data directory that leaked without its key does not open the private signing key, but step 3 applies to it all the same.

## Audit log

**Configure → Audit log** lists what Uptime Goblin recorded, newest first: what happened, who did it (the admin signed in, a script with the password, someone not signed in, Uptime Goblin itself, `goblin-admin` as the user who ran it, or, in entries of earlier 1.5 pre-releases, their passwordless local preview), from which address and browser, and how it ended. The address is the one the sign-in lockout counts, as in the sessions list: an IPv6 client shows as its /64 network, the Uptime Goblin computer itself, and every client of a proxy on it that `GOBLIN_TRUST_PROXY` does not name, as `loopback`, and every client behind another proxy that `GOBLIN_TRUST_PROXY` does not name (under Docker Compose without it, the Docker gateway) as that proxy's address. **Show details** gives what changed, and **Export CSV** or **Export NDJSON** downloads what the filters select, with every entry's signature. An entry that a request made shows that request's id as **Request** (`request_id` in exports): the `X-Request-Id` of Uptime Goblin's answer, which Uptime Goblin's log lines for unexpected failures name too ([headers](architecture.md#headers-retries-and-busy-answers)).

- **What is recorded.** Sign-ins, sign-outs, session revocations and password changes; how the admin account was set up (from `GOBLIN_PASSWORD`, from `auth.json`, or kept from `control.sqlite` and written to `auth.json`; entries of earlier 1.5 pre-releases can also say without a password, for their local preview) and each failure to update `auth.json`; every settings and source change, Uptime Kuma imports included, with what changed (the settings before and after, compared value by value); source tests, test emails and refreshes; delivery **Retry** and **Resume**; changes of the ntfy and Gotify settings (`channel.settings`, with what changed: tokens, passwords and the ntfy topic only as set, changed or cleared) and their test notifications (`channel.test`); the webhook signing key replaced or created (reading its public key is not recorded); configuration and audit exports; delivery's own events (a channel paused or working again, notifications kept in memory only); Uptime Goblin's starts and stops, every 1.5 release that opened `control.sqlite` since the last start Uptime Goblin recorded, the snapshots and restores it finds, changes to `config.json` or the admin password made outside Uptime Goblin, and changes to the security settings it takes from the environment (legacy Basic, plain-HTTP sign-in, the trusted proxy, the allowed hosts, whether a webhook is set, where the key comes from, how many connections one client may hold open at once); the log's own prunes and the gaps Uptime Goblin finds in it; and the `goblin-admin` key commands (`key rotate`, `key rewrap`, `key reset`, `key remove-data-copy`), named after the user who ran them (with `sudo`, the user sudo reports, which is not proof of who it was).
- **What is never recorded.** A password (right or wrong, the admin's or a script's), the private signing key, a key, a cookie value, a source's API key or password, the SMTP password, the webhook URL or its token, an ntfy or Gotify token or password, the ntfy topic, or an error text from another system. A secret shows only as "set", "changed" or "cleared" (a change from one value to another shows too: Uptime Goblin compares keyed HMACs of the values, never the values). The name typed at a refused sign-in is kept only as "admin" or "another name": not the name itself, nor anything derived from it, so a password typed into the name field never lands in the log. Configuration values (host names, source addresses) appear only in the list of what changed, and every address there has its user name, password and token parameters removed first.
- **Refusals are counted, not listed one by one.** For each kind (refused sign-ins, refused password changes, refused script sign-ins, and requests refused by authorization or by step-up and admin locks, listed under the kind **Refused requests** on the Audit log page) the first refusal of each hour gets an entry at once, and the others of that hour are summed into one entry when the hour ends, with the reasons, the number of different addresses (counted up to 1,000) and up to 10 of them. Scripts signing in with the password get one entry a day and a daily summary. Refused password changes include those sent without a current session (none at all, or one that has ended), listed as someone not signed in; an hour's summary that also counts a session's refused changes is listed under that session, its reasons telling the two apart. Clients that are not signed in therefore add at most 144 entries a day (a guessing attack at most 96), however many addresses they use, and none while the disk is full.
- **Signed and chained.** Each entry is signed (HMAC-SHA256 under the audit key of the [keyring](#encryption-key-and-sealed-secrets)) together with the one before it, so a changed, inserted or removed entry shows. **Check integrity** on the page, or `goblin-admin verify-audit` ([goblin-admin](installation.md#goblin-admin)), checks every entry and lists every restore, upgrade and key reset it passes. Each time Uptime Goblin records something it also prints a checkpoint line, `{"orbit":"audit.checkpoint",…}`, to its own log (journald, `docker logs`). Kept outside the data directory, those lines detect entries removed from the end, which no check of the database alone can ([keeping Uptime Goblin's log](installation.md#keeping-uptime-goblins-log)). The `goblin-admin` key commands print none: their entries are covered only by the checkpoint of Uptime Goblin's next entry, such as its start, so start Uptime Goblin after a key command and keep that start's lines. `key remove-data-copy` runs beside a running Uptime Goblin, so no start follows it: sign in once afterwards, and keep that sign-in's line. Until then, someone who can write `control.sqlite` can remove those entries from the end, and no check shows it, not even against Uptime Goblin's log: while they are there, `verify-audit --checkpoints` says only "Entries after #… are covered by no journal checkpoint"; once they are removed, it reads intact, and Uptime Goblin's next entry takes the number of the first one removed. Keep each key command's output too. A removed `key reset` entry still shows: the entries signed with the lost key then read CHANGED.
- **Tamper-evident, not tamper-proof.** Whoever holds the encryption key and the data can rewrite both the log and its signatures; only checkpoint lines kept elsewhere show what was removed or rewritten. Under the default Docker setup the key is in the same volume as the data (`/var/lib/uptime-goblin/secret.key`), so a copy of the volume can rewrite the log too: use `compose.secret.yaml` ([the encryption key](installation.md#encryption-key)) and keep the container's log outside the volume. Someone who can write the data directory without the key can make removed entries look like a restore of a snapshot (**Check integrity** lists every restore it finds, so check that each one was yours), or remove the whole log. Deleting `control.sqlite`, or restoring a snapshot or a copy without one (the pinned pre-1.5 snapshot, a backup from before the upgrade), leaves Uptime Goblin no trace of the old log: the next start begins a new log that checks intact and lists no restore. Its first entries read "Set up the admin account …", "Uptime Goblin … opened this data" and "Uptime Goblin … started for the first time", and its checkpoint lines name a new `instance`. Outside a first install or the upgrade from 1.4.x, treat that as the log having been removed. Only the checkpoint lines kept outside the data directory show it, and only as "not fully checked" (lines signed with keys the keyring does not hold), never as CHANGED. A whole-file restore of `control.sqlite` (a backup, a copy or a move) whose first start is by an earlier 1.5 build is not recorded, and a lost-key reset made by an earlier 1.5 build, which recorded nothing, makes the entries signed with the lost key read as changed. A run of 1.4.x after a rollback never opens `control.sqlite` and is not named: it shows only through the changes it made to `config.json` and the admin password, recorded at the next start as made outside Uptime Goblin, and one that changed neither (sign-ins, scripts and reads only) leaves no trace in the log.
- **`goblin-admin migrate --apply`, `snapshot` and `restore-snapshot`** run without the key (`restore-snapshot` reads one only to check a keyring it brought back: [snapshots](installation.md#snapshots)) and write no entry: Uptime Goblin records what they did at its next start (the release that opened the data, the snapshots it finds, the restore), as Uptime Goblin itself rather than as the user who ran them. A snapshot removed before that start is not recorded, and neither is a restore that removed `control.sqlite` (of the pinned pre-1.5 snapshot): that start begins a new log, which lists no restore.
- **Retention and privacy.** Entries hold client addresses, browser names (user agents) and session ids (the public `s_…` id, never a cookie) and are kept for 90 days by default, at most 250,000 entries; `GOBLIN_AUDIT_RETENTION_DAYS` (30 to 3650) changes it ([environment settings](configuration.md#environment-settings)). An hourly job removes older entries once the oldest is a day past the retention, or the log is 1,000 entries over the cap, so an entry can stay up to about a day longer. It removes none while the disk is full, and none by age while the host's clock is more than an hour behind the newest entry (Uptime Goblin's log then says "Uptime Goblin's clock is behind its newest audit entry…" once a day). It checks the entries it removes, and stores and prints a signed checkpoint of the last one, so what remains still checks. When one of them does not check (it reads CHANGED, or a newer Uptime Goblin wrote it before a rollback), it removes none, neither by age nor by the 250,000 cap, for as long as that entry is in the log, and Uptime Goblin's log says "Uptime Goblin did not remove old audit entries, because entry #… does not check: use Check integrity on the Audit log page." once a day. Entries then stay past the retention, with their addresses, browser names and session ids, and the log keeps growing: 1.5 has no command that resumes the prune ([Uptime Goblin's log mentions old audit entries](troubleshooting.md#uptime-goblins-log-mentions-old-audit-entries)). Backups and snapshots of the data directory carry the log. `GOBLIN_AUDIT_LOG=stdout` also copies every entry to Uptime Goblin's log, with its address, browser name and session id (`stdout-full` with what changed too); keep that log as private as the data. An entry Uptime Goblin could not write is printed to its log (stderr) in full, whatever `GOBLIN_AUDIT_LOG` says, so that log, and every export of it, can hold addresses, browser names, session ids and what changed beyond the retention.
- **When an entry cannot be written.** A change outside `control.sqlite` (settings, sources, **Retry**, **Resume**) and an export are recorded first, and refused when that fails: 503 `audit_unavailable`, "Uptime Goblin cannot write its audit log, so nothing was changed.", and nothing was changed, sent or shown. A sign-in or a password change succeeds or fails together with its entry; a sign-out or a session revocation that cannot be saved with its entry is made without it. An entry that cannot be written after its change (the change stands) goes to Uptime Goblin's log (stderr) at once, as one line starting `{"orbit":"audit.unwritten"`; the change then shows "Outcome unknown" on the page, and the page says how many entries could not be written since Uptime Goblin started. A change Uptime Goblin was in the middle of when it crashed, was killed or lost power shows "Outcome unknown" too, with no such line and no count. No notice is sent for it (a full disk, the usual cause, sends its own), and the entry is not written later: a settings change among them is recorded again at the next start, as a change made outside Uptime Goblin, with what changed.
- **Exports** are accepted with a session only from Uptime Goblin's own page: another site, also one on the same host or another port of it, cannot make your browser start one. Scripts using [legacy Basic](authentication.md#scripts-and-legacy-basic) can export when they send `X-Goblin-Request: 1`, as with every change (1.4.x needed no extra header on an export). Without a credential there is no export. Every export is recorded.

## Outbound requests and TLS

HTTP collectors use bounded reads and reject redirects to avoid forwarding credentials through a redirect chain. What a source answers is checked before it is used: a body or list entry of an unexpected shape is reported as "Source returned an unexpected response" and not retried; names, IDs and units from a source become measurement keys and labels only as one line of text (one space for each run of control characters and line or paragraph separators, direction embeddings, overrides and isolates removed, and from labels and units the direction marks and outer white space too; long ones shortened, keys within the 150 characters an alert rule takes), and an entry without a usable name or ID, or a reading whose key an earlier one already has, is left out with a note; readings outside their unit's range (negative counts, sizes, rates or durations, percentages above 100) are left out, except for custom mappings; NPM, CrowdSec and AMP session tokens must be one token of at most 8,192 characters, or the sign-in fails and nothing is kept. In email text, each control character and line or paragraph separator in a source name or label becomes a space, and direction embeddings, overrides and isolates are removed (the direction marks stay, as names you save keep them), and Uptime Goblin limits an SMTP server's reply to 64 KiB. HTTPS uses the runtime's certificate validation; UniFi local login requires HTTPS. SMTP uses verified implicit TLS or mandatory STARTTLS, TLS 1.2 minimum. Add a public CA certificate through `NODE_EXTRA_CA_CERTS` when necessary; never disable verification globally.

Some integrations support HTTP, but credentials/tokens sent to an HTTP endpoint are unencrypted on that hop. Use HTTPS or a protected local network/tunnel appropriate to the service. Uptime Goblin permits private endpoints because that is its purpose; it is not an isolation boundary against a malicious authenticated administrator.

Collection destinations are checked before connecting. Link-local addresses (including the `169.254.169.254` cloud metadata service), multicast, unspecified and reserved ranges are always refused. Loopback (`127.0.0.0/8`, `::1`, `localhost`) is refused unless `GOBLIN_ALLOW_LOOPBACK=1`, so a source cannot reach services that listen only on the Uptime Goblin host. The same address policy applies to the SMTP server for email alerts. Hostnames are resolved and every returned address is checked. Answers are reused for up to 30 seconds, and checks of the same name running at the same time share one lookup, so one unresolvable name cannot tie up DNS for every other source. A failed lookup is shared only by checks running at that same moment, so a retry always asks DNS again. HTTP collectors and Website checks connect only to the addresses the check approved, without resolving the host name again (as SMTP does), so a DNS answer that changes after the check, or a hostile DNS server answering differently a moment later, cannot send a source's request or its credentials to a refused address; TLS is still verified against the configured host name. Each connection serves one request. Private LAN ranges stay allowed, and connection errors stay specific so you can troubleshoot. An authenticated administrator can therefore still tell open, closed and unreachable ports on your network apart.

The alert webhook (`GOBLIN_WEBHOOK_URL`) follows its own rule: loopback and `http:` stay allowed, as in 1.4.x (a receiver on the Uptime Goblin host is common), but link-local, multicast, unspecified and reserved addresses are refused, also when written inside an IPv6 address (NAT64 `64:ff9b::/96` and the local-use `64:ff9b:1::/96`, IPv4-compatible `::a.b.c.d`, IPv4-translated `::ffff:0:a.b.c.d` and 6to4 `2002::/16` addresses carry an IPv4 address, which is checked like the address itself), so `64:ff9b::a9fe:a9fe` is refused like `169.254.169.254`. Collection destinations follow the same rule. Other translation prefixes are not recognised: a NAT64 gateway with a prefix of its own (a network-specific `/96`, or the local-use `64:ff9b:1::/48` laid out otherwise) writes addresses that cannot be told from ordinary IPv6 ones, so do not let such a gateway translate to link-local addresses. Host names are checked at connect time against every address they resolve to, so a name that changes its answer between a check and the connection cannot reach a refused address. Redirects are never followed, requests are at most 64 KiB, and at most 4 KiB of an answer is read. The URL comes from the server's own configuration, so this is defence in depth against a mistake, not a boundary against whoever sets it.

The ntfy and Gotify servers, which an admin sets in the web app, follow the collection destinations' rule instead (loopback only with `GOBLIN_ALLOW_LOOPBACK=1`, link-local, multicast, unspecified and reserved addresses never, also inside an IPv6 address), checked at connect time against every address a host name resolves to, as for the webhook. Their address must be `https:` unless it is this computer's loopback or **Allow plain HTTP** is switched on; it never carries a user name, password, query or fragment, and the token travels in a header, never in the address. Redirects are never followed, TLS is verified, requests are at most 16 KiB and at most 4 KiB of an answer is read, within 8 seconds ([which addresses ntfy and Gotify may use](notifications.md#which-addresses-ntfy-and-gotify-may-use)).

SMTP uses the exact IP addresses returned by Uptime Goblin's outbound-policy check, including the host resolver's `/etc/hosts` entries, without a second DNS resolution by the mail library. Multiple approved addresses can be tried during connection setup; slow pending attempts remain eligible while alternatives start, within one eight-second deadline and a limit of 32 pending sockets. Only the winning socket reaches the mail library; the others are closed before authentication or message delivery. TLS still verifies the original configured hostname, and STARTTLS remains mandatory when implicit TLS is off. DNS or connection failure occurs before any message is sent; a later delivery timeout can still leave acceptance unknown.

Mail rendering escapes user-provided content and disables file/URL content loading. Delivery errors discard raw SMTP provider responses. Session cookies that collectors receive from the services they sign in to remain in server memory only. Still keep application logs private: names/labels and operational context can identify infrastructure.

## Installer, release signing and supervision

Release archives from 1.4.3 on carry `SHA256SUMS.sig`, an SSH signature over `SHA256SUMS` made with `ssh-keygen -Y sign -n orbit-release`. The public key is in `deploy/allowed_signers`, and its fingerprint is published in the [README](../README.md#release-signing) and [SECURITY.md](../SECURITY.md#release-signing). Verify with a copy of `allowed_signers` from a trusted place, never the one inside the archive you are checking, and compare the fingerprint `ssh-keygen` prints with the published one; see [verifying a release](installation.md#verifying-a-release). The `orbit-release` namespace keeps a signature made for another purpose (a Git commit, another file) from verifying as a release signature, and the reverse.

The native installer installs exactly the files in `deploy/manifest.txt`, never the whole staging directory, so stray files there are not deployed. From a release archive it checks each of those files against `SHA256SUMS`; it does not check the signature itself. It refuses to run from the installed copy and refuses a Node binary under `/root`, `/home` or `/run/user`, which the sandboxed service cannot read. All of these checks run before anything on the host changes. Application files are owned by root and readable, not writable, by the `uptime-goblin` account. The data directory `/var/lib/uptime-goblin` is the `uptime-goblin` account's, so the installer, running as root, reads files there (`secret.key`, `control.sqlite` and its `-wal`, `run/status.json`) only as regular files, never through a symbolic link and never from a FIFO; it refuses, before opening it, a key file that `/etc/uptime-goblin.env` or a credential drop-in names there (`GOBLIN_SECRET_KEY_FILE`, `GOBLIN_SECRET_KEY_PREVIOUS_FILE`, `LoadCredential=`, also through a link from elsewhere into it), which root (and systemd at every start, for a credential) would otherwise read through whatever link the `uptime-goblin` account put in its place; no key file anywhere is waited on; and the key it copies to `/etc/uptime-goblin/secret.key` (which the `uptime-goblin` group can read) is the one it checked, not the data directory's file read again: the service account cannot make the installer read or copy another file as root. After an upgrade it keeps the previous code in `/opt/uptime-goblin.previous`, and a failed upgrade in `/opt/uptime-goblin.failed`; both are root-owned copies of application code, not data.

The systemd unit and the Docker image set `GOBLIN_SUPERVISED=1` and start Uptime Goblin with `--supervised`, which `/etc/uptime-goblin.env`, an `-e` option of `docker run` or a Compose override cannot turn off (a `GOBLIN_SUPERVISED` that says no is ignored, with a line; one that is neither yes nor no refuses the start). Uptime Goblin then exits with status 0 only after a stop signal; an exit with status 0 that no stop signal caused is reported as 1, so the service manager restarts it instead of treating it as a clean stop, as it does every other unexpected failure (1). A refusal to start (invalid settings or `auth.json`, the password rules, an invalid `GOBLIN_TRUST_PROXY`, an encryption key problem, no admin password, data from a newer release, an interrupted snapshot restore, a resource limit not in force, a malformed `GOBLIN_ALLOW_UNLIMITED`) exits 78. systemd does not restart it, so a service that would never pass its startup checks is not restarted every few seconds, and `systemctl status` shows why it stopped. Another process holding `goblin.lock` in the data directory (another Uptime Goblin, or a `goblin-admin` command) makes a start exit 75, and systemd tries again after 5 seconds ([exit statuses](troubleshooting.md#exit-statuses)).

**Resource limits.** Supervised, Uptime Goblin reads its memory, CPU and process limits back from its own cgroup at every start and refuses to start (78) unless each is in force or `GOBLIN_ALLOW_UNLIMITED` names it ([resource limits](installation.md#resource-limits)): neither Docker nor systemd says when an override file, a drop-in or an LXC host that does not delegate a controller leaves a limit without effect. The check runs in `server.mjs`'s main block after its modules have loaded, and before the start sequence takes `goblin.lock` or reads Uptime Goblin's data; what the modules do as they load is outside it. A `cpu.max` quota Uptime Goblin reads as valid (positive, not `max`) is a CPU limit by itself, whatever the CPU set; without one, a CPU set counts only as Uptime Goblin verifies it at the start: its own cgroup's set (`cpuset.cpus`) and the CPUs it runs on (`cpuset.cpus.effective`) are both CPU lists it can read, neither empty, every CPU its own set names is one the host has online (as Uptime Goblin sees `/sys/devices/system/cpu/online`), the CPUs it runs on are all within its own set, and each set is some, not all, of the CPUs the host has online. Holding fewer CPUs than the host is not enough, and a set that names a CPU the host does not have online cannot be verified. `GOBLIN_ALLOW_UNLIMITED` lowers a security control, so it is read only from Uptime Goblin's environment at the start: no page or API sets it, `config.json` cannot hold it, **Configure → System** shows it read-only, and the audit log's start entry records the limits Uptime Goblin runs without (`unlimited`; its coming and going is a security change). Docker Compose retries a refusal (`restart: unless-stopped`), unlike the unit (`RestartPreventExitStatus=78`). Docker in an LXC, rootless Docker, cgroup v1, one-CPU hosts and CPU hot-plug are not qualified.

**Readiness (systemd).** The unit is `Type=notify` with `NotifyAccess=all`: Uptime Goblin reports ready through `systemd-notify --ready`, started by absolute path (`/usr/bin` or `/bin`, read-only under `ProtectSystem=strict`), with fixed arguments, no shell, a 10-second bound and an environment of `NOTIFY_SOCKET` alone, so no password or other setting reaches it; a `NOTIFY_SOCKET` that is not an absolute path or an `@` name of at most 107 bytes without control characters is refused. `NotifyAccess=all` lets any process in the service's cgroup send systemd notifications (ready, stopping, status, a main PID within the cgroup); Uptime Goblin starts no other program there, and code that could run there already runs as the service, so it adds no capability an attacker in the service lacks. A failure to notify is logged and leaves the unit activating; it never stops Uptime Goblin from serving.

`run/status.json` in the data directory (mode 600, directory mode 700) names the running version, build, process ID, listening address and a per-start nonce. The nonce is not a credential, but keep the file private like the rest of the data directory. `Idempotency-Key` answers are kept in memory for 10 minutes, separately for each signed-in user (and its sign-in epoch, which an imported password or a restore advances), so a save retried after signing in again joins or replays its first attempt instead of running twice. Request bodies are compared by a keyed digest and never stored, and password changes are never kept or replayed; nor are 401, 403, 429 and 503 answers, which applied nothing. A retry held across a sign-out, a revoked session or a password change is refused before it can run or receive a saved response, including when it was waiting for another request to finish.

## State and backups

Stop Uptime Goblin before making a full filesystem backup of its data. Save the whole directory, including `auth.json` when present, `control.sqlite`, runtime environment and required CA configuration.

`created-by.json` (1.5) names the release that created the data directory and holds no secret; keep it with the rest, since it keeps [legacy Basic](authentication.md#scripts-and-legacy-basic) off on an install created by 1.5 if `control.sqlite` is ever removed. `control.sqlite` (1.5) holds the admin's salted scrypt hash, the SHA-256 of each session secret (never the secret), the node-local record of where the password came from (the `auth.json` fingerprint, a scrypt verifier of the imported `GOBLIN_PASSWORD`) and the platform's own tables. Startup snapshots under `snapshots/` (mode 700, files 600) copy `config.json`, `auth.json` and `control.sqlite` whole, so they carry the same secrets as the data directory; they never contain `secret.key`, `goblin.lock` or, when taken before a migration, `history.sqlite`. Restoring a snapshot restores the admin password of its time and signs every session out at the next start, so sessions revoked since the snapshot cannot come back. A backup of the whole data directory holds the same: the password and every session of its time, including those signed out since. Uptime Goblin records which file `control.sqlite` is (its inode, and its creation time where the file system reports one) and signs every session out at a start that finds another file there: a backup restored with `tar` or `cp`, a copied Docker volume, a restored Proxmox backup, a data directory copied or moved to another disk. It cannot notice a rollback of a file-system snapshot (a Proxmox LXC or VM snapshot, ZFS or LVM), which brings back the same file, or a backup copied over the existing file in place: after one, sign in and use **Sign out other devices** at once, or change the password. Do not copy only `history.sqlite` while SQLite WAL writes are active. Rehearse restores in isolation with email/webhook delivery disabled. See [backup instructions](installation.md#backups).

`control.sqlite` also holds, from 1.5, the delivery queue and history: for each notification its channel, the alert's name, rule, category, message and time (what the notification says), attempts, answer codes and Uptime Goblin's own error texts. It never holds a webhook URL, a secret, a rendered request or a receiver's answer body, and neither do the Notifications page, the logs or the API. The ntfy and Gotify settings are kept in its settings table, their tokens and password sealed. Finished notifications are kept 7 days, failed ones 30 days. A restored `control.sqlite` (another file than before) never sends the notifications that were waiting in it.

Configuration export intentionally cannot restore passwords and has no import endpoint. Monitoring data and alert events are sensitive operational information even when they contain no authentication secret. Deleting a source removes its local history/events; protect backups from accidental reuse or disclosure.

## Preparing a source-only upload

Before pushing to a public repository, confirm `git status` lists no `data/`, `.env`, `release/`, backups or exports (all are in `.gitignore`), and enable **Private vulnerability reporting** under the repository's security settings so [SECURITY.md](../SECURITY.md) works.

Prepare the source-only package from the reviewed project:

```sh
npm run package
```

The script creates `release/uptime-goblin-<version>/`, `SHA256SUMS`, and a matching `.tar.gz` archive. With `ORBIT_SIGNING_KEY=<path to the release key>` (or to its `.pub` file when the private key is in ssh-agent or on a hardware key), it also signs `SHA256SUMS` as `SHA256SUMS.sig` and checks the signature, against `deploy/allowed_signers` once the release key is listed there; if signing or the check fails, it removes the half-built release. It refuses a release that would leave out a file listed in `deploy/manifest.txt`, and never packs the upgrade-simulation fixtures (`test/fixtures/releases`, `test/fixtures/npm`). It refuses to overwrite an existing staging directory. Move the earlier output aside if deliberately rebuilding. It copies explicit root files and approved code/docs directories, rejects symlinks and selected private/generated file extensions, and does not copy the root `data/`, `.env`, `node_modules` or Git history.

**Inspect before upload.** The packager is not a content secret scanner: a secret embedded in an otherwise allowed `.js`, `.md` or `.json` file would still require removal. Do not put live configuration, credentials, exported topology, incident reports or local inventories in an approved source directory. Review the staged file list and contents, run a suitable local secret scan, and compare hashes as needed.

The release inputs are README/contribution/security/changelog files, example environment/ignore files, package/lockfile, server/Docker/Compose files, and the approved `lib`, `public`, `deploy`, `docs`, `examples`, `test`, `scripts`, `.github` directories. Keep real data, backups and operational artifacts elsewhere. `.gitignore` excludes common private/generated outputs but cannot untrack files already in a repository. The Docker build uses its own stricter context allowlist, so private working-directory files are not sent to the builder.

Review examples for real addresses, emails, usernames, organization names and paths. Use reserved example domains and fictional fixture identities. No screenshots are included; sanitize any screenshots you add. Include `package-lock.json` so installs are reproducible. Do not run `npm publish` or upload a tar of the entire working directory as a shortcut.

## Maintenance

Keep Node.js, the host OS, Docker base image and exact locked dependencies current. Rebuild the image with `docker compose build --pull` at each update: the Dockerfile pins `node:24-bookworm-slim` by digest, so every build uses exactly that image, with `--pull` or without it, and an Uptime Goblin release that moves the pin brings the base image's security updates. Until then the build adds the Debian security update the pinned image lacks, `libpcre2-8-0` at exactly `10.42-1+deb12u2` ([updates](installation.md#updates-and-rollback)). Review dependency audit findings in context; audits do not cover the host, all integration versions or the network. Fixture tests are not a full live security assessment. Use the private reporting process in [SECURITY.md](../SECURITY.md) for a suspected vulnerability.
