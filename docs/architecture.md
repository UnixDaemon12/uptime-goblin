# How Uptime Goblin works

[Back to Uptime Goblin](../README.md) · [Configuration](configuration.md) · [Security](security.md)

Uptime Goblin is one Node.js server, a static browser interface, and a local SQLite database. There is no browser extension, cloud ingestion service, external database, message broker or frontend build pipeline. The exact Nodemailer dependency supplies SMTP delivery; SQLite comes from Node.

## Data flow

```text
Browser configuration and dashboard
                 |
        Uptime Goblin HTTP server
                 |
     scheduled source workers ----> source API / exporter
                 |                  (read or session-login requests)
        normalized measurements
                 |
       SQLite readings/latest
                 |
       alert state transitions
          /                \
    in-app events       event rows (history.sqlite, relayed = 0)
                                 |
                          relay: one row per channel
                                 |
                  delivery queue (control.sqlite outbox)
                                 |
                  delivery worker ----> email / webhook
```

The server keeps collecting when the browser closes. It checks scheduling roughly once a second, chooses enabled configured sources, and runs a bounded number of workers. Each source has its own interval and cannot overlap its own active collection. Scheduling ticks fill free worker slots independently, so one slow source does not hold up all otherwise available slots. A source becomes due again after its previous request/collection work finishes plus its configured interval; cadence includes request time and can drift. API/exporter requests reject redirects, bound response size and timeout, and participate in source cancellation.

Website checks use a separate unauthenticated GET/HEAD probe with normal TLS verification and the source's cancellation/deadline. It evaluates the returned status against `httpExpectedStatus` (default `200-399`) without following redirects or sending saved source credentials. Accepted responses produce response time (until headers arrive), availability and HTTP status measurements; the response body is cancelled without being downloaded. Unexpected statuses and network/TLS failures enter the normal failed-collection and history-gap path. Selecting `collector: "http"` applies this behavior to any source type without changing its display identity.

Each logical collection may retry classified transient failures, with a bounded count and delay. The total source timeout covers every attempt and wait. Rejected credentials, invalid responses and configuration errors are not retried. Only the final outcome is stored/evaluated; retry attempts do not inflate failure or recovery counts. Source monitoring overrides inherit individual workspace values when omitted. Draft connection tests use the same retry policy without persistence.

A collector returns numeric `{key, label, value, unit}` measurements. When a limit leaves readings out (see [resource bounds](#resource-bounds)), the collection also returns notes, `{code, message}` with an optional `omitted` count: at most 8 per source, one per code, each message fixed text of at most 200 characters with no upstream content. The notes of the latest successful collection are kept in the `latest_notes` table, shown on the card (not while the source is paused) and returned by connection tests. Raw upstream payloads are not stored as dashboard metrics or returned as source responses. Some tokens are supplied with each request; session-based collectors cache credentials received from login only in server memory. A source edit or isolated connection test resets the corresponding collector cache.

## State and history

Private `config.json` stores connections, credentials and preferences. Writes use a uniquely named, exclusively created temporary file plus rename, with restrictive permissions. Numeric source IDs are never reused; if a saved ID or counter exhausts the safe integer range, new sources use UUID suffixes instead of incrementing an imprecise number. Separate private `auth.json` stores a versioned, salted scrypt hash after an in-app login-password change; it overrides the environment bootstrap password. From 1.5 its write also flushes the data directory to disk after the rename, and only then does `control.sqlite` record the new file's fingerprint, so a power loss just after a change cannot bring the previous file back under a record that names the new one (which the next start would import as a change made outside Uptime Goblin). An invalid authentication file fails startup closed. SQLite uses WAL mode and keeps readings, latest successful values/errors, active/pending alert state, and transition events in `history.sqlite`; from 1.5 also 5-minute summaries of the readings for long charts (`history_summaries`, below). Configuration, authentication state and databases all belong in private backups.

`control.sqlite` (from 1.5) holds small, uncapped state that must survive a full history: `meta` (instance id, the release that created the directory, the last release that ran and the upgrade history, `credentials_ever`, a restore marker, and the start of a disk-full or history notice not yet followed by its recovery, `notice_disk_since` and `notice_storage_since`), the migration record and fences, and identity's `users` (the built-in admin: its password hash and an epoch that an imported password or a restore advances), `sessions` (the SHA-256 of each session secret, its lifetimes, device and address, and the transport it signed in over) and `identity_settings` (where the password came from on this data directory, and which file `control.sqlite` was at the last start, so that a restored backup signs everyone out: never backed up or transferred). Its tables are declared in one registry (`lib/db/registry.mjs`) and created by migration steps (`lib/db/control.mjs`); `goblin-admin migrate --plan` shows the steps a start would apply. The admin password lives in `control.sqlite`, and every change made in Uptime Goblin is written back to `auth.json` so a rollback to 1.4.x uses the current password (see [signing in](authentication.md)).

Before a start migrates `control.sqlite`, Uptime Goblin takes a snapshot under `snapshots/`: `config.json`, `auth.json` and `control.sqlite`, never `history.sqlite`, which these migrations do not change (restoring such a snapshot keeps the live history). Those taken on data from 1.4.x are pinned: they are the way back to 1.4.x as the data was when that start migrated it. A crash loop reuses the snapshot already taken while `config.json` and `auth.json` are unchanged; after a restore of the pinned snapshot and changes under 1.4.x, upgrading again takes a new one. A snapshot is taken only when a migration is pending: after a code-only rollback, `control.sqlite` stays migrated, so changes made under 1.4.x before the next upgrade (a password, settings) are in no snapshot, and the newest pinned one still holds the data of the first upgrade. Leftovers of a snapshot interrupted by a crash are removed at the next start. A snapshot's copies, its manifest and its name (and a new `snapshots/` folder) are flushed to disk (fsync) before the start goes on to migrate, so a power loss just after the first 1.5 start cannot keep the migrated `control.sqlite` and lose its pinned snapshot, which the next start would have removed as such a leftover, or left without its files. A restore records itself in `snapshots/.restore-in-progress.json` until it completes: a start of Uptime Goblin 1.5 or later refuses (exit 78) while that record exists, because a crash part way through leaves the data directory part restored, and running the same restore again finishes it, keeping what the directory held before the first attempt as the undo, also when the crash came after everything was in place and only the record was left (the re-run reopens that attempt's pre-restore snapshot instead of setting the restored files aside again). A restore over an interrupted one that leaves some of that one's files as they are (a snapshot without history over one that had already set `history.sqlite` aside, say) keeps what is left of that one's record: inside its own record while it runs, and as the record once it completes, also when it was itself interrupted and run again, so a start of 1.5 refuses until the earlier restore has been run again too (`restore-snapshot` names it). The restore removes the record only once the restored files, the data directory and the pre-restore snapshot are on disk (fsync), so a power loss just after it cannot leave an empty `history.sqlite`, which a start would take for an empty history, or an undo without its manifest. A file the directory did not hold before the restore stays absent in the undo, so restoring the undo removes it again. 1.4.x does not read the record: after a code rollback it starts on such a directory and writes to it. The record therefore also holds the size and SHA-256 of each copy the restore puts in place, and the re-run deletes a live file only while it is that copy (or the file from before the attempt, unchanged): any other is kept in a pre-restore snapshot of its own, never deleted. `config.json` and `auth.json` are copied aside and the snapshot's copy renamed over them, so neither is missing part way (1.4.x without `auth.json` would accept the `GOBLIN_PASSWORD` bootstrap password, or on loopback none). A live database that cannot be read (damaged) is moved aside as it is, with its `-wal` and `-shm`, and does not stop the restore. A restore first copies the snapshot's files into the data directory under hidden names (`.config.json.restoring`, `.history.sqlite.restoring`, …), then renames each into place; the copies a crash leaves there are as large as the files, so `goblin-admin status` and `goblin-admin snapshots` list them, and the next start of Uptime Goblin 1.5 or later, or the next restore, removes them (the start logs "Removed … temporary copies …"); 1.4.x leaves them. Those of files that an interrupted restore's record still names are kept until a restore takes those files over (running the interrupted one again replaces them with fresh copies). The record is written before the restore makes its `snapshots/.restoring-…` folder, so a crash never leaves a folder that nothing names; an empty one that no record names holds nothing (its restore stopped before it moved a file, and a later restore has since finished its record), and the next start of 1.5 or later, or the next restore, removes it. `goblin-admin snapshots` lists them and `goblin-admin restore-snapshot` restores one (Uptime Goblin stopped; how to run `goblin-admin` is in [installation](installation.md#goblin-admin)); a restore signs every session out at the next start. Uptime Goblin 1.5 never deletes a snapshot, and `goblin-admin` has no command for it yet: [snapshots](installation.md#snapshots) says how to delete one.

A failed collection records a failure marker but retains the last successful measurements. The dashboard distinguishes live, stale, error, collecting, paused, unconfigured and bookmark states. Numeric zero is a reading; absence of a measurement is not zero.

Charts use 1-hour, 6-hour, 24-hour, 7-day and 30-day windows. To bound work, each time bucket retains its last successful sample, last failure and last pause/restart marker, so a pause cannot hide a real failure; a long silence is flagged on the first point after it. Graphs do not interpolate through collection failures or long gaps. A sampled chart is not a full-resolution export or a min/max/average aggregate. Available history starts with Uptime Goblin collection and is limited by retention.

Charts of 7 and 30 days (from 1.5) have buckets of whole 5-minute slots, starting at a slot boundary: 35 and 145 minutes wide, at most 299 buckets, and the window can start up to 5 minutes before the period. They are built from `history_summaries`, one row per source and slot (from a multiple of 5 minutes since the epoch) holding what a bucket needs of it: its last success, last failure, last pause marker, first failure and success count, its first and last reading, the source's reading before it, and per point the longest silence before a reading that the point closes. The chart is the same as the one read from every reading over the same buckets (a property test compares them), at a fraction of the cost: one indexed range of slots per bucket, then the readings of the points shown. The row of a slot is rewritten in the transaction of every write that changes the slot's readings (a reading, a pause marker, recycling on a full disk, pruning, removing a source). Each start checks every source's summaries against its readings, in transactions of about 5 ms that yield to collection and requests between them, and rewrites what differs: readings written without summaries (by 1.4.x or an earlier 1.5 build after a rollback, by a restore, by a tool) are summarised, and summaries without readings removed. Until a source is checked, while a prune runs and while a source is being removed, its long charts read its readings, as do charts whose last slot also holds readings after the chart's end (a clock set back) and sources with a reading time Uptime Goblin never writes (not a whole number). Shorter charts always read the readings. The check's first step of a source covers at most an hour of slots (fewer when its newest hour holds more than about 1,000 readings), and a step that finds nothing skips to the source's next reading or summary, so a stray reading far from the others costs a step, not one per empty stretch. A clean shutdown writes a mark per checked source (`history_summary_marks`): a fingerprint of its readings with a whole-number time (their count, first and last time, and the sums modulo 2^24 of the times of all of them, of the successes and of the pause markers) and its summary count, read from the history index rather than the readings. It spends at most a second on this, so a stop is not held by a large history (about 0.2 s for 40 sources with 30 days each); sources it does not reach keep their old marks, which match only while their readings are unchanged. A start skips the slot-by-slot check of a source whose fingerprint still equals its mark, so its cost follows what changed: a reading written, replaced, moved or deleted by a release or tool that keeps no summaries changes the fingerprint and the source is checked. Marks are written only at a clean shutdown, and none when another connection wrote to `history.sqlite` while Uptime Goblin ran (SQLite's `data_version`) or while a prune was deleting readings, so after a crash or such a write the changed sources are checked as before. A summary edited in place while the readings stay the same is outside what a mark covers; deleting the marks table makes the next start check every source. When the summaries cannot be created, kept or read (a full disk at start, a table of that name with other columns, a summary read that fails), Uptime Goblin logs it, keeps charts on the readings (the chart whose read failed included) and tries again at the next start; a read that fails once for a passing reason (busy, locked, out of memory, an I/O error) affects only that chart, unless the same happens three reads in a row.

Pausing cancels the active result, stops scheduled polling, clears alert state and keeps history. Hiding a card changes presentation only. Removing a source deletes its stored readings/latest/alerts/events; large deletions run in short steps, so collection of other sources continues meanwhile. Changing appearance or email settings does not itself force a collection or database prune.

From 1.5, `control.sqlite` also holds the delivery queue and history (`alerting_outbox`: one row per notification and channel, with its attempts, last answer and error, next attempt and why it ended; `alerting_channel_status`: each channel's health, pause, counters and last error), the keyring (data keys wrapped by the encryption key) and settings sealed with it (the webhook's private signing key). Neither alerting table is ever in a registry backup or transferred. `history.sqlite`'s `events` gain `since`, `uid` and `relayed` (0 while the event's notifications are not yet in the queue, 1 once they are, NULL for rows 1.4.x wrote), with a partial index on `relayed = 0`. The encryption key itself is never in the data directory unless Uptime Goblin generated `secret.key` there; `run/space-reserve` (8 MiB) is the reserve for a full disk.

## Alert evaluation and delivery

The store evaluates availability and configured numeric rules after each recorded logical poll. Threshold rules require at least two qualifying samples plus their duration. Availability uses the configured failure count plus duration. Recovery of either kind requires consecutive successful healthy samples plus the recovery duration. A metric rule may define a separate recovery threshold; values between its trigger and recovery boundaries retain the firing state. Missing data cannot resolve a firing metric alert and resets recovery progress. Only a transition into firing or into confirmed recovery creates an event/notification, so repeated bad readings do not send repeated emails.

Disabling global alerts clears active/pending alert state silently while readings and event history continue. Re-enabling starts evaluation from scratch. Notification switches select future firing/recovery events independently of in-app evaluation. Old alerts are not replayed. A message already queued or submitted can still arrive after the source or global alerts are disabled.

Notification categories distinguish connection availability from measured thresholds. Each category has a workspace default and optional per-source override. These filters affect email/webhook delivery only; active warnings and history remain visible. Workspace alert-enabled and transition-delivery switches still gate delivery.

Delivery is durable (1.5; the user-facing rules are in [alerts and notifications](notifications.md)):

1. **The event row is the outbox record.** The history transaction that changes an alert's state also writes its event, with a random `uid` and `relayed = 0`. SQLite cannot commit across two files, so the event commits with the state change, and the relay catches up from it.
2. **The relay** routes each event as 1.4.2's `notify()` did (the same switches; email only once it is set up) into the queue, one row per channel, with a delivery id derived from the event and the channel, unique in the queue: a copy made twice is stored once. Only then does it mark the event relayed, by `uid`, never by id (SQLite reuses the highest id after a source is deleted). It runs right after each evaluation, and a sweep every 10 seconds (and at every start) relays what a crash or a failed write left behind. All of it runs one operation at a time, so the rows of one alert enter the queue in the order the alert changed. Uptime Goblin's own notices (storage, a full disk, a paused channel) enter the same way, with no event row; the storage and disk notices keep their start in `meta` until their recovery is queued, so a restart in between still sends the recovery, or carries the notice on without a second one.
3. **The worker** (the job runner's `notify.delivery` task) sends: at most one send per channel and four in all; per alert in order (a recovery waits for its alert); email gathered into digests (60 s quiet, 180 s at most, 100 alerts a message) with a stable `Message-ID`, a digest tried before sent again whole or not at all (a claim that gets only part of it is given back), and a digest that waits holding back the later notifications of its alerts; when a pass can start nothing else, a digest that waits only for rows past its 200 candidates is read whole from the queue and sent, provided its rows are due and the earliest waiting ones of their alerts; the webhook one signed request per row. Each answer is classified per channel as accepted, retry (backoff 30 s doubling to 15 minutes with jitter; a channel-wide `Retry-After` up to 1 hour; a circuit after 5 in a row), unknown (one resend, same delivery id: 2 minutes for the webhook, 5 for email), pause (rows held; a probe every 15 minutes for causes that may pass, and one at every start; a channel that is not paused keeps no held rows, each pass releases any it finds), failed or skipped. A webhook answer counts once its status arrives, however its body ends; "unknown" is a request whose answer did not start in time. Rows end after 24 hours. Before each claim Uptime Goblin checks the row again: a deleted source or an alert kind switched off is skipped unsent. A send-time lease (60 s), an owner and an epoch make each claim and completion apply once.
4. **When `control.sqlite` cannot be written**, rows, completions and channel status are kept in memory and still delivered ("Notifications are not being saved"); events delivered that way stay `relayed = 0` until their rows are final, so a restart sends again what was not yet delivered rather than losing it. A completion the database refused is kept and applied later, never sent again while Uptime Goblin runs; when it ends its row (delivered, failed), the row holds no later notification of its alert back, and the history and counts show that result. Rows that ended in memory are written to `control.sqlite` as they are once it can be written again (new ids), so only rows still in progress stay "kept in memory"; a new row whose alert still has a row in memory goes to memory too, and a row is written only after the earlier rows of its alert, so ids keep each alert's order, and a row kept in memory comes after every saved row of its alert (the order never compares times, which a clock step puts out of order). When the system clock jumps by more than a minute, the rows' expiry and retry times are adjusted ([clock changes](notifications.md#clock-changes)); an adjustment `control.sqlite` cannot take is kept and written first once it can be written, and none of its rows expires before then.
5. **Restored data** (a snapshot restore, or a `control.sqlite` that is another file than before) marks every waiting row stale and every unrelayed event relayed, unsent. **After a rollback to 1.4.x**, which never reads the queue, a waiting row whose alert 1.4.x changed later is superseded at the next 1.5 start, before anything is sent.

Jobs (`lib/jobs.mjs`): `notify.delivery` (continuous), `notify.relay` (10 s: start work a full disk held back, then the sweep), `notify.prune` (hourly: finished rows after 7 days, at most 50,000; failed ones after 30 days, at most 5,000), `storage.guard` (10 s) and `audit.maintain` (hourly, the first run 60 s after the start: the audit summaries a missed timer left, the entries a first start recorded before its keyring existed that a full disk kept out of the log, then the prune of audit entries past the retention or the 250,000 cap). Job status is written at most every 5 minutes per job unless its outcome changed (a write that fails counts too, so a full `control.sqlite` is not tried at every run), so an idle Uptime Goblin writes nothing else.

**The storage guard** (`lib/storage-guard.mjs`) reads the file system's free space every 10 seconds. Below 2 MiB, or on a write that failed because the disk is full (configuration, `control.sqlite`, identity; never history's own `SQLITE_FULL`, which recycles old readings by design), it deletes the 8 MiB `run/space-reserve`, checks that space was freed, refuses configuration writes with 503 `storage_full`, pauses the saving of readings and sends a notice. With at least 24 MiB free it makes the reserve again and everything returns (a failed attempt waits 5 minutes before the next).

Email and webhook are independent channels: a channel that pauses tells you on the other one. SMTP acceptance is not inbox delivery. An independent monitor is needed for Uptime Goblin/server failure.

## HTTP API

All endpoints share the Host allowlist. A request needs exactly one `Host` header (400 otherwise) and a request target that is a path: `//host/…`, `/\host/…` and absolute `http://host/…` targets get 400 "Malformed request address", so a reverse-proxy rule written for a path always sees the request Uptime Goblin serves. Uptime Goblin always has an admin password, and only `/health`, `POST /api/auth/login` and the web app's own files (its page and the scripts, styles and images it loads) answer without a credential; everything else needs a session cookie (browsers) or, while legacy Basic is on, HTTP Basic as `admin` (scripts without browser headers; on the `http` transport only with `GOBLIN_INSECURE_HTTP_SESSIONS`; see [signing in](authentication.md#scripts-and-legacy-basic)), and gets 401 without one. Writes additionally require `Content-Type: application/json` and `X-Goblin-Request: 1`; with a session cookie they also need an `Origin` naming the request's `Host` or a `GOBLIN_ALLOWED_HOSTS` entry. The two exports need `X-Goblin-Request: 1` too, with a session cookie or Basic, on every transport (below). Use HTTPS for any request carrying credentials. A request body is limited to its route's size: 150,000 bytes, 4,096 for sign-in and the password change, 1 KiB for the delivery actions. Writes that take no body (`POST /api/refresh`, `POST /api/auth/logout`, `DELETE /api/services/:id`, `DELETE /api/account/sessions` and `/api/account/sessions/:id`) accept only none or `{}` (400 otherwise), and reads none at all. A larger body gets 413 "Request is too large", and the connection is closed. One whose `Content-Length` says so gets it after the `Host` and request-target checks above. Until a credential signs in, every request is held to the default 150,000 bytes, before the credential is checked (a public route, the sign-in, `/health` or the web app's files, to its own), so a request without a credential learns nothing from a 413 about which paths and methods exist or what they take; once it signed in, its route's own limit applies, before the route's own checks (a sign-out whose cookie no longer signs in is held to its own limit too). One sent without a length (chunked) gets it at once on a read once signed in (on `/health` and the web app's files at once), and otherwise when a handler reads past the limit, after the credential and the route's own checks (a request that fails one of those gets that answer instead, and is closed without its body being read). Bodies are UTF-8 JSON: a `charset` other than UTF-8 gets 415, and bytes that are not UTF-8, a `\u` escape of half a surrogate pair (text that is not Unicode), a member name given twice in one object ("Field name … is given twice") or nesting deeper than 64 levels get 400. A client sending `Expect: 100-continue` gets `100 Continue` only when Uptime Goblin reads the body, after the Host, the credential and the route's own checks. A request whose headers have not all arrived within 20 seconds, or the whole request within 30, gets 408 and its connection is closed (Uptime Goblin checks every second, so within 21 and 31 seconds); at most 256 connections are open at once, and at most 32 from one client (one address, an IPv6 one by its /64; `GOBLIN_MAX_CONNECTIONS_PER_CLIENT` changes it): one more is closed at once, without an answer, so one client cannot take every connection. A proxy named in `GOBLIN_TRUST_PROXY` carries many clients' connections and is held only to the 256. A query parameter a route reads (`range`, `doc`, `instance`, the delivery history's) may be given only once (400). This is an internal administrative API, not a separately versioned public API contract.

`GOBLIN_PASSWORD` supplies the bootstrap only while `auth.json` is absent; with neither, Uptime Goblin refuses to start (exit status 78), since it always requires an admin password. Password changes require an already authenticated request. Successful changes take effect for subsequent requests without restarting the server: other sessions end, and the old Basic credential no longer works.

Answers without a usable sign-in are 401 `{error, code, transport: {kind, insecureAllowed}}`, where `code` is `signin_required`, `session_expired`, `invalid_credentials`, `multiple_credentials` or `basic_disabled` and `transport.kind` is `https`, `loopback` or `http`; only requests without browser headers (neither `Sec-Fetch-Site` nor `X-Goblin-Client`) get `WWW-Authenticate: Basic`, and only while legacy Basic is on and accepted on the request's transport. Browsers send no `Sec-Fetch-Site` to a plain-HTTP address on the network (they do to `localhost`, `127.x` and `[::1]`), so where Basic is accepted over plain HTTP (the `http` transport with the opt-in, and the `loopback` transport through a proxy on the Uptime Goblin host that sends no forwarding headers and keeps a loopback `Host`) a browser that opens an API address while it is not signed in gets the challenge too, and may show its own Basic prompt; scripts such as `wget` need the challenge before they send Basic. On the `http` transport without the plain-HTTP opt-in (`GOBLIN_INSECURE_HTTP_SESSIONS`) Basic is not accepted: a 401 there carries no Basic challenge, and, while legacy Basic is on, a script's Basic there gets 403 `https_required` before its password is checked; with it off, Basic gets 401 `basic_disabled` there as on every transport ([legacy Basic](authentication.md#scripts-and-legacy-basic)).

Every change, disclosure and export is recorded in the [audit log](security.md#audit-log). Sign-ins, sign-outs, session revocations, the password change and the signing key's replacement are recorded in the same `control.sqlite` write as the change. Configuration writes, **Retry**, **Resume** and both exports are recorded before they act, and refused with 503 `audit_unavailable` (`Retry-After: 30`) when that cannot be written: nothing was changed. Their result is recorded after the answer. Source tests, test emails and refreshes are recorded after they ran. A replayed `Idempotency-Key` answer records nothing new.

### Headers, retries and busy answers

Every answer after the Host allowlist, 401 and 403 included, carries `X-Goblin-Build`, except `/health`; only signed-in answers also carry `X-Goblin-Version` (such as `1.5.0`). A 1.4.3 page therefore notices the upgrade from its first refused request and reloads itself into the sign-in page. `X-Goblin-Build` is 12 hexadecimal digits identifying the exact release: the first 12 digits of a SHA-256 over the version and the SHA-256 of every file under `public/`, every `.mjs` file under `lib/` (both recursively, dot names skipped) and `server.mjs`. A 1.4.x tree has no modules in `lib/` subfolders, so it keeps the build it had. The installer computes the same value (`node lib/healthcheck.mjs --print-build <directory>`).

Every answer carries `X-Request-Id`, `/health`, refusals and the answers given while Uptime Goblin starts or stops included. It is the id that a proxy named in `GOBLIN_TRUST_PROXY` sent in `X-Request-Id`, when that is 1 to 64 letters, digits, dots, hyphens or underscores; otherwise a new UUID, so a client cannot put text of its own into Uptime Goblin's log. Uptime Goblin's log lines for unexpected failures end with `(request <id>)`, and each audit entry that a request made keeps it (**Request** on the Audit log page, `request_id` in exports). With nginx, `proxy_set_header X-Request-Id $request_id;` passes nginx's own id on (add `$request_id` to its `log_format` to log it).

Configuration writes (`PATCH /api/settings`, `POST /api/services`, `PATCH` and `DELETE /api/services/:id`, and `POST /api/import/uptime-kuma`, which requires it) accept `If-Match: <revision>`, the `config.revision` number from `/api/dashboard` (also as an entity tag, `"12"` or `W/"12"`). A mismatch returns 409 with `{error, revision}` and changes nothing; any other value (`*`, a list, `0x1`, `12.0`) gets 400 `if_match_invalid` and changes nothing.

Writes accept `Idempotency-Key: <8–128 letters, digits, hyphens or underscores>`. Uptime Goblin keeps the answer for 10 minutes (memory only, at most 1,000 answers and 4 MiB, answers over 64 KiB are not kept) for the same key, method, path and signed-in user (with its epoch, which an imported password or a restore advances), so a save retried after signing in again in a new session joins or replays its first attempt. A retry with the same key gets the same answer with `Idempotent-Replayed: true`, and a retry arriving while the first attempt still runs waits for it. The same key with a different body returns 422. 401, 403, 429 and 503 answers are not kept, so a retry (for example after signing in again) can still run. A write already applied when its session ended (**Replace signing key**, **Retry**, **Resume**, a test email the mail server was tried with) is answered 401 all the same, but its outcome is kept, so the retry signed in again is answered with it instead of applying the write twice. `POST /api/account/password` (and its alias `POST /api/auth/password`), `POST /api/auth/login`, `POST /api/auth/logout`, `DELETE /api/account/sessions` and `DELETE /api/account/sessions/:id` ignore the key and are never replayed. A restart forgets every key; the web app's retry across a restart relies on `If-Match`.

Configuration writes are applied one at a time. At most 16 wait for their turn, each for at most 20 seconds. Beyond either limit Uptime Goblin answers 503 `{"error": "…", "code": "busy"}` with `Retry-After: 5`, and nothing was applied: retry later. A write whose client disconnected before its turn is skipped. A shorter retention policy is saved before its cleanup starts; if saving fails, that request deletes no history. After a successful save, the response waits at most 20 seconds for pruning, which can then continue in the background. Each deletion batch checks the saved retention policy and stops if a later save increases it. Increasing retention cannot restore batches already deleted. Cleanup errors after a successful save raise a storage notice without undoing the saved policy.

The web app sends `X-Goblin-Client: web/<build>` with every request (the System page's "Open tabs by version" comes from it; the header also marks the request as a browser's, whose `Authorization` is ignored) and `X-Goblin-Activity: background` for requests no person made, which do not extend a session's 12-hour idle limit. A page opened with `?kiosk=1` sends it with every read, whoever asked for it; a write never carries it.

Docs keys are exactly `installation`, `configuration`, `notifications`, `integrations`, `architecture`, `security`, `troubleshooting` and `authentication`. Arbitrary paths are not read, and a guide is served only when it is a regular file of at most 1 MiB (not a symlink); anything else answers 404 "Documentation is not installed" without waiting for it. A docs JSON response is not an API to browse private files.

Export `version: 1` identifies the export wrapper format, not the app's version. `containsSecrets: false` refers to the removed credential fields; names, URLs, usernames and mail addresses still need privacy review. No import endpoint exists.

Previously cached UniFi, AMP, Nginx Proxy Manager, and CrowdSec sessions rejected with HTTP 401/403 may be renewed once within the same logical check. The refresh shares its original deadline and cancellation signal. A rejected fresh login or fresh session stops immediately; credentials are not retried in a loop.

## Updates and open pages

Uptime Goblin reads `public/` once at startup and serves `index.html` with its build in `<meta name="orbit-build">` and in the script and style URLs (`/app.js?v=<build>`). The page itself is never cached. Assets of the current build are revalidated (`no-cache` with an ETag); a request for another build's `?v=` gets the current file with `no-store`, never a 404, and that page then reloads itself.

The page compares its own build with `X-Goblin-Build` on every answer. When they differ, it reloads itself only when nothing would be lost: no unsaved form or source editor, no save on its way or without an answer, no open dialog and no password change in progress. A visible tab waits until 10 seconds after the last key press or click, shows "Uptime Goblin was updated. Reloading this page…", and reloads a second later, returning to the same route, expanded card, range, measurement and scroll position. Otherwise it shows a banner with **Reload** and checks again after each load, closed dialog and finished save. Tabs in the background do not poll; they ask `/api/version` every 5 minutes. A page opened with `?kiosk=1` always reloads. At most 2 unsuccessful automatic reloads happen per 10 minutes; a successful response matching the current page resets this guard and withdraws an obsolete update banner; if the page is still the old one after that (a proxy or browser cache serving an old copy), the banner says so. Without session storage the page shows the banner instead of reloading. A build that stops being reported (a rollback to 1.4.2) also counts as a change. Pages opened on 1.4.2 or earlier contain none of this and need one manual reload.

Every request has a time limit: 30 seconds for reads, 60 for saves and 150 for connection tests (Uptime Goblin allows a test 120 seconds). A dashboard load still running after 45 seconds is abandoned and started again, and the page loads again when the browser reports the network is back. While Uptime Goblin does not answer, the header shows "Reconnecting…" and the page keeps trying by itself. A save that gets no answer is retried once with the same `Idempotency-Key` and `If-Match`, but only when a fresh load shows the settings revision unchanged; otherwise the page says the change "may have been saved", shows the latest settings and keeps the edits.

## Process lifecycle

First, in `server.mjs`'s main block (after its modules have loaded and its launch setup has run, before the steps below), a start under a service manager (`--supervised`, or `GOBLIN_SUPERVISED=1`) checks the memory, CPU and process limits of its own cgroup and refuses (78) while one is not in force unless `GOBLIN_ALLOW_UNLIMITED` names it ([resource limits](installation.md#resource-limits)); a malformed `GOBLIN_ALLOW_UNLIMITED` refuses there, supervised or not. What it found reaches `/api/system` and the audit log's start entry. Then a start runs these steps in order, and a failure or a stop signal undoes the ones already taken:

1. Read the admin password sources (`auth.json`, or `GOBLIN_PASSWORD` when there is no `auth.json`) and apply the start guard: no start without one, on loopback as on any other address. Nothing is written.
2. Take `goblin.lock` in the data directory. Another Uptime Goblin process (usually the previous one, still stopping after a restart) or a `goblin-admin` command holding it makes the start exit 75; the service manager starts it again shortly.
3. Check `config.json` without writing it, so a corrupt file refuses the start before anything else changes.
4. Open `control.sqlite`: refuse when a snapshot restore was interrupted part way (its journal is still there) or when its data comes from a newer release, each before this step writes anything (exit 78; the data directory then differs only as after a key refusal, below); remove leftovers of an interrupted snapshot; take the pre-migration snapshot (without `history.sqlite`); apply the migration steps, each all or nothing; and write `created-by.json` when the directory was created by 1.5 or later and lacks one, so a new `control.sqlite` still knows it was (legacy Basic stays off by default). The encryption key is read here (and removed from the environment), and checked against an existing keyring, before this step writes anything: a key refusal exits 78, and the data directory then differs only by `goblin.lock`, which step 2 creates (with the data directory) where it is missing, and, on a disk already full, by the space reserve deleted before this step. Before this step, when the disk is already full, Uptime Goblin deletes its space reserve so the start has room.
5. Identity: take a password changed outside Uptime Goblin, sign everyone out after a snapshot restore or when `control.sqlite` is not the file of the last start (a restored backup, a data directory copied or moved to another disk), retry a pending `auth.json` mirror, and print one line saying where the admin password comes from and whether legacy Basic and plain-HTTP sessions are on. Only once identity has accepted the start is a missing keyring created (and `secret.key` generated when no key source exists), so no refusal leaves a keyring or a generated `secret.key` behind; then a line names the key's source and fingerprint.
6. Open `config.json` and `history.sqlite`, then the delivery service. Signing settings are preserved in the current schema before retired authority is cleared. Keys from formerly revealable HMAC fields, including possibly equivalent active keys when retired material cannot be read, are never adopted or overlapped. With a webhook, replacement creates fresh authority and a persisted hold until receivers have its public key and an administrator presses Resume; without a webhook, retired authority is cleared without creating a key. A safe current-format key may continue signing while a separate normalization write waits. Uptime Goblin never sends an unsigned webhook. If signing settings cannot be read or no usable signing key is available, delivery waits. With newer read-only settings, a usable current key may keep signing only when no saved signing hold applies; saved holds stay effective. **Replace signing key** always refuses such settings. **Resume** cannot clear an immutable saved hold or resume without a usable current key. These compatibility refusals answer 409 `signing_compatibility` with no `Retry-After`: "A newer Uptime Goblin saved these signing settings. Upgrade Uptime Goblin or restore a compatible backup before changing them.". A missing usable key in writable settings instead answers 503 `signing_unavailable` with `Retry-After: 60`; concurrent changes answer 409 `signing_conflict`. Probe paused channels except those held for signing, restore data and roll-forward handling, then start the scheduler, storage guard, audit's hourly job and delivery jobs, and listen. Failed writes wait and are retried every 10 seconds; they never permit unsigned delivery.

A stop signal during the start stops it at the next step (a snapshot or migration step already running completes) and exits 0 ("Uptime Goblin stopped while it was starting."). A stop closes in the reverse order and releases `goblin.lock` last.

Once listening, Uptime Goblin writes `<data directory>/run/status.json` (directory mode 700, file mode 600, replaced atomically):

```json
{"version":"1.4.3","build":"…","pid":1234,"nonce":"…","startedAt":1800000000000,"listen":{"host":"127.0.0.1","port":4317},"observed":{"forwardedProto":"https"}}
```

`nonce` is new for every start, and `/health?instance=` compares against it. `observed.forwardedProto` records the protocol (`http` or `https`) that the trusted proxy (`GOBLIN_TRUST_PROXY`) reports in `X-Forwarded-Proto` or `Forwarded: proto=`; a proxy that sends forwarding headers without a protocol counts as `http`. It is `null` until the first request through that proxy after each start. On a clean stop the file is removed, but only if it still belongs to this process.

| Exit status | Meaning |
|---|---|
| 0 | Stopped by SIGINT or SIGTERM, also during the start. Supervised (`--supervised` or `GOBLIN_SUPERVISED=1`, which the systemd unit and Docker image both give), an exit that no stop signal caused is changed to 1; without it, it is still logged ("Uptime Goblin stopped although no stop signal was received.") |
| 1 | A failure that may pass on its own: a full, busy or failing disk, no free file handles or memory, a busy or locked SQLite database, the address already in use or not yet available (a LAN address at boot), or a stop that did not finish cleanly. systemd restarts Uptime Goblin after 5 seconds. |
| 75 | Another process holds `goblin.lock`: the previous Uptime Goblin is still stopping, or a `goblin-admin` command runs. systemd starts Uptime Goblin again after 5 seconds. |
| 78 | A refusal: starting again cannot help until someone corrects it. Invalid `config.json` or `auth.json`, the password rules (such as a too-short `GOBLIN_PASSWORD`, or no admin password at all: neither `auth.json` nor `GOBLIN_PASSWORD`), data from a newer release, an encryption key problem (`key_missing`, `key_mismatch`, `key_invalid`, `key_file_unreadable`), an invalid `GOBLIN_TRUST_PROXY`, an invalid `GOBLIN_MAX_CONNECTIONS_PER_CLIENT`, a memory, CPU or process limit not in force under supervision that `GOBLIN_ALLOW_UNLIMITED` does not name, a malformed `GOBLIN_ALLOW_UNLIMITED` or `GOBLIN_SUPERVISED`, a `GOBLIN_LEGACY_BASIC` that is neither yes nor no, Docker Compose's plain-HTTP default on a port published beyond loopback without a trusted proxy, an argument to `server.mjs` other than `--supervised`, a privileged port, or a start path that does not resolve to `server.mjs`. The log says "Uptime Goblin refused to start (exit status 78)". The systemd unit does not restart it (`RestartPreventExitStatus=78`). Only these checked refusals exit 78: disk, database and unexpected errors exit 1 and are retried. |

On a stop, Uptime Goblin first sends what is due, email digests included (for up to 8 seconds), then stops the delivery worker (up to 7 seconds; a claim made during the stop starts no send) and the background jobs (up to 2 seconds), closes connections still open after 10 seconds, records sign-outs it could not yet write (up to 5 seconds) and closes the audit log (up to 2.5 seconds): about 36 seconds at most. Notifications waiting to retry, held or in the middle of a send stay queued for the next start. Compose gives the container 40 seconds; systemd's default of 90 seconds is enough.

Limits bound individual work; they are not a measured hardware sizing guarantee. Total memory scales with the collection concurrency; allow at least 512 MiB of RAM, and 1 GiB with the maximum concurrency or several very large sources. If a history write still fails (for example a disk filled by other programs), collection and alerts keep running, Uptime Goblin sends one "cannot write its history database" notification, and the dashboard shows a notice. The all-clear notification follows once every source whose write failed has written again and writes have succeeded for five minutes (a reading the storage guard paused on a full disk was not written, so it does not count), so an intermittent fault does not send a stream of notices. Large retained histories and many sources still consume storage and API capacity. Review [installation and backups](installation.md) before increasing retention substantially.
