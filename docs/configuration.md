# Configuration

[Back to Uptime Goblin](../README.md) · [Integrations](integrations.md) · [Alerts and notifications](notifications.md) · [Examples](../examples/README.md)

Use Uptime Goblin's configuration page to change the login password, appearance, collection, alerts and email, to see whether notifications were delivered (**Configure → Notifications**) and who changed what (**Configure → Audit log**), and the source editor for individual connections. Saved preferences belong to the server and are shared by its browsers. Browser refreshes do not stop the collector.

## Uptime Goblin login password

Open **Configure → Account** while signed in to Uptime Goblin (1.4.x called this page Security; old `#configure/security` links open it). Enter your **Current password**, fill **New password** and **Confirm new password**, then choose **Change password**. A wrong current password is refused and counts toward the [sign-in lockout](security.md#failed-sign-in-throttling). Use at least 12 characters; the maximum is 1,024 UTF-8 bytes. Passwords are not trimmed, and an empty password cannot disable authentication. Save the password in your password manager before leaving the form.

After success the page says "Password changed. Other devices were signed out." This browser stays signed in; every other browser and device is signed out, and scripts using Basic must use the new password. Collection, history and source credentials are unchanged; no service restart is needed.

The same page shows your sign-in (when it started and ends) and your sessions, where **Sign out** ends one of them and **Sign out other devices** all but this one; a device that signed in after this one ("Signed in later") only a newer sign-in can end. See [signing in](authentication.md) for how long sessions last and for HTTPS.

Uptime Goblin keeps the password as a salted scrypt hash in its control database (`control.sqlite`) and writes every change back to private `auth.json` inside `GOBLIN_DATA_DIR`, so 1.4.x uses the current password after a rollback (once `auth.json` has been written: while it cannot be, every page shows "Uptime Goblin saved the admin password but could not update auth.json", and 1.4.x would still use the previous password). When `auth.json` exists, it takes precedence over `GOBLIN_PASSWORD`, including after restarts or upgrades. The environment password is only the initial bootstrap when `auth.json` is absent; changing the environment does not reset a saved password. A password changed outside Uptime Goblin (a new `auth.json`, or a new `GOBLIN_PASSWORD` on an install without one) is imported at the next start and signs every session out. Authentication data is separate from `config.json` and is never included in configuration exports. Include the whole data directory, with `auth.json` and `control.sqlite`, in private backups. See [forgotten-password recovery](troubleshooting.md#forgotten-uptime-goblin-password) if you cannot sign in.

## First connection

1. Add a source or edit an included empty card. Choose a recognizable name and group.
2. Set the destination URL to the page you want a click to open. Set the collection address to the API/exporter reachable **from Uptime Goblin's server**.
3. Choose a **Monitoring method**. Use the service default for native statistics, or **Website check** for a simple HTTP(S) response check without API credentials. Native integrations should use a dedicated credential with the narrowest useful permissions; see the [integration matrix](integrations.md).
4. Use **Test connection** to inspect draft settings using their retry policy without saving, recording history, enabling monitoring or creating alerts. A rate-based measurement may need recurring samples to become available.
5. Save with monitoring enabled when ready. Expand the card to inspect readings, then add thresholds in the values' recorded units.

Empty cards are not connected. Uptime Goblin does not discover the lab or fetch old history. Adding multiple sources of the same type creates independent credentials, history and alert state. Three empty Cosmos slots are included; they do not imply three detected servers.

| Initial graph range / `appearance.defaultRange` | `1h`, `6h`, `24h`, `7d`, `30d` | `24h` |
| Sort / `appearance.sortBy` | `manual` (saved source order), `name`, `status` | `manual` |
| Summary / `appearance.showSummary` | Boolean | `true` |
| Show paused cards / `appearance.showPaused` | Boolean | `true` |
| Show unconfigured cards / `appearance.showUnconfigured` | Boolean | `true` |
| Open links in a new tab / `appearance.openInNewTab` | Boolean | `true` |
| Reduce motion / `appearance.reduceMotion` | Boolean | `false` |
| Time zone / `appearance.timezone` | `local`, `UTC`, a fixed offset written `UTC±HH:MM` such as `UTC+05:30`, `UTC-08:00` or `UTC+05:45` (hours 00–14; minutes 00, 15, 30 or 45), or a region-based IANA name such as `Europe/London` or `America/Chicago`. Abbreviations (`BST`, `IST`), other offset spellings (`+05:30`, `GMT+5`, `UTC+5:30`) and legacy aliases are refused because browsers disagree about them. | `local` |
| Clock format / `appearance.timeFormat` | `auto`, `12h`, `24h` | `auto` |

`local` follows each browser's time zone; stored timestamps remain absolute timestamps. A fixed offset never changes for daylight saving time and shows correctly in every browser, including those that cannot handle offsets themselves; use a region name when you want daylight saving time followed. `UTC+00:00` and `UTC-00:00` are saved as `UTC`, and a minus sign (−) as a hyphen. A zone written differently in a hand-edited `config.json` is rewritten once at startup and logged, and one Uptime Goblin cannot use is replaced by `local`. A region name that a particular browser does not know is shown in that browser's local time, with a note in the settings. Orbit 1.4.2 and earlier do not accept offsets: rolling back replaces an offset with `local`, and it stays `local` after upgrading again, so set it again. A chosen graph range cannot recover data older than the retained collection history. Column layout still adapts to available screen space.

## Collection and retention

| JSON field | Accepted values | Default / meaning |
|---|---|---|
| `pollSeconds` | Integer 15–3600 | 60 seconds between completed polls unless overridden per source |
| `retentionDays` | Integer 1–365 | 30 days of readings/events |
| `monitoring.concurrency` | Integer 1–8 | 4 source workers |
| `monitoring.timeoutSeconds` | Integer 5–120 | 90-second total deadline for all attempts and retry delays in a collection/connection test |
| `monitoring.retryCount` | Integer 0–3 | 2 extra attempts after a transient failure; 0 disables retries |
| `monitoring.retryDelaySeconds` | Integer 1–30 | 2 seconds between retry attempts |
| `monitoring.availabilityFailures` | Integer 1–10 | 2 qualifying failed samples before an availability alert |
| `monitoring.availabilitySeconds` | Integer 0–3600 | Failure must also persist for 60 seconds |
| `monitoring.recoverySuccesses` | Integer 1–10 | 2 consecutive healthy checks before an active alert can recover |
| `monitoring.recoverySeconds` | Integer 0–3600 | Recovery must also persist for 60 seconds |

Each individual source HTTP request may use a quarter of the overall deadline (12–25 seconds, covering the destination check, connection setup, TLS and the whole answer) and has a 16 MiB body limit. A source becomes due after its prior collection completes plus its interval, so request time contributes to cadence drift. Independent scheduler ticks fill free worker slots, but capacity limits can still delay a due source; intervals are not a real-time sampling guarantee. Uptime Goblin never intentionally polls the same source concurrently with itself. Start conservatively for overloaded controllers or large media libraries.

Retries apply to transient network failures, timeouts, and HTTP 408/429/5xx responses. Rejected authentication, malformed responses, and configuration errors are not retried. All attempts form one logical check: only its final outcome is saved, and attempts do not count as separate failure/recovery confirmations. The total deadline can stop a check before all permitted attempts are used. **Test connection** uses the same policy without writing history or alert state. Email and webhook delivery retry by rules of their own: see [alerts and notifications](notifications.md#durable-delivery).

Availability alerts require both the failed-check count and failure grace. Recovery of an active connection or metric alert requires both consecutive healthy checks and the recovery grace. A metric must also reach its recovery boundary. Missing/error readings reset recovery progress; they cannot establish recovery.

Reducing retention prunes older readings/events and is not reversible without a backup. Periodic pruning also occurs during collection (at startup, then hourly). Pruning deletes in short steps, so collection keeps running while a large history is trimmed. The [5-minute summaries](architecture.md#state-and-history) of the deleted readings go with them; while a prune runs, 7- and 30-day charts read the readings instead. A lower retention setting must save successfully before its cleanup starts; a failed save preserves that history. The response then waits at most 20 seconds for pruning, which can continue in the background. A later increase stops further batches but cannot restore deleted readings. Deleting rows can grow SQLite's write-ahead log and does not necessarily shrink its files, so free host disk space first if Uptime Goblin cannot save settings. A dashboard/exported preference file is not a database backup.

## Source options

| Field | Behavior |
|---|---|
| `name`, `group`, `color` | Display identity and grouping; colors use the accent choices above. Names, groups, usernames, metric labels and units, and the dashboard name and subtitle are single lines: control characters (line breaks, tabs), line separators and text-direction overrides (U+202A–U+202E, U+2066–U+2069) are refused. Values saved by older releases are repaired once at startup (a line break becomes a space, a direction override is removed), and the log names the field, never its text. A Prometheus mapping's label filters (`labels` values) are not display text and keep any character but NUL: they must equal the exporter's values. Any saved text holding half of a surrogate pair (a `\u` escape older releases accepted) is made whole at startup, U+FFFD in place of the half, logged by its place in the file. A rule key, a label filter or a JSON mapping path made whole this way is compared with the source's text made whole too (for a label filter or a path step, only when nothing matches it as the source sent it; see [mappings](integrations.md#exporter-and-json-mappings)). Which half a label filter or path held is lost: its mapping reads as before while the source sends neither U+FFFD itself nor another half at that place. With U+FFFD there it reads that series or member instead, and with two different halves there it reads nothing, with a note on the source; the start log says so once. Two rule keys of one source that differed only in such a half are one key once made whole: the first rule is kept and the later ones are removed, logged by their place (the start was refused). A key saved twice as the same text still refuses the start. |
| `url` | Destination opened when clicked; independent from collection. |
| `apiUrl` | HTTP(S) API/exporter base. No embedded credentials, query or fragment. Website checks may use the destination when this is empty. |
| `enabled` | Monitoring switch. Off pauses polling, cancels its active result and suppresses new source alerts. |
| `showOnDashboard` | Default `true`; hiding is visual only and does not stop polling, history or alerts. A [wall display](authentication.md#wall-displays) signed in with a display code does not receive a hidden source at all. |
| `pollSeconds` | `0` follows the global interval; otherwise integer 15–3600. |
| `monitoring` | Per-source overrides for retry count/delay, total timeout, availability count/grace, and recovery count/grace. Same names/ranges as above, without `concurrency`. Omitted fields inherit; setting a field to `null` removes its override. |
| `alerts` | Per-source notification-category overrides: `notifyAvailability` and `notifyMeasurements`. Boolean values override workspace category defaults; `null` removes an override. These control delivery, not alert evaluation/history. |
| `apiKey`, `username`, `password` | Collector-specific authentication. Stored keys/passwords are never returned; flags indicate whether they exist. |
| `collector` | `native`, `none`, `http`, `linux`, `windows`, `prometheus`, `json`. An override changes collection while preserving the card's service type. |
| `siteId` | UniFi Integration API site UUID, or local-login site name; meanings differ by authentication mode. Letters, digits, hyphens and underscores, at most 100; a value saved by an older release keeps loading. |
| `nodeName` | Native Proxmox only: exact, case-sensitive node name, up to 63 characters. Empty (default) collects the whole visible cluster. |
| `httpMethod` | Website checks: `GET` (default) or `HEAD`. |
| `httpExpectedStatus` | Website checks: comma-separated HTTP status codes or inclusive ranges. Default `200-399`; examples: `200`, `200-299`, `200-399,401,403`. |
| `metricPath` | Optional path used by custom/exporter/HTTP collectors, such as `/metrics`; no query, fragment or backslash. |
| `metrics` | Additional numeric mappings; see below. |
| `rules` | Above/below numeric threshold rules; see alerts below. |

Leaving credential inputs blank in the source editor preserves existing secrets. Use its explicit clear option to remove them. An API caller preserves a secret by omitting the field; sending an empty string clears a source credential. Email password behavior is different and is described below.

Pausing retains old readings as history and clears current/pending source alerts without announcing recovery. Resuming starts evaluation again. Removing a source deletes that source's saved readings, latest state, alerts and event history. Back up first if you need to retain them.

In the source editor, **Retry & confirmation overrides** shows inherited workspace values as hints. Leave an input blank to inherit. Zero is an explicit override for retry count and failure/recovery grace; it does not mean “use default.” Source notification selectors offer the workspace default, send, or mute. The workspace alert-enabled and alert/recovery transition switches still apply.

### One Proxmox card per node

Add a Proxmox source for each host and enter its exact **Proxmox node name**, such as `Proxmox-1`. All cards can use the same reachable cluster API address and appropriately scoped read-only token; each card's destination URL can open its own node. Leave the node name blank for a separate cluster-wide overview. Each card keeps independent history and alert rules.

For a selected node, `node_online` is `1` when online and `0` when the cluster reports it offline. Add a **Below 1** rule for this measurement to alert on an offline node even while the cluster API remains reachable. Set the sustained duration to suit the host. Offline node runtime measurements are omitted; an unknown or invisible node fails collection rather than silently showing cluster totals. API connection failures still use the workspace availability-alert settings.

### Check a service's website

Every source offers **Website check** under **Monitoring method**, including cards named for Docker-hosted applications. Enter the **Website URL to check**, or leave it blank to use the card's destination URL. No API key, password or cookie is sent. The source keeps its name, icon and launch link while its readings become response time (`response`, milliseconds), availability (`available`, 1 for an accepted response) and HTTP status (`http_status`). This replaces native collection for that card; add a second source if you want both kinds of readings. The check never sends saved credentials. If you point it at a different server than the card's saved collection address, the saved API key and password are cleared (you are told so when saving), so switching back to native collection later needs them re-entered.

The default accepted statuses are `200-399`. Redirects are accepted by status but **never followed**: a redirect to sign-in proves that the front door responds, not that the application behind it works. Enter `200-299` to require success without a redirect. Add `401` or `403` explicitly only when an authentication response is expected. Other status codes, network failures and TLS errors are collection failures, produce history gaps and use the normal connection-alert settings.

`GET` works with most services. `HEAD` requests only headers, but some applications do not support it. Response time measures receipt of the response headers; the page body and its assets are not downloaded. Under **Optional website path**, a saved `metricPath` is appended to the URL. Clear a previous `/metrics` or API path when you intend to check the website root. Switching monitoring methods preserves saved native connection settings; they are not used by the website probe. Changing the effective collector clears old active metric warnings without recovery notifications and starts a gap in the source's history, so measurements from different methods are not joined. Always test the selected URL from Uptime Goblin before saving.

## Importing from Uptime Kuma

**Configure → Sources → Import from Uptime Kuma** turns the monitors of an Uptime Kuma 1.x backup into Website checks. In Uptime Kuma, open **Settings → Backup** and choose **Export** (JSON); the file holds a `version` and a `monitorList`. Choose that file in Uptime Goblin. The browser reads it, refuses anything that is not a 1.x backup (a file over 8 MB, invalid JSON, another version, more than 1,000 monitors, two monitors with one id, or a field named `__proto__`, `constructor` or `prototype` in the backup or in a monitor), and sends Uptime Goblin only the fields the import reads, with every credential replaced by `redacted` and removed from each address. Uptime Goblin then shows what it would do, and saves nothing until you choose **Import**. Nothing is fetched while importing: no monitor's address is contacted until its Website check runs.

The preview has three lists:

- **Will be added**: each HTTP(S) and keyword monitor as a new Website check, with its name, group, address, method and interval. The group is the Uptime Kuma group the monitor belongs to, otherwise **Utilities**. A paused monitor is added paused.
- **Will be changed (same name)**: a monitor whose name (ignoring case) is already that of one Uptime Goblin Website check changes that check: its address, method, accepted statuses and interval follow the monitor, its group follows the monitor's Uptime Kuma group (a monitor in no group leaves the check's Uptime Goblin group as it is), and a separate check address or website path it had is cleared so the check tests the monitor's address. Whether it is paused stays as it is. A second monitor with a name already used in the same import is added with a number, such as `Plex (2)`.
- **Skipped**, each with its reason: every other monitor type (ping, TCP port, DNS, Docker, push, JSON query, groups and the rest), a monitor in upside down mode, one that sends a method other than `GET` or `HEAD`, one whose address is not HTTP(S) or not one Uptime Goblin accepts, one whose accepted statuses Uptime Goblin cannot express (codes outside 100–599, or more than 20 entries), one already in Uptime Goblin with the same settings, a name used by an Uptime Goblin source of another type or by several sources, a malformed entry, and any monitor beyond Uptime Goblin's 200 sources.

How each setting is carried over:

| Uptime Kuma | Uptime Goblin Website check |
|---|---|
| Friendly name | `name`, one line of at most 100 characters (control characters become spaces; a longer name is shortened and noted) |
| URL | `url`, the address the check requests; a user name, password or credential-like parameter (`?token=`, `#access_token=`) is removed and noted |
| Method | `httpMethod`, `GET` or `HEAD` |
| Heartbeat interval | `pollSeconds`, clamped to 15–3600 seconds (noted when changed); none means Uptime Goblin's default interval |
| Accepted status codes | `httpExpectedStatus`; none means Uptime Kuma's default, `200-299` |
| Keyword (and inverted keyword) | Not checked: the Website check tests the status only. The monitor is imported and the keyword is listed as unsupported |
| Max redirects | Uptime Goblin never follows redirects. When the monitor followed them and its accepted statuses leave out part of `300-399`, the preview says to use the final address or accept `300-399` |
| Ignore TLS/SSL errors | Not imitated: Uptime Goblin always verifies certificates, so a self-signed or expired one fails the check (noted) |
| Upside down mode | Skipped |
| Proxy | Not imitated: Uptime Goblin connects to the address directly, so it must be reachable from Uptime Goblin (noted) |
| Basic auth, NTLM, OAuth, headers, body, client certificates | Never imported. The monitor is marked **Needs credentials re-entered** when it sent any: a password, OAuth client secret, client key, header or body whatever its authentication method, or the user name, domain, client ID or certificate of the method it used. A monitor with no method saved (an older Uptime Kuma, or none) that has a basic-auth user name is marked too, since such releases sent it whenever it was set. The method alone, and settings Uptime Kuma saves for every monitor (such as the OAuth authentication method), mark nothing. A Website check sends no credentials, so such a site may answer 401 or 403; accept that status, or check a public address |
| Notifications, maintenance, status pages, tags, history | Not imported |

**Import** saves every added and changed source in one configuration revision, and only if the configuration is still the one the preview was made from: if anything was saved meanwhile (another tab, another device), Uptime Goblin refuses, the page shows the new preview, and you confirm again. The import is one entry in the audit log, **Imported from Uptime Kuma: n added, n changed, n skipped**, with the settings before and after. Test a few of the new checks with **Test connection** afterwards.

For scripts the import is two API calls, both signed in with the `config:import` permission (held by the admin) and the write headers (`X-Goblin-Request: 1`), and both taking the backup as the JSON body, at most 150,000 bytes (413 above): `POST /api/import/uptime-kuma/preview` answers `{version, add, change, skip, notes, revision}` and changes nothing, and `POST /api/import/uptime-kuma` with `If-Match: <revision>` saves that plan (428 without `If-Match`, 409 when the configuration changed). A backup that is not a readable 1.x backup gets 400 with the reason. A larger backup can be sent reduced to the fields the import reads, as the web app sends it. `goblin-admin` has no import command.

## Numeric mappings

JSON mappings use dot-separated paths. Exporter mappings use exact metric names and optional exact label filters. Matching exporter series are summed; select labels when a single device or gauge is intended. `scale` multiplies the value and defaults to 1. PromQL and custom scripts are not supported.

```json
[
  {"key":"temperature","label":"Temperature","path":"system.temperature","unit":"°C"},
  {"key":"free","label":"Free disk","path":"storage.freeBytes","unit":"bytes"}
]
```

Use the [JSON](../examples/json-mappings.json) and [Prometheus](../examples/prometheus-mappings.json) examples as shapes, then inspect your actual source. A nonexistent field remains unavailable; it does not become zero.

## Alerts and notification controls

| JSON field | Default | Meaning |
|---|---|---|
| `alerts.enabled` | `true` | Evaluate and retain active/pending alert state. Turning off clears that state silently; sampling and prior event history continue. Re-enabling evaluates from scratch. |
| `alerts.notifyOnAlert` | `true` | Permit future firing notifications through configured email/webhook channels. |
| `alerts.notifyOnRecovery` | `true` | Permit future recovery notifications through those channels. |
| `alerts.notifyAvailability` | `true` | Default delivery for connection-check alerts/recoveries; individual sources can override. |
| `alerts.notifyMeasurements` | `true` | Default delivery for metric-threshold alerts/recoveries; individual sources can override. |

Notification switches do not disable in-app alert evaluation. A notification still waiting (to be sent, or to retry) when its kind of alert is switched off, or its source is deleted, is not sent: Uptime Goblin checks again just before sending. One already being sent may still arrive. No existing alerts are replayed when a channel or notification switch is enabled. A future recovery can therefore arrive for an alert whose initial notification was not sent.

**Connection check** means Uptime Goblin could not complete its configured API, exporter or website request. It does not prove the application is unavailable to everyone. **Metric threshold** means a reported value crossed a configured boundary: a reachable service can still have high memory, a full disk or application health warnings. Retrying a successful reading does not remove a valid metric warning.

Threshold rules use `key`, `operator` (`gt` or `lt`), finite `threshold`, and `forSeconds` (0–86400, default 120). A rule's `key` must equal a reading's key exactly, white space included: a key made from a source's ID or path keeps white space at either end. The source's **Metric thresholds** editor keeps a key chosen from its **Measurement** list, and the key of a rule you edit, as they are, and trims a key you type. One rule per measurement, at most 30 per source. Keys starting with `__` are reserved. Rules require at least two qualifying samples plus the sustained duration. Connection availability uses the separate failure-count/duration settings instead.

Optional `recoveryThreshold` gives a firing metric alert a separate recovery boundary. Blank/omitted/`null` uses the original threshold. For an **Above** rule it must be at or below the trigger; recovery readings must be at or below this boundary. For a **Below** rule it must be at or above the trigger; recovery readings must be at or above it. Values between trigger and recovery keep an active warning in place and reset recovery confirmation. For example, memory above 90% can trigger an alert and 88% or below can confirm recovery, reducing repeated notifications around 90%. Both the healthy-check count and recovery grace still apply. Select **Edit** on an existing rule, update it, then save the connection.

Connection alerts say why the check failed (for example "Source is unavailable: DNS lookup failed…"), recoveries say how long the outage lasted, and every failed reading keeps its reason: hover a failed point on a chart, or export the history as CSV.

### Fewer, more meaningful alerts

Email alerts are gathered until a minute passes without a new one (at most three minutes), then sent as one message listing each source (up to 100), so a network or DNS outage produces one email instead of one per source. A single alert therefore arrives up to a minute later than it fires. When Uptime Goblin stops it first sends what is due, gathered email included, for up to 8 seconds; anything still waiting (a retry, a paused channel) is sent after the next start. Webhooks still receive one call per event.

If a source alerts and recovers repeatedly:

- Raise **Failed checks before alerting** and **Failure grace** (workspace or per source) so a short blip must last longer before it alerts. For example 3 checks over 180 seconds.
- Raise **Recovery grace** (for example 300–600 seconds) so a source that fails again soon after recovering continues the same alert instead of sending a new alert/recovered pair.
- Give metric rules a recovery boundary (memory above 90% alerts, 88% or below recovers) so a value hovering at the threshold does not flap.
- If many hostname-based sources fail at the same moment, the cause is usually DNS or the network path, not the services. See [troubleshooting](troubleshooting.md).

Use the numeric units stored by the collector: CPU is 0–100 percent; a bytes threshold is raw bytes, not the displayed GiB. Missing/error readings reset pending metric timers and cannot falsely resolve an already-firing metric alert. Changing a rule's operator, threshold or duration (or removing it) resets that rule's alert state; changing only its recovery boundary keeps a firing alert and restarts its recovery confirmation. Changing the monitoring method or Proxmox node resets all of the source's alerts.

## Email

Open email settings over HTTPS. For Gmail, create a new [Google app password](https://support.google.com/accounts/answer/185833) on an eligible account with 2-Step Verification. Enter the sender address (also the SMTP username), one recipient, and that app password. Default transport is `smtp.gmail.com`, port 465, implicit TLS. Other authenticated SMTP hosts can use implicit TLS or required STARTTLS; certificate validation is mandatory.

Save while email is disabled if you want to test before automatic mail begins. **Send test email** uses saved settings and sends one real message even when automatic email is off. It requires an authenticated Uptime Goblin login and is limited to one per minute, and to none while an email is being sent. Check the inbox/spam folder after success: server acceptance is not proof of inbox delivery. If your session ends while the test is being sent, the **Sign in again** dialog shows what the mail server answered for that test instead of sending a second one. A test the mail server accepts also resumes email delivery that was paused (for example after a sign-in failure). Email must be enabled, set up, global alerts enabled, and the corresponding transition switch enabled for automatic messages; while email is enabled but not set up, Uptime Goblin makes no email notifications at all.

The stored `email` object contains `enabled`, `host`, `port`, `secure`, `from`, `to`, and private `password`. `secure: false` means mandatory STARTTLS, never plaintext SMTP. A blank/missing email password preserves the saved secret. Changing host, port, TLS mode or sender is refused unless the same save re-enters the app password (or clears it with `clearPassword: true` while email is off), so a saved password is never sent to a different server or account. The recipient can change freely. Email still waiting or held when you save goes out with the new settings, to the new recipient. `clearPassword: true` removes it only while email is disabled. Public responses expose `passwordConfigured`, not the password. Gmail's grouped spaces are removed.

Delivery is durable: each notification is saved in Uptime Goblin's control database before it is sent, sent one message at a time with a 20-second deadline that also covers looking up the SMTP server's address, retried after a temporary failure (30 seconds, doubling up to 15 minutes, for up to 24 hours), and kept across restarts. A sign-in failure, a refused sender, an SMTP server whose address is not allowed or incomplete settings **pause** email until you save corrected settings, send a test email that is accepted, or press **Resume** on **Configure → Notifications** (Uptime Goblin also tries once at each start, and every 15 minutes when the server's certificate is not trusted). A message whose acceptance is unknown is sent once more after 5 minutes with the same `Message-ID`. Each message has a `Message-ID` of `<orbit.g_…@your sender's domain>`. The Email page's status says what happened, survives a restart, and links to the **Delivery history**; saving email settings clears its last error. See [alerts and notifications](notifications.md). An external monitor is needed to detect loss of Uptime Goblin's own host.

## Webhook

Set `GOBLIN_WEBHOOK_URL` on the server and restart. It may be at most 2,048 characters (a longer one pauses the webhook); plain `http://` to another computer works but starts with a warning, since the URL (with any token in it) and every notification then cross the network unencrypted. The receiver gets a generic JSON POST, not provider-specific Slack/Discord formatting, with 1.4.2's body unchanged:

```json
{"source":"orbit","service":"linux-1","name":"Example host","kind":"firing","category":"measurement","rule":"cpu","message":"CPU is 95 % (above 80)","time":1800000000000}
```

`kind` is `firing` or `resolved`; `category` and `rule` say which alert it is, and a recovery has the same `service` and `rule` as its alert ([the fields](notifications.md#the-webhook)). Each request also carries `X-Goblin-Delivery` (the same on every attempt of one notification) and `X-Goblin-Signature` (Ed25519 over the delivery id, the time and the body; receivers verify it with the public key under **Configure → Notifications → Show public key**). Webhooks have an 8-second deadline and do not follow redirects. A failed request is retried (30 seconds, doubling up to 15 minutes, for up to 24 hours; a `429` or `503` with `Retry-After` holds the webhook that long); a request the receiver does not answer within 8 seconds is sent once more after 2 minutes; a redirect or a `401`, `403`, `404` or `410` answer, or an untrusted certificate, pauses the webhook until it works again (Uptime Goblin tries every 15 minutes and at each start) or you press **Resume**. Loopback and `http:` addresses work; link-local, multicast and reserved addresses, and a URL with a user name or password, are refused (the webhook pauses). Email and webhooks operate independently and obey the shared future-transition switches; when one pauses, the other tells you, and again when it works again, as those switches allow ([paused channels](notifications.md#paused-channels)). How to verify signatures and drop repeats: [the webhook](notifications.md#the-webhook). Protect webhook URLs as credentials if the receiver embeds a secret in its address.

## Audit log

**Configure → Audit log** lists what Uptime Goblin recorded, newest first: sign-ins and sign-outs, password and session changes, every settings and source change, tests, refreshes, delivery actions, the webhook signing key's creation and replacement, exports, `goblin-admin` key commands and Uptime Goblin's own starts, upgrades, snapshots and restores ([what is and is never recorded](security.md#audit-log)). Each entry says when, what, who (the admin signed in, a script with the password, someone not signed in, Uptime Goblin, or `goblin-admin` as the user who ran it), from which address and browser, and how it ended: **Succeeded**, **Refused**, **Failed**, **Changed elsewhere** (another device saved first), **Recorded** (Uptime Goblin's own events), **In progress**, or **Outcome unknown** (Uptime Goblin could not record how a change ended: either the entry it could not write is in Uptime Goblin's own log, in a line starting `{"orbit":"audit.unwritten"`, and the page says how many there were since Uptime Goblin started, or Uptime Goblin stopped during the change (a crash, a kill or a power loss), which leaves no such line and no count: Uptime Goblin's next start then reads "its previous stop was not recorded", and a settings change that was saved is recorded at that start as made outside Uptime Goblin).

- **Filters**: **Period** (the last 24 hours to the last 90 days, or every entry kept; the page opens at **Last 7 days**, also from the System page's link), **Kind**, **Outcome** and **Who**. **Refresh** reads the newest entries again; **Load more** reads older ones. The kind **Scripts with a password** lists the scripts that sign in with the password ([legacy Basic](authentication.md#scripts-and-legacy-basic)): one entry the first time each UTC day, then a summary with how many times, from how many addresses and up to 10 of them; the System page links there while legacy Basic is on. The kind **Refused requests** lists requests the signed-in account may not make and those refused by step-up or an admin lock, counted as refused sign-ins are ([security](security.md)).
- **Show details** lists what a change changed, as `path: before → after` (a password or key only as set, changed or cleared), a summary's addresses, and every other fact Uptime Goblin recorded. Refused sign-ins are counted rather than listed one by one: the first of each hour, then one summary at the end of the hour.
- **Check integrity** checks that no entry was changed, inserted or removed since Uptime Goblin wrote it, and lists every restore and upgrade it passes; a large log can take a minute. Entries removed from the very end are detected only against Uptime Goblin's own log ([keeping Uptime Goblin's log](installation.md#keeping-uptime-goblins-log)).
- **Export CSV** and **Export NDJSON** download the entries the filters select (the newest 50,000 at most, fewer when they pass 16 MiB), with their signatures. When older ones were left out the page says so; every **Period** counts back from now, so a shorter one does not reach them: narrow **Kind**, **Outcome** or **Who**, or export them from a script with `to=` ([exporting from a script](#exporting-from-a-script), [the HTTP API](architecture.md#http-api)). The CSV starts with a byte order mark for spreadsheet programs, and a cell starting with `=`, `+`, `@`, `-`, a tab or a carriage return, also after direction marks, gets a leading `'`, so a value cannot run as a formula. Direction embeddings, overrides and isolates (U+202A–U+202E, U+2066–U+2069) are left out of every CSV cell, the signed detail included, so a spreadsheet cannot show a cell's text in another order; names Uptime Goblin saves never hold them, and the NDJSON export keeps them (as `\u` escapes). Exports are recorded too.

`config.json` must be a regular file (a symlink to one is fine) of at most 128 MiB: anything else in its place, such as a FIFO or a directory, refuses the start (exit status 78) instead of waiting for it, and so does a file that grows while Uptime Goblin reads it, a symlink to a file that does not exist (Uptime Goblin would otherwise save its defaults over it), and a file that is not UTF-8 text. `auth.json` and the encryption key files are read the same way (`auth.json` at most 8,192 bytes and never through a symlink). A setting given twice in one object, or a `__proto__` member, is logged by its place (`services[0].name`), never by its value; the last value is used, as in 1.4.x, and the file is saved once without it. A start sets `config.json` to mode 600 when other users could read it (a link's target is left as it is). Metric label names are at most 100 characters.

A hand edit of `config.json` while Uptime Goblin is stopped (or one Uptime Goblin's start had to repair) is recorded at the next start as "Settings were changed outside Uptime Goblin (config.json)", with what changed. Uptime Goblin compares the settings' content with what it last recorded, not their `revision`, so an edit that keeps `revision` is found too; secrets in it are compared by keyed HMACs, never stored.

### Exporting from a script

Without [legacy Basic](authentication.md#scripts-and-legacy-basic), which is off on installs created by 1.5, a script signs in first and keeps the session cookie. Keep the password in a private file, not on the command line: run this line, type `{"login":"admin","password":"<password>"}`, press Enter and Ctrl-D. What you type shows on the screen. The line is JSON: in the password, write a `"` as `\"` and a `\` as `\\`.

```sh
(umask 077 && cat > signin.json)
```

Then sign in, export and sign out, with `HOST_NAME` replaced by the host name of Uptime Goblin's HTTPS address (with `:port` after it when that is not 443), and `TIME_MS` by the `time` of the oldest entry in the NDJSON export you have, in milliseconds (the export holds the newest entries up to and including that time, so that entry comes again); a shell passes both on as plain words. A CSV export gives `time` as a date and time instead: `node -p "Date.parse('<time>')"` turns it into milliseconds.

```sh
(
umask 077
curl -sS -c uptime-goblin-jar -H 'Origin: https://HOST_NAME' -H 'X-Goblin-Request: 1' -H 'Content-Type: application/json' -d @signin.json https://HOST_NAME/api/auth/login -o /dev/null -w '%{http_code}\n'
curl -sS -b uptime-goblin-jar -H 'X-Goblin-Request: 1' -OJ 'https://HOST_NAME/api/audit/export?format=ndjson&to=TIME_MS'
curl -sS -b uptime-goblin-jar -X POST -H 'Origin: https://HOST_NAME' -H 'X-Goblin-Request: 1' -H 'Content-Type: application/json' -d '{}' https://HOST_NAME/api/auth/logout -o /dev/null -w '%{http_code}\n'
rm -f uptime-goblin-jar signin.json
)
```

The sign-in prints `200` and the sign-out `204`; the export is saved as `uptime-goblin-audit-<time>.ndjson`, private like the other files under `umask 077`, which holds only inside the parentheses, so your shell's own umask is unchanged. Until the sign-out, the cookie in `uptime-goblin-jar` is as good as the password. The sign-in, the export and the sign-out are recorded like any other.

A `GOBLIN_` variable this release does not read (a misspelt name, or a later release's such as `GOBLIN_DATABASE_URL`) is named in a start warning, never with its value. `npm start` warns while `.env`, which holds the password, can be read by other users (`chmod 600 .env`). The systemd unit reads `/etc/uptime-goblin.env`; `npm start` reads `.env`. Compose passes only variables explicitly listed in its service configuration, so custom CA mounts/variables need a Compose override.

## Diagnostics, export and documentation

System information shows the Uptime Goblin version and build, uptime, any history database write failure, database/config sizes (the control database included), sample/event counts, collection activity, configured limits, the disk's free space and Uptime Goblin's reserve, the notifications waiting or failed, where the encryption key comes from (its source and fingerprint, never the key) with any warning about it, and the memory, CPU and process limits a supervised start found, with the `GOBLIN_ALLOW_UNLIMITED` it was given, read-only (**Resource limits**). It is not a full host-monitoring integration. **Open tabs by version** lists the Uptime Goblin pages that checked in during the last 10 minutes by build: this version, an older build (such a page updates itself), or "Before 1.4.3" (such a page needs one manual reload).

Open pages update themselves when Uptime Goblin is upgraded; see [updates and open pages](architecture.md#updates-and-open-pages). For a wall display, open Uptime Goblin with `?kiosk=1` (for example `https://goblin.example.com/?kiosk=1`): it always reloads itself for a new version, without waiting for a safe moment, and signs in with a one-time display code from `goblin-admin display code`, which lets it read the dashboard and nothing else ([wall displays](authentication.md#wall-displays)).

The configuration export removes service API keys/passwords and the SMTP password, and excludes the Uptime Goblin login hash, but **retains usernames, sender/recipient addresses, hostnames, URLs, labels, mappings and topology**. Review it before sharing. It cannot restore credentials and there is no configuration-import feature. Use a stopped-service private data backup for recovery.
