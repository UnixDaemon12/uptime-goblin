# Installation

[Back to Uptime Goblin](../README.md) · [Configuration](configuration.md) · [Troubleshooting](troubleshooting.md)

Both Docker Compose and native Linux installer delivery are required. macOS is for development/tests only, not the server support target. See [delivery gates](delivery.md) and use `sh deploy/install-plan.sh --dry-run docker` or `--dry-run linux` for a read-only prerequisite checklist. This planner has no apply mode and does not run the installer.

Choose one deployment. Uptime Goblin needs Node.js 24+ with built-in SQLite and npm; Docker supplies that runtime. No external database or Prometheus server is required. Exporter-based sources still need their exporters installed separately.

## Local Linux

From the project directory:

```sh
npm ci --omit=dev --ignore-scripts
test -e .env || install -m 600 .env.example .env
```

Set `GOBLIN_PASSWORD` in `.env` (12 to 1024 characters, inside the single quotes), then run `npm start`. Uptime Goblin always requires an admin password: without `GOBLIN_PASSWORD` or a saved `auth.json` it refuses to start (exit status 78), and it never makes one up.

Open <http://127.0.0.1:4317> and sign in as `admin`. This binds to loopback and stores data in `data/`. Ctrl+C stops the server; it does not delete data. This command is a foreground process, not a macOS native app or automatic startup service.

`npm start` loads `.env`; a plain `node server.mjs` invocation does not. Uptime Goblin keeps an encryption key; without one configured it generates `data/secret.key` and warns at each start. To keep the key apart from the data, see [the encryption key](#encryption-key). Keep `.env` private and enter secrets through a local editor, not command arguments or shell history. To listen beyond loopback, set `HOST` and exact `GOBLIN_ALLOWED_HOSTS` entries. A browser on the same computer (`http://127.0.0.1:4317`) signs in without HTTPS; from another computer, sign-in needs HTTPS through a reverse proxy, or `GOBLIN_INSECURE_HTTP_SESSIONS=1` on a trusted network (see [signing in](authentication.md#https-cookies-and-plain-http)). Once signed in, use **Configure → Account** to save a new password; its private `auth.json` takes precedence over the environment. See the [password reference](configuration.md#uptime-goblin-login-password).

## Docker Compose

Use an existing Docker host. The project does not install Docker or configure LXC nesting.

```sh
cp .env.example .env
```

Edit `.env`: set a unique `GOBLIN_PASSWORD` (in single quotes, so Compose keeps any `$` in it) and your allowed browser hosts. Then build and start:

```sh
docker compose build --pull
docker compose up -d
```

The Dockerfile pins its `node:24-bookworm-slim` base image by digest, so every build uses exactly that image, with `--pull` or without it (`--pull` makes Docker ask the registry for it even when the host has it); a newer one, with Debian and Node.js security fixes, comes with an Uptime Goblin release that moves the pin. The pinned image predates Debian's `libpcre2-8-0` security update, so the build installs exactly that version (`10.42-1+deb12u2`) on top: it needs Debian's package servers as well as npm's registry, and it fails, rather than keep the older version, when Debian no longer offers that one.

Compose requires a bootstrap password in its environment and publishes port 4317 only on host loopback by default. Retain that environment setting after an in-app password change; Uptime Goblin uses the saved password in the data volume. Set `GOBLIN_BIND_ADDRESS` to the intended host LAN address if a separate reverse proxy must reach it, and name that proxy in `GOBLIN_TRUST_PROXY`: without it, or a `GOBLIN_INSECURE_HTTP_SESSIONS` line in `.env`, Uptime Goblin refuses to start on that address (below). `compose.yaml` limits the container to 1 GiB of memory (with no swap on top, on a kernel that accounts swap), 1 CPU and 256 processes. They are written in `compose.yaml` itself, not read from `.env`: Docker reads `0` as no limit at all (and, for processes, a negative number too), and Compose cannot check what `.env` gives it. To change one, set it in a `compose.override.yaml` beside `compose.yaml` (below), then run `docker compose up -d`. Docker refuses to create a container allowed more CPUs than the host has ("range of CPUs is from 0.01 to 1.00, as there are only 1 CPUs available"), so raise `cpus` only on a host with that many; on a host whose kernel has no CPU bandwidth control (some NAS systems), Docker refuses any CPU limit, and a CPU set takes its place ([resource limits](#resource-limits), [troubleshooting](troubleshooting.md)). At every start Uptime Goblin reads all three back from its own cgroup (cgroup v2) and refuses to start (exit status 78) while one of them is not in force, unless `GOBLIN_ALLOW_UNLIMITED` names it ([resource limits](#resource-limits)); on a cgroup v1 or hybrid host it cannot verify them, and refuses too. It also allows 4096 open files and no core dumps, which would write the encryption key and passwords from Uptime Goblin's memory to the Docker host's disk; a supervised Uptime Goblin on Linux names core dumps allowed after all at every start, whatever the cgroup layout. On a host with swap, it also says at every start when it cannot read its swap limit ("Uptime Goblin cannot tell whether its memory can be swapped out"): a kernel without swap accounting has none, and Docker starts the container without `memswap_limit` ([troubleshooting](troubleshooting.md)).

```yaml
services:
  uptime-goblin:
    mem_limit: 2g
    memswap_limit: 2g
```

That `compose.override.yaml` gives Uptime Goblin 2 GiB (keep `memswap_limit` equal to `mem_limit`, so that none of it is swap). Compose reads the file by itself only for a command given no `-f` while `.env` sets no `COMPOSE_FILE`; with `compose.secret.yaml`, name it there too, `COMPOSE_FILE=compose.yaml:compose.secret.yaml:compose.override.yaml`, as the last `COMPOSE_FILE` line in `.env` (the last one counts), and add `-f compose.override.yaml` to a command given `-f compose.yaml` ([the encryption key](#encryption-key) has such commands). `docker compose config` shows the limits that apply.

While `.env` does not set `GOBLIN_INSECURE_HTTP_SESSIONS` (no line, or the line commented out, as `.env.example` ships it), Compose passes `compose-default`, and Uptime Goblin decides by where the port is published (`GOBLIN_BIND_ADDRESS`, which `compose.yaml` passes in as `GOBLIN_PUBLISHED_ADDRESS`). On a loopback address (`127.0.0.1`, the default, or `::1`) sign-in over plain HTTP is allowed: browsing the published port (`http://localhost:4317` on the Docker host) is plain HTTP to Uptime Goblin, because inside the container the browser's connection comes from the Docker gateway, and the traffic never leaves the Docker host. The page shows a plain-HTTP banner. On any other address (a LAN address, `0.0.0.0`, or anything that is not an IP address) the password and the cookie would cross that network in clear, so Uptime Goblin does not allow it by itself: plain-HTTP sign-in is off when `GOBLIN_TRUST_PROXY` names a proxy (browsers sign in through its HTTPS), and otherwise Uptime Goblin refuses to start (exit status 78; Compose restarts it, and `docker compose logs uptime-goblin` repeats the reason), with "Docker Compose publishes Uptime Goblin on … (GOBLIN_BIND_ADDRESS), which is not a loopback address, with no reverse proxy Uptime Goblin trusts (GOBLIN_TRUST_PROXY), …", until `.env` chooses: serve Uptime Goblin through an HTTPS proxy and set `GOBLIN_TRUST_PROXY` to the address it connects from (not `loopback`: inside the container that is the container itself), or set `GOBLIN_INSECURE_HTTP_SESSIONS=1` to keep plain-HTTP sign-in on that network (Uptime Goblin then warns at every start), or `0` to refuse it. `1` and `0` decide as written wherever the port is published (an empty value is off too, but removing the line is not: Compose then passes `compose-default` again); a change needs `docker compose up -d`. Uptime Goblin learns where the port is published only from `GOBLIN_BIND_ADDRESS`: a Compose override that publishes it elsewhere must set that variable to the same address, or Uptime Goblin decides and warns by the wrong one. An override that makes Uptime Goblin reachable without the published port (`network_mode: host`, a macvlan or ipvlan network, a network shared with other containers) must set `GOBLIN_INSECURE_HTTP_SESSIONS` in `.env` itself (`0`, or `1` on a network you trust): while `GOBLIN_BIND_ADDRESS` is a loopback address, Compose's default allows plain-HTTP sign-in, and the start warnings assume that only the Docker host reaches Uptime Goblin. A host firewall such as `ufw` does not guard a published port: Docker inserts its own rules ahead of it, so limit who may reach the port with Docker's `DOCKER-USER` chain, or keep the port on loopback behind a proxy. Check what Compose passes with `docker compose config | grep GOBLIN_INSECURE_HTTP_SESSIONS`, which prints `compose-default` while `.env` does not set it, and `GOBLIN_INSECURE_HTTP_SESSIONS: "0"` (or `""`) when it is off; after the start `docker compose logs uptime-goblin | grep 'plain-HTTP sessions'` says `allowed` or `refused`. See [signing in](authentication.md). In `GOBLIN_ALLOWED_HOSTS`, include the public-facing private hostname (for example `goblin.example.com`) and any direct non-default port you actually use (for example `goblin.example.com:4317`). Those entries are Host header values, not URLs.

Uptime Goblin can take up to about 36 seconds to stop (up to 8 of them sending notifications still due; [the steps](architecture.md#process-lifecycle)), so `compose.yaml` gives the container `stop_grace_period: 40s` (Docker's default of 10 seconds would kill it part way; with a plain `docker run`, pass `--stop-timeout 40`). Uptime Goblin keeps an encryption key: without `compose.secret.yaml` it generates `/var/lib/uptime-goblin/secret.key` inside the volume, with a warning at every start that every copy of the volume carries the key; see [the encryption key](#encryption-key) to keep it apart.

The named `orbit-data` volume persists settings, history and `auth.json` after a password change. The process runs as uid and gid 1000 (the image's `node` account, which `compose.yaml` names itself, so an image re-tagged as `uptime-goblin:local` cannot make it root) with a read-only root filesystem, no Linux capabilities, no new privileges, and no Docker socket. Normal `docker compose down` retains the volume. `down -v` deletes it and is not an update step.

Docker uses the project lockfile during build. The supplied `uptime-goblin:local` name is a local build tag, not a published registry image. Inspect startup with `docker compose logs --tail=100 uptime-goblin`; keep logs private if they contain infrastructure details.

Docker and native-installer readiness checks use `/health`, which answers without signing in, so they need no password and keep working after password changes. Only Uptime Goblin's `200 {"status":"ok"}` counts as ready; the sign-in challenge that 1.4.2 and earlier returned no longer does. Readiness confirms the process is responding; verify actual sign-in and source collection separately after an update.

The image sets `GOBLIN_SUPERVISED=1` and starts Uptime Goblin with `--supervised`, which no environment setting turns off ([resource limits](#resource-limits)). Uptime Goblin then exits with status 0 only when it is stopped (`docker compose stop`, `down` or a restart), 78 when it refuses to start (for example a too-short `GOBLIN_PASSWORD`, or a resource limit that is not in force), 75 while another process (another Uptime Goblin, or a `goblin-admin` command) holds `goblin.lock` in the data directory, and 1 for anything else ([exit statuses](troubleshooting.md#exit-statuses)). Compose's `restart: unless-stopped` restarts the container after any exit, so a refusal repeats in `docker compose logs`, with growing delays, until you correct it: unlike the systemd unit's `RestartPreventExitStatus=78`, Compose retries a refusal (78) too, the one for want of a resource limit included, so stop the service (`docker compose stop`) while you correct it, then run `docker compose up -d`. The health check allows a 60-second start period before failed checks count. The build stops with `Missing from the image:` when a file listed in `deploy/manifest.txt` did not reach the image, for example because a changed `.dockerignore` excludes it. The image also contains `deploy/manifest.txt` and `deploy/allowed_signers`.

## Native Debian or Ubuntu LXC

An existing unprivileged systemd-based container can run Uptime Goblin directly without Docker. Install Node.js 24+ and npm from a trusted source first. Start with modest resources and measure your workload; history size and API payloads vary with the number of sources. The installer does not create an LXC, upgrade the distribution, modify Proxmox, or change firewalls.

Place the source, an extracted release archive (see [verifying a release](#verifying-a-release)) or a checkout, in a staging directory such as `/usr/local/src/uptime-goblin`, and run the installer from there. It refuses to run from the installed copy (`/opt/uptime-goblin`, `/opt/uptime-goblin.previous` or `/opt/uptime-goblin.failed`) with "Run the installer from a staging directory such as /usr/local/src/uptime-goblin, not from the installed copy." With an HTTPS reverse proxy (such as nginx) on the same container, keep Uptime Goblin on loopback and trust that local proxy:

```sh
sudo bash deploy/install-lxc.sh --allowed-hosts goblin.example.com --trust-proxy loopback
```

With the proxy on another host, listen on the container's address, trust only the proxy's address, and firewall port 4317 so only the proxy can reach it:

```sh
sudo bash deploy/install-lxc.sh --listen 192.0.2.20 --allowed-hosts goblin.example.com --trust-proxy 192.0.2.10
```

Without a proxy, browsers and scripts sign in over plain HTTP, and the password at each sign-in, every script's Basic password and the sign-in cookie cross the network in clear. The installer refuses to set that up unless you choose it, on a network you trust, with `--allow-insecure-http` (it writes `GOBLIN_INSECURE_HTTP_SESSIONS=1`, and every signed-in page then shows a plain-HTTP banner):

```sh
sudo bash deploy/install-lxc.sh --listen 192.0.2.20 --allowed-hosts 192.0.2.20:4317 --allow-insecure-http
```

Add `--allow-loopback` if a source runs on the container itself (for example a node_exporter on `127.0.0.1:9100`). Use your real private hostname and addresses. The installer also sets up Uptime Goblin's encryption key, `/etc/uptime-goblin/secret.key`, or keeps the one you have after checking that it opens your data ([the encryption key](#encryption-key)). The installer installs under `/opt/uptime-goblin`, creates the `uptime-goblin` service account, uses `/var/lib/uptime-goblin` for data, and starts a systemd service. It generates a unique password in root-only `/etc/uptime-goblin.env`; retrieve it locally without posting it or printing it into shared logs.

Before anything on the host changes, the installer checks its options, Node and npm, that every file listed in `deploy/manifest.txt` is present, and, when installing from a release archive, that each of those files matches the archive's `SHA256SUMS`. It reads an existing `/etc/uptime-goblin.env` as systemd reads it (described below) and refuses, changing nothing, a file that systemd would not read ("systemd would not read /etc/uptime-goblin.env") or that continues a setting or a comment onto the next line ("/etc/uptime-goblin.env continues a setting or a comment onto the next line"). It checks `HOST`, `PORT`, `GOBLIN_LEGACY_BASIC`, `GOBLIN_ALLOW_UNLIMITED`, `GOBLIN_SUPERVISED`, `GOBLIN_MAX_CONNECTIONS_PER_CLIENT` and `GOBLIN_TRUST_PROXY` (not when `--trust-proxy` replaces it) in that file by the new release's rules: a value the new release would refuse to start with, such as `PORT=04317`, which 1.4.x read as 4317, or `GOBLIN_TRUST_PROXY=0.0.0.0/0`, which 1.4.3 accepted, ends the install with "This release of Uptime Goblin would refuse to start with /etc/uptime-goblin.env" and the reason, changing nothing (an upgrade would otherwise stop Uptime Goblin, fail to start it and roll back, and with `PORT` the restored release could not be verified either, because the verifier reads `PORT` by the same rule). The verifier reads the file with `node --env-file`, which reads some lines otherwise than systemd: an `export PORT=…` line, which systemd ignores, sets `PORT` for it; a carriage return without a line feed ends a line for systemd only; and Node keeps a backslash outside quotes, which systemd takes as an escape, ends a value at its closing quote (systemd reads `PORT="43"17` as 4317) and takes a backquote for a quote. Where that gives `HOST` or `PORT` another value, or one the new release refuses, the install ends with "… read /etc/uptime-goblin.env differently:" and both values, changing nothing. The installer first removes `HOST` and `PORT` from its own environment (root without sudo, `sudo -E` or a wrapper that exports them can pass them in): systemd starts Uptime Goblin without that environment, and `node --env-file` keeps a variable already set over the file's, so the verifier reads both from `/etc/uptime-goblin.env` alone. It then works out `HOST` and `PORT` as systemd gives them to Uptime Goblin: from the unit it installs and the drop-ins systemd has loaded for `uptime-goblin.service` (`systemctl show uptime-goblin.service --property=DropInPaths`) or, where systemd has not loaded `uptime-goblin.service` (as on a first install, where it lists no drop-in for it), the drop-ins it will find once the unit is written (the `.conf` files in the `uptime-goblin.service.d` and `service.d` directories of its search path for system units, in the order systemd takes them), from the files those name and from systemd's own environment (`systemctl show-environment`). It reads the unit and the drop-ins with an emulation of part of systemd's unit-file parser, checked against systemd 257 (Debian 13) but not a copy of it: line ends (LF, CR, CRLF), comments, lines continued with a backslash, a UTF-8 byte order mark at the very start of a file, sections (only `[Service]` counts), a line that is not UTF-8 or a section header without its `]` (systemd stops reading the file there), the quotes and C escapes of `Environment=` and `UnsetEnvironment=`, and the order in which systemd applies these settings. A drop-in can add an `EnvironmentFile=` read after `/etc/uptime-goblin.env`, set a name that file does not set (`Environment=`, `PassEnvironment=`, systemd's own environment) or remove one (`UnsetEnvironment=`). Where the result differs from `/etc/uptime-goblin.env`, the install ends with "systemd would give Uptime Goblin another HOST or PORT than /etc/uptime-goblin.env gives", both values and where systemd takes its value from, changing nothing. It ends there too, changing nothing, with "HOST and PORT as systemd would give them to Uptime Goblin could not be checked" where a specifier (such as `%i`), a file pattern (`*`, `?`, `[`) or a `PassEnvironment=` would decide the value (the installer expands neither and does not read the environment of systemd's own process), or where it cannot read what it needs (`systemctl show` or `show-environment` fails, a drop-in cannot be read, or a file a drop-in names, with a leading `-` or without, is not a regular file or is larger than 1 MiB), or where a drop-in holds one of six forms, in each of which systemd 257 reads some inputs otherwise than the emulation (the installer refuses the whole form, also an input of it that the two read alike): a NUL character, a UTF-8 byte order mark other than at its very start, a line feed followed by a carriage return after a line that a backslash continues, a section header with a quote, a backslash or a control character in it, an `EnvironmentFile=` path that is not in normal form (a `.` or `..` component, two slashes in a row or a slash at its end) or is longer than systemd takes (a component of more than 255 bytes, or 4096 bytes or more, a leading `-` included), or a `PassEnvironment=` value with a backslash in it (the message names the drop-in and the form); with "systemd would not start Uptime Goblin" where a drop-in names, without a leading `-`, a file that cannot be read or that systemd does not read (a NUL, or text that is not UTF-8); and with "systemd has not read the drop-ins of uptime-goblin.service as they are now" while systemd reports `NeedDaemonReload=yes` and the drop-in directories of its unit search path hold other drop-ins than those it lists (run `sudo systemctl daemon-reload` first). The emulation does not cover a setting that systemd rejects in a way that makes it stop reading the rest of that drop-in (under systemd 257, an `ExecStartPre=` path that is neither absolute nor a plain name does): the installer reads the lines after it as settings. Set `HOST` and `PORT` in `/etc/uptime-goblin.env` alone. It works out `GOBLIN_PASSWORD` the same way, since Uptime Goblin always requires an admin password and refuses to start without one (exit status 78): where the data directory has no `auth.json` and systemd would give Uptime Goblin no `GOBLIN_PASSWORD`, or an empty one, the install ends with "This release of Uptime Goblin would refuse to start (exit status 78): Uptime Goblin needs an admin password, and none is set: …", where systemd takes it from (or that nothing sets it), and what Uptime Goblin's own refusal says to do (set `GOBLIN_PASSWORD` in `/etc/uptime-goblin.env`, and let no drop-in empty or remove it; or restore `auth.json`), changing nothing; it never prints the password. A `GOBLIN_PASSWORD` that Uptime Goblin refuses (under 12 characters, only spaces, or over 1024 bytes, by this release's own check) stops it too, changing nothing and naming where systemd takes it from: `This release of Uptime Goblin would refuse to start (exit status 78) with "GOBLIN_PASSWORD must be 12 to 1024 characters and not only spaces. …": …`. It reads `/var/lib/uptime-goblin/auth.json` with the new release's own reader, the one Uptime Goblin's start reads it with, but as root, and only reads it: never through a symbolic link, never waiting on a FIFO, only a regular file of at most 8192 bytes that holds a valid password record. One that Uptime Goblin would refuse (a symbolic link, a directory, a FIFO, an empty or cut-off file, `{}`, a record of other parameters, or one over 8192 bytes) ends the install with `This release of Uptime Goblin would refuse to start (exit status 78) with "Saved authentication could not be loaded. …": …`, changing nothing, whatever `GOBLIN_PASSWORD` is, since Uptime Goblin ignores `GOBLIN_PASSWORD` while `auth.json` exists: restore `auth.json` from a backup, or move it out of `/var/lib/uptime-goblin` and set `GOBLIN_PASSWORD`, which then becomes the admin password and signs out every session. Without this check such an upgrade would stop Uptime Goblin, fail to start it and roll back, and an install over an existing `/etc/uptime-goblin.env` would leave Uptime Goblin down with nothing to restore. A new install, which writes a random `GOBLIN_PASSWORD` into the new `/etc/uptime-goblin.env`, passes unless a drop-in removes or empties it. Where `/var/lib/uptime-goblin/auth.json` cannot be opened or read at all, even as root (an error other than its absence, such as `EIO` from a failing disk), a specifier, a file pattern or a `PassEnvironment=` in a drop-in would decide `GOBLIN_PASSWORD`, or `systemctl show-environment` fails, the install ends with "Whether Uptime Goblin would have an admin password could not be checked", changing nothing: set `GOBLIN_PASSWORD` in `/etc/uptime-goblin.env` and remove the drop-in line that decides it (or, for `auth.json`, check the data directory and its disk). Root reads a file that the `uptime-goblin` account, which Uptime Goblin runs as, may not be able to read (an `auth.json` copied in from a backup with `sudo cp` is `root:root`, mode `0600`), so later, once that account exists (the installer creates it on a first install) and has the data directory, and before it stops the service or changes `/etc/uptime-goblin.env`, the installer also tries an existing `auth.json` as that account (`runuser`, from util-linux): one it cannot read ends the install with "/var/lib/uptime-goblin/auth.json cannot be read by the uptime-goblin account, which Uptime Goblin runs as, …" and the fix (`sudo chown uptime-goblin:uptime-goblin /var/lib/uptime-goblin/auth.json && sudo chmod 0600 /var/lib/uptime-goblin/auth.json`), since every start of Uptime Goblin would fail with it (exit status 1, which systemd retries every 5 seconds): an upgrade would stop Uptime Goblin and roll back to code that cannot read it either, and an install with no previous version would leave Uptime Goblin down. It works out `GOBLIN_LEGACY_BASIC`, `GOBLIN_ALLOW_UNLIMITED`, `GOBLIN_SUPERVISED`, `GOBLIN_MAX_CONNECTIONS_PER_CLIENT`, `GOBLIN_TRUST_PROXY` (with `--trust-proxy` applied as it will rewrite `/etc/uptime-goblin.env`) and `GOBLIN_INSECURE_HTTP_SESSIONS` the same way, since a drop-in or systemd's own environment can set them too: one of the first five that the new release would refuse to start with ends the install with "This release of Uptime Goblin would refuse to start with the settings systemd would give it (exit status 78): …", the reason and where systemd takes the value from, changing nothing; and where a specifier or a `PassEnvironment=` in a drop-in, or a failing `systemctl show-environment`, would decide one of the six, it ends with "… as systemd would give it to Uptime Goblin could not be checked" and what decides it, changing nothing: set it in `/etc/uptime-goblin.env` alone, if anywhere, and remove the drop-in line that decides it. (An `EnvironmentFile=` named with a specifier or a file pattern could set any name, so it ends the install at the `HOST` and `PORT` check above, unless a file read after it sets both; only then does it reach `GOBLIN_PASSWORD` or these six.) An install that would listen on the network (`HOST` not a loopback address) without a trusted proxy stops there, changing nothing, unless systemd would already give Uptime Goblin a decision whether browsers and scripts may sign in over plain HTTP, or `--allow-insecure-http` chooses it (below). Upgrading from 1.4.x behind a reverse proxy, it also checks that the running Uptime Goblin saw the proxy send `X-Forwarded-Proto: https` ([the proxy preflight](#upgrading-to-15)). It then prepares the locked dependencies with lifecycle scripts disabled, stages the complete new copy in `/opt/uptime-goblin.new` and prepares the new unit beside its destination. Only then does it stop the service, save the running copy, move the new copy into `/opt/uptime-goblin`, publish the unit and restart the service. Different code replaces `/opt/uptime-goblin.previous`; an identical reinstall uses `/opt/uptime-goblin.reinstall` and preserves the older rollback copy. Apart from the locked dependencies, it installs exactly the files in the manifest.

**Node path.** The installer uses the `node` that `command -v node` finds under sudo (for example `/usr/bin/node` or `/usr/local/bin/node`) and writes that path into the unit as it is, not the versioned file it currently points to. It must exist, be Node.js 24 or newer with SQLite, and live outside `/root`, `/home` and `/run/user`, which the service cannot read. Upgrading Node through the package manager, or pointing `/usr/local/bin/node` at a new version, therefore no longer stops the service. Installs made by 1.4.2 and earlier wrote the resolved, versioned path; after a Node upgrade removed it, the service failed to start with `status=203/EXEC`. Re-running the installer reports such a unit ("The installed service starts Node from …, which no longer exists") and repairs it.

The unit restarts Uptime Goblin 5 seconds after any exit that `systemctl stop` did not request (`Restart=always`), except exit status 78, which means Uptime Goblin refused to start because of its settings; that leaves the unit failed until you correct the problem (see [exit statuses](troubleshooting.md#exit-statuses)). It sets `GOBLIN_SUPERVISED=1` and starts Uptime Goblin with `--supervised` (`/etc/uptime-goblin.env` can override the variable, not the argument), so an exit that no stop request caused is reported as a failure and restarted, and every start checks the resource limits ([resource limits](#resource-limits)).

**Ready means serving.** The unit is `Type=notify`: systemd shows it `activating` until Uptime Goblin listens and has written `run/status.json`, and only then `active`, so `systemctl start` and `systemctl restart` return once it serves (add `--no-block` to return at once), and a unit ordered after it waits for that. Node cannot send systemd's datagram, so Uptime Goblin runs `systemd-notify --ready` (from `/usr/bin` or `/bin`, with nothing of its environment but `NOTIFY_SOCKET`), and the unit has `NotifyAccess=all`, which lets any process in Uptime Goblin's cgroup notify; Uptime Goblin starts no other program there. A start is never stopped for taking long (`TimeoutStartSec=infinity`: a migration or an index build on a large history may take minutes), as before with `Type=simple`. The installer starts the unit with `--no-block` and still verifies the running process itself, bounded by `--verify-timeout`. An earlier release does not report ready: the installer's rollback keeps the new unit (its limits, sandbox and `--supervised`) but makes it `Type=simple`, and the next upgrade writes the `Type=notify` unit again. To swap the code back by hand, run that release's installer, or give the unit `Type=simple` too (`sudo systemctl edit uptime-goblin`: `[Service]`, `Type=simple`; a drop-in outlasts upgrades, so remove it once a release that reports ready runs again).

A new install prints "Created private settings in /etc/uptime-goblin.env. Sign in as admin with GOBLIN_PASSWORD from that file." Re-running preserves existing `/etc/uptime-goblin.env`, connections, history and the saved login hash at `/var/lib/uptime-goblin/auth.json`. The generated environment password is the initial login only; after an in-app change, use the new password. Listen/allowed-host arguments only initialize a missing environment file; given for an install that has one, the installer says they were not applied. `--trust-proxy` and `--allow-loopback` also update an existing file, so re-running the installer with them is the simplest way to add those settings; `--trust-proxy off` (or `0`, `false`, `no`) turns proxy trust off. `--allow-insecure-http` adds `GOBLIN_INSECURE_HTTP_SESSIONS=1` to a new or existing file that does not set it (below). An unknown option is refused with the list of options, which the start of `deploy/install-lxc.sh` also describes. Each option may be given once, and a missing value exits with status 2 before anything changes. A release older than the installed one is refused the same way, changing nothing (exit status 2), with "Uptime Goblin … is installed, and this release, …, is older. Nothing was changed." (compared as Uptime Goblin orders releases: `1.5.0-rc.1` is older than `1.5.0`): the newer copy would become `/opt/uptime-goblin.previous` and the older code would run on data the newer release may have changed. To go back to an earlier release, restore its data first ([updates and rollback](#updates-and-rollback)); `--allow-downgrade` installs the older release anyway, with a warning. An installed version that is not a release the installer can compare is warned about, and the install goes on. One installer run at a time: a second run while one is in progress stops before anything changes with "Another Uptime Goblin installer run is in progress on this host; wait for it to finish, then run this again. Nothing was changed." (the lock is `/run/uptime-goblin-install.lock`, held with `flock` from util-linux until the run ends). The unit limits Uptime Goblin to `MemoryMax=1G` (no swap on top, `MemorySwapMax=0`, on a kernel that accounts swap), `CPUQuota=200%`, `TasksMax=256` and `LimitNOFILE=4096`, with no core dumps (`LimitCORE=0`); change them with a drop-in (`sudo systemctl edit uptime-goblin`), which the installer keeps. Uptime Goblin refuses to start (exit status 78) while its memory, task or CPU limit is not in force ("Uptime Goblin refused to start without its resource limits: …"): a drop-in set it to `infinity` (or emptied `CPUQuota=`), or the LXC's host does not delegate that cgroup controller to the container. The unit is then left failed, and the installer's verification names the refusal ([resource limits](#resource-limits)). Besides the 1.4.2 sandbox, the unit denies Uptime Goblin the clock, the hostname and the kernel log, and allows only the system calls of an ordinary service (`SystemCallFilter=@system-service @pkey`; any other fails with `EPERM`), as Debian's own `systemd-logind` runs. The installer warns when a public hostname is allowed (`GOBLIN_ALLOWED_HOSTS` in `/etc/uptime-goblin.env`) but systemd would give Uptime Goblin no trusted proxy (`GOBLIN_TRUST_PROXY`, from `/etc/uptime-goblin.env`, a drop-in or its own environment): every client then shares one sign-in lockout, and, unless systemd would give Uptime Goblin `GOBLIN_INSECURE_HTTP_SESSIONS=1`, browser sign-in through the proxy is refused, because Uptime Goblin cannot believe what the proxy says about HTTPS. The installer reads `/etc/uptime-goblin.env` with a copy of the parser systemd reads an `EnvironmentFile=` with (compared with systemd 257, Debian 13's): when a name is set more than once the last one counts (and is the one `--trust-proxy` rewrites); a line ends at LF, CRLF or a carriage return alone; spaces and tabs around the name, the `=` and the value are left out (no other character: a no-break space at the end stays part of the value, as for systemd); a line starting with `#` or `;` is a comment; outside quotes a backslash takes the next character as it is; single or double quotes may enclose any part of a value (`PORT="43"17` is 4317); and a name of anything but ASCII letters, digits and `_`, or one starting with a digit, is ignored (so is an `export PORT=…` line). It refuses, changing nothing, a file that systemd would not read, and so would not start Uptime Goblin with: one that holds a NUL character, or a name or value that is not valid UTF-8 (to systemd, a noncharacter such as U+FFFF is not). It also refuses, changing nothing, a file that continues a setting or a comment onto the next line: systemd joins the next line to a value after a quote still open at the end of a line or a backslash at the end of one, and, before version 254 (Debian 12 has 252), to a comment that ends in a backslash. The installer rewrites the file line by line, and `node --env-file`, with which it checks that Uptime Goblin serves, reads such lines otherwise. When it rewrites `/etc/uptime-goblin.env` (for `--trust-proxy`, `--allow-loopback`, the line below, or the `GOBLIN_SECRET_KEY_FILE` line it adds for the [encryption key](#encryption-key)), every line of it then ends in LF; systemd reads LF, CRLF and a carriage return alone alike. The installer never allows sign-in over plain HTTP by itself. When `/etc/uptime-goblin.env` (or, for a new install, `--listen`) listens on the network (`HOST` other than a loopback address: `127.x.x.x`, `::1` or `localhost`) with no trusted proxy (`GOBLIN_TRUST_PROXY` as systemd would give it to Uptime Goblin, with `--trust-proxy` applied, names none) and systemd would give Uptime Goblin no `GOBLIN_INSECURE_HTTP_SESSIONS` that Uptime Goblin reads as yes or no (from `/etc/uptime-goblin.env`, a drop-in or its own environment), it stops before anything changes, with "Uptime Goblin would listen on … with no reverse proxy it trusts (GOBLIN_TRUST_PROXY), so browsers and scripts would sign in over plain HTTP, …" and the two ways on: put Uptime Goblin behind an HTTPS reverse proxy (`HOST=127.0.0.1` with `--trust-proxy loopback` for nginx on the same host, or `--trust-proxy <proxy address>` for one elsewhere), or, on a network you trust, run it again with `--allow-insecure-http`. That option appends `GOBLIN_INSECURE_HTTP_SESSIONS=1` with a comment naming the date, who ran the installer (`sudo`'s account) and that passwords and the sign-in cookie cross the network in clear, and warns. It adds it only where neither `/etc/uptime-goblin.env` nor anything else systemd would give Uptime Goblin (a drop-in or its own environment) says yes or no: an existing decision is kept as it is (`=1`, or `=0`, where the option says it was not applied), and so is one that a drop-in or systemd's own environment gives (with a no, the option says it was not applied and names where the no comes from: a line added to `/etc/uptime-goblin.env` would override a drop-in's `Environment=`, since systemd reads `EnvironmentFile=` after it); a commented-out line, an empty value or another value decides nothing; a line you removed is not added again (the next run stops instead). The `GOBLIN_INSECURE_HTTP_SESSIONS=1` that installers of earlier 1.5 pre-releases added by themselves, with the comment "# Added by the Uptime Goblin 1.5 installer: keeps plain-HTTP sign-in working as in 1.4.x. Set it to 0 once Uptime Goblin is served over HTTPS." on the line just before it (the last line in `/etc/uptime-goblin.env` that sets it), decides nothing either: no one chose it. Without `--allow-insecure-http`, every install whose `/etc/uptime-goblin.env` holds it stops before anything changes, also one that listens on loopback or behind a trusted proxy (a browser or script that reaches an Uptime Goblin on the network directly, not through the proxy, or a proxy on the Uptime Goblin host that relays plain HTTP to its loopback address, would still sign in over plain HTTP under that line), and on the upgrade from 1.4.x before the proxy preflight. The message starts "/etc/uptime-goblin.env sets GOBLIN_INSECURE_HTTP_SESSIONS=1 on line … under the comment that an earlier Uptime Goblin 1.5 pre-release installer wrote with it on line …" and names the three ways to decide: set that line to `0` to refuse sign-in over plain HTTP; keep it, on a network you trust, by removing the comment line or putting a comment of your own in its place; or run the installer again with `--allow-insecure-http`, which keeps the line and puts its own comment (who chose it, and that passwords cross the network in clear) in place of the old one. A `=1` without that comment just before it is a decision, kept as it is. To change other settings, edit the file (for example `sudoedit /etc/uptime-goblin.env`) and restart the service. Useful checks:

```sh
sudo systemctl status uptime-goblin.service
sudo journalctl -u uptime-goblin.service --since '10 minutes ago'
```

### Verification and automatic rollback

The readiness deadline also bounds responses that trickle bytes. The status path must be a regular file; symlinks and FIFOs cannot stall verification. A restored release from 1.4.3 onward must pass the same process/build/nonce proof. Older releases lack that proof, so a legacy health response is reported as process identity unverified and needs an operator check. Failures while reloading or enabling the service also enter rollback.

After restarting the service, the installer waits up to 120 seconds for proof that the new release is the one serving: `/var/lib/uptime-goblin/run/status.json` must name the new version and build and the process systemd started, and `/health?instance=<nonce from that file>` must answer `match`. Change the wait with `--verify-timeout <seconds>` (1–1800), for example on slow storage. On success it prints "Uptime Goblin <version> is running and will start automatically after reboot." with the version it installed and, when a previous copy is kept, "The previous version is kept in /opt/uptime-goblin.previous.". After the upgrade from 1.4.x to 1.5 it then prints "Sign in as admin with the same password. Reload Uptime Goblin tabs that were open before this upgrade once." and, with the installer's key file, "Encryption key: /etc/uptime-goblin/secret.key. Back it up separately from /var/lib/uptime-goblin.". Otherwise it says "Open Uptime Goblin tabs now update themselves after an upgrade; tabs opened before 1.4.3 need one manual reload."

If verification fails, or unit publication or service management fails after the stop, the installer:

1. prints the failure reason (`Uptime Goblin is not verified:` for readiness failures), then `systemctl status` and the last 50 lines of the service log;
2. stops the service, moves the new copy to `/opt/uptime-goblin.failed` and restores the saved copy to `/opt/uptime-goblin` (from `/opt/uptime-goblin.reinstall` during an identical reinstall, otherwise `/opt/uptime-goblin.previous`), unless that copy is an earlier 1.5 pre-release build that signs webhooks with an HMAC secret (below);
3. starts the previous version and verifies it. For 1.4.3 onward, the new verifier requires its expected build, process ID and startup nonce; a successful rollback exits with status 1 and "The previous version is running again; the upgrade to … was rolled back." A legacy release is checked with its own health check, bounded by `--verify-timeout`: a passing check is reported as process identity unverified; a failed or timed-out check is reported separately. A failed unit reload produces a warning, but the installer still attempts restart using the loaded definition and verifies the result. A failed restart reports unconfirmed recovery.

**An earlier 1.5 pre-release build that signs webhooks with an HMAC secret is never started by the rollback, with or without a webhook.** Such a build signs webhooks with an HMAC secret, kept in a settings field that it opens without checking what it holds, and shows it under **Show signing secret**. This release keeps the webhook's private signing keys in other fields, and its start, with or without `GOBLIN_WEBHOOK_URL`, saves those settings in a form such a build can read but not change, with a key that a 1.5 pre-release build before this release kept in that field moved out of it: on that data such a build shows no signing secret and sends webhooks unsigned. But a failed start may stop before that, and a key still in that field is the earlier build's to take for its secret, to sign with its text and to show, at once with `GOBLIN_WEBHOOK_URL` set or once it is set later (the key stays in the data without a webhook). The installer cannot tell which without opening the sealed settings, so where the copy to restore is a 1.5 pre-release (a 1.5 version with a pre-release part, such as `1.5.0-dev.1`, or one whose version cannot be read) whose `lib/` does not declare this release's public-key route (`'/api/notifications/webhook/public-key'`) or still holds the earlier builds' reveal route (`/api/notifications/webhook/signing-secret/reveal`), the installer neither restores nor starts it, whatever systemd would give Uptime Goblin for `GOBLIN_WEBHOOK_URL`. It stops the service, leaves the new release in `/opt/uptime-goblin` (so a reboot starts that one, never the earlier build) and the earlier one in `/opt/uptime-goblin.previous`, and exits with status 1 and "The upgrade to … was not rolled back: the previous version in /opt/uptime-goblin.previous, Uptime Goblin …, is an earlier 1.5 pre-release build that signs webhooks with an HMAC secret …". Fix the problem the log shows and run the installer again. To go back to the earlier build instead, first restore Uptime Goblin's data from before the upgrade (a [snapshot](#snapshots) or a backup), then swap the two copies, make the unit `Type=simple` (such a build never reports ready to this release's `Type=notify` unit, so `systemctl start` would wait for good; the next upgrade writes `Type=notify` again; see **Ready means serving** above) and start the service, as the message shows. Data from before the upgrade can hold such a key too: if an earlier build that signs with an HMAC secret runs, or ran before the upgrade, on data that a 1.5 pre-release build that signs with Ed25519 ran on (this data or data from before the upgrade alike), press **Replace signing key** twice once this release runs again (with `GOBLIN_WEBHOOK_URL` set) and give receivers the new public key ([rolling back 1.5 to 1.4.3](#rolling-back-15-to-143)). The rollback does restore and start a 1.5 pre-release build that already signs with Ed25519 (its `lib/` declares this release's public-key route and not the reveal route), as any earlier release: if the failed start of this release got as far as saving the signing settings in its form, that build reads them read-only, answers **Show public key** with 503 `signing_unavailable` and sends webhooks unsigned (its log says "The webhook signing key could not be saved (…); alerts are sent unsigned until it can be."; the installer does not), so receivers that check signatures refuse them, a `401` or `403` pausing the webhook and a `400` or `422` ending each alert as **Failed**, until this release runs again or the data from before the upgrade is restored.

From just before it stops the service until the new release is verified, or the previous one is restored and checked, a signal does not end the installer halfway. A hangup (`SIGHUP`, the SSH session or terminal went away) is noted and the installer goes on, writing the rest of its output to `/run/uptime-goblin-install.log`. An interrupt (Ctrl-C, `SIGINT`) or `SIGTERM` counts as a failed verification: the installer ends the wait at once and restores the previous version as above, saying "Uptime Goblin … was not verified: the installer received SIGINT." (one before the stop ends the installer with the service and its code unchanged). The commands that stop, start and move run with these signals ignored, so none is cut short. A signal during the rollback's own check ends that check with "The previous code was restored and its service restarted, but a signal ended the check that it serves." Running the installer under `tmux` or `screen` still keeps its output in view if the connection drops.

Only code is rolled back. `/etc/uptime-goblin.env`, the data directory and the unit stay as the failed attempt left them, except that the new unit becomes `Type=simple` (without `NotifyAccess=` and `TimeoutStartSec=infinity`), since an earlier release never reports ready to a `Type=notify` unit; if that fails, the installer warns. If unit publication failed, the old unit is still on disk. Version 1.4.2 runs under the 1.4.3 unit without changes. A first install has nothing to restore and stops with "There is no previous version to restore." If the previous version does not start either, the installer says so; check `journalctl -u uptime-goblin.service`. The reasons are explained in [troubleshooting](troubleshooting.md#installer-verification-failed). Each upgrade to different code replaces `/opt/uptime-goblin.previous`, so one previous version is kept. Reinstalling identical code uses a temporary `/opt/uptime-goblin.reinstall` copy and preserves the older `/opt/uptime-goblin.previous`, and each failed upgrade replaces `/opt/uptime-goblin.failed`; remove `/opt/uptime-goblin.failed` once you no longer need it.

## Resource limits

`compose.yaml` and the systemd unit limit Uptime Goblin's memory, CPU time and processes (1 GiB, `cpus: 1` or `CPUQuota=200%`, and 256 processes; this release does not change the values). A supervised Uptime Goblin reads the three back from its own cgroup at every start and refuses to start (exit status 78) while one of them is not in force, unless `GOBLIN_ALLOW_UNLIMITED` names it. The check runs in `server.mjs`'s main block, after its modules have loaded and its launch setup has run, and before the start sequence takes `goblin.lock` or reads Uptime Goblin's data; it does not say that nothing was read or written before it. Started by hand (`npm start`, `node server.mjs`) it checks no limit, as before, but a malformed `GOBLIN_ALLOW_UNLIMITED` still refuses the start.

**Supervision.** The systemd unit and the Docker image start Uptime Goblin with `--supervised` on its command line, besides setting `GOBLIN_SUPERVISED=1`. `/etc/uptime-goblin.env` overrides the unit's `Environment=` lines, and an `-e` option of `docker run` or a Compose override the image's environment, but neither changes the command line: with `--supervised`, a `GOBLIN_SUPERVISED` that says no (`0`, `false`, `no`, `off`) is ignored, with a line at the start. A value that is neither yes nor no (`bogus`, `enabled`, a space before the `1`) refuses the start (78), with `--supervised` or without it, and so does any argument to `server.mjs` other than one `--supervised`. Only a start without `--supervised` and without `GOBLIN_SUPERVISED=1` is unsupervised and checks nothing.

**What counts as a limit.** Uptime Goblin reads its limits under Linux cgroup v2 only, from its own cgroup: `memory.max` a number of bytes up to 2^52, `pids.max` a number, and for CPU a `cpu.max` quota or, where there is none, a CPU set of Uptime Goblin's own. A CPU set counts only when all of these hold: Uptime Goblin's own `cpuset.cpus` is not empty, is a CPU list, and every CPU it names is one the host has online (`/sys/devices/system/cpu/online`); its `cpuset.cpus.effective` is not empty, is a CPU list, and every CPU of it is in that own set; and both hold fewer CPUs than the host has online. So each set is some, not all, of the CPUs the host has online: holding fewer CPUs than the host is not enough. A set Uptime Goblin only inherits (an empty `cpuset.cpus`, as in a container with no `cpuset` of its own inside a Docker or LXC held to some CPUs), a set the kernel did not grant (effective CPUs outside it), a set of every online CPU, the sole CPU of a one-CPU host and a CPU list Uptime Goblin cannot read do not count. A set that names a CPU the host does not have online (an offline CPU, one the host does not have, or one hidden from what Uptime Goblin sees in `/sys`, as LXCFS can hide the host's CPUs in an LXC) cannot be verified, however few CPUs it holds; without a `cpu.max` quota, Uptime Goblin then refuses to start for want of a CPU limit unless `GOBLIN_ALLOW_UNLIMITED=cpu`. Uptime Goblin checks that each limit is applied, not that it is small. A limit that is missing (`max`, no controller) and one Uptime Goblin cannot verify (a file it cannot read, cgroup v1, a hybrid layout, a system that is not Linux) both refuse.

**When a host cannot apply one.** The refusal names each limit that is not in force, why, and how to apply it under Docker, systemd and in an LXC ([troubleshooting](troubleshooting.md#resource-limits)). Apply it, or, only on a platform that cannot, name it in `GOBLIN_ALLOW_UNLIMITED` in Uptime Goblin's environment (`/etc/uptime-goblin.env` for the systemd unit, `.env` for Docker Compose): `memory`, `cpu` and `pids`, separated by commas, each at most once, in lower case and without spaces, such as `GOBLIN_ALLOW_UNLIMITED=cpu`. There is no `all`: a limit added later is never waived without someone naming it. Any other value refuses the start (78), also under `npm start`. Uptime Goblin then starts without the named limits and says so at every start ("Uptime Goblin runs without a … limit, as GOBLIN_ALLOW_UNLIMITED allows: …"), names a limit the setting gives needlessly, records the limits it runs without in the audit log's start entry, and shows what it found in **Configure → System**. The setting is read only from Uptime Goblin's environment at its start: no page or API sets it, and `config.json` cannot hold it.

**A kernel without CPU bandwidth control.** There Docker refuses any `cpus` ("NanoCPUs can not be set …"). Limit Uptime Goblin to one CPU with a CPU set instead: put `cpus: 0` and `cpuset: '0'` under `services:` → `uptime-goblin:` in `compose.override.yaml` (`cpus: 0` lifts the CPU time limit Docker refuses there, and `cpuset: '0'` holds Uptime Goblin to CPU 0). Uptime Goblin starts only where it finds that set applied: the CPU set counts as Uptime Goblin's CPU limit only where Uptime Goblin verifies at its start that it applies (above). Docker can discard a CPU set it cannot apply with only a warning ("… Cpuset discarded."); Uptime Goblin then refuses to start for want of a CPU limit, unless `GOBLIN_ALLOW_UNLIMITED=cpu`. On a host with one CPU the set is every CPU, so Uptime Goblin refuses there too unless `GOBLIN_ALLOW_UNLIMITED=cpu`. Where CPU 0 is not one Docker may give Uptime Goblin (the refusal lists the CPUs online and those Uptime Goblin runs on), give one of the CPUs that message lists instead, such as `cpuset: '2'`.

**Under each service manager.** Under systemd the unit is left failed (`RestartPreventExitStatus=78`), and the installer's verification names the refusal. Docker Compose's `restart: unless-stopped` restarts the container after a refusal too, so the refusal repeats in `docker compose logs`, with growing delays, until you stop the service (`docker compose stop`) and correct the limit or the setting; then run `docker compose up -d`. In an LXC, its host must delegate the memory, cpu and pids cgroup controllers to the container.

**Check before upgrading.** Read the files the check reads while the running release serves: natively `cat /sys/fs/cgroup/system.slice/uptime-goblin.service/memory.max /sys/fs/cgroup/system.slice/uptime-goblin.service/cpu.max /sys/fs/cgroup/system.slice/uptime-goblin.service/pids.max`, and under Docker Compose `docker compose exec uptime-goblin cat /sys/fs/cgroup/memory.max /sys/fs/cgroup/cpu.max /sys/fs/cgroup/pids.max` (on a cgroup v2 host, where the container has a cgroup namespace of its own). `max`, or a file that does not exist, is a limit that is not in force (for CPU, unless a CPU set counts as above). These commands only read.

Not measured for this release: a real kernel without CPU bandwidth control, rootless Docker, cgroup v1, Docker in an LXC (where `/sys` may show the container's CPUs rather than the host's), a Proxmox host, a NAS, CPU hot-plug, or a host with one CPU.

## Verifying a release

Release archives from 1.4.3 on carry `SHA256SUMS` and `SHA256SUMS.sig`, an SSH signature over `SHA256SUMS` by the Uptime Goblin release key (signer `release@orbit-homelab`, namespace `orbit-release`). The public key is in `deploy/allowed_signers`, and its fingerprint is published in the [README](../README.md#release-signing) and [SECURITY.md](../SECURITY.md#release-signing). Use a copy of `allowed_signers` you already trust, from the project repository or from `/opt/uptime-goblin/deploy/allowed_signers` once 1.4.3 is installed, never the copy inside the archive you are checking:

```sh
sudo tar -xzf orbit-homelab-1.4.3.tar.gz -C /usr/local/src
cd /usr/local/src/orbit-homelab-1.4.3
ssh-keygen -Y verify -f /path/to/trusted/allowed_signers -I release@orbit-homelab -n orbit-release -s SHA256SUMS.sig < SHA256SUMS
sha256sum -c --strict SHA256SUMS
```

`ssh-keygen` prints `Good "orbit-release" signature for release@orbit-homelab` followed by the key's fingerprint; compare it with the published fingerprint. `sha256sum` must report `OK` for every file (on macOS, use `shasum -a 256 -c SHA256SUMS`). Then run the installer from that directory. The installer checks each installed file against `SHA256SUMS` again and stops with "The release files do not match SHA256SUMS" on any difference, but it does not check the signature, so verify it first. A source checkout has no `SHA256SUMS`, and the installer skips that check.

## HTTPS, trust and network access

Uptime Goblin serves HTTP. Put remote browser access behind a private HTTPS reverse proxy and/or an authenticated VPN. Forward the original Host header, include that hostname in Uptime Goblin's allowlist, and allow the proxy to reach the intended listening address.

Tell Uptime Goblin which proxy to believe so failed sign-ins are throttled per real client instead of per proxy: set `GOBLIN_TRUST_PROXY=loopback` for a proxy on the same host (native installs only), or the proxy's address or CIDR range otherwise. Under Docker Compose the proxy never connects from loopback: use the address the proxy connects from, such as the Docker network's gateway (`docker network inspect <network>`) (see [sign-in throttling](security.md#failed-sign-in-throttling)). Name the proxy as narrowly as you can: every client in a trusted range chooses the address Uptime Goblin records for it and whether it counts as HTTPS, so a range wider than /24 (IPv4) or /64 (IPv6) starts with a warning, and one wider than /8 or /32, such as `0.0.0.0/0` or `::/0`, refuses the start (exit status 78), as do the NAT64 prefix `64:ff9b::/96` (and the local-use `64:ff9b:1::/96`), the IPv4-translated prefix `::ffff:0:0:0/96`, the IPv4-compatible prefix `::/96` and any range that holds one of them (each stands for every IPv4 address), more than 64 entries and ranges that together cover more than two /8 (or /32) ranges (loopback is not counted; the private ranges and `100.64.0.0/10` together fit). The proxy must set `X-Forwarded-For`. Nginx Proxy Manager, Caddy and Traefik do by default; a hand-written nginx site needs:

```nginx
# Optional, in the http block: trims request bursts from any single address.
limit_req_zone $binary_remote_addr zone=uptime_goblin:10m rate=10r/s;

location / {
    limit_req zone=uptime_goblin burst=40 nodelay;
    proxy_pass http://127.0.0.1:4317;
    proxy_set_header Host $http_host;
    proxy_set_header X-Forwarded-For $remote_addr;
    # The scheme the browser used, never a fixed value: 1.5 signs browsers in only when it
    # knows the connection is HTTPS.
    proxy_set_header X-Forwarded-Proto $scheme;
    # Connection tests can take up to the collection deadline (120 s at most).
    proxy_read_timeout 150s;
}
```

`X-Forwarded-Proto $scheme` and `Host $http_host` decide whether browsers can sign in: without them, 1.5 refuses sign-in through the proxy with a message naming the missing line (see [when sign-in is refused](authentication.md#when-sign-in-is-refused)). A fixed `X-Forwarded-Proto https` would tell Uptime Goblin that a request reaching this location over plain HTTP came over HTTPS, and 1.5 refuses such a sign-in (`proxy_proto_mismatch`).

Serve Uptime Goblin's host name over HTTPS only. Let plain HTTP do nothing but redirect, and tell browsers to keep to HTTPS (HSTS), so that no password or cookie crosses the network in clear, even when someone types or follows an `http://` address:

```nginx
server {
    listen 80;
    server_name goblin.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name goblin.example.com;
    ssl_certificate /etc/ssl/uptime-goblin/fullchain.pem;
    ssl_certificate_key /etc/ssl/uptime-goblin/privkey.pem;
    add_header Strict-Transport-Security "max-age=31536000" always;
    # The location block above goes here.
}
```

Add HSTS only once HTTPS works: for a year, the browser then opens every port of that host name over HTTPS only, another reason to give Uptime Goblin a host name of its own. nginx ignores a server's `add_header` in a location that has `add_header` lines of its own; the location above has none. Until a browser has seen that header once, a typed `http://` address still sends its first request in clear before the redirect, with any cookie it holds for that name without `Secure`; no password goes with it.

Also consider `server_tokens off;` in nginx so responses do not advertise its version. Uptime Goblin already throttles sign-in per client; the optional `limit_req` only trims bursts from a single address (and counts each IPv6 address separately). If Uptime Goblin faces the internet, the stronger protection is restricting who can reach it at all: a VPN, an IP allowlist or client certificates. TLS at the proxy does not encrypt a remote proxy-to-Uptime-Goblin HTTP hop; keep that hop within a trusted network or encrypted tunnel.

Outbound source/API requests use normal certificate verification. For a private CA, set `NODE_EXTRA_CA_CERTS` to a readable PEM containing the public CA certificate and restart Node. It must be in the real process environment: Node reads it before `.env` is loaded, so a line in `.env` is silently ignored by `npm start`. Export it in the shell (`NODE_EXTRA_CA_CERTS=/path/ca.pem npm start`), or put it in `/etc/uptime-goblin.env` for the systemd service. With Docker, add a read-only mount and the variable to the Compose service; merely putting an unused variable in `.env` does not mount a certificate or pass it into the container. With systemd, choose a path outside home directories, which the service sandbox blocks. Do not set `NODE_TLS_REJECT_UNAUTHORIZED=0`.

Allow outbound connections only to the APIs/exporters and mail/webhook destinations you configure. DNS must resolve to a reachable interface whose certificate matches the URL hostname. Monitoring does not require opening unrestricted access to an entire subnet.

## Encryption key

Uptime Goblin seals the secrets it keeps (in 1.5, the webhook's private signing key) with an encryption key of 32 random bytes, written as 64 hexadecimal digits. Each start reads it from the first of these that exists:

1. `GOBLIN_SECRET_KEY` in the environment (removed from Uptime Goblin's environment once read, but `/proc/<pid>/environ` and `docker inspect` still show it to root and to the user Uptime Goblin runs as: prefer a file);
2. the file `GOBLIN_SECRET_KEY_FILE` names;
3. a systemd credential named `orbit-secret-key` (`LoadCredential=orbit-secret-key:<path>` in a drop-in, `sudo systemctl edit uptime-goblin`: the installer replaces `uptime-goblin.service` itself, so it refuses a credential set there). Name a file only root can read, such as `/etc/credstore/orbit-secret-key` (root, mode 0400, in `/etc/credstore`, mode 0700), or an encrypted one (`sudo systemd-creds encrypt --name=orbit-secret-key KEY_FILE /etc/credstore.encrypted/orbit-secret-key`, with `KEY_FILE` replaced by the path of the key file, then `LoadCredentialEncrypted=orbit-secret-key:/etc/credstore.encrypted/orbit-secret-key`). `SetCredentialEncrypted=` works for Uptime Goblin too (`sudo systemd-creds encrypt -p --name=orbit-secret-key KEY_FILE -` prints the line), but it has no file, and the documented way to run the `goblin-admin` key commands loads the credential from one ([with a systemd credential](#goblin-admin)): encrypt the key to a file and use `LoadCredentialEncrypted=` instead. Not `SetCredential=orbit-secret-key:<key>`, which keeps the key in plain text in the drop-in, readable by every local account (`systemctl edit` writes drop-ins with mode 0644), so the installer warns about it;
4. a Compose secret named `orbit_secret_key` (`/run/secrets/orbit_secret_key`);
5. `secret.key` in the data directory, which Uptime Goblin generates (mode 600) when none of the above exists and the data has no keyring yet. Every start then warns that every copy of the data directory carries the key.

A `secret.key` left in the data directory beside another source is reported at every start, with the line that deletes it, which runs beside the running Uptime Goblin: `goblin-admin key remove-data-copy` for a copy of the key Uptime Goblin uses, and `goblin-admin key remove-data-copy --unused` for an older key, which Uptime Goblin does not use, as after `key rewrap` ("… is an older key, which Uptime Goblin does not use: …"). The first deletes it only while the key the command is given holds the same key and opens the data, the second only while that key opens every data key and the file opens none; otherwise each says why and deletes nothing ([goblin-admin](#goblin-admin) has both lines, natively and under Docker Compose). No line is given for a `secret.key` that `GOBLIN_SECRET_KEY_PREVIOUS_FILE` names, which Uptime Goblin reads at every start. When that source reads the data directory's `secret.key` itself (`GOBLIN_SECRET_KEY_FILE` naming it, or a Compose secret mounted from it), Uptime Goblin says instead that the key travels with every copy of the data directory and to copy it to a file outside it first: delete `secret.key` only once Uptime Goblin has started with the copy, since until then it is the key Uptime Goblin reads. A systemd credential is a copy systemd makes, so Uptime Goblin cannot see whether it comes from that file: beside one that holds the same key, it says to delete the data directory's copy only once `LoadCredential=` no longer names it.

The start log names the source and the key's fingerprint, never the key: `Encryption key: GOBLIN_SECRET_KEY_FILE (/etc/uptime-goblin/secret.key) · fingerprint 0123456789abcdef`. **Configure → System** shows the same. Once the data has a keyring, Uptime Goblin refuses to start (exit status 78) without the key that opened it, or with another one; see [exit statuses](troubleshooting.md#exit-statuses).

**Native installs.** The installer chooses the key in the same order, and when the data already has a keyring, checks that the key it chose opens it, before it stops the service: a key that does not refuses the install with nothing changed. It keeps a `GOBLIN_SECRET_KEY` line (with a warning to move it to a file), a `GOBLIN_SECRET_KEY_FILE` line or a systemd credential set in a drop-in (one set in `/etc/systemd/system/uptime-goblin.service` itself, which the installer replaces with its own unit, is refused with nothing changed: "The systemd credential orbit-secret-key is set in /etc/systemd/system/uptime-goblin.service itself (…), which this installer replaces with its own uptime-goblin.service, so Uptime Goblin would lose its key. Move that line into a drop-in (sudo systemctl edit uptime-goblin), then run this installer again."; a `SetCredential=` or `SetCredentialEncrypted=` value is named there only by its setting, `SetCredential=orbit-secret-key:…`, never printed). It reads the drop-ins as systemd does: a `LoadCredential=` file outranks `SetCredential=`, which stands in only when that file is not there, and an empty assignment clears its own list (`LoadCredential=` the files, `SetCredential=` the values). It checks a `LoadCredential=` file, or the key a `SetCredential=` line holds, against the data like any other key ("Encryption key: the systemd credential orbit-secret-key (SetCredential= in /etc/systemd/system/uptime-goblin.service.d/override.conf)."), and warns about a `SetCredential=` line, also when another source outranks it: "WARNING: SetCredential=orbit-secret-key in … keeps Uptime Goblin's encryption key in plain text: a drop-in made with sudo systemctl edit can be read by every local account (mode 0644), and systemd's manual says not to use SetCredential= for secrets. …". An encrypted credential, one systemd finds by name in its credential stores, or a `SetCredential=` beside an `ImportCredential=` line cannot be checked: the installer says so ("It could not be checked against the data; Uptime Goblin checks it at start."). Otherwise it uses `/etc/uptime-goblin/secret.key`, copies a `secret.key` Uptime Goblin generated in `/var/lib/uptime-goblin` there (once Uptime Goblin has started, delete the one in `/var/lib/uptime-goblin` with the `key remove-data-copy` line it prints), or creates `/etc/uptime-goblin/secret.key` (root:uptime-goblin, mode 0440), and adds `GOBLIN_SECRET_KEY_FILE=/etc/uptime-goblin/secret.key` to `/etc/uptime-goblin.env`. Uptime Goblin opens the key file as the `uptime-goblin` account, so the installer also makes sure that account can read it, before it stops the service: `/etc/uptime-goblin/secret.key` (not a link) goes back to root:uptime-goblin, mode 0440, in `/etc/uptime-goblin` (root:uptime-goblin, mode 0750), as a restore from a root-only backup leaves it otherwise ("Gave /etc/uptime-goblin/secret.key to root:uptime-goblin, mode 0440, …"), and any other key file Uptime Goblin opens (`GOBLIN_SECRET_KEY_FILE`, `GOBLIN_SECRET_KEY_PREVIOUS_FILE`) that the `uptime-goblin` account cannot read is refused with Uptime Goblin unchanged: "<file> cannot be read by the uptime-goblin account, which Uptime Goblin runs as, so Uptime Goblin would refuse to start (exit status 78, key_file_unreadable). Let the group uptime-goblin read it: sudo chown root:uptime-goblin <file> && sudo chmod 0440 <file>, …". Data with a keyring and no key on the host is refused: restore `/etc/uptime-goblin/secret.key` from your backup ([below](#backups)) and run the installer again (only if the key is truly lost: [lost encryption key](troubleshooting.md#lost-encryption-key)). The `uptime-goblin` account controls `/var/lib/uptime-goblin`, so the installer, which runs as root, reads `secret.key`, `control.sqlite` and `control.sqlite-wal` there only as regular files, never through a symbolic link (the two databases, to check the key against them, through a private copy in `/tmp` of at most 1 GiB each, removed before the key it copies out is written), and writes to `/etc/uptime-goblin/secret.key` the key it checked, without reading the data directory's file again; a link or any other kind of file there is refused with nothing changed. For the same reason it refuses, with nothing changed and before opening it, a key file that `/etc/uptime-goblin.env` or a credential drop-in names inside `/var/lib/uptime-goblin` (`GOBLIN_SECRET_KEY_FILE`, `GOBLIN_SECRET_KEY_PREVIOUS_FILE`, `LoadCredential=` or `LoadCredentialEncrypted=`, or `/etc/uptime-goblin/secret.key`, also when a link leads there): "GOBLIN_SECRET_KEY_FILE (/var/lib/uptime-goblin/secret.key) is in /var/lib/uptime-goblin, Uptime Goblin's data directory, which the uptime-goblin account controls: …". For `/var/lib/uptime-goblin/secret.key`, remove the line (or the drop-in's `LoadCredential=` line) and run the installer again: it copies that key to `/etc/uptime-goblin/secret.key` and names it, as above. Any other key file it reads (outside `/var/lib/uptime-goblin`) must be a regular file; a FIFO or a directory is refused at once ("… is not a regular file, so it holds no key."). `goblin-admin key …` does not read `/etc/uptime-goblin.env`, which only systemd reads for the service: give it the key file in its own environment ([goblin-admin](#goblin-admin)).

**Docker Compose.** Use the override `compose.secret.yaml`, and name it once in `.env` with `COMPOSE_FILE`, so that every later `docker compose` command includes it: updates, rollbacks, settings changes and `goblin-admin`. A command run with `compose.yaml` alone recreates the container without the key; once the volume's own copy is deleted, every start then refuses (exit status 78, `key_missing`) and `restart: unless-stopped` repeats it. With a `compose.override.yaml` (on a host where Docker refuses any CPU limit, it holds `cpus: 0`: [troubleshooting](troubleshooting.md)), which Compose reads by itself only for a command given no `-f` while `.env` sets no `COMPOSE_FILE`, write `COMPOSE_FILE=compose.yaml:compose.secret.yaml:compose.override.yaml` wherever a recipe below writes `COMPOSE_FILE=compose.yaml:compose.secret.yaml` (the last `COMPOSE_FILE` line in `.env` counts), and add `-f compose.override.yaml` after `-f compose.yaml` in the check and in the copy and `MOVE` recipes. Otherwise those commands, and the starts after the `COMPOSE_FILE` line, run without the override, so with `compose.yaml`'s `cpus: 1`, and on such a host Docker refuses to create their containers ("NanoCPUs can not be set …").

Which of the recipes below applies depends on what the volume holds, not on the release running now, nor on which key files exist: a volume whose data moved to `orbit_secret_key` with `key rewrap` still holds its older `/var/lib/uptime-goblin/secret.key`. On an install that has run before, ask before you make or copy a key. The check runs `goblin-admin key compose-check` in the 1.5 image (build it first, with `docker compose build --pull`), with `compose.secret.yaml` when `orbit_secret_key` exists, so that it sees that key too: it compares each key there is with the data and changes nothing. Its first line is `NEW`, `KEEP`, `COPY`, `MOVE` or `RESTORE`, and the next says why, with the keys' fingerprints; after `KEEP` beside a `/var/lib/uptime-goblin/secret.key` that Uptime Goblin does not use, a third line is the command that deletes it (see below). Anything else means it did not run, for example because the image is not built; when it names a key file it cannot read, nothing was compared: on a Linux host, `sudo chown 1000 orbit_secret_key` and run it again. The check:

```sh
docker compose -f compose.yaml $(test -e orbit_secret_key && echo '-f compose.secret.yaml') run --rm --no-deps uptime-goblin node lib/cli/goblin-admin.mjs key compose-check
```

`COPY` means there is no `orbit_secret_key` and the volume's `/var/lib/uptime-goblin/secret.key` opens the data: 1.5 has run on this volume without the override, also when 1.4.x runs on it again after a [rollback](#rolling-back-15-to-143) (1.4.x leaves `secret.key` alone), so it takes the second recipe. `KEEP` means your `orbit_secret_key` opens the data: 1.5 has run on it with `compose.secret.yaml` (Uptime Goblin never writes `secret.key` there), also when 1.4.x runs on it again after a rollback, or the data moved to that key: take none of the recipes: keep `orbit_secret_key` and `COMPOSE_FILE` (a new key cannot open that data: exit status 78), also when the volume still holds a `secret.key` (below). `MOVE` means your `orbit_secret_key` does not open the data and `/var/lib/uptime-goblin/secret.key` does, as after a new key made for a volume that needed `COPY` (Uptime Goblin then refuses to start, exit status 78, names that file, and `restart: unless-stopped` starts it again and again): take the third recipe, which puts the volume's key in a new `orbit_secret_key` and keeps yours as `orbit_secret_key.unused`, then starts Uptime Goblin in a new container. `RESTORE` means no key there opens the data: make no key and copy none; put back the `orbit_secret_key` the data was sealed with (its fingerprint is in the start lines of earlier starts) and run the check again; only if it is truly lost, see [lost encryption key](troubleshooting.md#lost-encryption-key). `NEW` (or a new install) takes the first; its first line never replaces an `orbit_secret_key` you already have.

With `KEEP`, a `/var/lib/uptime-goblin/secret.key` still in the volume is not the key Uptime Goblin uses, and every copy of the volume carries it. The check's second line says what it is, and its third line is the command that deletes it, in Uptime Goblin's container, once Uptime Goblin runs with `orbit_secret_key` (`COMPOSE_FILE` in `.env`, then `docker compose up -d`). A copy of your key, left by a copy recipe that stopped before its last line, goes with that last line, `key remove-data-copy`. An older key, one that opens none of the data's keys, as after `key rewrap` (Uptime Goblin names it at every start as an older key it does not use), goes with this line, which deletes it only while Uptime Goblin's key opens every data key and that file opens none, and otherwise says why, deletes nothing and exits with status 1 (for a copy, it sends you to the line without `--unused`):

```sh
docker compose exec uptime-goblin node lib/cli/goblin-admin.mjs key remove-data-copy --unused
```

A backup of the volume from before the key changed still needs that older key (a backup of the whole volume holds its own copy), and so does a [snapshot](#snapshots) taken before the change: keep the older key with them.

Each recipe is three blocks: the command that makes or copies the key, the `chown` a Linux host needs, and the start. A start that recreates a running Uptime Goblin's container discards its log, which holds the audit log's checkpoint lines, so the second and third recipes, and a key change below, keep it first with `(umask 077 && f=~/uptime-goblin-journal.txt && test ! -L "$f" && touch "$f" && test -f "$f" && n=$(mktemp "$f.XXXXXX") && { cat "$f" >> "$n" && mv -f "$n" "$f" || { rm -f "$n"; false; }; } && docker compose logs --no-log-prefix uptime-goblin >> "$f") || { echo "Uptime Goblin's log was not kept"; false; }` ([keeping Uptime Goblin's log](#keeping-uptime-goblins-log)); the first needs none, since no 1.5 has run on its data. Paste them one at a time and read what each prints before the next. The command blocks carry no comments: zsh, the macOS shell, runs a trailing `# …` as more words unless `interactivecomments` is set. On a Mac, skip the `chown` block: OrbStack, where these recipes were measured, lets the container's user read the file as it is (Docker Desktop was not tested). On a Linux host the file must belong to the container's uid 1000 (see below). Without user-namespace remapping, that uid is also a uid of the host, often the first person's account (`getent passwd 1000` names it), which then owns the key file and can read it, and Uptime Goblin's processes (Docker's init and Node, which hold no Linux capabilities) run as that same host uid, with gid 1000 (`user: '1000:1000'` in `compose.yaml`). What keeps the key from that account is a host where uid 1000 is no one's: no person logs in as it, and nothing but Uptime Goblin's containers runs as it. Root, and every account that can use Docker (`docker compose exec`), can read the key in any case. Docker's user-namespace remapping (`userns-remap`), which runs the container's uid 1000 as a host uid of its own, is the other way; it was not measured with these recipes, and their `chown` must then name that host uid instead of 1000. A Compose project directory that only root can enter does not keep the key from host uid 1000. It keeps the key file, `.env` (which holds `GOBLIN_PASSWORD`) and the Compose files from being opened by their paths, but while Uptime Goblin runs, any process of host uid 1000 that runs with gid 1000 as well (as the processes of a login whose own group is gid 1000 do: `id` shows it) can read the mounted key through `/proc/<pid>/root/run/secrets/orbit_secret_key` and the `GOBLIN_PASSWORD` the container started with through `/proc/<pid>/environ`, and read and change the files of Uptime Goblin's data volume through `/proc/<pid>/root/var/lib/uptime-goblin` (`/app/data` before 1.5), where `<pid>` is either process of Uptime Goblin's container: Linux's ptrace read check, which guards these entries, passes for a reader whose user and group ids are both the target's, unless the target holds a capability the reader lacks or has made itself undumpable, and Uptime Goblin's processes have done neither; that path never enters the directory ([the environment](security.md#encryption-key-and-sealed-secrets) Uptime Goblin started with stays readable there even after Uptime Goblin removes `GOBLIN_PASSWORD` from its own). If you keep the directory root's all the same, mode 0700 with `compose.yaml`, `compose.secret.yaml` and `.env` in it, run every command of these recipes, and every other `docker compose` command for Uptime Goblin, as root in that directory (`sudo -i`, then `cd` to it; the `chown` then needs no `sudo`): the recipes make, read and copy files there, which an account that cannot enter the directory cannot do. Docker mounts the key into the container itself, so Uptime Goblin still reads it. Measured with Docker 27.5.1 on Linux (in a test container): the check and the first recipe, run as root in such a directory, gave `NEW`, then a start with the Compose secret and `KEEP`, and uid 1000 could neither read the key file nor list the directory. Measured with Docker 29.4.0 (OrbStack, Linux 7.0, cgroup v2, no AppArmor or SELinux): the key file in such a directory was mounted read-only into a container running as `1000:1000` with a read-only root, every capability dropped and `no-new-privileges`, and a process of uid 1000 that could see the host's processes (a container run with `--pid=host --user 1000:1000 --cap-drop ALL`, standing in for a host login) could not read the file or list the directory, but read the key and `GOBLIN_PASSWORD` through the `/proc` entries of both of the container's processes, Docker's init (`--init`, which `init: true` gives) and Node, and read and wrote a file in a data volume mounted at `/app/data`. Run with gid 100 (`--user 1000:100`), also with 1000 as an added group (`--group-add 1000`), that process could read or write none of these through `/proc`; a member of group 1000 can make gid 1000 its group with `newgrp` (not measured). Hosts where AppArmor or SELinux confine the containers were not measured.

The first recipe is for a new install, or a volume only 1.4.x has run on (`NEW`: its data has no key yet). It makes a key unless `orbit_secret_key` exists, under `umask 077`, so the file is private from its first byte (made under the usual umask 022 and then given `chmod`, every local account could read it until the `chmod` ran):

```sh
test -e orbit_secret_key && echo 'orbit_secret_key exists: keep it' || { (umask 077 && openssl rand -hex 32 > orbit_secret_key) && chmod 0400 orbit_secret_key; }
```

On a Linux host:

```sh
sudo chown 1000 orbit_secret_key
```

Then name the override in `.env` and start Uptime Goblin:

```sh
echo 'COMPOSE_FILE=compose.yaml:compose.secret.yaml' >> .env
docker compose up -d
```

Data that only 1.4.x has run on has no key and no keyring (1.4.x never writes `secret.key`), so the upgrade of such a volume uses the recipe above: 1.5 seals the data with that key at its first start. A volume that 1.5 has already run on without the override (`COPY`) keeps the key it generated there (a new key cannot open that data: exit status 78, and the refusal names `/var/lib/uptime-goblin/secret.key`, its fingerprint and that it opens the data). Its first command never replaces an `orbit_secret_key` you have: with one there, it copies nothing and says so; run the check. It reads the volume's key with a container of its own (`docker compose run`, in the 1.5 image like the check) into a new file, not with `docker compose cp`, which reads through Uptime Goblin's container and fails ("Could not find the file /var/lib/uptime-goblin/secret.key in container") while that container mounts an `orbit_secret_key` that is no longer there; `goblin-admin key status` then checks that the file holds a key that opens the data, and only then is it copied to `orbit_secret_key`. When a step fails, the command stops there, removes its new file and says "Stopped before the end: run the check".

```sh
test -e orbit_secret_key && echo 'orbit_secret_key exists: not replaced; run the check' || {
  volume_key=$(mktemp orbit_secret_key.XXXXXX) &&
  docker compose -f compose.yaml run --rm --no-deps -T uptime-goblin cat /var/lib/uptime-goblin/secret.key >| "$volume_key" &&
  test -s "$volume_key" &&
  docker compose -f compose.yaml run --rm --no-deps -T uptime-goblin sh -c 'umask 077 && cat > /tmp/key && GOBLIN_SECRET_KEY_FILE=/tmp/key node lib/cli/goblin-admin.mjs key status > /dev/null' < "$volume_key" &&
  cp "$volume_key" orbit_secret_key && chmod 0400 orbit_secret_key && rm -f "$volume_key" ||
  { rm -f "$volume_key"; echo 'Stopped before the end: run the check'; false; }
}
```

On a Linux host:

```sh
sudo chown 1000 orbit_secret_key
```

Then keep Uptime Goblin's log, `(umask 077 && f=~/uptime-goblin-journal.txt && test ! -L "$f" && touch "$f" && test -f "$f" && n=$(mktemp "$f.XXXXXX") && { cat "$f" >> "$n" && mv -f "$n" "$f" || { rm -f "$n"; false; }; } && docker compose logs --no-log-prefix uptime-goblin >> "$f") || { echo "Uptime Goblin's log was not kept"; false; }`, since the start recreates the container. Name the override in `.env` first, since every command after it needs it, and start Uptime Goblin. The `Encryption key:` start line must name the Compose secret with the same fingerprint as before, and `docker compose config` must list `orbit_secret_key`, which later commands then mount too. The last line deletes the copy in the volume with `goblin-admin key remove-data-copy`, run in Uptime Goblin's container, which deletes `/var/lib/uptime-goblin/secret.key` only while the key Uptime Goblin is given comes from another file (here the Compose secret), holds the same key byte for byte and opens the data; otherwise it says why, deletes nothing and exits with status 1 (for example while Uptime Goblin still runs without the secret, or in a container that mounts another key):

```sh
echo 'COMPOSE_FILE=compose.yaml:compose.secret.yaml' >> .env
docker compose up -d
docker compose logs uptime-goblin | grep 'Encryption key'
docker compose config | grep orbit_secret_key
docker compose exec uptime-goblin node lib/cli/goblin-admin.mjs key remove-data-copy
```

The third recipe is for `MOVE`. Uptime Goblin refuses in a container that mounts your `orbit_secret_key`, so its first command reads the volume's key and checks it as the second recipe does, before it changes any file. Only then does it set your file aside, kept as `orbit_secret_key.unused` until Uptime Goblin has started with the volume's key (a copy, then the file removed: on OrbStack a new container could still mount a renamed file for a while, and Docker Desktop was not tested; an `orbit_secret_key.unused` that is there already is never replaced: the command stops and says so), and copy the volume's key to a new `orbit_secret_key`.

```sh
test -e orbit_secret_key.unused && echo 'orbit_secret_key.unused exists: not replaced; choose another name' || {
  volume_key=$(mktemp orbit_secret_key.XXXXXX) &&
  docker compose -f compose.yaml run --rm --no-deps -T uptime-goblin cat /var/lib/uptime-goblin/secret.key >| "$volume_key" &&
  test -s "$volume_key" &&
  docker compose -f compose.yaml run --rm --no-deps -T uptime-goblin sh -c 'umask 077 && cat > /tmp/key && GOBLIN_SECRET_KEY_FILE=/tmp/key node lib/cli/goblin-admin.mjs key status > /dev/null' < "$volume_key" &&
  cp -p orbit_secret_key orbit_secret_key.unused && rm -f orbit_secret_key &&
  cp "$volume_key" orbit_secret_key && chmod 0400 orbit_secret_key && rm -f "$volume_key" ||
  { rm -f "$volume_key"; echo 'Stopped before the end: run the check'; false; }
}
```

On a Linux host:

```sh
sudo chown 1000 orbit_secret_key
```

Uptime Goblin then starts in a new container, with `docker compose up -d --force-recreate` after those lines: the container that refused has the same configuration, so a plain `docker compose up -d` could keep it. Keep Uptime Goblin's log first, `(umask 077 && f=~/uptime-goblin-journal.txt && test ! -L "$f" && touch "$f" && test -f "$f" && n=$(mktemp "$f.XXXXXX") && { cat "$f" >> "$n" && mv -f "$n" "$f" || { rm -f "$n"; false; }; } && docker compose logs --no-log-prefix uptime-goblin >> "$f") || { echo "Uptime Goblin's log was not kept"; false; }`, since Docker discards it with that container. The `COMPOSE_FILE` line comes first (a second line that names the same files does no harm: the last `COMPOSE_FILE` line counts). The `Encryption key:` start line must name the Compose secret with the fingerprint the check gave for `/var/lib/uptime-goblin/secret.key`, and the last line deletes the copy in the volume only while Uptime Goblin's key is the Compose secret, holding the same key, and opens the data, as in the second recipe:

```sh
echo 'COMPOSE_FILE=compose.yaml:compose.secret.yaml' >> .env
docker compose up -d --force-recreate
docker compose logs uptime-goblin | grep 'Encryption key'
docker compose config | grep orbit_secret_key
docker compose exec uptime-goblin node lib/cli/goblin-admin.mjs key remove-data-copy
```

Instead of `COMPOSE_FILE`, you can give `-f compose.yaml -f compose.secret.yaml` to every `docker compose` command (and `-f compose.override.yaml` when you have one); the commands in these documents assume `.env` names both files. (On Windows, separate the two files with `;`.) Until the copy in the volume is deleted, every start warns about it ("/var/lib/uptime-goblin/secret.key holds the same key as the Compose secret …"); the recipes' last line deletes it once Uptime Goblin runs with the secret, and only then. Should the volume's copy be the only key that opens the data, which is the case whenever a step before it stopped (no `orbit_secret_key` was made, or the start that follows mounted another key), `key remove-data-copy` keeps it and says why: run the check again. The container runs as uid 1000 (`node`), which must be able to read the file. Compose mounts it with the host's owner and mode (0400), and on a Linux host that owner is whoever made it (root when the recipe ran under `sudo`), so each recipe gives it to uid 1000 before the first start (`sudo chown 1000 orbit_secret_key`); on a Mac, OrbStack lets the container's user read the file as it is, so skip that block there (Docker Desktop was not tested). A key file Uptime Goblin cannot read stops the start with exit status 78 (`key_file_unreadable`, "… cannot be read: EACCES"); by then the start has written nothing but `goblin.lock`, which it creates where it is missing (on a disk already full it has also deleted its space reserve, `run/space-reserve`), so `sudo chown 1000 orbit_secret_key` and `docker compose up -d` then start it. Never commit `orbit_secret_key` (the repository's `.gitignore` and `.dockerignore` leave it out), and back it up apart from the volume.

**`npm start`.** Keep the key in a file outside the data directory and name it in `.env` by its full path, since `.env` does not expand `~`: `GOBLIN_SECRET_KEY_FILE=/Users/you/.orbit-secret.key` on a Mac, `/home/you/.orbit-secret.key` on Linux. If Uptime Goblin has already started on this data directory (there is a `data/secret.key`, or one in the directory `GOBLIN_DATA_DIR` names), that key is the one that opens the data, and a new key would stop Uptime Goblin (exit status 78, `key_mismatch`): move it out instead, from the project directory (with `GOBLIN_DATA_DIR` set in `.env`, put that directory's `secret.key` in place of `data/secret.key`):

```sh
test -e ~/.orbit-secret.key && echo '.orbit-secret.key exists: not replaced' || install -m 600 data/secret.key ~/.orbit-secret.key
```

Then add the `GOBLIN_SECRET_KEY_FILE` line to `.env`, restart Uptime Goblin (its start line names `GOBLIN_SECRET_KEY_FILE` with the fingerprint it had before), and delete the data directory's copy, which this line does only while the file holds the same key and opens the data: `node --env-file-if-exists=.env lib/cli/goblin-admin.mjs key remove-data-copy` ([goblin-admin](#goblin-admin)). Make a new key only for a data directory Uptime Goblin has not started on yet. It is made under `umask 077`, so the file is private from its first byte:

```sh
test -e ~/.orbit-secret.key && echo '.orbit-secret.key exists: keep it' || (umask 077 && openssl rand -hex 32 > ~/.orbit-secret.key)
```

**Back the key up separately from the data.** A backup of the data directory cannot be started without its key, and a key kept next to the data protects nothing from whoever has the backup. Restoring needs the key the restored data was made with. If you deploy with a script that archives `/var/lib/uptime-goblin`, `/etc/uptime-goblin.env` and `/opt/uptime-goblin` before each upgrade, its archive does not contain `/etc/uptime-goblin/secret.key`: that is intended, so copy the key once to a private place of its own (a password manager, say) before the first 1.5 upgrade, and note where. A lost key is not the end: see [lost encryption key](troubleshooting.md#lost-encryption-key).

## Space reserve

Uptime Goblin keeps `run/space-reserve` in its data directory: 8 MiB of random bytes, so compression or sparse files cannot fake it. When the disk fills, Uptime Goblin deletes it, so that signing in and sending alerts keep working on that space, refuses settings changes (HTTP 503) and stops saving readings until space is freed, then makes it again. It may be deleted at any time (Uptime Goblin makes it again) and is never in a snapshot, but file-level backups that include `run/` grow by 8 MiB (random bytes do not compress).

Limits: on btrfs or ZFS with snapshots, or a full LVM-thin or ZFS pool, deleting the file frees nothing, because the snapshot or the pool keeps the blocks; the banner then says so, and sign-in and delivery may fail too. Under a user quota (`EDQUOT`) Uptime Goblin learns that the disk is full only from a failed write. Proxmox container volumes use `refquota`, which Uptime Goblin sees correctly. SQLite often finds room for small writes in its own files even with 0 bytes free, but after a restart or a checkpoint it needs new space at once; the reserve covers that case.

## Backups

A redacted export is a reference, **not a restorable backup**. It omits passwords/API keys and authentication hashes and has no import endpoint. Back up the whole private data directory while Uptime Goblin is stopped, including `auth.json` if present and any SQLite WAL/SHM files that remain. From 1.5 the [audit log](security.md#audit-log) is in `control.sqlite`, so a backup of the data directory carries it, with the client addresses and browser names it holds. Also preserve environment settings and any private CA configuration. Backups contain service credentials and need restrictive access and encryption. Restoring `auth.json` restores the password represented by that backup; omitting it falls back to the environment bootstrap password.

For native systemd installs, choose a private backup location, then stop, archive, and restart:

```sh
sudo install -d -m 700 /secure-backups
sudo systemctl stop uptime-goblin.service
sudo tar -czf /secure-backups/uptime-goblin-backup.tar.gz -C / var/lib/uptime-goblin etc/uptime-goblin.env
sudo chmod 600 /secure-backups/uptime-goblin-backup.tar.gz
sudo systemctl start uptime-goblin.service
```

Choose a new archive name for each backup; the example command overwrites a same-named file. If archiving fails, investigate and restart the service deliberately rather than assuming the backup succeeded.

Keep the encryption key apart from those archives, once (it does not change unless you replace it): `sudo cat /etc/uptime-goblin/secret.key` into your password manager, or `sudo install -m 600 /etc/uptime-goblin/secret.key /secure-keys/uptime-goblin-secret.key` on another disk or host. The archive alone cannot be started without it. Restore the key where the `uptime-goblin` account can read it, not the way the copy was made: `sudo install -d -o root -g uptime-goblin -m 0750 /etc/uptime-goblin`, then `sudo install -o root -g uptime-goblin -m 0440 /secure-keys/uptime-goblin-secret.key /etc/uptime-goblin/secret.key` (from a password manager: run `sudo install -o root -g uptime-goblin -m 0440 /dev/stdin /etc/uptime-goblin/secret.key`, paste the key, press Enter and Ctrl-D). A key file only root can read stops Uptime Goblin with exit status 78 (`key_file_unreadable`, EACCES); running the installer again gives `/etc/uptime-goblin/secret.key` back to the `uptime-goblin` group.

For Docker, stop the service before copying the named volume. One method using the already-built image is:

```sh
umask 077
mkdir -p "$HOME/uptime-goblin-backups"
chmod 700 "$HOME/uptime-goblin-backups"
docker compose stop uptime-goblin
docker compose run --rm --no-deps --entrypoint sh uptime-goblin -c 'tar -C /var/lib/uptime-goblin -czf - .' > "$HOME/uptime-goblin-backups/uptime-goblin-data.tar.gz"
docker compose start uptime-goblin
```

Separately protect `.env` and any Compose override/CA files, and keep the `orbit_secret_key` file of `compose.secret.yaml` apart from the archive (without the override, the key is `secret.key` inside the volume and travels with every copy of it). Confirm the archive lists the expected files and perform a restore rehearsal in an isolated environment with outbound notifications disabled. Do not replace a running SQLite database by copying individual files over it.

To restore, stop Uptime Goblin, replace the data directory with the archive's (remove or move the current one first, so the archive's files are written as new files), make sure the encryption key it was made with is in place, and start Uptime Goblin. Notifications that were waiting in the backup are not sent: Uptime Goblin notices that `control.sqlite` is another file and marks them not sent. A backup brings back the admin password of its time and, from 1.5, every session of its time, including those signed out since. Uptime Goblin notices that `control.sqlite` is another file and signs every session out (the log says "control.sqlite is not the file Uptime Goblin last ran with…"), so everyone signs in again. It cannot notice a rollback of a file-system snapshot (a Proxmox LXC or VM snapshot, ZFS or LVM) or a backup copied over the existing `control.sqlite` in place, which leave the same file: after one of those, sign in and use **Configure → Account → Sign out other devices** at once, or change the password. Snapshots that Uptime Goblin takes itself are restored with `goblin-admin restore-snapshot` ([below](#goblin-admin)), which signs everyone out the same way.

Natively, from the archive made above. The current data directory and `/etc/uptime-goblin.env` are moved aside, not deleted, until the restored Uptime Goblin runs; delete them yourself once you no longer need them:

```sh
sudo systemctl stop uptime-goblin.service
sudo mv /var/lib/uptime-goblin /var/lib/uptime-goblin.before-restore
sudo mv /etc/uptime-goblin.env /etc/uptime-goblin.env.before-restore
sudo tar -xzf /secure-backups/uptime-goblin-backup.tar.gz -C / var/lib/uptime-goblin etc/uptime-goblin.env
sudo chown -R uptime-goblin:uptime-goblin /var/lib/uptime-goblin
sudo chmod -R u=rwX,go= /var/lib/uptime-goblin
sudo chown root:root /etc/uptime-goblin.env
sudo chmod 600 /etc/uptime-goblin.env
```

Then put the encryption key the archive was made with back, if `/etc/uptime-goblin/secret.key` is not already that key (on a new host, say), with the two `sudo install` commands above. Before starting Uptime Goblin, check the restored data as the `uptime-goblin` account with the key Uptime Goblin uses (name the file that the restored `/etc/uptime-goblin.env` names, if it names another). Both commands only read: `key status` should say "The key opens every data key.", and `check-data` exits with status 1 when the databases are not as this release expects:

```sh
sudo -u uptime-goblin env GOBLIN_SECRET_KEY_FILE=/etc/uptime-goblin/secret.key node /opt/uptime-goblin/lib/cli/goblin-admin.mjs key status --data-dir /var/lib/uptime-goblin &&
  sudo -u uptime-goblin node /opt/uptime-goblin/lib/cli/goblin-admin.mjs check-data --data-dir /var/lib/uptime-goblin &&
  sudo systemctl start uptime-goblin.service
```

Under Docker Compose, from the archive made above. The second command keeps the volume's current files in an archive of their own before the third removes them and extracts the backup in their place; with `compose.secret.yaml`, `COMPOSE_FILE` in `.env` gives the two checks the key:

```sh
umask 077
docker compose stop uptime-goblin
docker compose run --rm --no-deps -T --entrypoint sh uptime-goblin -c 'tar -C /var/lib/uptime-goblin -czf - .' > "$HOME/uptime-goblin-backups/uptime-goblin-data-before-restore.tar.gz"
docker compose run --rm --no-deps -T --entrypoint sh uptime-goblin -c 'find /var/lib/uptime-goblin -mindepth 1 -delete && tar -C /var/lib/uptime-goblin -xzf - && chmod -R u=rwX,go= /var/lib/uptime-goblin' < "$HOME/uptime-goblin-backups/uptime-goblin-data.tar.gz"
docker compose run --rm --no-deps uptime-goblin node lib/cli/goblin-admin.mjs key status
docker compose run --rm --no-deps uptime-goblin node lib/cli/goblin-admin.mjs check-data
docker compose start uptime-goblin
```

An archive made under Orbit with its own backup line (`tar -C /app -czf - data`) holds its files in a `data/` folder: to restore it into 1.5, extract it with `tar -C /var/lib/uptime-goblin --strip-components=1 -xzf -` in the third command instead. A native archive made under Orbit holds `var/lib/orbit` and `etc/orbit.env`: restore it on a host with the Orbit layout before upgrading, or put its files in the new paths by hand.

## Updates and rollback

1. Record the installed source revision/archive and runtime version. Review the changelog and dependency changes.
2. Take a consistent backup and retain the previous source/image plus its lockfile. For Docker, tag the running image with its own version first, because every build replaces the local tag: for example `docker image tag uptime-goblin:local uptime-goblin:1.5.0` before an upgrade from 1.5.0, or `docker image tag orbit-homelab:local orbit-homelab:1.4.3` before the upgrade from Orbit 1.4.3 (Orbit's image was `orbit-homelab:local`).
3. [Verify the release](#verifying-a-release), or validate the new source in isolation: `npm ci --omit=dev --ignore-scripts` and `npm audit --omit=dev`.
4. For native LXC, run the installer from the new staging tree; it verifies the new version and rolls the code back by itself if it does not serve. The installer takes no backup of `/var/lib/uptime-goblin`, and Uptime Goblin snapshots `config.json`, `auth.json` and `control.sqlite` (not `history.sqlite`) only at a start that migrates its databases, so take the backup of step 2 first. For a local process, stop it, update the source, install locked dependencies and restart. For Docker, build first with `docker compose build --pull`. Then append the container's log to a file outside the volume, `(umask 077 && f=~/uptime-goblin-journal.txt && test ! -L "$f" && touch "$f" && test -f "$f" && n=$(mktemp "$f.XXXXXX") && { cat "$f" >> "$n" && mv -f "$n" "$f" || { rm -f "$n"; false; }; } && docker compose logs --no-log-prefix uptime-goblin >> "$f") || { echo "Uptime Goblin's log was not kept"; false; }`: recreating the container discards it, and with it the audit log's checkpoint lines ([keeping Uptime Goblin's log](#keeping-uptime-goblins-log)). Then recreate with `docker compose up -d --no-build` (with `compose.secret.yaml`, `COMPOSE_FILE` in `.env` keeps the key in this and every other `docker compose` command: [the encryption key](#encryption-key)).
5. Verify health, settings, a representative connection, new history samples, and notification status. Environment changes require a restart; browser settings usually do not.

Open Uptime Goblin tabs from 1.4.3 on notice the new version and reload themselves, returning to the same view; a tab with unsaved edits shows a banner with **Reload** instead. Tabs opened on 1.4.2 or earlier need one manual reload. The System page lists "Open tabs by version" seen in the last 10 minutes.

Proxy configuration validation is stricter from the 1.4.x maintenance candidate on, and so in 1.5: a `GOBLIN_TRUST_PROXY` entry with extra slash segments, such as `192.0.2.0/24/extra`, which 1.4.3 accepts, refuses startup with exit status 78. So do, in 1.5, an entry that trusts a range wider than /8 for IPv4 or /32 for IPv6, such as `0.0.0.0/0` or `::/0`, the NAT64 prefix `64:ff9b::/96` (or the local-use `64:ff9b:1::/96`), the IPv4-translated prefix `::ffff:0:0:0/96`, the IPv4-compatible prefix `::/96` or any range that holds one of them (each stands for every IPv4 address), more than 64 entries, and ranges that together cover more than two /8 (or /32) ranges, such as `10.0.0.0/8,11.0.0.0/8,12.0.0.0/8` (loopback is not counted; the private ranges and `100.64.0.0/10` together fit), all of which 1.4.3 accepts, and a value of only commas and blanks, such as `,`, which names no proxy (an empty value, `off`, `0`, `false` or `no` trusts none). Before upgrading, correct it in the private environment file (`/etc/uptime-goblin.env`, or `.env`) to one IP address and one prefix length, such as `192.0.2.0/24`, or use the exact proxy IP. Separate multiple entries with commas. The native installer checks a `--trust-proxy` value, and the `GOBLIN_TRUST_PROXY` in `/etc/uptime-goblin.env` (unless `--trust-proxy` replaces it) and as systemd would give it to Uptime Goblin, by the new release's rules before anything changes, and refuses the upgrade, changing nothing, with a value 1.5 refuses, as it does for `HOST`, `PORT` and `GOBLIN_MAX_CONNECTIONS_PER_CLIENT` ([native installs](#native-debian-or-ubuntu-lxc)).

Upgrading Orbit to 1.4.3: run the native installer from a staging directory, not from `/opt/orbit`. The unit now uses `Restart=always`, `ORBIT_SUPERVISED=1` and the unresolved Node path; the installer writes it. `/health` answers without signing in. Reload tabs opened on 1.4.2 once. Behind a reverse proxy with `ORBIT_TRUST_PROXY` set, open Orbit once through the proxy afterwards, so it records the protocol the proxy forwards (the next release checks it).

To roll back, stop Uptime Goblin and restore the previous complete application and its dependency lockfile/image (natively, with `Type=simple` for the unit, or through that release's installer: a release before this one does not report ready to a `Type=notify` unit, so `systemctl start` would wait for good). Restore its corresponding data backup if configuration/database changes are incompatible; this loses samples collected since the backup. Preserve a copy of the newer data before replacing it. Restore native ownership to `uptime-goblin:uptime-goblin`, directory mode 700 and private file mode 600. A rollback is not guaranteed merely because an older executable starts against newer state.

### Renamed from Orbit

Uptime Goblin was called Orbit until 1.4.x; 1.5 is the first release under the new name. An upgrade from Orbit keeps your settings, data, encryption key, password and signed-in browsers. The native installer moves the unit, account and paths for you (below), and under Docker Compose the volume keeps its name. The old settings, headers, cookie, admin command, lock and installer name keep working in 1.5 and 1.6, with a notice where Uptime Goblin can give one, and stop working in 1.7.

| What | Orbit (1.4.x) | Uptime Goblin (1.5) |
| --- | --- | --- |
| Settings | `ORBIT_*`, such as `ORBIT_PASSWORD` | `GOBLIN_*`, such as `GOBLIN_PASSWORD` |
| systemd unit | `orbit.service` | `uptime-goblin.service` |
| Service account and group | `orbit` | `uptime-goblin` |
| Code | `/opt/orbit` (and `.previous`, `.new`, `.failed`) | `/opt/uptime-goblin` (the same suffixes) |
| Data | `/var/lib/orbit` | `/var/lib/uptime-goblin` |
| Settings file | `/etc/orbit.env` | `/etc/uptime-goblin.env` |
| Key file | `/etc/orbit/secret.key` | `/etc/uptime-goblin/secret.key` |
| Native installer | `deploy/install-lxc.sh` | `deploy/install.sh` |
| Admin command | `lib/cli/orbit-admin.mjs` | `lib/cli/goblin-admin.mjs` |
| Data-directory lock | `orbit.lock` | `goblin.lock` |
| Request headers | `X-Orbit-Request`, `X-Orbit-Activity`, `X-Orbit-Client` | `X-Goblin-Request`, `X-Goblin-Activity`, `X-Goblin-Client` |
| Answer headers | `X-Orbit-Build`, `X-Orbit-Version` (the 1.5 pre-releases, still called Orbit, also sent `X-Orbit-Export-Rows`, `X-Orbit-Export-More`) | `X-Goblin-Build`, `X-Goblin-Version`, `X-Goblin-Export-Rows`, `X-Goblin-Export-More` |
| Webhook headers | none: 1.4.x sends no delivery or signature header (the 1.5 pre-releases, still called Orbit, sent `X-Orbit-Delivery`, `X-Orbit-Signature` and the User-Agent `Orbit`) | `X-Goblin-Delivery`, `X-Goblin-Signature`; User-Agent `Uptime-Goblin` |
| Session cookie | `orbit_session` (`__Host-orbit_session` over HTTPS) | `goblin_session` (`__Host-goblin_session` over HTTPS) |
| Docker image | `orbit-homelab:local` | `uptime-goblin:local` |
| Compose service | `orbit` | `uptime-goblin` |
| Data path in the container | `/app/data` | `/var/lib/uptime-goblin` |
| Release archive | `orbit-homelab-<version>.tar.gz` | `uptime-goblin-<version>.tar.gz` |

How the old names keep working:

- **Settings.** Each `GOBLIN_` setting that is not set is read from its `ORBIT_` name, and every start that does so logs one notice naming the settings to rename. When both names are set, to different values, Uptime Goblin and `goblin-admin` refuse to start (exit status 78), naming both and showing neither value; the same value under both names is accepted, with a notice to remove the old one. Under Docker Compose the same holds: `compose.yaml` passes each setting from `.env` as its `GOBLIN_` name, falling back to its `ORBIT_` one while the `GOBLIN_` line is missing, and passes each `ORBIT_` line as `GOBLIN_COMPOSE_LEGACY_<name>` too, which Uptime Goblin only compares with the setting, so both names with different values refuse the start (exit status 78) and an old name gets the notice. An empty `GOBLIN_` line counts as set, as it does natively (`GOBLIN_WEBHOOK_URL=` beside an old `ORBIT_WEBHOOK_URL` refuses rather than sending to the old URL), except for `GOBLIN_BIND_ADDRESS` and `GOBLIN_ALLOWED_HOSTS`: an empty line of either name counts as unset there, so that the port is never published on every address.
- **Headers.** A script that sends `X-Orbit-Request: 1` still passes the check; when it sends `X-Goblin-Request` too, the new header alone decides. Answers carry each header under both names. Webhooks carry `X-Goblin-Delivery` and `X-Goblin-Signature` and, with the same values, `X-Orbit-Delivery` and `X-Orbit-Signature`, in 1.5 and 1.6.
- **Signed-in browsers and wall displays.** An `orbit_session` cookie is still accepted while the browser has no `goblin_session`, and the next answer replaces it with the new cookie for the same session (still kept for 30 days when it was), so nobody signs in again. Signing in or out removes any old cookie.
- **The admin command.** `lib/cli/orbit-admin.mjs` prints one deprecation line to stderr and runs `goblin-admin` with the same arguments and exit status, so `--json` output on stdout is unchanged.
- **The lock.** Uptime Goblin takes `goblin.lock` and `orbit.lock` together, so an Orbit release and Uptime Goblin never run on the same data directory at once (exit status 75).
- **The native installer.** `deploy/install-lxc.sh` prints a deprecation line and runs `deploy/install.sh` with the same arguments and exit status.

What keeps its old name, because changing it would break existing installs, receivers or stored data: the systemd credential `orbit-secret-key` and the Compose secret file `orbit_secret_key` ([the encryption key](#encryption-key)); the Compose volume `orbit-data`; the release signing identity `release@orbit-homelab` and namespace `orbit-release` ([verifying a release](#verifying-a-release)); the webhook body's `"source":"orbit"` and the `"service":"orbit"` of Uptime Goblin's own notices ([notifications](notifications.md)); the `<orbit.…>` email `Message-ID`; the `{"orbit":"audit.…"}` lines in the log ([keeping Uptime Goblin's log](#keeping-uptime-goblins-log)); the `orbit-config` format of a configuration export; the `Basic realm="Orbit"` of legacy Basic, so browsers that remember a 1.4.x login are not asked again; and the databases, their tables and the audit log's action names.

**The native upgrade from Orbit.** Run `deploy/install.sh` from the new staging directory, as for any upgrade. On a host with the Orbit layout, every check reads the files where they are (`/etc/orbit.env`, `/var/lib/orbit`, `/etc/orbit`, the `orbit` account) and changes nothing until they pass. Then, in place of the service's stop, the installer moves the layout in one logged step: it stops `orbit.service`; renames `/var/lib/orbit` to `/var/lib/uptime-goblin`; writes `/etc/uptime-goblin.env` (mode 0600) from `/etc/orbit.env`, each `ORBIT_` name as its `GOBLIN_` one and each value as it was, except that a path in `/etc/orbit`, `/var/lib/orbit` or `/opt/orbit`, or `/etc/orbit.env` itself, becomes its new path (a path written so that it cannot be rewritten safely is refused), and keeps the old file as `/etc/orbit.env.migrated`; renames `/etc/orbit` to `/etc/uptime-goblin`, keeping modes; renames the `orbit` account and group to `uptime-goblin` (`usermod -l`, `groupmod -n`), so every file keeps its owner; renames `orbit.service.d` to `uptime-goblin.service.d`, disables `orbit.service` and keeps its unit file as `orbit.service.migrated`; and renames `/opt/orbit` to `/opt/uptime-goblin`, which the upgrade keeps as `/opt/uptime-goblin.previous`. The upgrade then installs and verifies 1.5 as usual.

Every move is a rename on one file system, never a copy. The installer refuses, before anything changes, a move that would cross file systems, a mount point or a symbolic link in the way, `.migrated` files left from an earlier run, an `orbit` account whose home is not `/opt/orbit`, a host without `usermod` or `groupmod`, `orbit.service` drop-ins outside `/etc/systemd/system/orbit.service.d` or that name an Orbit path, a host with parts of both layouts, and an `ORBIT_` and `GOBLIN_` setting in `/etc/orbit.env` with different values. A failed upgrade puts the Orbit layout back exactly, account, unit and settings file included, starts `orbit.service` again and checks that the previous release serves. One thing stays: on a host that had no encryption key, the key the upgrade wrote before the move (`/etc/orbit/secret.key`, named by `ORBIT_SECRET_KEY_FILE` at the end of `/etc/orbit.env`) is moved back there and kept, because settings the failed start sealed open only with it; 1.4.x ignores both, and the next upgrade moves and uses the same key. No Uptime Goblin path is left behind, so that next run is not refused as a host with parts of both layouts. A run that was cut short (killed, or the power lost) leaves `/var/lib/uptime-goblin.migrating`: the next run first undoes what it did, then migrates again.

**Docker Compose from Orbit.** Keep the running image under its own tag (`docker image tag orbit-homelab:local orbit-homelab:1.4.3`), take the [backup](#backups), replace the project files with the 1.5 release's and run `docker compose build --pull`. Then follow [the encryption key](#encryption-key) (its check names `/var/lib/uptime-goblin/secret.key` for the key in the volume) and start with `docker compose up -d --no-build --remove-orphans`: `--remove-orphans` removes the container of the old `orbit` service, which would otherwise keep running and hold port 4317. The `orbit-data` volume keeps its name and data and is now mounted at `/var/lib/uptime-goblin`. A container still started with the volume at `/app/data` (an older `compose.yaml`, or a container started by hand with its volume there) uses it there while nothing is at `/var/lib/uptime-goblin`, with a notice at every start; when both hold data, it refuses to start (exit status 78) until only one is mounted.

#### Upgrade checklist

- [ ] Settings: rename each `ORBIT_` line in `/etc/uptime-goblin.env` (the installer did this) or `.env` to its `GOBLIN_` name before 1.7, and remove the old one. Under Docker the [rollback override](#rolling-back-15-to-143) reads the `GOBLIN_` lines too, so no `ORBIT_` line is needed to roll back.
- [ ] Commands and scripts: `systemctl … uptime-goblin`, `journalctl -u uptime-goblin`, `sudo -u uptime-goblin`, `docker compose … uptime-goblin`, `lib/cli/goblin-admin.mjs` and `deploy/install.sh` in place of the Orbit names, and the new download names (`uptime-goblin-audit-….csv`, `uptime-goblin-config-redacted.json`).
- [ ] Scripts that call the API: send `X-Goblin-Request: 1` and read `X-Goblin-Build`, `X-Goblin-Version` and `X-Goblin-Export-Rows`/`-More`.
- [ ] Reverse proxies and firewalls: rules that name the `orbit_session` cookie, the `orbit` account or the Compose service `orbit`.
- [ ] Webhook receivers: verify `X-Goblin-Signature` and `X-Goblin-Delivery` ([verifying signatures](notifications.md#verifying-signatures)), and match the User-Agent `Uptime-Goblin` if they check it. The `X-Orbit-` copies stop in 1.7.
- [ ] Monitoring and backups: unit, account and paths (`/var/lib/uptime-goblin`, `/etc/uptime-goblin.env`, `/etc/uptime-goblin/secret.key`).
- [ ] Once 1.5 runs well: delete `/etc/orbit.env.migrated` and `/etc/systemd/system/orbit.service.migrated`, which hold your old settings, as you would a backup.

### Upgrading to 1.5

Browsers now sign in on Uptime Goblin's own page and stay signed in with a session cookie instead of the browser's Basic prompt (which a browser can still show over plain HTTP where Uptime Goblin accepts Basic: [legacy Basic](authentication.md#scripts-and-legacy-basic)). The admin password stays the one you use today. Read [signing in](authentication.md) first; in short:

- **A password is always required.** 1.5 does not start without `auth.json` or `GOBLIN_PASSWORD` (exit status 78). A 1.4.x install that ran without one (the local preview, on loopback only) needs `GOBLIN_PASSWORD` set before the upgrade ([a password is always required](authentication.md#a-password-is-always-required)).

- **Reverse proxy:** nginx must send `proxy_set_header X-Forwarded-Proto $scheme;` and forward the Host (`proxy_set_header Host $http_host;`). Check before upgrading: after browsing Uptime Goblin through nginx once, `sudo cat /var/lib/uptime-goblin/run/status.json` must show `"observed": {"forwardedProto": "https"}` (what `"http"` and `null` mean is in [before upgrading from 1.4.x](authentication.md#before-upgrading-from-14x)).
- **The installer's proxy preflight:** upgrading a 1.4.x install with `GOBLIN_TRUST_PROXY` set is refused, changing nothing on the host, until the running 1.4.3 has recorded `https`. The message says what it saw and how to fix it. Fix nginx, browse once and run the installer again without restarting Uptime Goblin in between (every start of 1.4.3 empties the record, so a script that stops Uptime Goblin for a backup must read `run/status.json` first and pass `--proxy-proto-checked` when it says `https`); or add `GOBLIN_INSECURE_HTTP_SESSIONS=1` to `/etc/uptime-goblin.env` on a trusted network (or run the installer with `--allow-insecure-http`); or, when you checked the proxy yourself, run it with `--proxy-proto-checked`. Do not stop 1.4.3 before running the installer: it removes the record when it stops, and the installer then says Uptime Goblin is not running (start it, browse once and run the installer again). 1.4.2 and earlier record nothing: upgrade to 1.4.3 first, or check nginx and use `--proxy-proto-checked`.
- **Plain HTTP:** the upgrade of an install that listens on the network without a trusted proxy stops, changing nothing, until you choose: put Uptime Goblin behind an HTTPS proxy (`HOST=127.0.0.1` and `--trust-proxy loopback`), or run the installer with `--allow-insecure-http` on a network you trust (see above), or set `GOBLIN_INSECURE_HTTP_SESSIONS=0` in `/etc/uptime-goblin.env` to keep sign-in over plain HTTP refused. With `=1` the password at each sign-in, every script's Basic password and the cookie cross the network in clear; scripts that call Uptime Goblin with Basic over plain HTTP need it too (403 `https_required` otherwise, except through a proxy on the Uptime Goblin host that sends no forwarding headers and keeps a loopback Host: see **Scripts using Basic** below), and send `X-Goblin-Request: 1` with a configuration or audit export, there as everywhere (403 `cross_origin` otherwise). Once Uptime Goblin is served over HTTPS, set it to `0` and restart. Docker Compose allows plain-HTTP sign-in by default only while it publishes the port on the Docker host's loopback (`GOBLIN_BIND_ADDRESS=127.0.0.1`, the default). With `GOBLIN_BIND_ADDRESS` set to a LAN address (or `0.0.0.0`) and neither `GOBLIN_TRUST_PROXY` nor `GOBLIN_INSECURE_HTTP_SESSIONS` in `.env`, 1.5 refuses to start (exit status 78) until `.env` names your HTTPS proxy in `GOBLIN_TRUST_PROXY` or sets `GOBLIN_INSECURE_HTTP_SESSIONS=1` (plain HTTP on that network, as 1.4.3 had) or `0` ([Docker Compose](#docker-compose)).
- **Docker:** keep the running 1.4.3 image under its own tag first, `docker image tag orbit-homelab:local orbit-homelab:1.4.3` (see [rolling back](#rolling-back-15-to-143)). Build the 1.5 image with `docker compose build --pull` (it is `uptime-goblin:local`), then follow [the encryption key](#encryption-key) and step 4 of [updates and rollback](#updates-and-rollback), starting it the first time with `docker compose up -d --no-build --remove-orphans`, which removes the container of the service `orbit` ([renamed from Orbit](#renamed-from-orbit)).
- **After the upgrade** the installer prints "Sign in as admin with the same password. Reload Uptime Goblin tabs that were open before this upgrade once." A 1.4.3 tab without unsaved changes reloads itself into the sign-in page; a 1.4.2 tab says to reload.
- **Escape hatches**, if the sign-in page shows a proxy message: [when sign-in is refused](authentication.md#when-sign-in-is-refused). A native install that listens on 127.0.0.1 (the default, as with `--trust-proxy loopback`) or on every address (`HOST=0.0.0.0` or `::`) also signs in through `ssh -L 4317:127.0.0.1:4317 <lxc>` at <http://localhost:4317>, without HTTPS. An install made with `--listen <address>` does not listen on 127.0.0.1, and a tunnel to its address is plain HTTP to Uptime Goblin: there, add `GOBLIN_INSECURE_HTTP_SESSIONS=1` on a trusted network until the proxy is fixed.
- **Scripts using Basic** keep working on upgraded installs over HTTPS (through a proxy named in `GOBLIN_TRUST_PROXY` that sends `X-Forwarded-Proto: https`), from the Uptime Goblin computer itself, or while plain-HTTP sign-in is on (`GOBLIN_INSECURE_HTTP_SESSIONS=1`, or Docker Compose's default on its loopback port); over plain HTTP otherwise they get 403 `https_required`, except through a proxy on the Uptime Goblin host that sends no forwarding headers and keeps a loopback Host: Uptime Goblin takes its requests for the Uptime Goblin computer's own (the `loopback` transport), so Basic through it is accepted with no opt-in and no warning in the log, also from clients that reach the proxy over plain HTTP (not under Docker Compose, where a proxy on the Docker host reaches Uptime Goblin from the Docker gateway, as plain HTTP). Make such a proxy send `X-Forwarded-For` and `X-Forwarded-Proto` and name it in `GOBLIN_TRUST_PROXY` (`--trust-proxy loopback`). They send `X-Goblin-Request: 1` with a configuration or audit export wherever they call Uptime Goblin from, over HTTPS, over plain HTTP (under Docker Compose also from the Docker host) and from the Uptime Goblin computer itself (403 `cross_origin` otherwise; 1.4.x needed no extra header on an export). New installs have Basic off (`GOBLIN_LEGACY_BASIC`). An nginx that injects `Authorization: Basic` for browsers no longer signs them in.
- **Wall displays:** a wall display signs in with a one-time display code (`goblin-admin display code --name <name>`, typed on its `?kiosk=1` page), not the admin password. It then reads only the dashboard, and stays signed in for up to 30 days while it refreshes. A display that kept its 1.4.x Basic login has to sign in again after the upgrade anyway: set it up with a code then ([wall displays](authentication.md#wall-displays)).
- **Restart after changing** `GOBLIN_INSECURE_HTTP_SESSIONS` or `GOBLIN_LEGACY_BASIC`. Under Docker Compose that is `docker compose up -d`, which reads `.env` again; `docker compose restart` keeps the values the container was created with.
- **Notifications are durable** (see [alerts and notifications](notifications.md)): saved before they are sent, retried for up to 24 hours, and listed under **Configure → Notifications**. Nothing 1.4.x sent is sent again. The webhook body is unchanged; requests add `X-Goblin-Delivery` and `X-Goblin-Signature`, a request not answered within 8 seconds is sent once more after 2 minutes, link-local, multicast and reserved addresses are refused, and a redirect or a `401`/`403`/`404`/`410` answer pauses the webhook (Uptime Goblin tries again every 15 minutes and at each start; **Resume** sends at once). An email sign-in failure pauses email until you save its settings, send a test email that is accepted, or press **Resume**.
- **Encryption key:** the installer creates `/etc/uptime-goblin/secret.key` (or keeps the key you have, after checking it opens your data) and sets `GOBLIN_SECRET_KEY_FILE`. Back it up separately from `/var/lib/uptime-goblin` ([the encryption key](#encryption-key)). Docker: use `compose.secret.yaml`, named in `.env` (`COMPOSE_FILE=compose.yaml:compose.secret.yaml`) so every later `docker compose` command keeps the key, or accept the generated `/var/lib/uptime-goblin/secret.key`. Its key comes from what the volume holds, not from the release running ([the check](#encryption-key)): a new key for a volume only 1.4.x has run on, which has none yet (`NEW`), but the copy of `/var/lib/uptime-goblin/secret.key` for a volume 1.5 has already run on without the override, also one that runs 1.4.x again after a rollback (`COPY`), and the `orbit_secret_key` you have for a volume 1.5 ran on with it, also when going forward again after a rollback (`KEEP`: make no new key). The check tries each key there is on the data, so a volume that still holds an older `secret.key` beside a working `orbit_secret_key` says `KEEP`, not `COPY`, and the copy recipe never replaces an `orbit_secret_key`. Compose now gives Uptime Goblin 40 seconds to stop.
- **Free space:** the first 1.5 start takes a pinned snapshot of `config.json` and `auth.json` under `snapshots/` in the data directory (the data as 1.4.x left it: `control.sqlite` does not exist yet, and `history.sqlite` is left out, since no migration step changes it and it can be large), then creates `control.sqlite`. 1.5 only adds to `history.sqlite`: three columns and a partial index on its `events` table, which 1.4.x ignores, and the `history_summaries` table with its index (5-minute summaries of the readings for 7- and 30-day charts, about 1 MB per source per 30 days, written in the background at the first start), which it ignores too; they stay through a restore of that snapshot and through a rollback. It needs about 16 MiB free plus the size of those two files.
- **Space reserve:** Uptime Goblin keeps 8 MiB in `run/space-reserve` for a full disk ([space reserve](#space-reserve)), and starts on a full disk too.
- **Rolling back** to 1.4.3 or 1.4.2 needs no preparation of the data and uses the current password (`auth.json` holds it), unless Uptime Goblin's pages show "Uptime Goblin saved the admin password but could not update auth.json". Until that banner has gone, `auth.json` still holds the previous password, and 1.4.x signs in with it: fix the disk and wait for the banner to go (or restart 1.5, which tries again at once) before you roll back, above all when you changed the password because the old one may be known. 1.4.x ignores `control.sqlite`, `snapshots/`, `secret.key`, `run/space-reserve` and `history_summaries`; the readings it records are summarised when 1.5 starts again, and until then 7- and 30-day charts read every reading. Webhook receivers that check signatures must accept unsigned requests first: 1.4.x sends none. See [rolling back 1.5 to 1.4.3](#rolling-back-15-to-143).
- **Audit log:** Uptime Goblin now keeps an [audit log](security.md#audit-log) of sign-ins, sign-outs, session and password changes, every settings and source change (with what changed; passwords and keys only as "changed"), source and email tests, refreshes, delivery **Retry** and **Resume**, the webhook signing key's creation and replacement, exports, the `goblin-admin` key commands, restores and snapshots, Uptime Goblin's own starts and upgrades, and changes to its security settings: **Configure → Audit log**. Entries are kept 90 days by default (`GOBLIN_AUDIT_RETENTION_DAYS`, 30–3650), at most 250,000. Docker Compose passes both audit settings (`GOBLIN_AUDIT_LOG`, `GOBLIN_AUDIT_RETENTION_DAYS`) from `.env`.
- **When Uptime Goblin cannot write its audit log**, settings and source changes, **Retry**, **Resume** and both exports are refused with "Uptime Goblin cannot write its audit log, so nothing was changed. Try again in a moment; if this continues, free up space or increase the disk size of the Uptime Goblin host." (503 `audit_unavailable`) until the disk is fixed; signing in fails for the same cause. Source tests, test emails and refreshes still run, and their entries then go to Uptime Goblin's log ([troubleshooting](troubleshooting.md#uptime-goblin-cannot-write-its-audit-log)).
- **Checkpoints in Uptime Goblin's log:** Uptime Goblin prints a line starting `{"orbit":"audit.checkpoint"` to its log each time it records something. Keep that log: `goblin-admin verify-audit --checkpoints <export>` (or `--checkpoints -` from a pipe) compares the audit log with it. Under Docker Compose the container's log holds 10 MB and is discarded when the container is recreated: export it before each `docker compose up -d` ([keeping Uptime Goblin's log](#keeping-uptime-goblins-log)). `GOBLIN_AUDIT_LOG=stdout` copies every entry to the log as well.
- **Rolling back the audit log** to an earlier 1.5 build or to 1.4.x needs no preparation; nothing is audited while it runs, and the next start of this release records the 1.5 builds that opened the data and what changed meanwhile (`config.json` by its content, and the admin password); a 1.4.x run is not named, so one that changed neither leaves no trace. After a rollback to an earlier 1.5 build, its `goblin-admin check-data` reports the four audit tables (`audit_log`, `audit_head`, `audit_checkpoints`, `audit_inbox`) and `history_summaries` as unregistered and exits 1; that is expected: they wait for the next upgrade, whose first start checks the summaries against the readings that build wrote. The webhook signing key is another matter: never start data that this release has run on with an earlier 1.5 pre-release build, which shows no signing secret there and sends webhooks unsigned (on data that 1.5 pre-release builds before this release left, such a build took the private signing key for its HMAC secret, signed with its text and showed it under **Show signing secret**; if one has run, see [rolling back 1.5 to 1.4.3](#rolling-back-15-to-143)). The native installer's automatic rollback never starts such a build that signs with an HMAC secret, with or without a webhook ([verification and automatic rollback](#verification-and-automatic-rollback)). It does restore and start a 1.5 pre-release build that already signs with Ed25519 (its `lib/` declares this release's public-key route and not the reveal route), as any earlier release: if the failed start of this release got as far as saving the signing settings in its form, that build reads them read-only, answers **Show public key** with 503 `signing_unavailable` and sends webhooks unsigned (its log says "The webhook signing key could not be saved (…); alerts are sent unsigned until it can be."; the installer does not), so receivers that check signatures refuse them, a `401` or `403` pausing the webhook and a `400` or `422` ending each alert as **Failed**, until this release runs again or the data from before the upgrade is restored.

### goblin-admin

`goblin-admin` reports on the data directory and changes it. What each command does, and when it may run (`node lib/cli/goblin-admin.mjs COMMAND --help`, with `COMMAND` replaced by one of the commands below, gives its options; a shell passes the placeholder on as a plain word: left as it is, goblin-admin answers `unknown command "COMMAND"`, exit status 2):

| Command | What it does |
|---|---|
| `status [--unit <file>]`, `snapshots [--verify]`, `check-data`, `migrate --plan`, `verify-audit [--checkpoints <file> \| -]`, `key status`, `key compose-check` | Only read, also while Uptime Goblin runs. `status --unit` checks the Node binary of another systemd unit file than `/etc/systemd/system/uptime-goblin.service`. `snapshots --verify` checks each snapshot's files against its checksums and its databases with SQLite's `integrity_check` (the check made before every restore), `check-data` compares the databases with the tables this release knows and reports any trigger or view in them, and any other catalog entry that is not a table or an index as SQLite writes one (Uptime Goblin creates none, and a trigger runs inside Uptime Goblin's own writes); both exit with status 1 when they find a problem. |
| `key remove-data-copy [--unused]` | Deletes a `secret.key` in the data directory that Uptime Goblin does not need (below). Runs beside a running Uptime Goblin. |
| `display code --name <name>`, `display list`, `display cancel <id> \| --all` | Runs beside a running Uptime Goblin. `display code` prints a one-time code that signs a wall display in, read-only, within 10 minutes ([wall displays](authentication.md#wall-displays)); it needs the key Uptime Goblin uses, as the key commands below do, and refuses to print the code into systemd's journal. `display list` shows the codes Uptime Goblin keeps, never a code. `display cancel` cancels a waiting code, or with `--all` every one. `display list` and `display cancel` work without the key. |
| `snapshot [--reason <word>] [--no-history] [--pin]` | With Uptime Goblin stopped: copies `config.json`, `auth.json`, `control.sqlite` and, unless `--no-history`, `history.sqlite` into `snapshots/`. `--pin` marks it `[pinned]` in the list, like the snapshot of the first 1.5 start. |
| `snapshots --delete <id> [--force]` | With Uptime Goblin stopped: deletes one snapshot ([snapshots](#snapshots)). A `[pinned]` snapshot only with `--force`; never one that an interrupted restore still needs. |
| `restore-snapshot <id> [--keep-history]` | With Uptime Goblin stopped: puts a snapshot's files back. When the snapshot holds `history.sqlite`, the live one is replaced too, unless `--keep-history`. The files it replaces, readings since the snapshot included, go into a pre-restore snapshot, which undoes it. |
| `migrate --apply [--no-snapshot]` | With Uptime Goblin stopped: applies pending changes to the databases, after a snapshot unless `--no-snapshot`. Uptime Goblin does the same at its start. |
| `key rotate [--purpose <p>]`, `key rewrap`, `key reset --confirm-lost-key [--use-data-dir-key]` | With Uptime Goblin stopped: change the keyring ([changing the key](#changing-the-key)). |

The installer does not put a `goblin-admin` command on the `PATH` yet; run the script with Node, as the user Uptime Goblin runs as, and name the data directory.

On a native install (commands that change the data directory refuse to run as root; `restore-snapshot` checks a keyring it brings back with the key in its own environment, so it is given the key Uptime Goblin uses, as the key commands below are: [snapshots](#snapshots)), with `SNAPSHOT_ID` replaced by an id that `snapshots` lists (a shell passes the placeholder on as a plain word: left as it is, `restore-snapshot` refuses with `"SNAPSHOT_ID" is not a snapshot id`, exit status 1):

```sh
sudo -u uptime-goblin node /opt/uptime-goblin/lib/cli/goblin-admin.mjs status --data-dir /var/lib/uptime-goblin
sudo systemctl stop uptime-goblin.service
sudo -u uptime-goblin node /opt/uptime-goblin/lib/cli/goblin-admin.mjs snapshots --data-dir /var/lib/uptime-goblin
sudo -u uptime-goblin env GOBLIN_SECRET_KEY_FILE=/etc/uptime-goblin/secret.key node /opt/uptime-goblin/lib/cli/goblin-admin.mjs restore-snapshot SNAPSHOT_ID --data-dir /var/lib/uptime-goblin
sudo systemctl start uptime-goblin.service
```

The key commands, natively, with the key Uptime Goblin uses named in their own environment (`goblin-admin` does not read `/etc/uptime-goblin.env`; here the installer's key file):

```sh
sudo -u uptime-goblin env GOBLIN_SECRET_KEY_FILE=/etc/uptime-goblin/secret.key node /opt/uptime-goblin/lib/cli/goblin-admin.mjs key status --data-dir /var/lib/uptime-goblin
sudo systemctl stop uptime-goblin.service
sudo -u uptime-goblin env GOBLIN_SECRET_KEY_FILE=/etc/uptime-goblin/secret.key node /opt/uptime-goblin/lib/cli/goblin-admin.mjs key rotate --data-dir /var/lib/uptime-goblin
sudo systemctl start uptime-goblin.service
```

Under Docker Compose, reports run while Uptime Goblin runs and changes with Uptime Goblin stopped. With `compose.secret.yaml`, `COMPOSE_FILE` in `.env` ([the encryption key](#encryption-key)) gives these commands the key too:

```sh
docker compose exec uptime-goblin node lib/cli/goblin-admin.mjs status
docker compose stop uptime-goblin
docker compose run --rm --no-deps uptime-goblin node lib/cli/goblin-admin.mjs restore-snapshot SNAPSHOT_ID
docker compose start uptime-goblin
```

With `npm start`, `goblin-admin` does not read `.env`, which `npm start` loads for Uptime Goblin. Run it from the project directory, as the user who runs Uptime Goblin, with the same file, so that it sees the `GOBLIN_DATA_DIR` and `GOBLIN_SECRET_KEY_FILE` Uptime Goblin sees (without `GOBLIN_DATA_DIR` it uses `data/` beside Uptime Goblin, as `npm start` does):

```sh
node --env-file-if-exists=.env lib/cli/goblin-admin.mjs status
```

The key commands take the same form (`… key status`, `… key remove-data-copy`; for a lost key `… key reset --confirm-lost-key`, with `--use-data-dir-key` only when `.env` sets no `GOBLIN_SECRET_KEY_FILE`). A variable set on the command line wins over `.env`. Uptime Goblin's own messages print the native line; use this form instead.

**The key commands** (`key status`, `key rotate`, `key rewrap`, `key reset`, `key remove-data-copy`) read the encryption key from their own environment, in the order Uptime Goblin does ([the encryption key](#encryption-key)), never from `/etc/uptime-goblin.env`: that file is root's, and systemd reads it for the service alone, while `sudo -u uptime-goblin` starts a clean environment. Name the key Uptime Goblin uses: the installer's `/etc/uptime-goblin/secret.key` as above, or the file your own `GOBLIN_SECRET_KEY_FILE` line names (a systemd credential: see below). A key change adds the old key in a file of its own ([changing the key](#changing-the-key)). Refusals that send you to a key command print it in this form. Uptime Goblin's refusals to start and its start warnings name the `GOBLIN_SECRET_KEY_FILE` and `GOBLIN_SECRET_KEY_PREVIOUS_FILE` it was started with; without them, `/etc/uptime-goblin/secret.key` and the placeholder `OLD_KEY_FILE`: put in your own files. A shell passes the placeholder on as a plain word: pasted without replacing it, the command looks for the old key in a file named `OLD_KEY_FILE` in its working directory, which `sudo -u uptime-goblin` keeps from the shell, and where it cannot read one there it stops with exit status 78: "GOBLIN_SECRET_KEY_PREVIOUS_FILE (OLD_KEY_FILE) cannot be read: ENOENT." where there is none, and "… cannot be read: EACCES." where the `uptime-goblin` account cannot enter that directory, such as a directory only root can enter. A key file that is a FIFO or another special file, or a symbolic link to one, is never waited on, as at Uptime Goblin's start: the command stops at once with "… is not a file." (exit status 1 for `key status`, `key compose-check`, `key remove-data-copy` and `verify-audit`; 78 for `key rewrap`, `key rotate` and `key reset`), changing nothing. A key command that finds no key also names the transient service for a systemd credential (below). A key command that finds no key cannot tell whether Uptime Goblin has one, so it never calls the key lost: `key status` says "Master key: not found by this command" and how to run it (exit status 1), `key rotate` and `key rewrap` stop, and `key reset` refuses (exit status 2), writing no key and no keyring, rather than make a key that Uptime Goblin does not read, which would leave it refusing to start. Only `--use-data-dir-key` lets a reset use or generate `secret.key` in the data directory, for an Uptime Goblin that has no other key source (Compose without `compose.secret.yaml`, `npm start` without `GOBLIN_SECRET_KEY_FILE`). Under Compose, `docker compose exec` runs in the running container, which has the secret; `docker compose run` mounts it only with `compose.secret.yaml` (`COMPOSE_FILE` in `.env`). `key compose-check`, read-only like `key status`, is the Compose check of [the encryption key](#encryption-key): run it as printed there. `key remove-data-copy` is the last line of the Compose copy and `MOVE` recipes there, and runs beside a running Uptime Goblin (it takes no lock): it deletes the data directory's `secret.key` only while the key it is given comes from another source (the Compose secret, a `GOBLIN_SECRET_KEY_FILE` outside the data directory, or `GOBLIN_SECRET_KEY`), is the same key byte for byte and opens the data, and while that source's file, read again just before the deletion, still holds it (a key file deleted, changed or replaced while the command runs is not taken for a lasting copy, and one replaced by a FIFO or other special file is not waited on); otherwise it says why, deletes nothing and exits with status 1. A systemd credential it never takes for a copy, since it cannot see where systemd loads one from. Under Compose it runs in Uptime Goblin's own container (`docker compose exec uptime-goblin node lib/cli/goblin-admin.mjs key remove-data-copy`), whose key is Uptime Goblin's. With `--unused` it deletes an older key instead, which it keeps otherwise: a `secret.key` the data moved from with `key rewrap`, which Uptime Goblin does not use and which every copy of the data directory still carries. It deletes it only while the key it is given comes from another source and opens every data key, and the file holds another key that opens none of them; a copy of the key it keeps and sends you to the line without `--unused`. Neither form deletes a `secret.key` that `GOBLIN_SECRET_KEY_PREVIOUS_FILE` names, which Uptime Goblin reads at every start. Each is the line Uptime Goblin's start warning gives for that file, and the check of `compose.secret.yaml` gives it after `KEEP`.

Natively, once Uptime Goblin has started: the first line deletes the copy the installer leaves in `/var/lib/uptime-goblin` when it copies that key to `/etc/uptime-goblin/secret.key` (its message gives the same line); the second, after a key change, deletes the older key left there.

```sh

```

```sh

```

**With a systemd credential** (`LoadCredential=` or `LoadCredentialEncrypted=` in a drop-in), `sudo -u uptime-goblin` cannot reach the key: the credential's file is root's, and an encrypted one holds no plain key. Do not make that file readable by `uptime-goblin`, and do not put the key on a command line. Run the command in a transient service instead, which loads the same credential, so that `goblin-admin` finds it as Uptime Goblin does (`$CREDENTIALS_DIRECTORY/orbit-secret-key`):

```sh

```

Give it the drop-in's own line after `-p` (for an encrypted credential `LoadCredentialEncrypted=orbit-secret-key:<file>`); a `SetCredentialEncrypted=` value has no file, so save the key encrypted to one first (`sudo systemd-creds encrypt --name=orbit-secret-key KEY_FILE /etc/credstore.encrypted/orbit-secret-key`, with `KEY_FILE` replaced by the path of the key file) and load that, in Uptime Goblin's drop-in too. `--pipe` passes standard input on, for `verify-audit --checkpoints -`, and `--wait` needs D-Bus on the host. This form has not been run on a host for this release: run `key status` with it first, which changes nothing, and go on only when it prints "The key opens every data key."

Run as root, a command that changes the data directory refuses (exit status 2) and prints the command to use instead (none when an argument holds a control character, a Unicode line or paragraph separator, or a text-direction embedding, override or isolate: it names that argument escaped instead). Stop the stack before any command that changes the data directory. Refusals elsewhere in Uptime Goblin that send you here name the native command line; use the Compose form above under Docker. Run natively, `goblin-admin`'s own messages (`status`, its refusals) name the copy you ran and the data directory you gave it instead, so the 1.5 copy kept after a rollback names itself, `/opt/uptime-goblin.previous/lib/cli/goblin-admin.mjs`. `node lib/cli/goblin-admin.mjs help` lists every command.

**Checking the audit log.** `verify-audit` checks the [audit log](security.md#audit-log) as **Check integrity** does: read-only, without a lock, while Uptime Goblin runs. It finds the key as `key status` does; without one it checks everything but the signatures and says so. It prints `Audit log: intact.`, `Audit log: empty. There is nothing to check yet.`, `Audit log: CHANGED at entry #…` with what was found, or `Audit log: not fully checked.` with what could not be checked, then one line for each restore, upgrade, gap and key reset. Its exit status is 0 (intact or empty), 1 (CHANGED, or the check could not run: a line starting `goblin-admin verify-audit:` instead of `Audit log:` says why), 2 (a usage error, such as a `--checkpoints` file it cannot read) or 3 (not fully checked) ([exit statuses](troubleshooting.md#exit-statuses)). `--json` prints the result as data. With `--checkpoints <file>`, or `--checkpoints -` to read standard input, it also compares the log with the checkpoint lines Uptime Goblin printed (any text holding them: a `journalctl` or `docker compose logs` export), which detects entries removed from the end, and says how far the lines reach. Natively, one root shell pipes the journal into the check, which runs as the `uptime-goblin` user, so no copy of the journal is written anywhere (it can hold more than checkpoints: [keeping Uptime Goblin's log](#keeping-uptime-goblins-log)):

```sh
sudo sh -c 'journalctl -u uptime-goblin -o cat | sudo -u uptime-goblin env GOBLIN_SECRET_KEY_FILE=/etc/uptime-goblin/secret.key node /opt/uptime-goblin/lib/cli/goblin-admin.mjs verify-audit --checkpoints - --data-dir /var/lib/uptime-goblin'
```

Under Docker Compose, inside Uptime Goblin's own read-only container, with the container's log piped in (add the lines you kept, below, in front of them):

```sh
docker compose logs --no-log-prefix uptime-goblin | docker compose exec -T uptime-goblin node lib/cli/goblin-admin.mjs verify-audit --checkpoints -
```

After a restore (of a snapshot, or of `control.sqlite` from a backup), the checkpoint lines printed before it name entries the restored log no longer holds: they are counted as not checkable, so the result is "not fully checked", never "CHANGED". Check with only the part of the log printed after the restore to get a full result. Checkpoint lines signed with a key the keyring does not hold cannot be checked either (another Uptime Goblin's lines; this Uptime Goblin's from before a restore of data older than a `key rotate`; this Uptime Goblin's from before `control.sqlite` was deleted, or before a snapshot or a copy without one was restored, which removed the whole audit log; or this Uptime Goblin's under a key that was then removed from the keyring by hand, which can hide entries removed with it): they are counted as not written by this Uptime Goblin, and the result is "not fully checked" ([not fully checked](troubleshooting.md#the-audit-log-check-says-not-fully-checked)). `migrate --apply`, `snapshot` and `restore-snapshot` write no audit entry; Uptime Goblin records what they did at its next start. The key commands write their own entry, as the user who ran them; when it cannot be written, the command says so on stderr and still does its work, except `key reset`, which then leaves the keyring as it was (exit status 1; a `secret.key` it generated in the data directory for `--use-data-dir-key` stays). They print no checkpoint line: their entry is covered by the checkpoint of Uptime Goblin's next entry, such as its start, so start Uptime Goblin soon after a key command and keep that start's lines (`key remove-data-copy` runs beside a running Uptime Goblin, so no start follows it: sign in once afterwards, and keep that line); until then, someone who can write `control.sqlite` can remove that entry unseen ([the audit log](security.md#audit-log)).

#### Changing the key

`key rewrap` wraps every data key with the current key. Use it to move to a new key when the old one was not exposed. `key rotate` also makes new data keys, for all four purposes (`seal`, `sessions`, `login`, `audit`) or for those `--purpose` names, and keeps the old ones, retired, so that they still open older values; given the previous key, it first wraps every data key with the current key, as `key rewrap` does. Use it when the old key may have leaked ([a leaked key](security.md#a-leaked-key)). In 1.5 neither seals a stored value again: the webhook's private signing key stays sealed under its old data key until it is replaced (**Replace signing key**). Both run with Uptime Goblin stopped, with the new key as Uptime Goblin's key and the old one in `GOBLIN_SECRET_KEY_PREVIOUS_FILE`. Uptime Goblin also starts with `GOBLIN_SECRET_KEY_PREVIOUS_FILE` (or `GOBLIN_SECRET_KEY_PREVIOUS`) set, and warns at every start ("Some data keys open only with GOBLIN_SECRET_KEY_PREVIOUS; …") until one of them has run. Afterwards remove that setting, and keep the old key only with the backups and [snapshots](#snapshots) made before the change, which open only with it. If the command fails, put the old key back before you start Uptime Goblin. Paste the lines one at a time.

Natively, the old key kept as `/etc/uptime-goblin/secret.key.old` (if `key rotate` fails, put it back with `sudo cp -p /etc/uptime-goblin/secret.key.old /etc/uptime-goblin/secret.key`):

```sh
sudo systemctl stop uptime-goblin.service
sudo test -e /etc/uptime-goblin/secret.key.old && echo 'secret.key.old exists: choose another name' || { sudo cp -p /etc/uptime-goblin/secret.key /etc/uptime-goblin/secret.key.old && openssl rand -hex 32 | sudo install -o root -g uptime-goblin -m 0440 /dev/stdin /etc/uptime-goblin/secret.key; }
sudo -u uptime-goblin env GOBLIN_SECRET_KEY_FILE=/etc/uptime-goblin/secret.key GOBLIN_SECRET_KEY_PREVIOUS_FILE=/etc/uptime-goblin/secret.key.old node /opt/uptime-goblin/lib/cli/goblin-admin.mjs key rotate --data-dir /var/lib/uptime-goblin
sudo systemctl start uptime-goblin.service
```

#### Snapshots

Uptime Goblin takes a snapshot at every start that migrates its databases (the first 1.5 start, and later upgrades that change them), `restore-snapshot` takes one of the files it replaces, `migrate --apply` one before it applies, and `goblin-admin snapshot` one when you ask; `goblin-admin snapshots` lists them. Uptime Goblin 1.5 never deletes a snapshot by itself: `goblin-admin snapshots --delete <id>` deletes one. Each holds the `config.json`, `auth.json` and `control.sqlite` of its time (the first 1.5 start's holds no `control.sqlite`, which did not exist yet): the admin password's hash, the sessions, the audit log (also entries older than `GOBLIN_AUDIT_RETENTION_DAYS`) and, in 1.5, the source and SMTP credentials in plain text; `goblin-admin snapshot` also copies `history.sqlite` (not with `--no-history`: a restore then keeps the live one). A snapshot is refused (exit status 78) before any of it is written when a file it copies is not a regular file or a link to one, such as a link to a volume that is not mounted ([exit statuses](troubleshooting.md#exit-statuses)); `migrate --apply` then applies nothing, also when every file of the data directory is such a link. Each database copy must also pass SQLite's `integrity_check`, the check `restore-snapshot` makes before it restores one: a damaged live database refuses the snapshot (exit status 78) and leaves nothing in `snapshots/`, so a start that would migrate it, or `migrate --apply`, changes nothing; restore an earlier snapshot or a backup first.

Snapshots are kept in `snapshots/` inside the data directory, on the same disk: they undo a change, and are **not an off-host backup**. A disk that fails takes them with the data, and the [backup](#backups) archive of the data directory includes them, so each `goblin-admin snapshot` that copies `history.sqlite` grows every later archive by that much. Back up to another disk or host as [Backups](#backups) describes.

Delete a snapshot you no longer need with Uptime Goblin stopped, as the user Uptime Goblin runs as:

```sh
sudo systemctl stop uptime-goblin.service
sudo -u uptime-goblin node /opt/uptime-goblin/lib/cli/goblin-admin.mjs snapshots --data-dir /var/lib/uptime-goblin --delete <id>
sudo systemctl start uptime-goblin.service
```

Under Docker Compose:

```sh
docker compose stop uptime-goblin
docker compose run --rm --no-deps uptime-goblin node lib/cli/goblin-admin.mjs snapshots --delete <id>
docker compose start uptime-goblin
```

It refuses a `[pinned]` snapshot unless you add `--force`, and, `--force` or not, a snapshot that an interrupted restore still needs (the snapshot it restores, and the pre-restore snapshot it set the replaced files aside in): run that restore again first. Keep the `[pinned]` snapshot of the first 1.5 start while you may still want the data back as 1.4.x left it. Never delete `snapshots/.restore-in-progress.json`, or a `.restoring-…` folder while `goblin-admin snapshots` says an interrupted restore needs it. A snapshot taken before a key change (`key rotate`, `key rewrap`) opens only with the older key: after restoring one, Uptime Goblin refuses to start (exit status 78, `key_mismatch`) until you run `key rewrap` with that key as `GOBLIN_SECRET_KEY_PREVIOUS_FILE` (`key rotate` after a leak, since the restored data keys are the old ones), or start it with that key, either as its key or as `GOBLIN_SECRET_KEY_PREVIOUS_FILE` beside the current one (it then warns at every start until a `key rewrap` or `key rotate` has run). Once the key has been changed back to the one the snapshot was taken with (`key rewrap` from A to B, then from B to A), the snapshot opens with the current key again. Every key change wraps the data keys anew, a change back too, so a keyring wrapped differently does not by itself tell which key it needs: `restore-snapshot` checks the keyring it brings back, and the one it replaced, with the key in its own environment, which it finds as the key commands do, and with `GOBLIN_SECRET_KEY_PREVIOUS_FILE` too when it is given one, as Uptime Goblin's start does. It says nothing of the key only when Uptime Goblin has started on the keyring it replaced and either the restored keyring is wrapped as that one and the key it finds, if any, opens it (with the previous key it was given), or a key it was given, not one it found in the data directory, opens both keyrings, the one it replaced alone (a key changed and changed back, or a snapshot holding data keys rotated after the keyring it replaced). The keyring it replaced stands for the key Uptime Goblin uses only when Uptime Goblin has started on that `control.sqlite` since a restore or a copy put it in place: not after a restore that Uptime Goblin has not started on yet, such as one you undo with the pre-restore snapshot it names, and not when what Uptime Goblin's starts recorded in it cannot be read. Like Uptime Goblin ([backups](#backups)), it cannot tell a backup copied over `control.sqlite` in place, or a rolled-back file-system snapshot, from the file Uptime Goblin last ran on: give it the key Uptime Goblin uses, not an older one, so that it can tell when that key does not open what it brings back. Given that key (natively `env GOBLIN_SECRET_KEY_FILE=/etc/uptime-goblin/secret.key` before `node`, as in the [goblin-admin](#goblin-admin) lines; under Docker Compose the Compose secret with `compose.secret.yaml`), it says so when Uptime Goblin has started on the keyring it replaced, that key alone opens that keyring and not the restored one, and any previous key file it was given can be read ("The restored control.sqlite holds the keyring of the snapshot's time, which the encryption key changed after …"), and names the previous key it was given when that one opens the rest (Uptime Goblin then starts only while given it too). A `secret.key` it finds in the data directory (the volume's key under Compose without `compose.secret.yaml`) may be an older key left there after a key change, so with that one it never says so for certain, nor says nothing of a keyring wrapped differently. Uptime Goblin's start also accepts a data key that only its previous key opens, so a key that opens the keyring it replaced only with the previous key it was given does not show which of the two Uptime Goblin uses as its key, and a key that does not open that keyring may still be Uptime Goblin's, with a previous key this command was not given. In every other case it says the key may have changed and gives the `key status` line to check with before you start Uptime Goblin, to which you add `GOBLIN_SECRET_KEY_PREVIOUS_FILE` when Uptime Goblin is given one ("The restored control.sqlite holds the keyring of the snapshot's time, wrapped differently from the keyring it replaced …", or, after a restore wrapped as the one before it, "The restored control.sqlite holds a keyring wrapped as the keyring it replaced …"): for a keyring wrapped differently from the one it replaced, without a key or with one it cannot read, with one that does not open the keyring it replaced alone, with one it found in the data directory, or with a previous key file it cannot read beside a key that opens the keyring it replaced and not the restored one; for a keyring wrapped as the one it replaced, with a key it cannot read or one that does not open it; after a restore or a copy that Uptime Goblin has not started on, or when what Uptime Goblin's starts recorded in the `control.sqlite` it replaced cannot be read; and with no keyring replaced to compare with (no `control.sqlite`, or a damaged one). A previous key file it cannot read (a mistyped `GOBLIN_SECRET_KEY_PREVIOUS_FILE`, say) is left out, not the key: it checks with the key alone, and when it gives the `key status` line it also says that the previous key could not be read, and why.

### Keeping Uptime Goblin's log

The checkpoint lines are only as good as the log that keeps them. Natively, journald keeps Uptime Goblin's log within its own limits (`SystemMaxUse=` in `journald.conf`); export it now and then into a file only root can read, in a directory only root can change (lines are compared by their signature, so a line kept twice does no harm):

```sh
sudo sh -c 'umask 077 && f=/secure-backups/uptime-goblin-journal.txt && test ! -L "$f" && touch "$f" && test -f "$f" && n=$(mktemp "$f.XXXXXX") && { cat "$f" >> "$n" && mv -f "$n" "$f" || { rm -f "$n"; false; }; } && journalctl -u uptime-goblin -o cat >> "$f"' || { echo "Uptime Goblin's log was not kept"; false; }
```

Check with it as above, with root's shell reading the file: `sudo sh -c 'sudo -u uptime-goblin env GOBLIN_SECRET_KEY_FILE=/etc/uptime-goblin/secret.key node /opt/uptime-goblin/lib/cli/goblin-admin.mjs verify-audit --checkpoints - --data-dir /var/lib/uptime-goblin < /secure-backups/uptime-goblin-journal.txt'`. Under Docker Compose, `compose.yaml` keeps at most 2 × 5 MB of the container's log, and Docker discards it when the container is recreated: every `docker compose up -d` after an update or a settings change. Before each `up -d`, append it to a file kept outside the volume, private before anything is added to it:

```sh
(umask 077 && f=~/uptime-goblin-journal.txt && test ! -L "$f" && touch "$f" && test -f "$f" && n=$(mktemp "$f.XXXXXX") && { cat "$f" >> "$n" && mv -f "$n" "$f" || { rm -f "$n"; false; }; } && docker compose logs --no-log-prefix uptime-goblin >> "$f") || { echo "Uptime Goblin's log was not kept"; false; }
```

Or raise `max-size` and `max-file` in a Compose override, or use the `journald` logging driver. Without that, entries removed from the end of the audit log can be detected only against the lines you kept. Check with them as above: `cat ~/uptime-goblin-journal.txt | docker compose exec -T uptime-goblin node lib/cli/goblin-admin.mjs verify-audit --checkpoints -`. The checkpoint lines hold no entry and no secret: an entry number, its time, a hash, the key's id, a signature and Uptime Goblin's instance id. The rest of an exported log holds more. An entry Uptime Goblin could not write is printed in full, as a line starting `{"orbit":"audit.unwritten"`, whatever `GOBLIN_AUDIT_LOG` says: who, the client address and browser, the session id and what changed (never a secret). With `GOBLIN_AUDIT_LOG` set, every entry is copied there too. Keep the exported file as private as the data directory: the audit retention does not apply to it.

The two lines that keep the log add only to a file that no one else can open, unless its folder hands an access list down to new files (below). `umask 077` makes a new file private from its first byte, but leaves a file that is there already as it was, such as one an export without `umask 077` left readable to every local account. `chmod 600` would not make that one private: a program that opened it while it was readable, such as another account's `tail -f`, goes on reading everything added to it, since a file's permissions are checked only when it is opened, and on macOS an access list (`ls -le`) can let others read a file whatever its mode. So each line first copies what the file holds into a new file beside it that only you can open (`mktemp`), puts that one in its place and only then adds to it: what the old file held may have been read already, but nothing added from then on can be. On macOS a new file also takes the access list entries its folder hands down to new files, and they can let others read it whatever its mode: if `ls -led` on the folder lists one with `file_inherit`, keep the file in a folder that hands none down. Your home folder hands none down as macOS sets it up (its one entry, `group:everyone deny delete`, has no `file_inherit`); on Linux a folder's default access list does not open the copy: `mktemp` makes it with mode 0600, and that mode masks the entries it hands down. Each run needs room for a second copy of the file while it copies, and a run cut short meanwhile, such as by Ctrl-C, can leave that copy beside the file, named `uptime-goblin-journal.txt.` and six more characters: it holds nothing the file does not, so delete it. Neither line writes through a link, or to anything but a regular file. When one prints "Uptime Goblin's log was not kept", the file is a link, is not a regular file or is not yours to change (`touch` then says why), or the copy or the export failed: it added nothing, or only what the export printed before it failed (a line kept twice does no harm, so run it again once the cause is fixed). Under Docker Compose, do not recreate the container until the log is kept. Root's shell would follow a link put in `/secure-backups` between the check and the write, hence a directory only root can change.

### Rolling back 1.5 to 1.4.3

The data directory works on 1.4.3 as it is (it ignores `control.sqlite`, `snapshots/` and the `history_summaries` and `history_summary_marks` tables, and `auth.json` holds the current password), so only the code goes back. The readings 1.4.3 records have no summaries; the next 1.5 start finds them and writes them, in short steps, and until it has, 7- and 30-day charts read every reading. Restoring the pinned snapshot leaves `history.sqlite` and its summaries as they are; restoring a backup of `history.sqlite` from any release needs nothing either, as that start checks the summaries against whatever readings it holds. While Uptime Goblin's pages show "Uptime Goblin saved the admin password but could not update auth.json", `auth.json` still holds the previous password, and 1.4.3 signs in with it: fix the disk and wait for that banner to go (or restart 1.5, which tries again at once) before you roll back. To go back to the data as it was before the upgrade too, restore the pinned snapshot first, with the 1.5 code still installed ([goblin-admin](#goblin-admin)). That snapshot was taken before 1.5 created `control.sqlite`, so the restore removes it (into the pre-restore snapshot), and with it the notifications still waiting, the delivery history, the webhook signing key and the [audit log](security.md#audit-log): the next 1.5 start begins a new, empty log, which lists no restore, and the old log stays only in the pre-restore snapshot. Export it first under **Configure → Audit log** if you need it. Restoring any other copy of the data from before the upgrade, such as a deploy script's tarball, does the same. Those notifications are then never sent, nor listed as not sent, and when 1.5 runs again it makes a new signing key (the log says "Uptime Goblin created a new signing key for the alert webhook…"): give its public key (**Configure → Notifications → Show public key**) to receivers before they check signatures again. The automatic rollback does the code part when verification fails, and on a host that the upgrade moved from the Orbit layout it also puts that layout back ([renamed from Orbit](#renamed-from-orbit)).

**On a native install moved from the Orbit layout**, go back with the installer, from the staging directory of the release you installed (`/usr/local/src/uptime-goblin`, say, not `/opt/uptime-goblin`): 1.4.3 reads only its `ORBIT_` settings and the Orbit paths (`orbit.service`, `/opt/orbit`, `/var/lib/orbit`, `/etc/orbit.env`), which the upgrade renamed, so swapping the code alone does not bring it back.

```sh
sudo bash deploy/install.sh --restore-orbit-layout
```

It installs nothing and takes no other option but `--verify-timeout`. It checks first, changing nothing on a refusal: that `/opt/uptime-goblin.previous` holds the Orbit release the upgrade kept (one before 1.5), that `/etc/orbit.env.migrated` and `/etc/systemd/system/orbit.service.migrated` are still there, that no part of the Orbit layout (nor an account or group `orbit`) is in the way, that no `/opt/uptime-goblin.failed` or `/etc/uptime-goblin.env.kept` would be replaced, that no drop-in in `uptime-goblin.service.d` names an Uptime Goblin path, and that every move is a rename on one file system. Then it stops and disables `uptime-goblin.service`, puts the Orbit layout back as the upgrade found it (the code from `/opt/uptime-goblin.previous` as `/opt/orbit`, the data, the key directory, the account and group, the drop-ins, `/etc/orbit.env` and `orbit.service` from the files the migration kept), keeps the settings Uptime Goblin ran with as `/etc/uptime-goblin.env.kept` (mode 0600, compare them with `/etc/orbit.env`, then delete it) and this release in `/opt/uptime-goblin.failed`, starts `orbit.service` and checks that Orbit serves. The data stays as 1.5 left it, which 1.4.3 reads (above). A run cut short is finished by the next run of the same command, and the next upgrade moves the installation to the Uptime Goblin layout again (delete `/opt/uptime-goblin.failed` first, or keep it elsewhere). A host installed as Uptime Goblin, or one whose kept files are gone, has no Orbit layout to go back to: restore the backup of [step 2](#updates-and-rollback) there instead.

**Before rolling back, webhook receivers that check signatures** ([verifying signatures](notifications.md#verifying-signatures)) must accept requests without them: 1.4.x sends each webhook without `X-Goblin-Delivery` and `X-Goblin-Signature`, so such a receiver rejects every one, and 1.4.x sends each once and never retries, so those alerts are lost for as long as the rollback lasts. Let the receiver accept Uptime Goblin's unsigned requests while 1.4.x runs, and turn the check back on once 1.5 runs again, with the new public key if you restored the data from before the upgrade (above). The webhook's private signing key stays in `control.sqlite`, which 1.4.x ignores, so a rollback to 1.4.x neither uses nor shows it. Do not start data that this release has run on with an earlier 1.5 pre-release build: such a build shows no signing secret, cannot make one and sends webhooks unsigned, because this release keeps the private keys in settings fields those builds never open, and every start of it saves those settings in a form they can read but not change. 1.5 pre-release builds that already signed with Ed25519 kept the private key in the HMAC secret's field, until a start of this release moves it out: an HMAC build started on their data before that took the key for its HMAC secret, signed with its text and showed it under **Show signing secret**. If one has run on the data, press **Replace signing key** twice once this release runs again (after the first press the exposed key keeps signing for 24 hours; the second press stops it at once), with `GOBLIN_WEBHOOK_URL` set (set it again first if it was removed: without it the key cannot be replaced, and the exposed key signs again once it is set), and give receivers the new public key ([verifying signatures](notifications.md#verifying-signatures)).

Nothing is added to the [audit log](security.md#audit-log) while 1.4.3 runs; when 1.5 starts again it records the settings and the admin password changed meanwhile, as changed outside Uptime Goblin. Notifications still waiting in 1.5's queue when you roll back are not sent by 1.4.x, which sends its own from then on. When you upgrade again, those less than 24 hours old are sent once (unless you restored the data from before the upgrade, which removed them), except those whose alert 1.4.x handled a later change of (for example it sent the recovery), and every paused channel tries once at that start, or leaves its pause when you switched it off under 1.4.x ([rolling back](notifications.md#rolling-back-to-14x-and-upgrading-again)). Under Docker Compose the same holds; the commands are below. Open 1.5 tabs reload themselves into 1.4.3, whose own sign-in prompt asks for the current password. A tab with unsaved changes keeps them and shows the update banner with **Reload** and "Uptime Goblin now runs an older release, which this page cannot sign in to…" instead of a **Sign in**, which could not work against 1.4.3: reload it once you no longer need those changes.

**Under Docker Compose**, the 1.4.3 image reads only the `ORBIT_` names and keeps its data at `/app/data`, while the 1.5 `compose.yaml` passes the `GOBLIN_` names and mounts the `orbit-data` volume at `/var/lib/uptime-goblin`, so re-tagging the 1.4.3 image under the 1.5 file alone would start 1.4.3 without your settings and data. Go back with an override instead, which runs the 1.4.3 image you kept (`orbit-homelab:1.4.3`, step 2 of [updates and rollback](#updates-and-rollback)) in the 1.5 `compose.yaml`, so with its limits and hardening (the 1.4.3 release's own `compose.yaml` sets no memory, CPU or process limits): it mounts the volume where 1.4.3 reads it and passes the five settings 1.4.3 reads under their old names, each from its `GOBLIN_` line in `.env`, else its `ORBIT_` one, as `compose.yaml` reads them. Write it as `compose.override.yaml` in the project directory (if you have one already, for `cpus: 0`, add these lines to its `uptime-goblin` service); `!override` needs Docker Compose 2.24.4 or later:

```yaml
services:
  uptime-goblin:
    image: orbit-homelab:1.4.3
    volumes: !override
      - orbit-data:/app/data
    environment:
      ORBIT_PASSWORD: ${GOBLIN_PASSWORD-${ORBIT_PASSWORD:?Set GOBLIN_PASSWORD in .env first}}
      ORBIT_ALLOWED_HOSTS: ${GOBLIN_ALLOWED_HOSTS:-${ORBIT_ALLOWED_HOSTS:-localhost:4317}}
      ORBIT_WEBHOOK_URL: ${GOBLIN_WEBHOOK_URL-${ORBIT_WEBHOOK_URL-}}
      ORBIT_TRUST_PROXY: ${GOBLIN_TRUST_PROXY-${ORBIT_TRUST_PROXY-}}
      ORBIT_ALLOW_LOOPBACK: ${GOBLIN_ALLOW_LOOPBACK-${ORBIT_ALLOW_LOOPBACK-}}
```

Where `.env` sets `COMPOSE_FILE` (with [`compose.secret.yaml`](#encryption-key)), add `:compose.override.yaml` to the end of its last such line: Compose then reads no file that line does not name. Then, before any command that recreates the container append its log to your kept copy (`(umask 077 && f=~/uptime-goblin-journal.txt && test ! -L "$f" && touch "$f" && test -f "$f" && n=$(mktemp "$f.XXXXXX") && { cat "$f" >> "$n" && mv -f "$n" "$f" || { rm -f "$n"; false; }; } && docker compose logs --no-log-prefix uptime-goblin >> "$f") || { echo "Uptime Goblin's log was not kept"; false; }`: recreating the container discards its log and the audit log's checkpoint lines in it, [keeping Uptime Goblin's log](#keeping-uptime-goblins-log)), and stop 1.5 and start 1.4.3 on the same volume, under the same service name:

```sh
docker compose stop uptime-goblin
docker compose up -d --no-build
```

To go forward to 1.5 again, delete those lines (or the file, and its name in `COMPOSE_FILE`), keep the log and run `docker compose up -d --no-build`. Keep the 1.5 image under its own tag meanwhile (`docker image tag uptime-goblin:local uptime-goblin:1.5.0`). 1.4.3 ignores the secret of `compose.secret.yaml`; keep `COMPOSE_FILE` in `.env` and the `orbit_secret_key` file, so that going forward again mounts it: [the check](#encryption-key) then prints `KEEP`, and no new key is needed. A volume that 1.5 ran on without `compose.secret.yaml` keeps its `/var/lib/uptime-goblin/secret.key` under 1.4.3: to adopt the override later, when going forward again or afterwards, copy that key ([the copy recipe](#encryption-key)); a new key cannot open that data.

### Rolling back 1.4.3 to 1.4.2

Both releases are Orbit, with its names and paths. The data directory works on 1.4.2 as it is, so only the code goes back. The automatic rollback does this when verification fails. To go back after a successful upgrade on a native install, swap the two copies and restart:

```sh
sudo systemctl stop orbit.service
sudo mv /opt/orbit /opt/orbit.1.4.3
sudo mv /opt/orbit.previous /opt/orbit
sudo mv /opt/orbit.1.4.3 /opt/orbit.previous
sudo systemctl start orbit.service
```

Keep the 1.4.3 unit: 1.4.2 runs under it unchanged, and it keeps the unresolved Node path. For Docker, re-tag the image you kept (`docker image tag orbit-homelab:1.4.2 orbit-homelab:local`) or build the 1.4.2 source, then run `docker compose up -d --no-build`.

On 1.4.2:

- Open 1.4.3 tabs notice the change and reload themselves into 1.4.2.
- A time-zone offset such as `UTC+05:30` is replaced by `local` and logged. It stays `local` after upgrading again, so set it again.
- Notes about readings left out are not shown; they return with the next collection after upgrading again.
- `/health` needs sign-in again, which 1.4.2's own readiness check accepts.

After upgrading again, reload tabs opened on 1.4.2 once more.

### Older releases

Rolling back from 1.4.1 or later to 1.4.0 or earlier: 1.4.1 adds an `error` column to the history database, which older releases cannot write. Restore the data backup taken before the upgrade, or stop Orbit and run `node -e "const {DatabaseSync}=require('node:sqlite');const d=new DatabaseSync('<data dir>/history.sqlite');d.exec('DROP INDEX IF EXISTS readings_history');d.exec('ALTER TABLE readings DROP COLUMN error');d.close()"` before starting the older version (the index, added in 1.4.2, must go first). 1.4.1 runs on a 1.4.2 data directory as it is.

Upgrading Orbit to 1.4.0: behind a reverse proxy, set `ORBIT_TRUST_PROXY` (native installs: re-run the installer with `--trust-proxy`), or one client's failed sign-ins lock out everyone. Sources on loopback addresses now need `ORBIT_ALLOW_LOOPBACK=1` (`--allow-loopback`). While no password has been saved in the app, `ORBIT_PASSWORD` must be 12 to 1024 characters or Orbit will not start. Sonarr and Radarr disk measurements have new keys, so update any rules that used the old `disk_0_free` style keys.
