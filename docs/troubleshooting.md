# Troubleshooting

[Back to Uptime Goblin](../README.md) · [Installation](installation.md) · [Integrations](integrations.md)

Use system information, per-source status and **Test connection** first. Keep configuration exports, raw responses and logs private. A successful browser link only proves your browser can reach that address; collection runs from the Uptime Goblin server.

| Symptom | What to check |
|---|---|
| Cannot open Uptime Goblin | Confirm the process/service is running, listening address/port, reverse-proxy target, and firewall path. Docker publishes loopback by default. |
| Parts of a page fail to load, or a script's connection is closed or reset without an answer, while many tabs or scripts use Uptime Goblin / Log: "Uptime Goblin closed … without an answer since the last such line (or the start) because the client already held … connections at once" | One client (one address, an IPv6 /64) may hold at most 32 connections at once; one more is closed at once. The log says so at most once a minute, naming the last client refused and how many connections were closed since the previous line; those closed within the minute after a line are written once the minute has passed. Every user behind one address shares that client's allowance: under Docker Compose every browser on the published port, when Docker hands the connections over from its gateway; the clients of a reverse proxy that `GOBLIN_TRUST_PROXY` does not name (name it there: a trusted proxy has no such limit); everything on the Uptime Goblin computer that connects from 127.0.0.1, the ssh tunnel included, unless `GOBLIN_TRUST_PROXY=loopback`; every IPv6 device on one /64 that connects to Uptime Goblin directly (on a home network usually every IPv6 device). Close idle tabs or reuse connections in scripts, reach Uptime Goblin over IPv4 or through a proxy named in `GOBLIN_TRUST_PROXY`, or raise `GOBLIN_MAX_CONNECTIONS_PER_CLIENT` (8 to 256) in the environment file and restart Uptime Goblin. |
| Old version still shown after an upgrade | Tabs opened on 1.4.2 or earlier contain no update check: reload them once. From 1.4.3 on, open tabs update themselves; **Configure → System → Open tabs by version** lists pages still on another version ("Before 1.4.3" needs the manual reload). |
| Banner "Uptime Goblin was updated. Reload to use the new version" | Uptime Goblin was upgraded while this page had something a reload would lose: unsaved edits in a form or the source editor, a save without an answer yet, an open dialog or a password change. Save or discard the edits and close the dialog; the page then reloads by itself. **Reload** reloads at once, and unsaved changes are lost. |
| "Uptime Goblin now runs an older release, which this page cannot sign in to, so what it shows is no longer updated" (and **Reload needed**) | Uptime Goblin was rolled back to 1.4.x while this 1.5 page had something a reload would lose (otherwise it reloads by itself). 1.4.x signs browsers in only through the browser's own password prompt, so the page offers no **Sign in**, and the sign-in dialog, if it was open, says the same, as do a **Refresh** or a save that was waiting to sign you in again. Copy anything you need from the unsaved form, then press **Reload** in the banner (or reload the page): 1.4.x's page asks for the current password. Until then the browser's own password prompt may come up when the page refreshes its readings; you can **Cancel** it. |
| Banner "…this page is still the older version after reloading" | The page reloaded itself twice within 10 minutes and still got the old version, so a reverse proxy or the browser cache is serving an old copy of the page. Make sure the proxy does not cache Uptime Goblin's pages, then reload, or clear this site's cached files in the browser. When the banner adds that the page checks again by itself, nobody needs to press **Reload**: the page fetches itself again, bypassing the browser's cache, after 30 seconds and then less often, up to every 10 minutes, and opens the new version once it is served. A wall display therefore recovers by itself once the cache is fixed. |
| "Reconnecting…" and "Uptime Goblin is not answering" | The page got no answer from Uptime Goblin: it is restarting (for example during an upgrade), the network dropped, or the reverse proxy cannot reach it. Displayed readings may be stale. The page keeps trying by itself and loads again at once when the network returns. If it lasts, check the service and the proxy as for **Cannot open Uptime Goblin**. |
| "Uptime Goblin did not confirm this change, and it may have been saved" | A save got no answer (60 seconds passed, the connection dropped or Uptime Goblin restarted). The page retries once by itself, but only when it can see the settings have not changed since; otherwise it shows this message and the latest settings, and keeps your edits in the form. Check whether the change is already there before trying again. |
| "Uptime Goblin is busy saving other changes" or "Uptime Goblin was busy and could not start this change" (HTTP 503) | More than 16 saves were waiting, or this one waited 20 seconds for its turn, for example behind a large retention change. Nothing was changed. Wait a few seconds (`Retry-After`) and save again. |
| Installer: "did not start correctly", then "The previous version is running again" | Verification of the new version failed and the installer restored the previous one, which is serving again. See [installer verification failed](#installer-verification-failed). |
| Installer: "Run the installer from a staging directory…" | It was started from the installed copy (`/opt/uptime-goblin`, `/opt/uptime-goblin.previous` or `/opt/uptime-goblin.failed`), which it replaces. Extract or copy the source to a directory such as `/usr/local/src/uptime-goblin` and run `deploy/install-lxc.sh` from there. |
| Installer `--restore-orbit-layout`: "This installation cannot go back to the Orbit layout: …" | Going back to Orbit after an upgrade from the Orbit layout found something it cannot undo by renames alone, and changed nothing: the message names each problem (no Orbit release in `/opt/uptime-goblin.previous`, `/etc/orbit.env.migrated` or `orbit.service.migrated` gone, an Orbit path, account or group in the way, an `/opt/uptime-goblin.failed` or `/etc/uptime-goblin.env.kept` it would replace, a drop-in that names an Uptime Goblin path, a mount point or another file system). Fix those it names and run it again; a host installed as Uptime Goblin, or one whose kept files are gone, has no Orbit layout to go back to: see [rolling back 1.5 to 1.4.3](installation.md#rolling-back-15-to-143). |
| Installer: "The release files do not match SHA256SUMS" or "Missing application file: …" | The staging directory does not hold the complete, unchanged release. Nothing on the host was changed. Download and [verify the archive](installation.md#verifying-a-release) again and extract it into an empty directory. |
| Installer: "Install Node in a system directory" or "Node.js 24+ with SQLite is required" | The `node` found under sudo lives under `/root`, `/home` or `/run/user` (for example a version manager's copy), which the service cannot read, or it is too old. Install Node.js 24 or newer system-wide, such as from your distribution or vendor packages, or under `/usr/local` or `/opt` with `/usr/local/bin/node` pointing at it. |
| `status=203/EXEC`, "Failed at step EXEC spawning …/node" | The unit names a Node binary that no longer exists, usually after a Node upgrade on an install made by 1.4.2 or earlier, which wrote the versioned path. Re-run the installer (1.4.3 or later) from your staging directory: it reports "The installed service starts Node from …, which no longer exists" and writes the stable path that `command -v node` finds, so later Node upgrades no longer break the service. |
| Uptime Goblin refused to start (exit status 78) | See [exit statuses](#exit-statuses). |
| Host is not allowed | Add the exact browser hostname and non-default port to `GOBLIN_ALLOWED_HOSTS`, without a scheme. Restart after environment edits. Make the proxy preserve Host. |
| Sign-in page: "The login name or password is incorrect." | The login name is `admin`; use the latest Uptime Goblin password, not a source password. After a change under **Configure → Account**, the saved password overrides `GOBLIN_PASSWORD`; update the browser's saved login. Avoid printing secrets into logs. |
| Sign-in page: "Sign-in needs HTTPS, or a browser on the Uptime Goblin computer itself" (`https_required`) | The browser reaches Uptime Goblin over plain HTTP, or through a proxy on the Uptime Goblin host that sends no forwarding headers (the log says so). Open Uptime Goblin through its HTTPS proxy, or, on a native install that listens on 127.0.0.1 or on every address, through `ssh -L 4317:127.0.0.1:4317 <uptime-goblin-host>` at <http://localhost:4317> (an install made with `--listen <address>` is not reached that way). Under Docker the published port is plain HTTP to Uptime Goblin even from the Docker host, so it needs plain-HTTP sign-in on: `GOBLIN_INSECURE_HTTP_SESSIONS=1`, or the Compose default while `.env` does not set it and the port is published on loopback. On a network you trust set `GOBLIN_INSECURE_HTTP_SESSIONS=1` and restart Uptime Goblin (Docker: in `.env`, then `docker compose up -d`); the password then crosses that network in clear. On an `http://` page the sign-in page shows this message without the form, since Uptime Goblin would refuse the sign-in only after the password had crossed the network; so does an open page, at the top, and an action such as **Save**. See [when sign-in is refused](authentication.md#when-sign-in-is-refused). |
| Sign-in page: "Your browser uses HTTPS, but the reverse proxy in front of Uptime Goblin does not tell Uptime Goblin so" (`proxy_proto_missing`) | Add `proxy_set_header X-Forwarded-Proto $scheme;` to Uptime Goblin's nginx location and reload nginx, and make `GOBLIN_TRUST_PROXY` name the proxy (`loopback` on the same host). The log line says whether the header was missing, the proxy is not trusted, or the proxy sends no forwarding headers at all (it must send `X-Forwarded-For` and `X-Forwarded-Proto`). Until then `GOBLIN_INSECURE_HTTP_SESSIONS=1` and a restart let you sign in. |
| Sign-in page: "This page uses plain HTTP (http://), but the reverse proxy … tells Uptime Goblin the connection is HTTPS" (`proxy_proto_mismatch`) | nginx sends a fixed `X-Forwarded-Proto https`. Use `$scheme` instead, or open the `https://` address. `GOBLIN_INSECURE_HTTP_SESSIONS=1` alone does not help here; as a temporary measure remove `GOBLIN_TRUST_PROXY` too (every client behind the proxy then shares one lockout, and the password crosses the network in clear). The sign-in page shows this message without the form: the password would cross the network in clear before Uptime Goblin refused it. |
| Sign-in page: "Uptime Goblin refused this sign-in because this page's address does not match what the reverse proxy tells Uptime Goblin" (`cross_origin`) | The proxy does not forward the Host header (nginx's default sends its upstream address). Add `proxy_set_header Host $http_host;`, or add the hostname to `GOBLIN_ALLOWED_HOSTS` and restart. The log line names both values. |
| Sign-in page, or the top of an open page: "Your browser sent two Uptime Goblin sign-in cookies" | Another site on a parent domain, or another port of the same host, may set a cookie with Uptime Goblin's name. Remove this site's cookies in the browser and sign in again (an open page stops refreshing meanwhile, and offers **Sign in** when you come back to it; or reload it); better, give Uptime Goblin a hostname of its own. |
| Sign-in page after **Sign out**: "You are signed out, but this browser still has an Uptime Goblin sign-in cookie that another site set" | The browser sent Uptime Goblin's cookie and another one of the same name. Uptime Goblin ended this browser's session and removed its own cookie, but cannot remove the other site's (it does not know its domain or path). Remove this site's cookies in the browser before signing in again; if no site of yours sets `goblin_session`, someone may have planted it. |
| Sign out: "Uptime Goblin could not sign this browser out: it sent two Uptime Goblin sign-in cookies, and another site set one of them" | Not expected from 1.5 on: a sign-out sent with two Uptime Goblin cookies still ends this browser's session, and the sign-in page then says to remove this site's cookies (row above). If you see this text, Uptime Goblin refused the sign-out outright (`multiple_credentials`) and this browser may still be signed in: remove this site's cookies in the browser, sign in again and use **Sign out other devices**. |
| Sign-in page: "You signed in, but this browser did not keep Uptime Goblin's sign-in cookie" | The page was opened at `http://` while Uptime Goblin issued a `Secure` cookie for HTTPS. Open the `https://` address. |
| "Uptime Goblin's disk is full, so it cannot save your sign-in or password change" (`storage_full`, HTTP 503) | `control.sqlite` could not be written. Anyone already signed in stays signed in. Free space on the Uptime Goblin host (history retention, old snapshots under `snapshots/`, which Uptime Goblin never deletes itself: [snapshots](installation.md#snapshots), other files), then try again. |
| Signed out after 12 hours, or a "Sign in again" dialog | Sessions end after 12 hours without use (the automatic refresh does not count), 7 days, or 30 days with **Keep me signed in on this device**; a password change or a sign-out elsewhere ends them too. Sign in again: unsaved changes stay open. A wall display signed in with the admin password is signed out after 12 hours too; one set up with a display code stays signed in for up to 30 days while it refreshes: see [wall displays](authentication.md#wall-displays). |
| A wall display says "The display code is not valid" | The code expired (a code lasts 10 minutes), was used already, was cancelled (`goblin-admin display cancel`, or a password change), or was mistyped. Create a new one with `goblin-admin display code --name <name>`. A code sent over plain HTTP, where Uptime Goblin refuses sign-in that way, is refused and cancelled ("If this was a valid display code, it crossed the network unencrypted and Uptime Goblin cancelled it"): open the display at Uptime Goblin's HTTPS address and create a new code. If a code you typed correctly was refused as used, look under **Configure → Account** for a wall display you do not recognise and sign it out ([wall displays](authentication.md#wall-displays)). |
| `goblin-admin display code`: "10 display codes are already waiting" | Use one, wait for them to expire (10 minutes), or cancel them: `goblin-admin display cancel --all`. |
| Account page: a device marked "Signed in later", or "That session signed in after this one, so only a newer sign-in can end it" (`session_newer`, HTTP 403) | A session can end only sessions that signed in no later than it did, so a session cookie taken from a lost device cannot end your new sign-ins. Sign out on this device and sign in again, then sign the other device out. If you do not recognise it, change the password instead: someone signed in with it, and the change signs out every other session. |
| Signed out again right after each sign-in | Someone may hold one of your session cookies (a lost device, malware, or a cookie captured over plain HTTP) and keep ending your older sessions with **Sign out other devices**. It cannot end a newer sign-in: sign in again, then use **Sign out other devices** under **Configure → Account** at once, and change the password if it could be known too. None of this needs the Uptime Goblin host. |
| A device you had signed out is signed in again after a restore | A restored backup of the data directory brings back the sessions of its time. Uptime Goblin signs everyone out when `control.sqlite` is another file (the log says "control.sqlite is not the file Uptime Goblin last ran with…"), but not after a rollback of a file-system snapshot (a Proxmox LXC or VM snapshot, ZFS or LVM) or a backup copied over the existing file in place, which leave the same file. Sign in, then use **Sign out other devices** at once, or change the password. On the host, moving `auth.json` aside and setting `GOBLIN_PASSWORD` signs every session out too ([forgotten password](#forgotten-uptime-goblin-password)). |
| Log: "control.sqlite is not the file Uptime Goblin last ran with: its data directory was restored from a backup, copied or moved. Every session was signed out, …" | Expected after restoring a backup of the data directory, copying a Docker volume, or copying or moving the directory to another disk: everyone signs in again, so sessions that ended after the backup cannot come back. If nobody restored, copied or moved it, find out what replaced `control.sqlite` on the Uptime Goblin host. |
| A script gets 401 `basic_disabled` | Legacy Basic is off (installs created by 1.5 have it off). Set `GOBLIN_LEGACY_BASIC=1` and restart; see [legacy Basic](authentication.md#scripts-and-legacy-basic). |
| A script gets 403 `https_required` ("Sign-in needs HTTPS, or a browser on this computer"); log "A script's HTTP Basic sign-in from … over plain HTTP was refused (https_required)" | The script sends Basic over plain HTTP (directly to Uptime Goblin on the network, or through a proxy that does not tell Uptime Goblin the request came over HTTPS), and `GOBLIN_INSECURE_HTTP_SESSIONS=1` is not set: Basic carries the password in every request, so it takes the same opt-in as browser sessions. Its password was not checked and the refusal is not counted as a failed sign-in. Call Uptime Goblin through its HTTPS address (a proxy named in `GOBLIN_TRUST_PROXY` that sends `X-Forwarded-Proto`) or from the Uptime Goblin computer itself, or set `GOBLIN_INSECURE_HTTP_SESSIONS=1` on a network you trust and restart. A reverse proxy on the Uptime Goblin computer must send `X-Forwarded-For` and `X-Forwarded-Proto`: Basic through one that sends no forwarding headers and keeps a loopback `Host` is treated as coming from the Uptime Goblin computer itself and accepted without `GOBLIN_INSECURE_HTTP_SESSIONS=1`, since Uptime Goblin cannot tell such requests from local scripts. See [legacy Basic](authentication.md#scripts-and-legacy-basic). |
| A script's configuration or audit export gets 403 `cross_origin` ("Requests from other sites cannot use your Uptime Goblin session.") | An export with Basic needs `X-Goblin-Request: 1`, as every change does, and an `Origin`, when sent, naming the `Host`, over HTTPS, over plain HTTP and from the Uptime Goblin computer itself alike: wherever a browser sends no `Sec-Fetch-Site` (at a plain-HTTP address on the network, not `localhost`, `127.x` or `[::1]`, Uptime Goblin's own or that of a proxy on the Uptime Goblin computer that sends no forwarding headers; or from a browser too old to send it), Uptime Goblin cannot tell another site's image or link that carries a browser's remembered Basic login from a script. Add `-H 'X-Goblin-Request: 1'` to the script's request; a 1.4.x script that downloads the configuration export needs it added, since 1.4.x needed no extra header there. The export was not built and has no audit entry (the script's Basic sign-in is still counted under **Scripts with a password**). See [legacy Basic](authentication.md#scripts-and-legacy-basic). |
| A browser shows its own sign-in prompt (HTTP Basic) for Uptime Goblin | While legacy Basic is on, for an address the browser opens itself while it is not signed in (an API address, typed or bookmarked), over plain HTTP where Uptime Goblin accepts Basic: with the plain-HTTP opt-in (`GOBLIN_INSECURE_HTTP_SESSIONS=1`, or Docker Compose's default on its loopback port), or through a proxy on the Uptime Goblin host that sends no forwarding headers and keeps a loopback Host (Uptime Goblin takes its requests for the Uptime Goblin computer's own, with no opt-in). Browsers send no `Sec-Fetch-Site` to a plain-HTTP address on the network (they do to `localhost`, `127.x` and `[::1]`), so Uptime Goblin answers as it answers a script, with the Basic challenge scripts such as `wget` need. Open Uptime Goblin's page (`/`) and sign in there, and serve Uptime Goblin over HTTPS; make such a proxy send `X-Forwarded-For` and `X-Forwarded-Proto` and set `GOBLIN_TRUST_PROXY=loopback` (the [recipe](installation.md#https-trust-and-network-access)). |
| Browsers no longer signed in by the proxy's Basic header | 1.5 ignores `Authorization` from browsers. Remove the injected header from nginx and sign in on Uptime Goblin's page. |
| Banner "Uptime Goblin saved the admin password but could not update auth.json" | The password change worked, but `auth.json` could not be written (a read-only or full disk). Uptime Goblin retries hourly and at every start; until then a rollback to 1.4.x uses the previous password. Fix the disk, then restart Uptime Goblin or wait. Open pages check again about every five minutes, so the banner goes by itself once a retry worked. |
| Log: "auth.json now holds the current admin password, but Uptime Goblin could not record that in control.sqlite (…)" | The password change worked and `auth.json` holds the new password, so a rollback to 1.4.x uses it; the disk filled (`full`) or failed before Uptime Goblin could note that in `control.sqlite`, or the data directory could not be flushed to disk after the write (`EIO`, a failing disk: Uptime Goblin notes the file only once it is on disk). Free space on the Uptime Goblin host, or check the disk; the next start notes it, without signing anyone out, or writes `auth.json` again if a power loss undid the write. |
| Installer: "Uptime Goblin 1.5 signs browsers in with a cookie and must know whether the browser uses HTTPS" | The proxy preflight refused the upgrade from 1.4.x; nothing was changed. Follow the message: add `proxy_set_header X-Forwarded-Proto $scheme;`, reload nginx, open Uptime Goblin through nginx once and run the installer again; or add `GOBLIN_INSECURE_HTTP_SESSIONS=1` to `/etc/uptime-goblin.env` (or run the installer with `--allow-insecure-http`); or run it with `--proxy-proto-checked` if you checked the proxy yourself. Every start of 1.4.3 empties what it recorded, so a reboot or a backup that stops and starts Uptime Goblin between browsing and the installer brings the refusal back: browse after the last start. A message saying Orbit 1.4.3 "is not running" means the service is stopped (1.4.3 removes its record when it stops, so nginx is not the problem yet): `sudo systemctl start uptime-goblin`, open Uptime Goblin through nginx once, and run the installer again without stopping Uptime Goblin. A message saying the running Uptime Goblin "does not record what your reverse proxy sends" means 1.4.2 or earlier: upgrade to 1.4.3 first and browse once, or check nginx and use `--proxy-proto-checked`. See [before upgrading from 1.4.x](authentication.md#before-upgrading-from-14x). |
| Installer: "Uptime Goblin would listen on … with no reverse proxy it trusts (GOBLIN_TRUST_PROXY), so browsers and scripts would sign in over plain HTTP" | The install or upgrade stopped before changing anything (status 1): `HOST` in `/etc/uptime-goblin.env` (or `--listen`) is not a loopback address, systemd would give Uptime Goblin no trusted proxy (`GOBLIN_TRUST_PROXY`, with `--trust-proxy` applied), and nothing systemd would give Uptime Goblin (`/etc/uptime-goblin.env`, a drop-in or its own environment) says whether sign-in over plain HTTP is allowed. The installer never allows it by itself. Put Uptime Goblin behind an HTTPS reverse proxy (`HOST=127.0.0.1` in `/etc/uptime-goblin.env` and `--trust-proxy loopback` for nginx on the same host, or `--trust-proxy <proxy address>` for one elsewhere), or, on a network you trust, run the installer again with `--allow-insecure-http`, which adds `GOBLIN_INSECURE_HTTP_SESSIONS=1` with a comment (passwords and the sign-in cookie then cross the network in clear). To keep plain HTTP refused, add `GOBLIN_INSECURE_HTTP_SESSIONS=0` to `/etc/uptime-goblin.env` instead. See [HTTPS, cookies and plain HTTP](authentication.md#https-cookies-and-plain-http). |
| Installer: "/etc/uptime-goblin.env sets GOBLIN_INSECURE_HTTP_SESSIONS=1 on line … under the comment that an earlier Uptime Goblin 1.5 pre-release installer wrote with it on line …" | The install or upgrade stopped before changing anything (status 1), wherever Uptime Goblin listens and whether or not a proxy is trusted: an earlier 1.5 pre-release installer added that line by itself, under the comment "# Added by the Uptime Goblin 1.5 installer: keeps plain-HTTP sign-in working as in 1.4.x. …", so no one chose it, yet Uptime Goblin would allow sign-in over plain HTTP while it says `1` (also for a browser or script that reaches Uptime Goblin on the network directly, not through the proxy, or through a proxy on the Uptime Goblin host that relays plain HTTP). Decide (`sudoedit /etc/uptime-goblin.env`), then run the installer again: set that line to `0` to refuse sign-in over plain HTTP (browsers and scripts then sign in over HTTPS through a proxy that `GOBLIN_TRUST_PROXY` names, or from the Uptime Goblin computer itself); or, on a network you trust, keep it by removing the comment line or putting a comment of your own in its place; or run the installer again with `--allow-insecure-http`, which keeps the line and replaces the comment with one that names who chose it. See [HTTPS, cookies and plain HTTP](authentication.md#https-cookies-and-plain-http). |
| Installer: "This release of Uptime Goblin would refuse to start (exit status 78): Uptime Goblin needs an admin password, and none is set" | The install or upgrade stopped before changing anything (status 1): `/var/lib/uptime-goblin` has no `auth.json`, and systemd would give Uptime Goblin no `GOBLIN_PASSWORD`, or an empty one (the message says where systemd takes it from). Uptime Goblin always requires an admin password, so it would refuse to start: the upgrade would have stopped Uptime Goblin and rolled back, and an install over an existing `/etc/uptime-goblin.env` would have left it down. Set `GOBLIN_PASSWORD` (12 to 1024 characters) in `/etc/uptime-goblin.env` (`sudoedit /etc/uptime-goblin.env`), and let no drop-in (`sudo systemctl edit uptime-goblin`) empty or remove it, then run the installer again. If Uptime Goblin had a password before, restore `/var/lib/uptime-goblin/auth.json` from a backup instead, or set `GOBLIN_PASSWORD`: it becomes the admin password and signs out every session. "Whether Uptime Goblin would have an admin password could not be checked" means `/var/lib/uptime-goblin/auth.json` could not be opened or read at all, even by root, as the installer reads it (the message gives the error, such as `EIO`: check the data directory and its disk), or a specifier, a file pattern or a `PassEnvironment=` in a drop-in would decide `GOBLIN_PASSWORD`, or `systemctl show-environment` failed: set `GOBLIN_PASSWORD` in `/etc/uptime-goblin.env`, and remove the drop-in line that decides it. See [a password is always required](authentication.md#a-password-is-always-required). |
| Installer: `This release of Uptime Goblin would refuse to start (exit status 78) with "Saved authentication could not be loaded. Restore a valid auth.json backup before starting Uptime Goblin.": …` | The install or upgrade stopped before changing anything (status 1): `/var/lib/uptime-goblin/auth.json`, read with the new release's own reader, the one Uptime Goblin's start reads it with (never through a symbolic link, never waiting on a FIFO, only a regular file of at most 8192 bytes that holds a valid password record), is one Uptime Goblin refuses: a symbolic link, a directory or another file that is not a regular one, an empty or cut-off file, `{}` or another record that is not a valid one, or a file over 8192 bytes. While `auth.json` exists Uptime Goblin ignores `GOBLIN_PASSWORD`, so it would refuse to start whatever `GOBLIN_PASSWORD` is: the upgrade would have stopped Uptime Goblin and rolled back, and a first install would have left it down with nothing to restore. Restore `/var/lib/uptime-goblin/auth.json` from a backup, or move it out of `/var/lib/uptime-goblin` and set `GOBLIN_PASSWORD` (12 to 1024 characters) in `/etc/uptime-goblin.env` (`sudoedit /etc/uptime-goblin.env`): it becomes the admin password and signs out every session. Then run the installer again. The installer never prints what `auth.json` holds. |
| Installer: "/var/lib/uptime-goblin/auth.json cannot be read by the uptime-goblin account, which Uptime Goblin runs as, …" | The install or upgrade stopped before Uptime Goblin was stopped and before its code or settings changed (status 1). The installer reads `auth.json` as root, who can read any file, so once it has given the data directory to the `uptime-goblin` account it tries an existing `auth.json` as that account too (`runuser`), and that account cannot read this one: often it was copied in from a backup as root (`sudo cp` leaves it `root:root`, mode `0600`). ## Collector-specific checks

- **Proxmox:** Check both user/token privileges when separation is enabled. Missing guests can reflect ACL scope rather than a stopped server. Hypervisor summaries do not replace guest exporters.
- **UniFi:** A saved Integration key takes priority. Local login needs an HTTPS console root and local Network View Only account; blank site means `default`. API key site IDs are UUIDs. Check DNS selects a reachable console interface. If a controller is overloaded, back off instead of repeatedly logging in.
- **Cosmos:** Native monitoring must be enabled and return recent samples. Check token/API-version compatibility; an HTTP link working does not establish monitoring permission.
- **AMP:** Use a direct managed-instance URL. The controller API may authenticate but not return instance metrics.
- **Docker:** Permit inventory reads through a restricted proxy; full daemon access is unnecessary.
- **SABnzbd:** Use the full API key, not the add-only key. **NZBGet:** use credentials allowed to read status.
- **Synology/WireGuard:** Install/configure an appropriate exporter and actual metric mappings; DSM credentials or VPN tunnel keys do not enable these collectors.

## Measurement keys after an upgrade from 1.4.x

A collector makes a reading's measurement key from the ID or path the source sends, as 1.4.3 did, except in the cases below. They are the differences found by running the collectors of 1.4.3 and 1.5 on the same answers, for each collector that builds a key from what a source sends, with IDs and paths that are missing, empty, blank, not text, a number, over 150 characters or starting with `__`, or that hold control characters, U+2028, U+2029, direction marks, embeddings, overrides or isolates, half of a surrogate pair or an emoji; an ID of another kind was not compared. A reading with another key starts a new history, and an alert rule on its old key matches nothing until you choose the reading again in the source's **Metric thresholds**. A reading left out is counted in the card's note.

In the table, *blank* means nothing but white space (U+FEFF included), control characters, U+2028, U+2029 and the direction marks, embeddings, overrides and isolates (U+061C, U+200E, U+200F, U+202A–U+202E, U+2066–U+2069). *Not text* means an object, a list, `true`, or a number too large to hold, such as `1e999`.

| The source sends | 1.4.3 | 1.5 |
|---|---|---|
| An ID or path holding a control character (C0, DEL or C1), U+2028 or U+2029, other than an AMP metric name (AMP's key turns each character but an ASCII letter or digit into `_`, in 1.4.3 as in 1.5) | Kept it | One space for each run of them |
| An ID or path holding a direction embedding, override or isolate, other than an AMP metric name | Kept it | Removed |
| A Linux, Windows, Sonarr or Radarr disk path whose key is over 150 characters, with a character such as an emoji across the 137th | Its first 137 characters, the last of them half of that character, then `~` and a hash; a rule on that key never fired | Its first 136 characters, then `~` and the same hash |
| A UniFi device, Proxmox node, guest or storage, Prowlarr indexer or AMP key over 150 characters | Kept it up to 200 characters, but no alert rule could be saved on it; over 200 the whole source failed | Its first 137 characters (136 when the 137th is the first half of a character such as an emoji), then `~` and a hash |
| A Proxmox node, guest or storage key starting with `__` | Kept it, but no alert rule could be saved on it | `~` in front |
| A Proxmox node or guest ID that is blank or not text | Used it as text (`[object Object]`, `true`) | The node's name, or the guest's VMID; left out with a note when that is blank or missing too |
| A Proxmox guest ID that is missing, empty, `null` or `false` | The name of the node the guest runs on | The guest's VMID, as in the row above |
| The number 0 as a Proxmox node or guest ID | The node's name | `0` |
| A UniFi device (local controller), keyed by one of its `_id`, MAC and `device_id` | The first of the three that is not missing, empty, 0, `false` or `null`, when that one is text (blank text too); when it is a number such as `5`, `true` or an object, no reading and no note | The first of the three that is text and not blank, or a number (`0` included, `1e999` not); left out with a note when none is. So an `_id` of 0 beside the MAC `aa:bb` gave `device_aa:bb_cpu` and gives `device_0_cpu`, and the MAC 5 without an `_id` gave no reading and gives `device_5_cpu` |
| A blank Sonarr or Radarr disk path | Used it | The disk's place in the list (`disk_0_free`), as both do for an empty path |
| A Proxmox storage, Prowlarr indexer or UniFi Integration device ID that is missing, empty, blank, `null`, `false` or not text, and a UniFi Integration device ID that is a number | Used it as text (`undefined`, `null`, `[object Object]`, `5`) | Left out with a note |
| An empty or blank Linux mountpoint or Windows volume | Used it | Left out with a note |
| Two IDs or paths that differ only in what the rows above change, such as `/x y` and the same path with a tab in place of the space | Two readings | One key: the later reading is left out with a note |

Half of a surrogate pair in an ID or path, other than an AMP metric name, becomes U+FFFD, as it does in an alert rule saved on that key, which the start makes whole: a rule on such a key, which never fired in 1.4.3, now matches.

## Installer verification failed

After restarting the service, the installer waits for proof that the new version is the one serving. When that check fails, it prints `Uptime Goblin is not verified:` with a reason, then the service status and the last 50 log lines, and restores the previous version. A failed unit publication, service reload, enable or restart skips the readiness check and enters the same diagnosis and rollback path.

| Reason | What it means |
|---|---|
| `uptime-goblin.service failed (…) and systemd will not restart it` | The new version refused to start, usually with exit status 78. The log lines show why; see [exit statuses](#exit-statuses). A refusal for want of a resource limit names each limit and how to apply it in its own lines ([resource limits](#resource-limits)). The installer shows the status and the log lines as the journal returns them, then rolls back: it does not work out from them which start refused or why, and recommends no setting of its own, since a line in that log may be an earlier start's. |
| `Uptime Goblin has not written run/status.json yet` or `uptime-goblin.service has no running process` | The new version did not finish starting within the wait: it crashed and is restarting, or starting takes longer on this host. Read the log. If it was only slow, run the installer again with a longer `--verify-timeout` (up to 1800 seconds). |
| `run/status.json belongs to process …, not the service's process …` | Another Uptime Goblin process uses the same data directory, for example a copy started by hand. Stop it. |
| `the service runs Uptime Goblin …, expected …` or `the service runs build …, expected …` | Another copy of Uptime Goblin runs as the service, for example because the unit was edited to point elsewhere. |
| `a different Uptime Goblin process is answering on this port` | Another Uptime Goblin, or another program, answers on Uptime Goblin's port. Stop it, or change one of the `PORT` settings. |
| `cannot reach Uptime Goblin (…)` or `/health did not answer in time` | Nothing answers on the `HOST` and `PORT` in `/etc/uptime-goblin.env`. Check those settings and the log. |

After restoring the code, `/opt/uptime-goblin` holds the previous version again and `/opt/uptime-goblin.failed` the new code; `/etc/uptime-goblin.env`, the unit (made `Type=simple` for the earlier release) and the data are as the new version left them. The final message distinguishes code restoration from confirmed recovery. All outcomes below exit with status 1, including a successful rollback.

| Final message | What it means |
|---|---|
| "The previous version is running again; the upgrade to … was rolled back." | The restored release (1.4.3 onward) passed verification of its expected version, build, process ID and startup nonce. |
| "The previous version could not be verified after restoring its code." | Code was restored, but recovery could not be confirmed. Inspect `/etc/uptime-goblin.env`, the data directory, disk space, Node and service logs. |
| "The previous code was restored and its legacy health check answered. Its process identity is unverified" | A pre-1.4.3 release passed its own health check, which cannot prove which process answered. Confirm the service status and logs before relying on it. |
| "The previous code was restored, but its legacy health check did not pass." | A pre-1.4.3 release was restored, but even its limited health check failed. Recovery is not confirmed. |
| "The previous code was restored, but its service could not be restarted." | The rollback's restart command failed. The code is back in place, but recovery is not confirmed. |
| "There is no previous version to restore." | A first install failed and has no saved code to restore. |

A warning that systemd could not reload unit files does not end the recovery attempt: the installer still tries the loaded unit and verifies the restored process. Read the preceding systemd error (for example insufficient space in `/run/systemd`), then the final recovery result. A legacy health check that exceeds `--verify-timeout` is stopped and reported as failed, even if the endpoint keeps sending bytes.

Read `journalctl -u uptime-goblin.service`, correct the reported cause and run the installer again from the same staging directory.

## Resource limits

A supervised Uptime Goblin (the systemd unit and the Docker image start it with `--supervised`) reads its memory, CPU and process limits back from its own cgroup at every start, and refuses to start (exit status 78) while one of them is not in force, unless `GOBLIN_ALLOW_UNLIMITED` names it ([resource limits](installation.md#resource-limits)). The refusal is a first line, a line for each limit it names (why, and how to apply it), and a last line with the two ways out. Under systemd the unit is left failed; Docker Compose restarts the container, so the refusal repeats until you stop it (`docker compose stop`) and correct it.

| Message | What to do |
|---|---|
| Uptime Goblin refused to start without its resource limits: … | The lines after it name each limit that is not in force, why, and how to apply it; the last gives the `GOBLIN_ALLOW_UNLIMITED` value that would let Uptime Goblin start without them. Apply each limit, or, only on a platform that cannot apply it, set that value in `/etc/uptime-goblin.env` (systemd) or `.env` (Docker Compose), such as `GOBLIN_ALLOW_UNLIMITED=cpu` or `GOBLIN_ALLOW_UNLIMITED=memory,cpu,pids`, then start Uptime Goblin again (natively, after a failed upgrade, run the installer again). |
| To start Uptime Goblin, apply each limit named above … | The last line of that refusal: see the row above. |
| Memory limit: none (memory.max is max), or Process limit: none (pids.max is max), or CPU limit: none (cpu.max is max, and no CPU set of Uptime Goblin's own limits it: Uptime Goblin's cgroup has no cpuset controller) | The limit is lifted. Under Docker Compose an override file (`compose.override.yaml`, or a file `COMPOSE_FILE` names) sets `mem_limit`, `pids_limit` or `cpus` to `0` (for `pids_limit`, a negative number too) or removes it: `docker compose config` shows what applies; with `docker run`, pass `--memory`, `--pids-limit` and `--cpus`. Natively, `systemctl cat uptime-goblin.service` shows a drop-in that sets `MemoryMax=` or `TasksMax=` to `infinity`, or empties `CPUQuota=`. Remove that line, then `docker compose up -d` or `sudo systemctl restart uptime-goblin`. Where Docker refuses any `cpus`, give a CPU set instead (the "NanoCPUs can not be set" row above). |
| Memory limit: none (Uptime Goblin's cgroup has no memory controller …), or Process limit: none (Uptime Goblin's cgroup has no pids controller …), or CPU limit: none (Uptime Goblin's cgroup has no cpu controller …) | Uptime Goblin's cgroup has no such controller, so the limit has no file to apply to: the LXC's host does not delegate that cgroup controller to the container (on Proxmox, check the container's cgroup settings), or Docker runs without it and started the container without that limit, with only a warning ("… Limitation discarded."). For CPU under systemd, check first for a drop-in that empties `CPUQuota=` (`systemctl cat uptime-goblin.service`). Delegate the controller, or, where the host cannot, name the limit in `GOBLIN_ALLOW_UNLIMITED`. |
| Memory limit: none (memory.max is … more than 2^52 bytes, which limits nothing) | `memory.max` is more memory than the machine can address, which limits nothing. Give a real `mem_limit` or `MemoryMax=`. |
| CPU limit: none (… sets none of its own …), or CPU limit: none (… holds every CPU this host has online …), or CPU limit: none (… may run on every CPU this host has online …), or CPU limit: none (… this host has one CPU …), or CPU limit: none (… are not all among those its cgroup sets …) | No CPU time limit, and no CPU set of Uptime Goblin's own limits it: its cgroup sets none (it only inherits the CPUs of the cgroup around it, as a container with no `cpuset` of its own inside a Docker or LXC held to some CPUs), or a set of every CPU the host has online, or the sole CPU of a one-CPU host, or a set the kernel could not grant and replaced with the CPUs of the cgroup around Uptime Goblin's. Give a `cpuset` of some, not all, of the CPUs the host has online, among those Docker may use (`cpuset: '0'`, or one of the CPUs the line lists), or a CPU time limit where the kernel has one; on a one-CPU host without CPU bandwidth control, set `GOBLIN_ALLOW_UNLIMITED=cpu`. |
| CPU limit: cannot be verified (… Uptime Goblin cannot tell whether a CPU set limits it instead: … this host does not have online …) | Uptime Goblin's own CPU set names a CPU that is not in `/sys/devices/system/cpu/online` as Uptime Goblin sees it: an offline CPU, one the host does not have, or one hidden from what the container sees in `/sys` (LXCFS can show an LXC its own CPUs rather than the host's, while Docker in that LXC names the host's). Fewer CPUs than the host's is not enough: every CPU of the set must be online, and the CPUs Uptime Goblin runs on must all be among them. Give a `cpuset` of CPUs the line lists as online (such as `cpuset: '0'`), or a CPU time limit where the kernel has one; where what Uptime Goblin sees in `/sys` cannot show the CPUs Docker gives it, set `GOBLIN_ALLOW_UNLIMITED=cpu`. |
| CPU limit: cannot be verified (Uptime Goblin's cgroup has the cpu controller but no cpu.max it can read …) | The kernel has no CPU bandwidth control, so there is no `cpu.max` to hold a CPU time limit, and no CPU set of Uptime Goblin's own limits it either (the rest of the line says why). Give a CPU set as in the "NanoCPUs can not be set" row above, or, where none can apply, set `GOBLIN_ALLOW_UNLIMITED=cpu`. |
| Memory limit: cannot be verified (Uptime Goblin cannot read memory.max of its cgroup as a limit), or Process limit: cannot be verified (Uptime Goblin cannot read pids.max of its cgroup as a limit), or CPU limit: cannot be verified (Uptime Goblin cannot read cpu.max of its cgroup as a limit …), or CPU limit: cannot be verified (… Uptime Goblin cannot read … to tell whether a CPU set limits it instead) | A limit file Uptime Goblin cannot read as a limit or a CPU list: not a regular file, longer than a limit file, empty where a CPU list is needed, or text that is not a number or a CPU list. A kernel does not show such a file, so check what mounts the container's cgroup or `/sys`; where that cannot be changed, name the limit in `GOBLIN_ALLOW_UNLIMITED`. |
| … limit: cannot be verified (Uptime Goblin reads its limits under cgroup v2 only, which it did not find here (cgroup v1 or a hybrid layout)) … | cgroup v1 or a hybrid layout (older Linux releases, some NAS systems): Uptime Goblin cannot verify any of its limits. Check them yourself (`docker inspect <container>` shows `Memory`, `NanoCpus` and `PidsLimit`, where `0`, `-1` or `null` is no limit; `systemctl show uptime-goblin.service -p MemoryMax -p CPUQuotaPerSecUSec -p TasksMax` shows the unit's), then set `GOBLIN_ALLOW_UNLIMITED=memory,cpu,pids`. On a host with cgroup v2 Uptime Goblin verifies them itself. |
| … limit: cannot be verified (Uptime Goblin reads its limits from Linux cgroups, and this system is …) | Uptime Goblin was started supervised on a system that is not Linux (a Mac, say), which has no cgroup for it to read. Start it unsupervised there (`npm start`, without `--supervised` or `GOBLIN_SUPERVISED=1`), or set `GOBLIN_ALLOW_UNLIMITED=memory,cpu,pids`. |
| Uptime Goblin runs without a … limit, as GOBLIN_ALLOW_UNLIMITED allows: … | Uptime Goblin started without that limit because `GOBLIN_ALLOW_UNLIMITED` names it, and says so at every start; **Configure → System** shows it, and the audit log's start entry records it. Nothing keeps a runaway from taking that resource of the host: apply the limit once the platform can, then remove the name. |
| GOBLIN_ALLOW_UNLIMITED names …, but Uptime Goblin's … limit is in force (…) | The setting names a limit that is in force, so it is not needed. Remove that name, so that it cannot hide the limit if it is lifted later. |
| GOBLIN_ALLOW_UNLIMITED must list the limits Uptime Goblin may run without, … | Uptime Goblin refused to start (exit status 78), supervised or not (`npm start` too): the value is not `memory`, `cpu` and `pids` separated by commas, each at most once, in lower case and without spaces. There is no `all`. Correct it, or remove it to run with every limit. |
| GOBLIN_SUPERVISED=… is ignored: Uptime Goblin was started with --supervised … | `/etc/uptime-goblin.env`, an `-e` option of `docker run` or a Compose override sets `GOBLIN_SUPERVISED` to a value that says no; the unit and the image start Uptime Goblin with `--supervised`, which that setting cannot turn off, so Uptime Goblin checks its limits as always. Remove the setting; to run without a limit, use `GOBLIN_ALLOW_UNLIMITED`. |
| GOBLIN_SUPERVISED must be 1 or 0 (true, yes or on; false, no or off), or empty; it is … | Uptime Goblin refused to start (exit status 78), with `--supervised` or without it: the value is neither yes nor no, and it turns a security check on, so a typo is not taken for off. Correct it (`1`), or remove the line. |
| GOBLIN_LEGACY_BASIC must be 1 or 0 (true, yes or on; false, no or off), or empty for the default; it is … | Uptime Goblin refused to start (exit status 78) before writing anything: the value is neither yes nor no, and legacy Basic is on by default for installs upgraded from 1.4.x, so a typo meant as off is not taken for that default. Correct it (`0` turns Basic off, `1` on), or remove the line for the default. The native installer checks it in `/etc/uptime-goblin.env` before an upgrade changes anything ("This release of Uptime Goblin would refuse to start with /etc/uptime-goblin.env"). |
| server.mjs takes no argument but --supervised, which the systemd unit and the Docker image give it; it was given … | Uptime Goblin refused to start (exit status 78): its command line has another argument than one `--supervised` (a misspelt one would otherwise start unchecked). Correct the `ExecStart=` line of a hand-written unit, or the command a container is given. |

## Exit statuses

`systemctl status uptime-goblin.service` shows how Uptime Goblin last exited, for example `code=exited, status=78/CONFIG`. For Compose, `docker compose ps` shows the exit code.

| Status | What to do |
|---|---|
| 78 (`78/CONFIG`), log "Uptime Goblin refused to start (exit status 78)" | Uptime Goblin refused to start, and systemd does not retry it. ## A full disk

When the disk of the Uptime Goblin host is full, the banner says "The Uptime Goblin host's disk is full (since …)", a notice is sent on your channels (while **Evaluate alerts** and **Notify when an alert begins** are on), and:

- settings changes answer HTTP 503 `storage_full` ("Uptime Goblin's disk is full, so this change was not saved…"); your changes stay in the form, so save again once there is space;
- readings are not saved (the charts show a gap), but alerts are still evaluated and sent;
- signing in and alert delivery keep working on the 8 MiB Uptime Goblin keeps in `run/space-reserve` ([space reserve](installation.md#space-reserve)). When the banner says the file system did not free that space (btrfs or ZFS snapshots, a full thin pool), they may fail too;
- Uptime Goblin starts and restarts on a full disk.
- the [audit log](security.md#audit-log) still records your own sign-ins and the changes that may still be made, on the same reserve; refused sign-ins are only counted, and Uptime Goblin's own entries (its starts, delivery events, tests and refreshes) go to Uptime Goblin's log as lines starting `{"orbit":"audit.unwritten"` instead. Uptime Goblin writes its start entries again at a later start.

Free space (old logs, Docker images, [snapshots](installation.md#snapshots)), not by lowering retention, which does not shrink the database files. Once at least 24 MiB is free, Uptime Goblin makes its reserve again within about 10 seconds, saves readings and settings again, and sends a notice that the disk has free space again (while **Evaluate alerts** and **Notify when a source recovers** are on). The same happens when you free space while Uptime Goblin is stopped, or roll back to 1.4.x meanwhile and upgrade again: the next start sends that notice ([a restart in between](notifications.md#a-full-disk)); a start on a disk that is still full sends no second disk-full notice.

## Uptime Goblin cannot write its audit log

A change answers "Uptime Goblin cannot write its audit log, so nothing was changed. Try again in a moment; if this continues, free up space or increase the disk size of the Uptime Goblin host." (503 `audit_unavailable`). Uptime Goblin records every settings and source change, **Retry**, **Resume** and every export before it makes it, and makes none of them when it cannot record it first: nothing was changed, sent or exported. The cause is almost always `control.sqlite` that cannot be written: a full disk (the disk banner says so; see [a full disk](#a-full-disk)) or a failing one. Signing in fails for the same cause, since a sign-in and its entry are saved together. Source tests, test emails and refreshes still run.

Free space, or give the Uptime Goblin host a larger disk, then try again. Entries Uptime Goblin could not write after their change (the change stands) are not written later: they are in Uptime Goblin's log, one line each starting `{"orbit":"audit.unwritten"` (`journalctl -u uptime-goblin`, `docker compose logs uptime-goblin`), the change shows "Outcome unknown" under **Configure → Audit log**, and the page says how many there were since Uptime Goblin started. A settings change among them is recorded again at the next start, as a change made outside Uptime Goblin, with what changed.

Uptime Goblin's log has one line for each refused request: `Request refused: Uptime Goblin could not write its audit log: <code> (request <id>)`, the id being the answer's `X-Request-Id`. The code is the failure's: a SQLite failure names `ERR_SQLITE_ERROR` whatever its cause, a full disk included, so the disk banner (or `df`) tells whether the disk is full.

**"Uptime Goblin could not read its audit log. Try again in a moment."** (503 `audit_read_unavailable`, on the Audit log page, its export or **Check integrity**; Uptime Goblin's log says `Request refused: Uptime Goblin could not read its audit log: <code> (request <id>)`): `control.sqlite` could not be read, or holds a value Uptime Goblin never writes. Try again; if it repeats, run `goblin-admin verify-audit` ([goblin-admin](installation.md#goblin-admin)), which says what it could not read.

## The audit log check says CHANGED

**Check integrity** (or `goblin-admin verify-audit`, exit status 1) found the first entry that is not as Uptime Goblin wrote it, and says what that means:

- **An entry was changed** ("does not match its signature") or **does not follow the one before it** ("an entry was changed, inserted or removed"): someone with write access to `control.sqlite` edited the log. The entries before it were checked.
- **Entries are missing** (a gap, "Entries before #… are missing", or "the log ends at entry #…, but Uptime Goblin last wrote entry #…"): entries were deleted, from the middle, the start or the end.
- **Uptime Goblin found its audit log cut or changed at the end**: at a start or a change, the record of Uptime Goblin's last entry did not match the log; Uptime Goblin wrote an entry saying so and went on.
- **A checkpoint does not match**, or **is not signed by this Uptime Goblin**: a stored prune checkpoint was changed, or the key that signed it was removed without a recorded reset.
- **An entry differs from the checkpoint Uptime Goblin printed**, or **Uptime Goblin printed a checkpoint past the end of the log** (only with `--checkpoints`): the log was changed or cut after Uptime Goblin printed that line, or the data is an older copy (a restore Uptime Goblin did not see happen).
- **Signed with a key that is not in the keyring** (`key_lost`): the keyring's audit key was removed by hand, or the key was lost and reset by an earlier 1.5 build, which recorded no reset. A lost-key reset by this release is recorded, and its entries read "not fully checked" instead.
- **Entries could not be read** ("a stored value is out of range"): `control.sqlite` holds a value Uptime Goblin never writes; the list and the export say the log is unavailable too.

Compare with Uptime Goblin's own log, which an edit of the data directory does not change: `goblin-admin verify-audit --checkpoints` ([goblin-admin](installation.md#goblin-admin)). Keep a copy of the data directory as it is before anything else changes it, and find out who could write it.

## The audit log check says not fully checked

Nothing was found changed, but not everything could be checked (exit status 3 from `goblin-admin verify-audit`):

- **No encryption key reached the command**: only the links between entries were checked. Run it with the key Uptime Goblin uses, as the message prints it.
- **The key given does not open this data** (`key_mismatch`, for example the old key after a `key rotate`): only the links between entries were checked. Run it with the key Uptime Goblin uses; the message gives the fingerprint of the key it was given, and Uptime Goblin's start line ("Encryption key: … · fingerprint …") that of the key Uptime Goblin uses.
- **Entries signed with keys that `goblin-admin key reset` removed**: their links were checked, not their signatures; the reset is listed with the date it was made.
- **Entries written by a newer Uptime Goblin** (after a rollback): their links were checked; the newer release checks them fully.
- **Checkpoint lines printed before a restore**: they name entries the restored log no longer holds. Check with only the part of Uptime Goblin's log printed after the restore to get a full result. Every restore that kept `control.sqlite` is listed: make sure each was yours. A restore that removed it is not (the next bullet).
- **Checkpoint lines signed with keys the keyring does not hold** (and no `goblin-admin key reset` recorded their loss): they cannot be checked. They are another Uptime Goblin's lines (check only this Uptime Goblin's log). Or they are this Uptime Goblin's from before a restore of data older than a `key rotate`. Or they are this Uptime Goblin's from before `control.sqlite` was deleted, or before a snapshot or a copy without one was restored (the pinned pre-1.5 snapshot, a backup from before the upgrade): the whole audit log went with that file, so the log starts again with "Uptime Goblin … started for the first time", and the lines before it name another `instance` than the lines after it. The old log is then only in older copies of `control.sqlite`, each as it was when made: the pre-restore snapshot that `restore-snapshot` made (deleting the file leaves none), a copy you moved aside, and earlier snapshots and backups. Or they are this Uptime Goblin's under a key that was then removed from the keyring by hand, which can hide entries removed together with it. If none of the first three applies, treat the log as changed. The result also says "Every entry is covered by a journal checkpoint." then: that covers only the entries the log holds now.

## Uptime Goblin's log mentions old audit entries

The hourly job that removes audit entries past the retention ([retention and privacy](security.md#audit-log)) says once a day in Uptime Goblin's log when it held back:

- **"Uptime Goblin's clock is behind its newest audit entry, so it did not remove audit entries older than … days this time. Check the time of the Uptime Goblin host."** The host's clock is more than an hour behind the newest entry. Nothing is removed by age until the clock is right (`timedatectl` shows it); the 250,000 cap still applies.
- **"Uptime Goblin did not remove old audit entries, because entry #… does not check: use Check integrity on the Audit log page."** One of the entries it would remove reads CHANGED, or a newer Uptime Goblin wrote it before a rollback. Until that entry is gone, nothing is removed, neither by age nor by the 250,000 cap, so entries stay past the retention, with their addresses, browser names and session ids, and the log keeps growing. 1.5 has no command that resumes the prune. Run **Check integrity** and see [the audit log check says CHANGED](#the-audit-log-check-says-changed); after a rollback, upgrading again lets the newer release check those entries. Keep an export of the log (**Configure → Audit log**) and report it.

## Lost encryption key

Only when the key the data was sealed with is truly gone (look in your password manager, your backups, `/etc/uptime-goblin/secret.key`, the Compose `orbit_secret_key` file, `secret.key` in old copies of the data directory). In 1.5 the key seals only the webhook's private signing key, so a reset loses only that key; later releases seal more.

1. Stop Uptime Goblin (`sudo systemctl stop uptime-goblin.service`, or `docker compose stop uptime-goblin`).
2. Put the key Uptime Goblin should use from now on in place, and keep the key file that does not open the data, in case it turns out to be the right one after all. Natively, set the old file aside, `sudo test -e /etc/uptime-goblin/secret.key.lost && echo 'secret.key.lost exists: choose another name' || sudo mv /etc/uptime-goblin/secret.key /etc/uptime-goblin/secret.key.lost`, then make a new `/etc/uptime-goblin/secret.key` that the group `uptime-goblin` can read: `sudo install -d -o root -g uptime-goblin -m 0750 /etc/uptime-goblin`, then `openssl rand -hex 32 | sudo install -o root -g uptime-goblin -m 0440 /dev/stdin /etc/uptime-goblin/secret.key` (`install` makes the file private before it writes the key); keep (or add, with `sudoedit /etc/uptime-goblin.env`) the line `GOBLIN_SECRET_KEY_FILE=/etc/uptime-goblin/secret.key` in `/etc/uptime-goblin.env`. The installer cannot do this: it refuses data whose key is missing. Under Compose with `compose.secret.yaml`, set the old file aside (a copy, then the file removed, as the `MOVE` recipe does), `test -e orbit_secret_key.lost && echo 'orbit_secret_key.lost exists: choose another name' || { cp -p orbit_secret_key orbit_secret_key.lost && rm -f orbit_secret_key; }`, then make a new `orbit_secret_key`, private from its first byte, `(umask 077 && openssl rand -hex 32 > orbit_secret_key) && chmod 0400 orbit_secret_key`, and on a Linux host `sudo chown 1000 orbit_secret_key`, with `COMPOSE_FILE=compose.yaml:compose.secret.yaml` in `.env`. Over an `orbit_secret_key` that is still there (mode 0400), the new-key command fails (permission denied) and changes nothing. Without the override, nothing: the reset below generates `secret.key` in the volume.
3. Reset the keyring, which forgets every sealed value, with the new key in the command's own environment (`goblin-admin` does not read `/etc/uptime-goblin.env`): `sudo -u uptime-goblin env GOBLIN_SECRET_KEY_FILE=/etc/uptime-goblin/secret.key node /opt/uptime-goblin/lib/cli/goblin-admin.mjs key reset --confirm-lost-key --data-dir /var/lib/uptime-goblin`. Compose with the override: `docker compose -f compose.yaml -f compose.secret.yaml run --rm --no-deps uptime-goblin node lib/cli/goblin-admin.mjs key reset --confirm-lost-key` (the `-f` pair is what `COMPOSE_FILE=compose.yaml:compose.secret.yaml` does; with a `compose.override.yaml`, add `-f compose.override.yaml` after `-f compose.yaml`); without it: `docker compose run --rm --no-deps uptime-goblin node lib/cli/goblin-admin.mjs key reset --confirm-lost-key --use-data-dir-key`. A reset that finds no key, or only `secret.key` in the data directory, refuses without `--use-data-dir-key`, writing no key and leaving the keyring as it was (it has taken `goblin.lock` by then, which it creates where it is missing): it cannot see the key Uptime Goblin reads, and a reset under another key would leave Uptime Goblin refusing to start.
4. The reset is recorded in the [audit log](security.md#audit-log) together with the keys it removed, in the same step: a reset that cannot record it leaves the keyring as it was (exit status 1). A `secret.key` it generated in the data directory for `--use-data-dir-key` stays there, as its message says, and a reset run again with `--use-data-dir-key` uses it. Entries signed with the lost key are then reported "not fully checked" (their links are checked, their signatures cannot be), never as changed.
5. Start Uptime Goblin. With a webhook set (`GOBLIN_WEBHOOK_URL`), it makes a new webhook signing key ("Uptime Goblin created a new signing key for the alert webhook…") and holds the webhook's notifications: give its public key (**Configure → Notifications → Show public key**) to receivers that check signatures, then press **Resume** on the webhook's card ([a new signing key waits for Resume](notifications.md#a-new-signing-key-waits-for-resume)). Then back the new key up apart from the data. The file set aside in step 2 opens none of this data now; keep it only while a backup or a snapshot made before the reset may need it.

## Runtime and storage checks

For a native service, inspect `systemctl status uptime-goblin.service` and recent `journalctl -u uptime-goblin.service` output. For Compose, inspect `docker compose ps` and `docker compose logs --tail=100 uptime-goblin`. `/health` needs no password: on the Uptime Goblin host, `curl -s http://127.0.0.1:4317/health` prints `{"status":"ok"}` while Uptime Goblin is serving. For an install listening on another address, add `-H 'Host: localhost:4317'` and use that address, because Uptime Goblin accepts only allowed Host values. `/var/lib/uptime-goblin/run/status.json` (native) names the version, build and process ID that are running. For other authenticated manual checks, use an interactive password prompt rather than putting a password directly in shell history.

The native `uptime-goblin` account needs its private data directory writable. The systemd unit prevents access to home directories and most system writes; a CA file or Node executable under a home directory may be inaccessible. Restore ownership/modes deliberately after moving data. Do not make the entire data directory world-readable as a fix.

If configuration becomes invalid, stop Uptime Goblin, preserve a private copy, and restore a known-good backup or repair the identified field offline. Do not discard history or replace secrets with a redacted export as a troubleshooting shortcut.

## Forgotten Uptime Goblin password

Changing the password under **Configure → Account** needs the current password, so it does not help when that is what you forgot, even in a browser that is still signed in. Recovery requires operator access to the Uptime Goblin host. There is no email reset or unauthenticated web bypass.

1. Stop Uptime Goblin: `sudo systemctl stop uptime-goblin.service` for the native installer, `docker compose stop uptime-goblin` for Compose, or stop the local process. Keep it stopped throughout the file changes.
2. Make and verify a new private backup of the **whole data directory and deployment environment**, preserving the existing `auth.json`. Use restrictive permissions; do not overwrite your only known-good backup. Native data lives in `/var/lib/uptime-goblin`, Docker data in the named volume at `/app/data`, and the local default is project `data/`.
3. Ensure the deployment has a nonempty bootstrap `GOBLIN_PASSWORD` that you know. Retrieve it privately from the password manager/environment, or replace it in the environment using a local editor such as `sudoedit /etc/uptime-goblin.env` for the native installer. Never put the password into a command argument, terminal transcript or shell history. For local/Compose deployments, edit the private `.env` or the actual environment source used by that deployment.
4. Move `auth.json` out of the active data directory into the private recovery backup. Do not delete the data directory, change `config.json`, or edit hash fields. With the authentication file absent, the next start uses the bootstrap password. Retain the moved file until recovery is verified.
5. Start Uptime Goblin with the intended environment. For Compose, recreate the container if the environment changed (`docker compose up -d`); `start` alone does not apply changed environment values. Uptime Goblin imports the bootstrap password (the log says "Imported the admin password from GOBLIN_PASSWORD…") and signs every session out. Sign in as `admin` using the bootstrap password, then set a new password under **Configure → Account**. Verify that the new login works and that monitoring settings/history remain intact.

This procedure also applies when an invalid `auth.json` prevents startup, after preserving the damaged file for diagnosis. Restore a known-good authentication file instead when you know its password. Keep recovered files and backups private; an old backup contains the authentication state from its own date.
