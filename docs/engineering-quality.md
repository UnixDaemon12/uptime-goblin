# Engineering quality and security

[Contributing](../CONTRIBUTING.md) · [Security boundaries](security.md) · [Vulnerability reporting](../SECURITY.md)

This policy applies to every Uptime Goblin repository, branch and worktree, including maintenance and unfinished feature work. Security takes priority over delivery speed. A passing scanner or test suite is evidence about its coverage, not proof that software has no vulnerabilities. A reviewed change, a commit, a release and a deployment are separate outcomes.

Follow the [AI development requirements](ai-development-security.md) for the additional Clair/Snyk checks, fresh Netxeo review, error handling, logging controls and measured performance work. Their pending implementation cannot be replaced by a passing older gate. Release review requires explicit evidence references for the skill audit, performance, Clair image scan and Snyk scan; references alone are not scan execution or release approval.

## Design and implementation

Apply the entire [security rule inventory](security-rule-matrix.md), pinned to the reviewed Netxeo rule set. Account for every rule, including a reason when it does not apply; an unreviewed item remains pending. This inventory supplements concrete analysis and tests and does not establish a security score or certification.

Validate input at every trust boundary: request paths, queries, headers, cookies, bodies, environment and command-line arguments, saved files and database content, upstream responses and exported/imported data. Define accepted types, syntax, ranges, lengths, depth, collection sizes and normalization. Reject unknown fields where the contract is closed, test missing and duplicate fields and malformed encodings, and recheck authorization after asynchronous boundaries. Browser validation is a usability aid; the server must independently enforce its contract. Errors and logs must not echo secrets.

Never hardcode real credentials. Sign-in passwords require a salted, deliberately expensive password hash; recoverable service credentials require encryption with separately protected keys. Apply restrictive permissions at creation, including temporary files, backups and error paths, and verify key rotation and recovery. File permissions alone are not encryption. Bind SQL data values using query parameters; allowlist identifiers and other SQL structure that cannot be bound. Container runs must specify memory, CPU and process limits, including development/scanner containers; document measured capacity and blocked limits instead of silently disabling them.

Before changing behavior, name the affected trust boundaries, data and failure modes. Keep changes small and cohesive, with explicit ownership when several contributors work at once. Preserve their unfinished work; review an exact checkpoint in a separate checkout when necessary.

Write readable code with clear names, short coherent responsibilities and explicit error handling. Prefer existing project patterns and the smallest justified abstraction. Explain invariants and unusual tradeoffs in comments; remove stale comments and dead code. Avoid unrelated rewrites, generated-looking repetition and dependency additions without a concrete need. Keep dependencies exact, review lockfile changes and lifecycle scripts, and preserve the AGPL-3.0 license and attribution.

Use synthetic identities, secrets and local fixture services in tests. Test behavior, negative cases and recovery, including cancellation, concurrent changes, retries and partially completed work. A regression should fail on the relevant old behavior and pass after the fix when practical; preserve positive controls. Do not make tests pass by suppressing errors, weakening assertions or replacing a required real integration with a mock.

## Every commit

The required entry point is:

```sh
node scripts/security-gate.mjs commit
```

Start the gate with `node`, as above, not with `npm run security:commit` (the same holds for `scan` and `release`). npm puts every `node_modules/.bin` from the worktree up first on `PATH` and passes the `node-options` of the worktree's and your `.npmrc` to the process it starts, so a dependency installed in the worktree (a bin named `node`, for example) or an `.npmrc` could replace or change the gate before it runs. The gate removes `node_modules/.bin` entries from `PATH` and drops `NODE_OPTIONS` and every `npm_config_*` variable before any stage runs, so no stage gets them however the gate was started, but it cannot undo what npm did before the gate started. npm also reads your `.npmrc` and its global `npmrc` by itself in every command, whatever the environment says, so each npm stage gets empty user and global npm configuration files instead: no setting there (`script-shell`, `node-options` or `audit-level`, and also a registry, proxy or certificate) applies to an npm stage. npm still uses the `HTTPS_PROXY` environment variables, and the built-in configuration of the npm installation still applies.

Run the full security gate for **every proposed commit**, including documentation, formatting, tests, dependency changes and merges. There is no documentation-only exception. Focused tests help development but do not replace this gate. Missing commands, unavailable tools, stale scanner data, cancelled jobs, skipped required cases and unexecuted checks are not passes. A required stage that cannot run leaves the candidate blocked; retain the reason and arrange a suitable environment before committing.

The gate must cover formatting, syntax, import/runtime manifests, the full applicable test matrix, source security analysis, secret detection, dependency and supply-chain checks, and container build/runtime security checks. Audit production and development dependencies: build and test tooling can affect the release. Run the required browser, historical upgrade/rollback, installer, real systemd and Docker tests with their dependencies required, rather than allowing environmental skips. Include branch-specific SQL/import rules and capacity or failure tests where that branch declares them as gates.

Record the supported runtime/platform matrix rather than inferring it from one local run. Test the minimum supported Node runtime (currently 24), the development runtime when different, and the actual release image runtime. A test that belongs only to another platform must have a named, passing run there; its local skip remains a skip. Do not add distinct platform counts together and call them one complete run.

An independent reviewer must also read the proposed change, tests and documentation. Review authorization boundaries, secret handling, external inputs, storage/concurrency and failure behavior as applicable, and assess whether the implementation remains understandable. Automated analysis does not replace this review, and review does not replace the gate. Record the reviewer, exact scope, findings and unresolved limitations.

### Coverage accounting on 1.5

The 1.5 gate adds two stages, two `candidate-policy` rules, a check before each npm stage and one test requirement to the maintenance gate (and, as a draft for independent review, the platform contract's environment, stages and companion runs: see [The gate's side of the platform contract](#the-gates-side-of-the-platform-contract) below):

- `sql-lint` and `import-lint` run `scripts/sql-lint.mjs` and `scripts/import-graph.mjs` in the commit, release and scan modes (a companion run runs neither), once the pre-dispatch barrier is open (see [What the gate starts, and what it withholds](#the-gates-side-of-the-platform-contract)): `npm run check` and the CI test jobs do not run them, and a candidate that breaks them must not get a green scan; a closed barrier records both pending, withheld before dispatch, so that scan is not green either. On a CI runner the security scan's barrier stays closed for every 1.5 commit: the scan's candidate is the checked-out commit's tree on top of that commit, which holds `test/platform-manifest.json`, so `platform-manifest` needs a commit the gate approved, or a reviewed baseline disposition, and both are kept only in the local `<git common dir>/orbit-security`, which a CI runner does not have. The CI scan therefore records `platform-manifest` blocked and both lints withheld, and runs neither, so nothing in CI runs them (the fourth round's scan did, because it did not judge `platform-manifest`); run them yourself with `npm run lint:sql` and `npm run lint:imports`. They run with the gate's own Node rather than through npm and without `NODE_OPTIONS`, before the candidate's dependencies are installed or any other stage runs candidate code, and `candidate-policy` requires `package.json` to be in canonical form (`JSON.stringify` with two-space indentation and a final newline, which is what Prettier writes for it, so no duplicate member such as a second `scripts` or `lint:sql` can read one way to a reviewer while JSON.parse and npm take the last one) and to name exactly those commands (`node scripts/sql-lint.mjs` as `lint:sql`, `node scripts/import-graph.mjs` as `lint:imports`), so, with the gate started by `node` as above, no `.npmrc`, `node_modules/.bin` entry or `package.json` change can make them pass without running. `sql-lint` loads only Node's built-in modules. `import-lint` also reads the table registry, which is server code: it runs `lib/db/registry.mjs` and the modules that imports (`lib/db/dialect/schema.mjs`, `lib/db/sql.mjs`, `lib/alerting/tables.mjs` and `lib/notify/limits.mjs` today) in a child process, after reading every source, and uses only the table list that process prints. Those modules therefore cannot end the lint by exiting, failing or printing something other than the list (a registry that cannot be read is a `table-registry` finding), and the gate starts the lint with `--disable-sigusr1`, so a signal from them cannot open the lint's inspector and run code in it. They still run with your privileges, like every candidate script the gate runs (see the limit in the next item), and they can give the table rule a wrong list, so review them as inputs of the lint. The commit guard requires each lint stage whose script the candidate's `package.json` defines, or a parent of the commit or the history behind it defined, so a 1.5 record without either stage is refused, and it refuses a candidate that removes or renames such a script (see the 1.5 adoption note below). The CI scan runs the candidate's own gate and has no such guard, so there only review catches a candidate that changes the gate to drop a lint. Neither Semgrep nor SonarQube implements these rules, so their results do not replace them.
- `candidate-policy` refuses a tracked `.npmrc`, in any directory or letter case, and each npm stage first refuses an `.npmrc` at the snapshot's root, tracked or not, and any entry in a `node_modules/.bin` that `npm run` searches before `PATH` (the snapshot's and that of every directory above it) that would replace a command: `node`, `sh`, `env`, `npm` or `npx`, or any name that `PATH` also provides, such as `bash` (which `npm run check` runs) or `git` (which `npm run docs:check` runs), whether a dependency or an earlier stage put it there. It also refuses such a `node_modules/.bin` that it cannot list, unless it is absent or not a directory: the shell runs a command from a directory it may search but not read (mode `0111`), so an earlier stage could otherwise hide a `bash` there. One left above the snapshot, in the gate's `TMPDIR`, blocks every later run until it is removed, and the gate gives the directories in its own scratch area back to itself before removing them, so such a directory there cannot end the run before it is recorded (a scratch area that still cannot be removed blocks the run as `scratch-cleanup`). A bin that no command on `PATH` has, such as `prettier`, is what the scripts mean to run; a global install of the same name on the gate's `PATH` (a global `prettier`, for example) therefore blocks the npm stages until it is removed from that `PATH`. Such a file can make an `npm run` stage pass without running its check while the log still names the script (an `.npmrc` through its `script-shell` or `node-options`), and an `.npmrc` can also change what an audit stage checks. For the same reason the CI security workflow starts the gate with `node scripts/security-gate.mjs scan`, not through npm. Your own `.npmrc` and npm's global one do not reach the npm stages at all: each runs with empty user and global npm configuration (see [Every commit](#every-commit)). These checks close known routes; they do not make the gate a trust boundary. Whatever candidate code the gate starts runs with your privileges (today the two lint sources, once the pre-dispatch barrier is open; the candidate's dependencies, scripts and tests once their authorities exist and they are no longer withheld, see [What the gate starts, and what it withholds](#the-gates-side-of-the-platform-contract)), so that code can still change what a later stage runs, or write a passing record where the commit guard looks for one, and the guard checks stage names and results, not what a stage ran. Review therefore covers every change: dependencies and `package-lock.json`, every script and test the gate runs, the gate itself and the lint sources.

**Platform tests.** A test that can run on one platform only is listed in `test/platform-manifest.json` and registered through `platformTest()` or `platformSubtest()` (`test/helpers/platform.mjs`), never with a platform check or a skip of its own. It is registered only on its platform: elsewhere it is absent, not skipped, and an absence is never counted as a pass. The platforms are `linux`, `darwin` (macOS) and `container`, the T8 driver's container (a run is there when `TEST_T8_DIR` is set). Each entry gives a stable id, the exact file and test name path (a subtest's parents first), its platforms, the Node runtimes it is required on, its prerequisites and the runs that must execute it. On its own platform a missing prerequisite fails the test, naming what is missing (`non-root`, `setfacl`, and `acl-tmpdir`, a temporary folder that takes access lists), except `docker`, which skips without `docker` in `TEST_REQUIRE` as the other Docker tests do. The manifest is strict data: unknown fields, a member named twice, an id or a file and name used twice, a run id that is also a name of every JavaScript object (`constructor`), an unbounded path, a name TAP cannot show exactly or a reviewer cannot read exactly (with `#`, `\`, a line break, a control character, ` > `, a lone UTF-16 surrogate, an invisible format or private-use character such as a zero-width space, a bidi control or a byte order mark, or a space other than U+0020), and inconsistent runs (among them a T8 image whose driver does not list `docker`, or two runtimes naming one driver) are refused. The entries today: the three T8 tests inside the container and the driver and its host check outside it (`test/disk-full.test.mjs`); the two macOS and the one Linux access-list tests of keeping Uptime Goblin's log (`test/docs-audit.test.mjs`); the `/proc` tests of `test/notifications.test.mjs` and `test/db/cli.test.mjs`; the two `/proc/self/fd` tests of `test/healthcheck.test.mjs`; the `OLD_KEY_FILE` subtest of `test/docs-keys.test.mjs` from a working directory it cannot enter (Linux, not as root); and the platform branches that asserted Linux behaviour on Linux and macOS behaviour on macOS inside one test, now one subtest per platform: the deleted-but-open key source in `test/keyring.test.mjs`, the reused process id in two tests of `test/db/cli.test.mjs`, and the rolled-back 1.4.2 of `test/upgrade/identity.test.mjs` (L6). Each kept every assertion; a Linux run without `/proc` now fails these where it took the macOS branch. The manifest names four runs: `linux-full` (every test file, Node 24 and 26, commit and release), `darwin-platform` (the files that hold a Linux or macOS entry, run whole on macOS, Node 24 and 26, commit and release; it is not a full macOS suite), `darwin-full` (every test file on macOS, release only) and `t8-container` (`test/disk-full.test.mjs` in the driver's container, Node 24 and 26). With `TEST_PLATFORM_RECORDS` (an absolute path to a directory, not a link) and `TEST_PLATFORM_RUN` (64 lowercase hex digits) set, each test process writes a record of every platform test it ran: its id, file, name, platform, Node version, result, the run's code and the manifest's sha256; one without the other, or a malformed value, fails the test file. Only the wrapper that `platformTest()` and `platformSubtest()` give a bound test writes a test's record (`writePlatformRecord()` writes only the T8 driver's `container` record), and every call of them passes its own file's `import.meta.url` with a literal id, which `test/platform-manifest.test.mjs` checks in every test file; test code that writes a record file itself is not stopped by this, so review remains the control there, as for the gate's logs. `node scripts/check-platform-coverage.mjs --run RUN_ID --runtime 26 --tap STAGE_LOG --records RECORDS_DIR --nonce RUN_CODE` (the run's id in the manifest, its Node major, its TAP log, its records directory and its `TEST_PLATFORM_RUN`) checks one run: exactly one line each for the totals, with nothing failed, cancelled, skipped or todo; every entry the run requires executed and passed exactly once, with one matching record of this run, manifest, platform and runtime; every entry of another platform absent from the log at any depth, also under another parent, and from the records; and no record of an id the manifest lacks. Its `judgeCandidateManifest()` judges a candidate's manifest against the manifests of its history, comparing two at a time with `coverageLoss()`: a removed entry or run, or one that loses a file, name, platform, runtime, evidence run, required gate, prerequisite, pinned image or driver, is a loss, which only an exact disposition bound to the candidate's tree and complete ordered parent vector, with a reason, a reviewer and a reference, excuses (one per loss; a new test excuses none). The candidate is judged against every valid manifest from its parents back to the last commit the gate approved on each path, that commit included, so a commit made without the commit guard (with `--no-verify`, or by `git revert`, `git cherry-pick` or `git rebase`, which run no pre-commit hook) can neither delete nor weaken the manifest unnoticed, and at least one of those baselines must be established by review: an approved commit's manifest, or a reviewed baseline disposition that names a commit behind the candidate and its manifest's sha256 (it adds a baseline, never removes one). Without one the candidate is refused. Once any commit behind the candidate held the manifest, the candidate must hold a valid one: deleting it or making it unusable is refused, and no disposition excuses that. A branch whose history never held the manifest (maintenance, B35) loses nothing and needs no platform run, and the commit that adds the first manifest loses nothing. The gate, the finalizer and the commit guard use all of this as [The gate's side of the platform contract](#the-gates-side-of-the-platform-contract) describes; that part is a draft for independent review and has not run as a full gate.

The driver gives the run its one-time code as `TEST_T8_RUN` and `TEST_PLATFORM_RUN`, mounts a folder for the records inside, and passes only when the run inside exited 0 with exactly one line for each total, every test passed (none failed, cancelled, skipped or todo), the environment test, part B and the measurements each passed once at the top level, the driver itself is absent there, the run reported the code the driver chose and a Node version of the image's runtime, and the coverage check of `t8-container` on that runtime passes over the TAP and records inside. A withheld stage is recorded pending, with no command, log or exit, and a reason that starts "withheld before dispatch, nothing ran" and names every reason; the stages that need its result (the npm script stages, a test stage's coverage, the T8 authenticity and activation, the Semgrep run after its image) are pending too, so no required stage is simply missing; and the run is never a pass and exits 1. `docker` stays in the test stages' `TEST_REQUIRE`: their coverage is withheld, not narrowed or skipped. The finalizer treats a withheld test stage as pending, with its coverage, its runtime gap and its network record, and refuses a coverage stage that claims a pass for a withheld test, a T8 container record that names an image whose inspect was withheld, and an activation binding when the inspect was withheld. This is a scheduling barrier in the gate's own process: it stops the gate from starting a command, and a command it does start is not contained by it: the two lints, the only candidate code it starts today without any authority (they need only the open barrier), inherit the gate's environment, `DOCKER_HOST` and the Docker client on `PATH` among it, and can reach a Docker client or the Docker endpoint themselves, as a test run given an authority could; containing a nested Docker client or a direct socket stays the environmental prerequisite of v5 C5 (decision 7), pending, as the listener stays gate-network's and int-d's. The tests (`test/security-dispatch.test.mjs`) show zero dispatches through the dispatch point, with refusing process stand-ins, for each kind of prerequisite above, for a missing or malformed authority and, for each of the four test stages, for each kind of `test-host` and `runtime-identity` record that must hold it back; through the real gate, with candidate canaries and logging stand-ins, for a blocked `candidate-policy`, a blocked `platform-manifest`, a missing or malformed authority, and, with a synthetic authority, a blocked, pending, absent or twice-recorded `test-host` or `runtime-identity` and a run that lacks a runtime its manifest needs; and, when a fixture gives a synthetic authority (and, for a test stage, identity records for its runtimes), exactly one dispatch of each command, the test file's nested `docker build` and its direct connection to the Docker endpoint included. The authority module is not an authority boundary yet. The gate runs the candidate's own copy of it, as of every gate file, and the trusted bootstrap that would check them first is pending, so a candidate that changes it can grant itself every authority, as it can change the gate itself. Nor is an authority tied to the stage that records its preconditions: a Semgrep or scan-build authority is not checked against the recorded `image-approval` stage, which this draft always records pending, and the finalizer does not read the authority a dispatched stage records. The reviewed producer of a real authority has to tie both.

- **Environment.** Before any stage runs, the gate removes from its own environment every variable named `TEST_*`, `UPDATE_GOLDEN` or `NODE_TEST_CONTEXT`, in any letter case, as it removes `NODE_OPTIONS` and `npm_config_*`, so no stage inherits them: not `TEST_REQUIRE`, `TEST_T8_DIR`, `TEST_TAG_TREES` or the record variables, and not `UPDATE_GOLDEN`, which is stripped before anything runs rather than left for `candidate-unchanged` to notice. Their names, never their values, are recorded as `inheritedTestInputs` in `result.json`. Each test stage then gets an environment of its own: `TEST_REQUIRE=browser,fixtures,systemd,docker,capacity,git`, `TEST_PLATFORM_RECORDS` (a new, empty folder of the gate's user in its scratch area that nobody else may read) and `TEST_PLATFORM_RUN` (32 new random bytes in hex), each checked before the stage starts. The gate's own inputs are `ORBIT_SECURITY_NODE24` and, on Linux, `ORBIT_SECURITY_NETWORK_STATE`. Everything else you export still reaches every stage, the test stages included (Git variables apart: since the eleventh round every stage gets only a few named ones, and since its corrective pass no Git configuration file of yours, as below): `PATH` (without `node_modules/.bin` entries) decides which `git`, `docker`, `setfacl`, `python3` and `curl` the tests run, `CHROME_PATH` which browser the browser tests start, `DOCKER_HOST`, `DOCKER_CONTEXT` and `DOCKER_CONFIG` which Docker daemon the T8 driver and the image check use, and `HOME` and `TMPDIR` where they write. The gate records, as `inheritedEnvironment` in `result.json`, the names of every variable it inherits from you after those removals (before it sets Git variables of its own, so a Git variable named there may reach no stage) and the values of those seven, so the review sees them; it records no other value. It also sets Git's history settings for every stage (below).
- **`platform-manifest`.** The gate judges the candidate's `test/platform-manifest.json` with `judgeCandidateManifest()` against its parents (HEAD and each `MERGE_HEAD`) and every commit behind them (at most 100,000), reading the bytes at that path in each commit with Git; a link, a folder or a submodule there counts as a manifest that cannot validate. So a branch whose history holds one of those there has a platform contract from that commit on, even if it never held a real manifest: its candidates are refused until one holds a valid manifest and a reviewed baseline disposition names a commit with one. Git reads each commit as it is: the gate (and so every stage it runs), the finalizer and the commit guard turn off grafts (an exported `GIT_GRAFT_FILE` included), replace refs (`refs/replace/*`, or another base in `GIT_REPLACE_REF_BASE`) and the commit-graph cache, whose parents and trees Git uses without checking them against the commits. They set `GIT_GRAFT_FILE` to a path that cannot exist, `GIT_NO_REPLACE_OBJECTS=1`, and `core.commitGraph=false` and `core.useReplaceRefs=false` at the end of `GIT_CONFIG_PARAMETERS`, and drop an inherited `GIT_SHALLOW_FILE`; the gate records the names of the inherited variables it replaced as `inheritedHistoryInputs`. Each refuses a shallow repository or an `info/grafts` file in the Git common directory outright. Without this, one exported variable could hide from all three a commit that deleted the manifest or a lint script with `--no-verify`. Writing Git's object store directly is beyond these checks, as is any record written with your privileges. A commit in the history counts as approved only when a finalization with status `pass` names exactly its tree and its complete parent vector, in order (never its tree and first parent: a different merge sharing those no longer inherits the approval and stops the walk, which hid the history of its other parent, security review GD-01), still matches its sealed run and review and records the manifest sha256 its platform check judged, and the commit's own object, read again, has that tree and those parents. Where a replace ref named after the commit, its tree or a parent, or a commit-graph, would make Git show other parents than the object's own, the candidate is refused rather than one view chosen; the same holds for the candidate's own parents. A finalization made before this draft does not count. Loss and baseline dispositions are kept outside the candidate, in `<git common dir>/orbit-security/coverage/<tree>.json`: a private regular file `{ "schemaVersion": 2, "tree", "parents", "dispositions": [...] }` bound to the candidate's tree and complete parent vector, each disposition exact as `coverageLoss()` requires (no blanket form), with `tree` and `parents` of its own; version 1, with one `parent`, is refused. The gate seals a copy of it, the candidate's manifest and the judgment with the run, so the finalization review binds them. Any problem, or a loss no disposition excuses, blocks. A candidate whose history never held the manifest, and which holds none, is maintenance: no platform stage runs and nothing more is required (B35).
- **Test stages.** In this draft every test stage is withheld before dispatch (above, and **Image builds** below); what follows is what a test stage does once it is dispatched, as the tests check with a synthetic authority. A test stage also starts only once `test-host` and `runtime-identity` have passed (the security review's GD5-CARRY-01 on the fifth round, which recorded both but did not consult them, so that given a synthetic authority a test stage started while either was blocked; v5 C3): its dispatch rule requires each to be recorded exactly once in this run, with status `pass` and a valid recorded start and end inside the run that ends no later than the decision, and to apply to the stage: `test-host` must name this host's platform, and `runtime-identity` must list the stage's own Node binary by its sha256 and version. One that is pending, blocked, failed, not run, absent, recorded twice, malformed, stale or for another host or binary keeps the stage withheld, pending, with that reason, whatever authority is given, and the run is blocking. A maintenance (B35) run, which is judged by the earlier gate's stage list, needs both as well (the security review's GDR6-REQ-01 on the sixth round, which let it start on `test-host` alone): no kind of run is exempt, and an absent record withholds the stage as a bad one does. So a gate started on Node 24, whose run of a manifest that needs Node 26 blocks at `runtime-identity` (below), starts no test stage at all. `test-host` requires Linux or macOS, a user other than root and, on Linux, `setfacl`. Each full-test stage records its Node version, the real path and sha256 of the Node binary and its run code, and seals its records folder as one file beside its log (only the files the harness writes are accepted). Packing and every reader of a pack (unpacking, and so the finalizer and the commit guard) validate its entries with one shared validator, `scripts/security-entries.mjs`, and one fixed profile, `record-pack` version 1 (maintainer decision 3; v4 C21, C24): at most 8,192 files, 8,192 directories (each counted once, listed or implied by a path), 16,384 entries and 40 MiB; paths of at most three segments (the starting bound the security review of v3 accepted, because the harness's names allow no deeper path; not yet frozen) and at most 84 bytes (the longest path those names allow); relative, normalised NFC paths without control characters or backslashes; only regular files and directories (no link or other type), files only with the extensions the harness writes (`.jsonl`, `.tap`), each with its declared size and sha256; no path twice, none that differ only in letter case, and no file where a folder is. The pack (schema 2) names its profile's name, version and sha256 (of the canonical JSON of the profile's definition and the validator's name, version and module sha256, so a producer and a consumer with different validator code name different profiles); a reader takes the profile it expects from its own code and refuses a pack that names another profile, version or digest, a schema 1 pack (which names none), and any unknown member, so an artifact cannot choose a looser profile. The pack's decoder is bounded: it reads the bytes once, from the start, and stops at the first entry over a count, at a path longer than 84 bytes and at a file's base64 longer than the remaining byte limit, so a pack of millions of entries is refused a few hundred kilobytes in instead of being parsed whole. Packing checks the limits folder by folder before it reads inside one, and unpacking checks the whole pack before it writes anything (v4 C21; security review GD-02). The approval of a candidate with the platform manifest binds the profile its packs were read with (`recordPack`: its name, version and sha256) with the platform evidence, so the commit guard, which judges that evidence again with its installed validator, and `--verify-commit` refuse an approval naming another. The catalog (version 2 of its format) names and binds the profile too (`recordPack`: its name, version and sha256, v5 C21 and C24): packing, every reader of a pack and the finalizer refuse to work when the installed catalog binds another profile than the installed validator's, and the gate identity's `closureSha256`, once the trusted bootstrap computes it, covers the validator module. The decided counts approve no path, depth or byte bound and no workload fit; those stay pending review (the catalog's `record-pack-bounds`). The captured evidence archive will need a stricter profile of its own; its proposed limits are pending, and its parser is not in this tree. The Git-export provenance-comment header (v4 C24) is a narrow rule of the gate-export parser, not part of any shared profile. `platform-coverage-current-runtime` (and `-minimum-runtime`) then runs `checkCoverage` for this host's full run of the manifest (the one non-container run on this platform that runs every file: `linux-full` on Linux, `darwin-full` on macOS) with the candidate's tracked test files, and `checkContainerEvidence` for the container runs it hosts: so the T8 driver's `ok` line is required and a result line naming a test of the run inside blocks, at any depth. While `images.26` is `null`, this stage blocks on every Linux or macOS full run, naming the missing Node 26 container evidence.
- **Runtime identity.** `runtime-identity` needs, for each Node binary a test stage ran, a record at `<git common dir>/orbit-security/runtime-identity/<binary sha256>.json`: its version, platform and architecture, and either `"distribution": "nodejs-release"` with the release archive (exactly `node-<version>-<platform>-<architecture>.tar.gz` or `.tar.xz` for that binary), the `SHASUMS256.txt` and signature hashes, the signer's key fingerprint, the isolated keyring's hash and `"outcome": "verified"`, or `"distribution": "homebrew"` with the formula (`node`, or `node@<major>` of that version), the formula version of that Node and the bottle hash, and a reviewed `exception`. A Homebrew build is never described as signed by the Node release keys. A Node release record's signer must be one of the reviewed Node release keys, and its keyring that list's keyring: `<git common dir>/orbit-security/runtime-identity/release-keys.json`, `{ "schemaVersion": 1, "keyringSha256", "fingerprints", "source", "sourceSha256", "reviewer", "reference", "reviewedAt" }`, which the gate seals with the run. Absent, invalid and unavailable outcomes block. `runtime-identity` runs before the test stages, on the runtimes they will run (v5 C23 puts `test-host` and `runtime-identity` before the full-test stages), and each test stage records the binary sha256 found then. A run of the manifest that needs a runtime no test stage of the run runs blocks there: start the gate with Node 26 and set `ORBIT_SECURITY_NODE24`, since a gate started on Node 24 runs one test stage and its run lacks Node 26. A maintenance (B35) run, which has no manifest, records `runtime-identity` too, for exactly the runtimes of its approved slots, the gate's own Node plus the configured Node 24 executable when that executable is different, and is asked for no other. The finalizer and the commit guard require of a maintenance run that `test-host` and `runtime-identity` passed before its test stages, that each test stage ran its slot's Node (the gate's own, or Node 24), and that `runtime-identity` lists that binary with a sealed record that holds for it; a maintenance run without them, as the earlier gate wrote, is refused. One approved B35 plan (`MAINTENANCE_PLAN` in `scripts/security-platform.mjs`) names every stage a maintenance run may record, with its execution class (record-only, a gate-owned command, a lint stage or a test slot): a stage it does not name, a command or test evidence under a name it records without one, and a test execution outside its two slots (a `platform-tests-*` stage, say) are refused, and the host and runtime check applies to every test execution the record shows, not only to stages named `full-tests-*`. Each stage record may hold only the members of its class's record form and the data its own check records (`MAINTENANCE_RECORD_FORMS` and `MAINTENANCE_STAGE_DATA`), so `steps`, the 1.5 gate's composite form, and a member no producer writes are refused, and so is any record shaped as a stage record nested inside one, a test execution nested in a stage among them. What each member holds has a closed schema at every depth (`MAINTENANCE_MEMBER_SCHEMAS` and `MAINTENANCE_STAGE_DATA_SCHEMAS`, the forms the gate and the fixtures write: `test-host`'s `host` is exactly `{ platform, uid, setfacl }`, say), so an unknown member nested anywhere, or a value of another shape, is refused whatever its name (GDR8-SCHEMA-01). This schema is a proposed shared interface, not an accepted one: the maintenance branch's own gate must still be shown to write exactly these forms, and a field a producer needs takes an explicit schema change with tests for and against it, never an open extension object. These checks read only the sealed run, so `--verify-commit` and the `reference-transaction` hook apply them again before a recorded maintenance approval gives authority over a new commit: an approval recorded under earlier rules for a run they now refuse gives none, and its evidence is kept as it is. They also judge again the stage results the finalizer requires and the sealed run shows (no pending or failed stage, none blocked but a scanner that reported findings, and a test stage's totals those of its log); each scanner's sealed report as the finalizer does (the report sealed and parsed, its findings worked out from it, and report, findings, exit and status in agreement), with the findings it gives bound to the approval's count and to the retained review's dispositions, one each (GDR8-AUTH-SCAN-01), and a scanner recorded as pending counting as one only when it has a reason and ran nothing, by the finalizer's own rule; a maintenance run's sealed coverage dispositions as the finalizer reads them; and the lint stages the commit's own `package.json`, its parents and their history require, which they derive from the commit as the commit guard does for its candidate, never from the checkout or a caller (GDR8-AUTH-LINT-01). They do not ask freshness again, and they are not every check of the finalizer. Still open, under the containment and trusted-bootstrap holds: these checks compare a test stage's runtime with the gate's own earlier observation, since the gate hashes each runtime once, by its real path, and then starts the test stage by its configured path, so a binary or link replaced between the hash and the start is not caught.
- **T8 images.** The gate starts `t8-image-identity`'s `docker image inspect` only with the pre-dispatch barrier open (the images are named by the candidate's manifest) and an authority for that inspect (its reviewed Docker stage policy, a qualified endpoint and the T8 operational hold lifted), and nothing gives that authority in this draft: the stage is withheld before dispatch, nothing is inspected, and `t8-image-authenticity` and `t8-image-activation` stay pending with nothing to check or bind (above). What follows is what happens once the inspect is dispatched, as the tests check with a synthetic authority. Where the run hosts a container run with a pinned image, `t8-image-identity` runs `docker image inspect` on each such image (a local query; nothing is pulled), and `t8-image-authenticity` checks each pinned image against `<git common dir>/orbit-security/image-authenticity/<index digest>-<os>-<architecture>[-<variant>].json`: the exact pinned image and index digest, the platform Docker reports, its platform manifest and config digests, and `"outcome": "verified"` with the publisher identity and trust root, or `"exception"` with a reviewed disposition. Other outcomes block. The record carries the exact bytes of the image index (`indexBase64`) and of the platform's image manifest (`platformManifestBase64`), and neither digest is taken on trust: the index must hash to the index digest and have exactly one image manifest entry for the platform Docker reports, that entry's digest must be the platform manifest digest, the manifest must hash to it, and the config it names must be the config digest. The image ID Docker reports must then be the index digest, as with Docker's containerd image store, or that config digest, as with the classic store. Even then the stage is pending, not pass: an authenticity record is evidence, not authority to run the image, which needs a reviewed activation record (security review IP-01; v3 C5), and none exists; an image ID equal to the index digest is also unverified (what the containerd store reports, v3 C17 item 4). GATE-CONTRACT v5 places `t8-image-identity` and `t8-image-authenticity` in phase N, before `container-build`, `systemd-test-image` and every other candidate-controlled build (which run the RUN steps of the candidate's own Dockerfiles; the Uptime Goblin Dockerfile's base is the pinned T8 Node 24 image), and adds `t8-image-activation` in phase O, before `sql-lint`, `import-lint`, every other stage that runs candidate code and the first use of the T8 image (the test stages, where the T8 driver runs it). This draft runs both phases as one local run: the gate runs the three stages one after the other right before `sql-lint` (a companion whose run hosts T8, before its test stages). `t8-image-activation` runs nothing and claims no authenticity: it seals `t8-image-activation.json`, its binding of the images to the two N records (the run, the candidate identity, the gate identity, the catalog, the run's platform, a consumer `t8-driver` and a purpose `t8-container-tests`, each N record's times and the sha256 of its sealed evidence, the images Docker described, and no result record, since no T8-related image is built here). That form is this draft's proposal for the maintainer: v5 leaves the exact forms of all three records pending, so all three stages are recorded pending, also when nothing is wrong, and the finalizer refuses any of them recorded as passed. A gate run that hosts no pinned image records all three as pending, with that reason. After the tests, every T8 container record must name an image observed there, with the image ID Docker reported then. The finalizer refuses a run whose `t8-image-identity` does not end before `t8-image-authenticity` starts (an inclusive handoff: equal times are accepted, any overlap is not), judged on both stages' recorded times, whatever order the record lists them in (GDR3-01, v5 change 18), whose T8 stages do not end before either build would start or before any stage that runs candidate code starts, or end after `t8-image-activation` starts, or whose activation does not end before `sql-lint`, `import-lint`, `format`, `syntax-manifest`, `documentation` or a test stage starts. Within the finalization's `image-approvals` obligation it rebuilds the activation's binding from the sealed run and refuses one that differs in any part, lacks a member, binds records that overlap, or holds anything else (an `outcome`, say, even with the value `null`); a consistent binding still leaves the stage, and the obligation, pending. What `docker image inspect` prints on the gate's host, its variant field included, has not been checked here.
- **Network (Linux).** The gate reads the file named by `ORBIT_SECURITY_NETWORK_STATE`, kept by the egress control outside the VM, right before and after each test stage, and `network-policy` requires: phase `test`, enforcement `outside-guest`, the same policy hash, counter epoch and counters (none lower) before and after, snapshots observed before the stage started and after it finished, and a reviewed policy record at `<git common dir>/orbit-security/network-policy/<policy sha256>.json`. It records; it changes no network setting. Its record is marked diagnostic: a reading can block, but none stands in for the controller's own observations, which v3 C13 makes the isolation authority.
- **Companion runs.** `node scripts/security-gate.mjs platform <run-id>` runs one run of the manifest on this host (its platform must be this host's), for the same staged tree: `candidate-policy` (without the CHANGELOG and release rules, which belong to the gate run), `platform-manifest`, `test-host`, the run's test files on the current runtime and Node 24, their coverage, the runtime check (and the image and network checks where its run hosts T8 or runs on Linux), and `candidate-unchanged`, then it seals the run in `orbit-security/<tree>-platform-<id>`. Its stages are the catalog's `darwin-platform` array; its snapshot and npm install are steps of one `prepared-inputs` stage, which stays pending because v3's prepared inputs come from the gate run's network phase (its npm install and its test stages are withheld before dispatch, as the gate run's are), and its `gate-identity` and `gate-import-closure` stages are pending as the gate run's are. No scanner runs there. On a Linux gate run the manifest requires `darwin-platform`; on a macOS gate run, whose `darwin-full` covers `darwin-platform`, it requires `linux-full`. A run made on another machine is copied into the same `orbit-security` folder first.
- **Finalization and the commit guard.** Name each companion run's folder after the run's (and the review's), as in `node scripts/finalize-security.mjs inspect /absolute/private/run-directory /absolute/private/companion-run-directory` and `node scripts/finalize-security.mjs finalize /absolute/private/run-directory /absolute/private/review.json /absolute/private/companion-run-directory`. Each must be beside the run, sealed, with nothing added after sealing, of the same tree, complete parent vector, candidate identity and file manifest (its refs are recorded, not compared, since another clone has other refs), on its run's platform, not as root, with the candidate's tool configuration, started at most 24 hours ago and finished by now (by its own host's clock: a companion host whose clock runs ahead gets a longer window by that much, and nothing compares the two hosts' clocks; v3 C22 asks for trusted intervals instead, which this draft has no source for, so a companion's evidence stays pending), every stage inside its times and passed or pending, exactly its catalog array, its totals and coverage recomputed from its sealed logs and records, and the same manifest judgment. The run's own coverage, runtime, image and network checks are made again from its sealed copies too. Every required run needs exactly one covering run; a missing one blocks (an absence is never a pass), and an unneeded or repeated one is refused. `inspect` prints the platform summary and its sha256 (`platformSha256`), which the review must name; the approval binds the summary, listing each run's stages and totals separately, never added together. The commit guard works the requirement out for every commit from the candidate's bytes and its history, reads the companion runs the approval names, and checks everything again now, so a stale, changed or missing companion run, or a new tree or another parent vector, approves nothing: a finalized candidate followed by a merge that keeps its tree and adds a parent is refused (security review GD-R1). While Git runs the guard for an automatic merge, whose other parents it cannot see, every candidate is refused, maintenance included (merge with `--no-commit`, then run `git commit`, which the guard judges with every parent).
- **The catalog.** `scripts/security-catalog.json` holds GATE-CONTRACT v5's C23 arrays as canonical JSON: the stages of a Linux gate run (`linux-full`: N, 28 stages with `t8-image-identity` and `t8-image-authenticity`; O, 25 stages with `t8-image-activation`), of a `darwin-platform` companion (14), the F obligations for commit (12) and release (22), and the scanner lists (9 and 14), the last four unchanged from v3. It names the contract it comes from (v5's sha256) and the maintainer's decision on change 19, binds the record-pack profile (above), and lists what stays pending (each entry's evidence contract, the `darwin-full` array, the order rules that need records this draft does not make, the exact T8, pre-build authority, result and activation record forms, the record-pack bounds, each scanner's record contract). Binding the profile needs a member the earlier form lacked, so this draft numbers the catalog's format version 2 and refuses version 1: that is this draft's proposal for the maintainer, since v5 C1 says the catalog's format does not change. `scripts/security-catalog.mjs` refuses a catalog that is not canonical, names no version or another one, names another contract or decision, holds an empty or repeated list or an id that is not one, a release list narrower than commit, or v4's placement (a T8 identity or authenticity stage, or a build, in O; no `t8-image-activation`; one of the stages v5's order rules name missing from its phase), and one whose seven arrays are not exactly v5's, entry for entry and in order (the module holds its own copy of them). A catalog with v4's arrays, or a run bound to an earlier catalog's sha256, is therefore refused. The gate identity stays version 3 (v5 C1); the catalog's content and digest change, as v5 says, and so does its format number (the proposal above). The gate records the catalog's sha256, the mode and its profile (`linux-full` on Linux; a macOS gate run has no reviewed array), reports the catalog's stage ids (`sast-rules` with its download, checksum and extraction as steps; `sast-image` as `docker image inspect`, without a pull; `gate-implementation`), and records each id this draft does not implement as pending with the reason: `gate-identity` and `gate-import-closure` (the trusted bootstrap), `pristine-copy`, `image-approval`, the three T8 stages, both image builds, `container-identity` and the two scans of the built image (below). A run that is not all pass exits 1. For a candidate with the platform manifest, the finalizer chooses the mode, the profile and the catalog itself and compares each with what the run records (the security review of v3): the mode is `commit`, the catalog is the installed one, and the main profile is the one profile with reviewed N and O arrays that the candidate's judged manifest declares as a full run (`linux-full`), never the run's host or its catalog binding, and the platform of each catalog profile is the finalizer's own (`linux-full` on Linux, `darwin-platform` on macOS; a proposed table in `scripts/security-catalog.mjs`, since the catalog file names no platform), not the one the candidate's manifest declares: a manifest that declares one of them on another platform is refused, and a gate run on another platform is refused as not the run it selected. Each companion's profile is a run of the manifest that covers a run the candidate still needs, which the finalizer works out itself; a companion of another run is refused. It refuses a run that misses, repeats or adds a stage, reports an earlier name (`sast-rules-download`, `sast-image-pull` and the like) or records another catalog, mode or profile; a pending stage leaves the verdict pending. One single-phase run stands for both phases here: the separate N and O records, with the grant between them, are the controller's lane and pending.
- **Order (v5 C23).** The finalizer checks the order rules of v5 that a run's records can show, on the stages' recorded times, for a gate run and, by the rules v5 proposes by analogy, for a companion run: each stage a rule names needs a start and an end, well formed (a real calendar date and time), inside the run's own times and the end not before the start, and "A before B" means A ends no later than B starts and is recorded before it. The rules: `candidate-policy`, `platform-manifest` and `pristine-copy` before `dependencies-install`; `image-approval` before both builds, the Semgrep run, the two scans of the built image and the test stages; the T8 rules (above); `platform-manifest` before either build (v5's change 19, a stricter rule that v5 added and the maintainer confirmed; no earlier round had it); `container-identity` directly after `container-build`; `sql-lint` and `import-lint` before the other stages that run candidate code; `test-host` and `runtime-identity` before the full-test stages; each coverage stage directly after its test stage; `candidate-unchanged` last. In v5 the end of phase N also orders every N stage before every O stage. This draft records both phases in one run, without that boundary, so it checks the part of it that change 19 and the companion-profile rule rest on: `platform-manifest` and `candidate-policy` end before every stage that runs candidate code (the two lints, `format`, `syntax-manifest`, `documentation` and the test stages, whose tests build images). The rest of what that boundary orders stays pending with the separate phase records. A stage's place in a catalog array orders nothing. Not checked, because they need records this draft does not make: each build's pre-build authority before its RUN steps, its result record sealed and checked before anything uses it, `systemd-test-image` checking its own result, and the trusted bootstrap's check before any stage. Neither catalog build starts instead (below). A stage withheld before dispatch is recorded in its place, with its time, so the rules hold for it too.

Preparing the pin's evidence is separate work; nothing here installs, downloads or runs an Actionlint.
- **Times.** Every stage of a gate run, as of a companion run, needs UTC start and finish times that name a real calendar date and time (31 September or hour 24 is malformed, although JavaScript's date parser would roll it over to the next day), inside the run's own, finishing not before it starts (security review GD-R3); a run started more than 24 hours before the check is stale (the ceiling is inclusive: a run of exactly 24 hours is inside, as the security review of v3 accepted), and every shorter bound, such as the scanner database's expiry and the review's, is still enforced on its own, the earliest winning. These are the gate host's own clock, and so are the times the order rules (above) are judged on: v4 and v5 C14 want trusted Mac times, which belong to the Mac-side finalization.
- **Release runs.** `final-artifacts` is an obligation of the finalization's release array (v4 C14, C23; the security review of v3 accepts it there), not a stage of a run, and release finalization does not exist. A release run therefore records `final-artifacts` and the catalog's other release-only obligations (`sonarqube`, the Snyk and Clair scans, the Netxeo release review, performance validation, release platform coverage, signatures and provenance) as pending under `releaseObligations`, prints each, and ends `pending` with exit 1: `security:release` still fails closed. It records no `sonarqube-analysis` stage either, a name the catalog refuses: SonarQube is the finalization's `sonarqube` release obligation (v4 C15), recorded pending with the others, and `scripts/check-sonarqube.mjs` is run by hand ([Local SonarQube](#local-sonarqube)).
- **Before HEAD moves, and after a commit exists.** Git runs the commit guard before it decides the commit's parents, and `git commit --amend` gives the new commit the parents of HEAD rather than HEAD, which nothing a pre-commit hook sees reveals (verify-1 found the guard approving `[HEAD]` for an amend, and so a one-parent approval for an amended merge). The installer therefore also installs a `reference-transaction` hook (Git 2.28 or later). When the guard approves a commit as a hook, it records what it approved (the tree, the complete parent vector, the HEAD and the branch it was on, the finalization and its sha256) in `<git common dir>/orbit-security/commit-intents/<pid>.json`, keyed by the Git process running the hook. In the `prepared` state, after Git has written the commit object and before any ref moves, the hook reads that record for the same Git process, recomputes the commit's tree and parents from its own object, and requires exactly the approved tree and vector, in order, the branch moving from the approved HEAD, and a finalization that still verifies as below; it refuses any replace or commit-graph ambiguity (v3 C18 and its clarification). Anything else aborts the update: the commit object is left unreferenced and HEAD does not move. An amend is therefore always refused; make a new commit instead. Other ref updates (a fetch, a checkout, a rebase or cherry-pick, `git commit --no-verify`) find no record and pass unchanged, and the guard approves nothing as a hook unless the `reference-transaction` hook is installed. This relies on Git running the guard and the ref update in one process, as `git commit` and `git am` do in the Git tested here (2.54); local hooks remain bypassable. `node scripts/check-security-approval.mjs --verify-commit <commit>` (HEAD by default) makes the same check of an existing commit, for CI or the Mac-side finalization: it needs a finalization of exactly the commit's tree and vector that still verifies as recorded (schema 2, status `pass`, bound to its sealed run, the candidate identity record behind its digest and its retained review; with a catalog binding only for a candidate whose manifest is valid, and then the installed catalog with exactly its F obligations passed, the reviewed platform evidence and companion runs that still verify as sealed; without one only for a candidate whose history never held the manifest). It does not ask about freshness again: the guard checked that before the commit was made. Since the tenth round every Git read of the guard, the hook and `--verify-commit` goes to the repository at its root (`process.cwd()`, the top level a hook runs in; GDR9-AUTH-ROOT-01): an inherited `GIT_DIR`, `GIT_WORK_TREE` or `GIT_COMMON_DIR` must name that repository, as Git's own hook environment does in the main and in a linked worktree, and another one is refused rather than followed; so are an object source other than the repository's own receive-pack quarantine, a `GIT_NAMESPACE` and, for the guard, an index other than the repository's `index`, `index.lock` or `next-index-<pid>.lock`. Since the round's corrective pass an alternates file that names another object store, in the repository's object directory or in its quarantine, is refused too (an empty one, or one of comments only, names none; since the eleventh round its records are read byte for byte as Git reads them, so only an empty record and one whose first byte is `#` name none, and a record that only looks like a comment or a blank once trimmed, a quoted path or a path ending in a carriage return refuses, GDR10-ALT-PARSE-01), and the root is canonicalized with the operating system's `realpath`, so on a case-insensitive file system a root spelled in another letter case binds the same repository at every entry point. Injected Git configuration (`GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`) is not passed on.

These are local consistency checks, not signatures: code a stage runs can still write a forged record, as it can forge the gate's logs, so review remains the control there.

### The private historical qualification

The published source tree holds no history of the project: no release tags, no commit ids and no map of how commit ids were rewritten. The tests that start from that history (the 1.4.2 fixture's provenance check, the export tool's tests, and the upgrade, installer, sign-in and web app tests that start from 1.4.3 or a 1.5 development milestone) read it from a private input that `TEST_HISTORY` names: a JSON file, kept with the private validation corpus and never committed, in the form `test/upgrade/history.mjs` describes. It names the repository that holds the history (a Git repository, or a Git bundle that is cloned once into a temporary folder), the commit ids of the milestones `1.5.0-dev.0` and `1.5.0-dev.1`, the tag and commit each checked release fixture was built from, and the reviewed rewrites of recorded commits with their trees.

Run it as a required job, so that a missing or wrong input fails rather than skips:

```sh
TEST_HISTORY=/absolute/private/path/history.json TEST_REQUIRE=browser,fixtures,systemd,docker,capacity,git,history \
  node --test --import ./test/setup.mjs --test-concurrency=1 "test/**/*.test.mjs"
```

With `history` in `TEST_REQUIRE`, a missing `TEST_HISTORY`, a repository without the tag or milestone, a recorded commit the tag does not name, a rewrite the input does not list and a rewrite whose tree differs all fail. A `TEST_HISTORY` that cannot be read or does not have exactly the input's form fails every test that reads it, with or without `TEST_REQUIRE`. Public CI has no such input and does not list `history`, so these tests skip there; that skip is not a qualification. The public tests in `test/upgrade/fixtures.test.mjs` check the same provenance logic on a synthetic repository, tag and rewrite list: the exact recorded commit, a listed rewrite with the same tree (also from a bundle), a missing mapping, a wrong commit, a wrong tree, changed files and a missing, unreadable or malformed input. For the git-less Node 24 run, export the history's trees on a host with the input (`test/upgrade/export-tag.mjs`, whose header shows the run).

### Capacity benchmark (audit log, 1.5)

The audit spec's capacity gate (§9.3, §11 item 12) is elapsed time: Check integrity on 250,000 rows finishes within 60 seconds, and no synchronous read unit holds the event loop for more than 250 ms. `test/audit/capacity.test.mjs` judges each unit by the wall clock in two ways, and both must be within 250 ms. The first is the check's own time for the unit, which this test has always gated: from just before the unit's read until the check has its result, so it includes anything that runs synchronously once the read resolves, before the event loop gets a turn. The second times every attempt at a read unit on its own, including the first unit (the log's ends, head and checkpoints) and each attempt SQLite makes again after `SQLITE_BUSY`. The test prints this thread's CPU time, the CPU time of the process's other threads and, on Linux, the thread's wait for a core beside each wall time. These are diagnostics only: none is subtracted from the wall time, and none turns a failure into a pass. A unit blocked for 324 ms uses about 0.2 ms of CPU, so a CPU-time gate would pass it; this one fails it. Three tests in the same file run in every test run. They check that a unit blocked for 320 ms, or computing for 300 ms, fails the gate on its first attempt or on a retry, and that a unit whose read is quick but which then blocks for 320 ms before the check has its result fails too.

Wall time also measures the machine. The normative run is therefore the test file alone, in the Node 24 container with fixed limits, on a quiet machine. Its limits, 4 GiB of memory, 4 CPUs and 1,024 processes, are those of the Node 24 gate's container (sessions spec §12 item 3), above the 1 GiB, 2 CPUs and 256 processes most test containers get, because the measurement is of that container. They come first, right after `docker run`, as in every `docker run` these documents give, and `--pull=never` runs the image you recorded rather than pulling one:

```sh
docker run --memory 4g --cpus 4 --pids-limit 1024 --memory-swap 4g \
  --rm --pull=never --network none --user node -e HOME=/tmp \
  --tmpfs /ktmp:rw,exec,size=1g,mode=1777 -e TMPDIR=/ktmp -e TEST_REQUIRE=capacity \
  -v "$PWD":/src:ro -w /src node:24-bookworm-slim@sha256:<recorded digest> \
  node --test --import ./test/setup.mjs test/audit/capacity.test.mjs
```

1. **Quiet machine.** From before the run until it ends, nothing else on the machine runs a test, build, scan, benchmark, load generator or injected pause. This covers the host and, with Docker Desktop or OrbStack, its VM. Just before the run starts, the 1-minute load average is at most a quarter of the logical CPUs, on the host and in its VM. This is checked before the run only: once the run starts, its own load raises the load average. Idle services may stay running; record them.
2. **Before the run, record** the candidate's tree ID, the image digest, the Docker version, the machine (model, logical CPUs and memory), its load average and the running containers.
3. **During the run, monitor from outside the container.** Every 5 seconds, log the host's load average, its busiest processes with their recent CPU use (not a lifetime average, which is what `ps` gives on Linux) and each container's CPU use, and keep that log with the run. Each CPU reading records the interval it covers, with the reading itself: it is the change in a cumulative CPU counter between two recorded times (for a process on Linux, `utime` and `stime` in `/proc/<pid>/stat`; for a container, `usage_usec` in its cgroup's `cpu.stat`, or the Docker stats API's `preread` and `read` times with its CPU totals). A sample's own time stamp is not the interval of its readings, and another reading's interval is never borrowed: a reading recorded without its own interval has none. Each reading, start and stop also names the workload lifetime it belongs to, not just a pid or a name: for a process, the pid namespace it was read in (the host's, the VM's or a container's), its pid and its kernel start time; for a container, its ID and its `StartedAt` (a name can be reused, and a restarted container has a new `StartedAt`). A reading is the change in one lifetime's counter: at both reads the monitor checks that the pid still has the same start time, or the container the same ID and `StartedAt`, and if either changed, there is no reading. The monitor records each lifetime it reads or sees, and when each outside workload it sees started and stopped, where that is known, and from what. Only a process's kernel start time (`/proc/<pid>/stat`, `ps -o lstart`), a time by which it had exited (as its waiting parent recorded it, or a sample in which that lifetime, by pid namespace, pid and start time, was gone), and `docker inspect`'s `StartedAt` and `FinishedAt` bound a counter's activity, and each bounds only the readings of its own lifetime. A workload's own log, or when a poller first or last saw it, is kept but never narrows a reading. Every time is written with its zone (`Z`, or an offset such as `-05:00`), to the millisecond at most, and names the clock it was read on. For each clock, record its offset from the test's clock and the most that offset may be wrong by. The test's clock is the one `from` and `to` are read on: the container's, so with Docker Desktop or OrbStack the VM's, while host `ps` readings are on the host's clock. Measure each offset before and after the run: read the clock (t1), read the test's clock in a container on the same machine or VM, and read the clock again (t2), each of the three to the millisecond (for example with `node -p 'new Date().toISOString()'`, on the host and in the container; a `date` that prints whole seconds, as `date -u +%FT%TZ` does, is not enough). The offset is the midpoint of t1 and t2 minus the container's reading, and it may be wrong by half of t2 − t1 plus the resolution of each of the three readings (1 ms for a reading to the millisecond; a reading to the second adds a whole second). Record an offset and error that cover both measurements, so any drift during the run, widened by the resolution of the times written on that clock (a whole second for `ps -o lstart`). The test's `capacity: machine` and `capacity: verify` lines add what it saw: its cgroup limits, the load average, when the verification started and ended (`from` and `to`, whole milliseconds read down from its clock), and the diagnostics.
4. **Keep every run.** Number the runs in order and keep failed and invalid ones with their logs and monitor records. No run is discarded, overwritten or replaced by a later one.
5. **Rerun only for contention placed within the verification.** A failed run may be rerun only when the monitor's records, or other records made outside the test, place contention from outside the run within the verification: between the `from` and `to` of `capacity: verify`. A reading places its activity there only when its own interval, moved onto the test's clock by its clock's recorded offset and widened on both sides by the most that offset may be wrong by, then narrowed to the recorded start and stop of the workload lifetime it measures (only records of that same lifetime, from the sources step 3 lets bound it, each moved and widened the same way), lies within `from` to `to`. Since `from` is read down to the millisecond, the window starts 1 ms after `from`. A workload's recorded stop before `to` can narrow a reading that spans `to` into the verification; a recorded start after `to` puts it outside. A reading that names no lifetime is not narrowed. When the records name more than one lifetime for a reading's pid in its pid namespace, or for its container ID, or two starts or two stops for its lifetime from those sources, they are ambiguous and narrow nothing: the reading's own interval must then lie within the window. None of these is such a record on its own: a sample taken after `to`, the first one included; a reading whose interval, moved and widened, reaches before `from` or after `to`, a reading spanning the end included, since all of its activity could fall outside the verification; a reading whose interval was not recorded with it, such as a sample with only its own time stamp (another reading's interval is never borrowed); a time without a zone, or a time on a clock with no recorded offset; a start or stop from the workload's own log, or from when a poller first or last saw it; and a start or stop of another lifetime: the same pid in another pid namespace, or in an earlier or later lifetime of that pid, another container that had the same name, or another run of the same container. Contention here is (a) another container using a core or more; (b) a host process using a core or more, other than the run's own: its container's processes, the `docker` client that started it and, with Docker Desktop or OrbStack, the VM process that carries its container; (c) that VM process using a core or more above the run's container, both read over the same interval on one clock; or (d) anything step 1 rules out, other than the run itself and its monitor, placed within the verification in the same way. Ambiguous, late or missing evidence leaves the failure standing. The run's own load never counts. Nor does the load average during the run: it includes the run's own load (one runnable thread lifts the 1-minute load average by about 0.6 in a minute), so a run that started within the bar of step 1 could cross it on its own. Mark that run invalid, citing the records, and rerun under this same procedure. After two invalid runs, report to the maintainer instead of rerunning. The test's own figures (its CPU and scheduler times, and the load averages it prints) never count as that record. Without such a record, the failure is the result. Contention only lengthens wall time, so a pass under contention is still a pass; record it as such.

Runs elsewhere apply the same limits and are kept as evidence. Examples are local Node 26 on macOS and the full test runs, where `capacity` in `TEST_REQUIRE` runs this file beside the other test files. A failure there fails that run, but only the normative run decides §9.3. The maintainer recommends keeping timing separate from the parallel functional tests. Until a separately reviewed integration makes the normative capacity stage mandatory, the full runs that set `TEST_REQUIRE=capacity`, the gate's full runs included, keep it, and this file stays mandatory in them. Nothing is removed from the full gates before then.

### Evidence tied to the candidate

Validate an immutable snapshot of the staged candidate, not a working directory another process can change. Keep evidence outside the publishable source unless it has been deliberately sanitized. Each gate record must include:

- Repository identity, base/parent commits, candidate Git tree ID, and the complete tested file manifest with content hashes and file modes. Record fixture/tag provenance and the gate configuration too.
- UTC start/end times, exact commands and relevant non-secret options, required suites, OS/architecture, Node/npm/browser/container/scanner versions, scanner rules and vulnerability-data timestamps.
- Exit status and separate totals for passed, failed, skipped, cancelled and todo cases; logs, finding dispositions and the independent review reference. Missing evidence is marked missing, not reconstructed as though captured at launch.
- The resulting commit ID and confirmation that its tree equals the validated candidate. For a release, also bind the archive checksum and container digest to that source.

Any candidate change after validation, including a documentation edit, invalidates that candidate's gate. Restage, rerun and review the resulting tree before committing. A merge result needs its own evidence; green parent branches do not validate their combination.

The 3,688-item [rule inventory](security-rule-matrix.md) is coverage accounting, not evidence that each rule passed. The commit guard is installed once per Git common directory and serves every linked worktree, so the maintenance and 1.5 worktrees of one repository run the same checker. The installed copy is the maintenance checker, which never requires the lint stages, so today it does not enforce them on 1.5 commits. The ported checker takes the lint requirement from the branch instead: it requires each lint stage whose script the staged `package.json` defines, or a parent of the commit or any commit behind them defined, so one copy checks a maintenance candidate (no lint script anywhere in its history) and a 1.5 candidate (both) correctly. The parents are HEAD and, while `git commit` concludes a merge, each `MERGE_HEAD`; history counts because `git revert`, `git cherry-pick` and `git rebase` run no pre-commit hook and a fast-forward moves a branch without one. An automatic `git merge` or `git pull` runs the guard before Git records the commit it joins, so the platform contract's draft refuses it outright, for every candidate (its complete parent vector is not known there: merge with `--no-commit` and then run `git commit`); the lint rule alone would require both lint stages there, as it does when the candidate or a parent has no `package.json` or one that is not in canonical form (the form `candidate-policy` requires, which cannot hold a duplicate member). The guard recognises an automatic merge by `GIT_REFLOG_ACTION`, which `git merge` and `git pull` give their hooks but keep, whatever its value, when it is already in the environment (`git commit` and `git am` give their hooks none), so it counts any `GIT_REFLOG_ACTION` while no merge is being concluded: a plain commit made with that variable exported, by a shell profile, a wrapper or a Git front end, needs both lint stages too. Older versions in the history count as JSON.parse reads them, so an ambiguous old version (well formed, but not in canonical form) cannot block a branch for good; since the tenth round's corrective pass one that is not well formed blocks, as below. A version whose `package.json` Git records but cannot read blocks instead, because its object is missing from the repository (a partial or damaged clone) or because it is a submodule: read as no `package.json`, it would hide a lint script that only that version defined, and its removal. Fetch or repair the missing objects; a version that has no `package.json` defines neither script. Since the tenth round every version, the candidate's and its parents' included, is read from its tree entry first and by its type (GDR9-AUTH-OBJECT-01): only a tree with no `package.json` entry has none; a missing or unreadable object, a directory, a submodule (also one whose commit is readable), a symbolic link, a file over 16 MiB, a file whose content is not well formed (since the round's corrective pass: not UTF-8 text, not JSON, not a JSON object, or a `scripts` member that is not an object) and any lookup error block, so a branch whose history once recorded `package.json` as anything but a regular, well-formed file cannot be approved by this guard. No read of the guard, `--verify-commit`, the `reference-transaction` hook or the gate's own Git runner fetches a missing object from a promisor remote (`GIT_NO_LAZY_FETCH=1`; Git 2.44 or later, and with an older Git a repository with a promisor remote is refused): fetch it yourself first. Since the eleventh round no stage of the gate does either (GDR10-AUTH-STAGE-01): every process the gate starts gets an environment with no inherited Git selector, no injected configuration, no Git configuration, attributes or ignore file chosen by your environment (since the round's corrective pass: `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` are `/dev/null`, `GIT_CONFIG_NOSYSTEM=1`, and `core.attributesFile` and `core.excludesFile` are `/dev/null`, so nothing under `HOME` or `XDG_CONFIG_HOME` is read either, but for a file that a `~/` include in the configuration of the repository a stage reads names: the history secret scan's Git reads the repository's own configuration, where such an include is resolved against your `HOME`, and its log options win over the settings measured) and `GIT_NO_LAZY_FETCH=1`; its snapshot is cloned with that environment alone, the snapshot's own steps are bound to the snapshot, and its history secret scan reads the repository the gate's binding validated. Since the twelfth round the gate's own reads and every authority read follow that policy too (GDR11-AUTH-CONFIG-01), with settings on Git's command line that win over the repository's own configuration: no fsmonitor (`core.fsmonitor=false`), Git's own output encoding (`i18n.logOutputEncoding=UTF-8`), no signature check in `git log` (`log.showSignature=false`) and each filter driver the repository defines switched off. Since the round's corrective pass those switch-off settings are given in Git's `'key'='value'` form, which keeps a driver named with `=` whole (the `'key=value'` form split it at its first `=` and left it on) and takes a driver with an empty name too; no hook runs for a bound read (`core.hooksPath=/dev/null`, for every read but `git rev-parse`, which runs none and is asked where the hooks Git runs are, and `hook.<name>.enabled=false` for each hook the repository's configuration defines); and the binding's `HOME` names no folder, so a `~/` path in the repository's own configuration names no file your environment chooses. A repository whose own configuration defines a filter driver or a hook needs Git 2.31 or later for those settings, and with an older Git it is refused (not measured). A submodule's own configuration is not switched off: the release check's `git status` would start a filter driver a submodule defines, but the gate refuses a candidate that holds a submodule before that check. The history secret scan's Git command is given `--all --root --text --no-textconv --no-ext-diff --no-color` with Git's default output form set (`--encoding=UTF-8 --pretty=medium --date=default --no-decorate --no-abbrev-commit --no-show-signature --no-notes --src-prefix=a/ --dst-prefix=b/`), so neither the repository's attributes (a committed or untracked `.gitattributes`, `info/attributes`, a binary diff driver, a text converter) nor its own configuration can hide content from the patches it shows (GDR11-HISTORY-ATTRS-01); a merge shows no patch, so content that only a merge introduces is in none, and `mailmap.file`, `core.quotePath=false` and `diff.renames=false` still change header bytes (the author line, a path's quoting, a rename's headers), though no content. The metadata secret scan reads every commit and tag object raw (`rev-list --all`, then `cat-file --batch`), each checked by type, size and hash, with the enumeration checked for every parent, ref, HEAD and tag of a tag; a missing or incomplete object, or one holding a NUL byte, blocks that scan instead of shrinking its input, and since the corrective pass so does a commit whose `encoding` header names anything but UTF-8, US-ASCII, ISO-8859-1 to -16 or Windows-1250 to -1258 (in UTF-7, ISO-2022-JP or HZ, Git shows ASCII text that the stored bytes do not hold). These inputs are measured with Git 2.54 and stand-ins only: the pinned Gitleaks 8.30.1 has not run on them, so its qualification on them is still to come. A repository that another user owns is refused by Git's own ownership check, since no `safe.directory` is honoured from any configuration file (not measured with a genuine other owner). A candidate that removes or renames a lint script that a parent or the history behind it defines is refused whatever its record says, so a candidate cannot drop the script and its gate stage together, rename the script now and drop the stage in a later commit, or drop them in a merge (a merge concluded with `git commit` is held to the scripts that every parent and its history define). The guard judges that removal by what JSON.parse and npm read in the candidate's `package.json`, whatever its layout (a second `scripts` member among them), and a `package.json` that is absent or has no `scripts` object defines neither script (since the tenth round's corrective pass one that does not parse is refused outright), so reformatting, breaking or deleting the file does not hide a removal. A commit made without the guard (with `--no-verify`, or by `git revert`) can still remove the scripts, but the next guarded commit on that branch is refused until they are back, whatever pathspec options Git passes the hook (`git --literal-pathspecs commit` exports one) and whatever that commit or an earlier one put at `package.json` (a file that is not canonical, or nothing; since the tenth round a directory, a submodule or a link there blocks, and since its corrective pass a file that is not well formed, as above). Removing or renaming a lint script on purpose therefore needs a reviewed update of the installed checker (its list names `lint:sql` and `lint:imports`) and of the gate, not `--no-verify`. The checker, like the finalizer, also checks when started through a symlinked directory, with or without `--preserve-symlinks-main`, or a symlinked file without it, and does nothing when imported (see the finalization section below). The installer refuses to replace a differing checker or helper module, so adopting it needs one reviewed, deliberate replacement per Git common directory, and the maintenance branch must carry the same checker and the same `scripts/security-finalization.mjs` (its other two helper modules, `security-findings.mjs` and `security-evidence.mjs`, are already identical) so the installer agrees from either worktree. The platform contract's draft adds four more files that the installer copies beside the checker, `scripts/security-platform.mjs`, `scripts/security-catalog.mjs`, `scripts/security-catalog.json` and `scripts/check-platform-coverage.mjs`; the maintenance branch must carry those too. This `security-finalization.mjs` requires no lint stage of a caller that names none, but since its second round it refuses a caller that names no platform inputs, because the candidate identity needs the platform judgment, and it gives no authority to a finalization bound to a single parent: the maintenance finalizer therefore needs the same change as the 1.5 one (pass the platform inputs) before it can finalize anything with this module, and earlier maintenance finalizations do not approve a commit under this guard (see the finalization section below). The maintenance guard tests need one fixture change with this checker: the synthetic repository in maintenance's `test/security-finalization.test.mjs` has no `package.json`, so the checker requires both lint stages there, as it does of any candidate whose `package.json` is missing, and 3 of the 60 tests in that file fail (the hook acceptance test and the two symlinked-checker decisions; maintenance's `test/security-evidence.test.mjs` passes). Adding a canonical `package.json` without lint scripts to that fixture (`{"scripts": {}}`, formatted as `candidate-policy` requires) makes all 60 pass. The real maintenance `package.json` is canonical and neither it nor its history defines a lint script, so the checker requires no lint stage of a maintenance commit. The port did not install or change any guard.

Stage the complete candidate before running the gate. On a development runtime other than Node 24, set `ORBIT_SECURITY_NODE24` to an absolute Node 24 executable. On 1.5 that and, on Linux, `ORBIT_SECURITY_NETWORK_STATE` are the gate's own inputs, and the test stages' switches are its own; the rest of your environment, such as `PATH`, `CHROME_PATH` and `DOCKER_HOST`, still reaches the stages, and the gate records it (see [The gate's side of the platform contract](#the-gates-side-of-the-platform-contract)). Install the versions recorded in `scripts/security-tools.json`, Docker and Chrome/Chromium; CI installs checksum-pinned scanner binaries using `scripts/install-security-tools.mjs`. On 1.5 the gate's own scanners still run: Gitleaks over the snapshot, the history and the commit and tag messages, `trivy config`, and `trivy --version`, whose database metadata it retains. What needs an authority this draft does not have is withheld before dispatch and recorded pending (see [The gate's side of the platform contract](#the-gates-side-of-the-platform-contract)). The checksum-pinned Semgrep rules may come only from a qualified host listener, with no direct download as a fallback, so `sast-rules` is pending. The digest-pinned Semgrep image is neither inspected nor run while `image-approval` is pending; once approved, it must already be in the local image store (`sast-image` inspects it and pulls nothing), and it runs with networking disabled. The CI scan's image build and its two `trivy image` scans, which would refresh vulnerability data through Trivy's normal online scan, wait for the build's pre-build authority. `workflow-analysis` stays pending until the qualified golden-tool manifest binds an Actionlint pin. The gate never uses `--ignore-unfixed` to hide vulnerabilities.

### Local SonarQube

Both Semgrep and SonarQube are required before a release. The shared local SonarQube service is bound to `127.0.0.1:19000`; it is not SonarCloud. The private `orbit-homelab` project uses overall-code conditions: no vulnerabilities or bugs, all security hotspots reviewed, and security and reliability ratings of A. Reviewing a hotspot requires evidence; marking it reviewed merely to clear a gate is not acceptable.

Set `ORBIT_SONAR_TOKEN_FILE` to the absolute path of the separately provisioned private project-analysis token file. Do not place the token in source, command arguments, this document or chat messages. For an immutable disposable source snapshot, run `node scripts/check-sonarqube.mjs /absolute/private/evidence-directory` (with `node`, not `npm run security:sonarqube`, for the reason given for the gate: the wrapper starts `docker` by name with the token in its environment); the full release gate invokes this itself. The source snapshot must have a self-contained Git object database, no untracked files other than installed dependencies, and unchanged tracked bytes matching its index. The wrapper uses a digest-pinned scanner with a read-only source mount, an internal Docker network, nonroot execution, no capabilities and finite memory/CPU/process limits. Its temporary analyzer directory permits execution because Sonar provisions its JRE and Node there. Results stay outside source in a new private directory.

Success requires the scanner to exit successfully, the exact submitted computation to finish, and that analysis's quality gate to pass the required conditions. Missing credentials, stale task files, incomplete computation, weakened/missing quality conditions or changed source block the check. This analysis supplements manual review and does not clear other release blockers. The server, database volumes, backups and token are sensitive local artifacts; OS administrators and Docker daemon access remain trusted. The local administrator and database passwords are held in the operating-system credential store; the running database configuration and expiring project token also need private file permissions and encrypted host storage.

An independent reviewer places a private JSON record at `<common-git-dir>/orbit-security/reviews/<candidate-tree>.json`, containing `tree`, `parents` (the candidate's complete ordered parent vector: HEAD, then each `MERGE_HEAD`; a record with a single `parent` is refused), `reviewer`, an evidence `reference`, `unresolved: []`, and a `documents` map. Each human documentation or text file outside `test/` needs `{ "status": "updated" | "checked unchanged", "reason": "..." }`. This records an actual review; writing the file is not the review itself. Reports and review files are local evidence, not cryptographic attestations. Install local guards with `node scripts/install-security-hooks.mjs` (optional additional repository paths are accepted). Each installation covers all linked worktrees and refuses to replace existing custom hooks. It installs `pre-commit`, `pre-merge-commit`, `pre-applypatch` and `reference-transaction` hooks and needs Git 2.28 or later; an installation made before the `reference-transaction` hook was added is refused rather than replaced, so review the update, remove the earlier hooks and helper files, and install again. The guard requires a verified finalization of the exact tree, complete parent vector, refs, raw reports, test logs and review evidence, with a run started less than 24 hours ago and unexpired review/database evidence; scan-only or release records cannot authorize a commit. Local hooks can be bypassed, so GitHub required-status and review rules must also be configured before publication. Until a branch adopts the full gate and clears its findings, its commits remain blocked. Release remains blocked regardless of a review file while its final artifact stage is incomplete.

### Review and finalize a completed commit run

Every candidate still runs `node scripts/security-gate.mjs commit` (started with `node`, [as above](#every-commit)). A complete commit run seals hashes of its raw reports, logs, tool configuration and source manifest in `run-manifest.json`. Raw finding exits stay nonzero: Gitleaks and Trivy use a distinct finding exit of 10; Semgrep uses 1. A successful finalization does not rewrite `result.json` or claim the scanners found nothing. Earlier unsealed runs cannot be retroactively approved.

Run these commands from the unchanged candidate checkout, using the private run directory printed by the gate:

```sh
node scripts/finalize-security.mjs inspect /absolute/private/run-directory
node scripts/finalize-security.mjs finalize /absolute/private/run-directory /absolute/private/review.json
```

On 1.5, name the folders of the companion runs a candidate with a platform manifest needs after the run's (and the review's) in both commands: see [The gate's side of the platform contract](#the-gates-side-of-the-platform-contract).

Inspection prints exact finding IDs, report hashes and eligibility blockers. It accepts no findings. In addition to the independent-review fields above, the private review needs `schemaVersion: 2`, the exact `runSha256`, `refsSha256`, `toolsSha256` and `candidateIdentitySha256` from inspection (and on 1.5 `catalogSha256` and, for a candidate with the platform manifest, `platformSha256`), UTC `reviewedAt` and `expiresAt`, and a `dispositions` array. Each reported occurrence needs exactly one entry containing its `id`, `status` (`false-positive` or `not-affected`), `reviewer`, concrete `reason`, evidence `reference`, absolute private `evidenceFile` and that file's `evidenceSha256`. The review must be written after the run completes. An empty array is correct only for a run with no findings. Never manufacture a review or mark an unresolved vulnerability not affected to clear the gate.

The finalizer reads and hashes the supporting evidence, keeps private copies, and atomically publishes a separate `finalization` directory. The hook rereads those copies and the raw evidence, verifies required stages and test totals, and checks the candidate files, complete parent vector, refs, review expiry, tool pins, scanned image and vulnerability-database freshness. Changed or missing evidence, a missing required stage, scanner errors, skipped tests, unknown findings and unsupported report formats block. A fresh unchanged run can be reviewed and finalized without rerunning its scans solely to obtain a new report ID. Any source/index/parent/ref change or stale run requires a fresh full gate.

On 1.5 the required stages also include each lint stage the commit guard requires of the candidate (`sql-lint` and `import-lint`, by the rule in the [1.5 adoption](#evidence-tied-to-the-candidate) paragraph). The guard passes them to the finalization check, and `--verify-commit` and the `reference-transaction` hook derive the same requirement from the commit itself, its parents and their history, so a run without them, finalized as the maintenance finalizer would, does not approve a 1.5 candidate or a 1.5 commit, while the same installed guard accepts a maintenance run for a maintenance candidate once its finalization passes (only the Mac-side finalization can pass its `actionlint-pin` obligation, maintainer decision 8, so none does yet). The 1.5 `scripts/finalize-security.mjs` requires both lint stages, which every 1.5 commit run records (run once the pre-dispatch barrier is open; otherwise withheld and pending, so that run is not a pass): it names them to `scripts/security-finalization.mjs`, which requires a lint stage only of a caller that names it, so a maintenance finalizer that names none but passes the platform inputs finalizes maintenance runs with the same module, and both branches can carry the one copy the installed guard needs. Both command-line entry points, the commit guard and the finalizer, run their checks when started through a symlinked directory, with or without `--preserve-symlinks-main`, or through a symlinked file without it: each compares the path it was started with to its own file, and then their real paths inside a guarded comparison. (Started with `--preserve-symlinks-main` through a symlink to its file alone, either resolves its helper modules beside the link, cannot load them and exits 1 without checking anything, which blocks.) Imported, also through stdin or `--eval` with an argument that is not a file, neither does anything.

Supported finding reports are the pinned Gitleaks 8.30.1, Semgrep 1.176.0 and Trivy 0.74.0 formats. Findings from other failing stages remain blocked; this first mechanism does not implement risk acceptance, dependency/Sonar/Snyk/Clair dispositions or release finalization. The Semgrep adapter supplies an empty project-level ignore outside the candidate, disables Git ignores and retains the explicit dependency-directory exclusion; candidate `.semgrepignore` files are refused. Every tracked JavaScript module, including tests, must appear in its scanned paths. This is file-selection evidence, not proof every rule analyzed every language or detected every defect. Trivy's supported configuration scope checks Dockerfiles; other formats still need their applicable checks and review.

Evidence inputs must be private regular files of at most 64 MiB; links, pipes and devices are refused. Hook installation includes the finalizer's helper modules and refuses to overwrite differing installed copies: review and update them together when adopting this change. Hashes establish consistency with the reviewed bytes, not the truth of a reviewer's reasoning, authorship authentication or protection against a trusted local writer fabricating an entire run. Protected remote review and required checks remain necessary before publication.

## Documentation and changelog ownership

The author owns documentation impact for each commit; its reviewer checks claims against the same source tree. Inventory all project documentation, including README, developer instructions, security policy, examples, deployment instructions and in-app help. Record each relevant document as updated or checked unchanged with a reason. Do not describe a planned feature as available or a source change as deployed.

| Change                                                         | Documentation to check                                                             |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| User-visible behavior, settings or UI                          | README, configuration, troubleshooting, in-app help and examples                   |
| API, storage, lifecycle or concurrency                         | Architecture, configuration, troubleshooting and developer instructions            |
| Authentication, outbound requests, secrets or data handling    | Security guide, SECURITY.md, configuration, installation and recovery guidance     |
| Runtime, dependencies, installer, container or release process | Installation, architecture, security, examples, CONTRIBUTING.md and this policy    |
| Integration or metric                                          | Integrations, configuration, permissions, units, fixtures and compatibility limits |
| Any change                                                     | CHANGELOG.md and the affected cross-links, commands, defaults and limitations      |

Every commit updates the appropriate changelog section with its concrete behavior or engineering change and any compatibility, migration or recovery consequence. Keep unreleased work distinct from dated releases. Preserve earlier release entries; correct inaccuracies explicitly rather than erasing the record. The changelog explains changes; Git retains the complete development history and attribution.

Before a release, audit **all** documentation against the exact candidate, not only the documents touched recently. Check commands in isolated fixtures, links, UI labels, supported versions, defaults, permissions, backup/restore instructions and known limitations. Keep an inventory with review date, source identity, reviewer and unresolved items. An incomplete documentation audit blocks final status.

## Safe history for GitHub

Preserve commits, parent relationships, tags, authors and attribution across Uptime Goblin repositories/worktrees. Inventory remotes and the exact refs to publish. Before a public push, scan **all history reachable from every publishable branch and tag**, including deleted files and historical commit/tag messages, plus the final source tree, release artifacts and any attached assets. Review scanner findings; a clean current checkout or `.gitignore` does not clear past history. Review repository metadata and any LFS/submodule content included in publication separately.

Keep live configuration, keys, password hashes, backups, topology-rich exports, private review evidence and collaboration messages out of publication. If history contains a real secret, block publication, report it privately and arrange credential rotation. Preserve a protected copy of the original history and propose a reviewed remediation plan to the maintainer. Do not automatically rewrite, squash, delete history, move tags or force-push. If preserving unsafe history conflicts with public publication, leave publication blocked until the maintainer resolves the plan.

## Final release validation

Run the full gate again on the exact release candidate:

```sh
node scripts/security-gate.mjs release
```

It includes the commit gate and final independent security/code review. Validate the packaged source and the **built container that will be published**, not just Dockerfile text or a different local image. Freeze source, version, lockfile, base-image identity, build inputs and artifact digests. A rebuild is a new artifact requiring its own validation; do not substitute a mutable tag for the tested digest.

The release evidence must close each applicable area:

- Authentication, authorization, session/password boundaries, origin/Host/proxy handling and retry/idempotency behavior; no stale credential can regain access after an await or replay.
- SSRF, DNS/address checks, redirects, TLS hostname verification, time/size limits, input validation, and secret redaction across logs, errors, API, exports and browser rendering.
- Data races, transaction retries, durability, migrations, upgrade/downgrade boundaries, disk-full behavior, interrupted writes, backup/restore, cancellation and shutdown recovery.
- Real browser behavior, keyboard/focus navigation, accessible names, contrast and reduced motion; review accessibility manually as well as with available automation.
- Fresh install, identical reinstall, upgrade, refusal and rollback with real supervision; health checks must prove the intended process/release, not merely receive an HTTP response.
- Container startup/health/stop, nonroot operation, filesystem permissions, writable paths, mounts, capabilities and network exposure; scan the actual image's OS and application packages and layers for vulnerabilities and secrets.
- Complete source/dependency/image inventories and SBOMs, license checks, artifact checksums, release signature verification against an independently trusted key, and verifiable build provenance tied to source and artifact digests. An SBOM or checksum alone is not a signature or provenance proof.
- The full documentation audit, complete changelog, safe publishable history and verified release/rollback instructions.

For every vulnerability or review finding, retain its identifier, affected component, evidence, impact, disposition, responsible person and any remediation deadline. Confirm fixes with regression evidence. Explain false positives and any proposed risk acceptance; a scanner suppression alone does not resolve a finding. The maintainer must explicitly accept any residual risk that requires a release exception. No unresolved release blocker, unavailable required check or unverified required artifact can be described as passed or final.

Release validation does not authorize publication, production access or deployment. Report exactly what was built, checked and approved, together with remaining limitations.
