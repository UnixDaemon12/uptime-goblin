# Signing in

[Back to Uptime Goblin](../README.md) · [Installation](installation.md) · [Security](security.md) · [Troubleshooting](troubleshooting.md)

From 1.5, browsers sign in to Uptime Goblin on its own sign-in page and stay signed in with a session cookie, not through the browser's HTTP Basic prompt. (While legacy Basic is on, a browser that opens an API address while it is not signed in can still show that prompt at a plain-HTTP address on the network (not `localhost`, `127.x` or `[::1]`, to which browsers send `Sec-Fetch-Site`) where Uptime Goblin accepts Basic: with the plain-HTTP opt-in (`GOBLIN_INSECURE_HTTP_SESSIONS=1` or Docker Compose's default), and through a proxy on the Uptime Goblin computer that sends no forwarding headers and keeps a loopback Host; see [legacy Basic](#scripts-and-legacy-basic).) Scripts can keep using HTTP Basic for now ([legacy Basic](#scripts-and-legacy-basic)). If the sign-in page shows a message about HTTPS, a proxy or a cookie instead of signing you in, go to [when sign-in is refused](#when-sign-in-is-refused).

## The admin and the password

Uptime Goblin 1.5 has one account, the built-in **admin**. Its password is the one your Uptime Goblin already used:

- **`auth.json`** in the data directory, when it exists (a password changed in Uptime Goblin is kept there);
- otherwise **`GOBLIN_PASSWORD`** from Uptime Goblin's environment (`/etc/uptime-goblin.env` for the native installer, `.env` for Docker Compose).

Uptime Goblin keeps the password in its control database, `control.sqlite`, and writes every change you make in Uptime Goblin back to `auth.json` (the _mirror_), so a rollback to 1.4.x signs in with the current password once `auth.json` has been written (while it cannot be, a banner says so: below). Only the salted scrypt hash is stored, never the password. A `GOBLIN_PASSWORD` that was never changed in Uptime Goblin stays in the environment only, as 1.4.x left it: no `auth.json` is created until you change the password in Uptime Goblin.

Change the password under **Configure → Account** (the page that 1.4.x called Security). It needs the current password. Afterwards every other browser and device is signed out; this one stays signed in. Scripts using Basic must use the new password.

**Changes outside Uptime Goblin.** At every start Uptime Goblin compares `auth.json` and `GOBLIN_PASSWORD` with what it recorded:

- `auth.json` changed (a password change under 1.4.x after a rollback, or an `auth.json` restored on its own from a backup): Uptime Goblin takes that password and signs every session out. The log says "Imported the admin password from auth.json, which changed outside Uptime Goblin; every session was signed out."
- `auth.json` is gone and `GOBLIN_PASSWORD` is set (the [recovery procedure](troubleshooting.md#forgotten-uptime-goblin-password)): Uptime Goblin takes `GOBLIN_PASSWORD` and signs every session out.
- On an install without `auth.json`, a different `GOBLIN_PASSWORD` (you reset it) is taken the same way. While `auth.json` exists, `GOBLIN_PASSWORD` is ignored, as in 1.4.x.

**Restoring a backup.** A backup of the whole data directory holds the password of its time and every session of its time, including those signed out since (a lost device, **Sign out other devices**, a password change); its `auth.json` matches the restored `control.sqlite`, so nothing above applies. Uptime Goblin therefore also checks which file `control.sqlite` is: when it is not the file of the last start (a backup restored with `tar` or `cp`, a copied Docker volume, a restored Proxmox backup, a data directory copied or moved to another disk), Uptime Goblin signs every session out and the log says "control.sqlite is not the file Uptime Goblin last ran with: its data directory was restored from a backup, copied or moved. Every session was signed out, …". `goblin-admin restore-snapshot` signs everyone out the same way. Uptime Goblin cannot notice a rollback of a file-system snapshot (a Proxmox LXC or VM snapshot, ZFS or LVM), which brings back the very same file, nor a backup copied over the existing `control.sqlite` in place: after one of those, sign in and use **Sign out other devices** at once, or change the password, which signs out every other session.

**When `auth.json` cannot be written** (a read-only or full disk), the change is kept and works, and every page shows: "Uptime Goblin saved the admin password but could not update auth.json. Until it does, a rollback to 1.4.x would still use the previous password. Uptime Goblin retries hourly." Uptime Goblin retries hourly and at every start. An open page asks again about every five minutes while it refreshes, so the banner goes within minutes of a retry that worked, and shows in the browser's other open tabs too. If you roll back to 1.4.x before it succeeds, 1.4.x uses the previous password; if you then change the password under 1.4.x, that newer password wins when you upgrade again. When the disk fills just after `auth.json` was written, the change stands too and you stay signed in, with no banner (a rollback uses the new password); only the note of it in `control.sqlite` is missing, and the log says "auth.json now holds the current admin password, but Uptime Goblin could not record that in control.sqlite (…); the next start of Uptime Goblin records it." The next start does so without signing anyone out. Uptime Goblin notes a new `auth.json` in `control.sqlite` only once the data directory has been flushed to disk after it, so a power loss right after a change cannot bring the previous password back (as a change made outside Uptime Goblin, signing everyone out). When that flush fails (a failing disk: `EIO`), the change stands the same way and the log line is the same; the next start flushes the directory before it notes the file, or writes `auth.json` again if a power loss undid the write.

## Signing in and out

Sign in with the login name **admin** and the password. The page stores nothing but the session cookie; the browser's password manager can fill the form.

| Session                                      | Ends                                                                                                                                                                                   |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Without **Keep me signed in on this device** | When the browser is closed (a browser that reopens your previous tabs may keep it), after 12 hours without use, and at the latest after 7 days. On a shared computer, use **Sign out** |
| With **Keep me signed in on this device**    | After 12 hours without use, and at the latest after 30 days; closing the browser does not end it                                                                                       |

The hint beside the box says: "Stays signed in on this device for up to 30 days, as long as you use Uptime Goblin at least every 12 hours. Without it, closing the browser signs you out (a browser that reopens your previous tabs may keep you signed in)." Without the box the cookie has no expiry date, so the browser decides when it goes; Uptime Goblin still ends the session after 12 hours without use or 7 days. Only what you do counts as use: the dashboard's automatic refresh every 15 seconds does not keep a session alive, so an unattended open tab is signed out after 12 hours. (Wall displays are the [exception](#wall-displays).) Uptime Goblin cannot tell you from a script, though: its own page marks the automatic refresh as background, and any other request counts as use. So the idle limit protects an unattended tab, not a stolen cookie: a cookie that someone else keeps using stays valid until its 7- or 30-day limit, unless you sign it out or change the password ([a stolen session](security.md#sign-in-sessions)).

When a session ends while a page is open, the next save opens a **Sign in again** dialog over the page. Your unsaved changes stay open, and after signing in the save continues where it stopped, exactly once. **Cancel** (or Escape) leaves the page signed out at the first press, whatever asked (a save, **Send test email**, a **Sign out** on the Account page): it stops refreshing, says "Signed out" at the top and offers **Sign in** on the dashboard and on configuration pages, and the focus goes back to the button you used (an export, **Test connection**, a source's **Show** or **Hide**, and that **Sign in** itself included). Signing in again there, or in another tab of the same browser, brings back the readings, and the Account and System pages and Help show their current contents again instead of "Your session has ended. Sign in again."; after any sign-in through the dialog the Account page lists the new session as this device. A page opened while Uptime Goblin is not answering yet (for example during a restart) offers none of its controls until Uptime Goblin answers; then it shows the sign-in page if nobody is signed in.

**Sign out** is in the menu under your name at the top of the page (on a phone, the person icon); it says "Signing out…" until Uptime Goblin answers. The page starts again at the sign-in page only once Uptime Goblin confirmed the sign-out. If Uptime Goblin does not answer (it is restarting, or the network dropped), the menu says "Uptime Goblin did not confirm the sign-out, so this browser may still be signed in. Try again." and the page stays as it is: the session may still be valid, and a fresh page would sign itself back in. Uptime Goblin may take up to a minute to answer; if you close the menu meanwhile, the message shows at the bottom of the page when the answer comes and stays in the menu until you open it. Selecting the message to copy it does not close the menu: only a click that starts and ends outside the menu does. If Uptime Goblin answers that it could not record the sign-out (a full or failing disk, `storage_full`), the page stays and says so: Uptime Goblin refuses the session now, but only until it restarts (see [revocation](security.md#sign-in-sessions)). Free some space on the Uptime Goblin host and press **Sign out** again: this browser keeps its cookie until Uptime Goblin has recorded the sign-out, so the second press removes the session and then shows the sign-in page. Signing in again from this browser removes it too. **Configure → Account** lists your sessions (device; address; when each started, was last used and ends). The address is the one the sign-in lockout counts: an IPv6 device shows its /64 network (for example `2001:0db8:0000:0001::/64`), a session signed in on the Uptime Goblin computer itself shows `loopback` (so does one signed in through a proxy there that `GOBLIN_TRUST_PROXY` does not name, and one through a proxy there that sends no forwarding headers and keeps a loopback Host, which Uptime Goblin cannot tell from it: [the ssh tunnel](#when-sign-in-is-refused)), a device behind a reverse proxy that `GOBLIN_TRUST_PROXY` names shows its own address, and a device behind another proxy it does not name shows that proxy's address (under Docker Compose without `GOBLIN_TRUST_PROXY`, every device shows the Docker gateway's address). In the list, **Sign out** ends one of them, **Sign out other devices** all but this one, except those that signed in after this one: a session can end only sessions that signed in no later than it did. If Uptime Goblin does not answer, the page says "Uptime Goblin did not confirm the sign-out, so that device may still be signed in. If it is still listed, sign it out again." (for **Sign out other devices**: "…so your other devices may still be signed in. If any are still listed, sign them out again."), and the list says "Uptime Goblin is not answering. Try again in a moment." until it can be read again. A device that signed in after this one is marked "Signed in later" instead of offering **Sign out**, and **Sign out other devices** says how many such devices are still signed in. That way a session cookie taken from a lost device cannot end your new sign-in, however often its holder presses **Sign out other devices**: signing in again always outranks every session there is. To end a device marked "Signed in later", sign out here and sign in again, then sign it out; if you do not recognise it, change the password instead (someone signed in with it), which signs out every other session. Signing in or out over HTTPS also ends the plain-HTTP session this browser may still hold from signing in over plain HTTP with `GOBLIN_INSECURE_HTTP_SESSIONS=1`, not only its cookie: its secret crossed the network in clear. A cookie of Uptime Goblin's name that another site set (another port of the same host, a site on a parent domain, or anyone who can change plain-HTTP traffic) does not stop that, nor a sign-in from ending the session the browser presented. If the browser sends such a cookie beside Uptime Goblin's own, **Sign out** still ends this browser's session and removes Uptime Goblin's cookie, and the sign-in page then says "You are signed out, but this browser still has an Uptime Goblin sign-in cookie that another site set. Remove this site’s cookies in the browser before you sign in again.": Uptime Goblin cannot remove the other site's cookie, and signing in fails until it is gone.

Sessions survive a restart or upgrade of Uptime Goblin within 1.5. Signing out, a password change, an imported password (above), restoring a snapshot or a backup of the data directory (above), or reaching a limit ends them. At most 20 sessions are kept; signing in a 21st ends the one least recently used.

Failed sign-ins are throttled as before, except that on the sign-in page the previous password counts like any wrong one: only scripts keep 1.4.x's one-day grace for it ([sign-in throttling](security.md#failed-sign-in-throttling)). After a password change, update the logins your browsers and phones have saved before they try the old one. Requests with a session cookie never count and are never refused by a lockout, so a guessing attack does not sign out browsers that are already signed in. A session does not make its address trusted, though: only a correct password does (a sign-in, a password change, or a script's Basic), so a stolen cookie gives its holder no way around the [global lock](#lockouts), which also holds a password change's check of the current password.

A session cookie works only on Uptime Goblin's own pages. A request that another site's page makes the browser send (an image or script on another app under the same parent domain, or on another port of `localhost`) is refused before the session is read (403 `cross_origin`), so such a page left open neither reads Uptime Goblin nor keeps an idle session signed in. Browsers say where a request comes from only over HTTPS and on `localhost`: a session over plain HTTP (`GOBLIN_INSECURE_HTTP_SESSIONS=1`) has no such check.

## HTTPS, cookies and plain HTTP

A session cookie is as good as the password while it lasts, so Uptime Goblin only issues it where it cannot be read on the way:

| How the browser reaches Uptime Goblin                                                                                                        | Uptime Goblin calls it | Sign-in                                                        |
| ------------------------------------------------------------------------------------------------------------------------------------ | -------------- | -------------------------------------------------------------- |
| Through a reverse proxy that serves HTTPS and tells Uptime Goblin so (`X-Forwarded-Proto: https`, from a proxy named in `GOBLIN_TRUST_PROXY`) | `https`        | Allowed; the cookie is `__Host-goblin_session`, marked `Secure` |
| A browser on the Uptime Goblin computer itself (`http://localhost:4317`, or an ssh tunnel), with no proxy in between                         | `loopback`     | Allowed; the cookie is `goblin_session`                         |
| Anything else: plain HTTP over the network, a proxy that does not say HTTPS, or a proxy that sends no forwarding headers at all      | `http`         | Refused, unless `GOBLIN_INSECURE_HTTP_SESSIONS=1`               |

`loopback` needs all three: the connection comes from the Uptime Goblin computer (`127.0.0.1` or `::1`), it carries no forwarding header (`X-Forwarded-For`, `X-Forwarded-Proto`, `X-Forwarded-Host`, `Forwarded`, `X-Real-IP`), and the page was opened at a loopback name (`localhost`, `127.x.x.x` or `[::1]`). A proxy on the Uptime Goblin host that sends no forwarding headers also connects from `127.0.0.1`, but it relays browsers from anywhere: when it forwards the browser's host name (`proxy_set_header Host $host;`), Uptime Goblin treats its requests as `http`, and when it keeps nginx's default `Host: 127.0.0.1:4317`, a sign-in from a page at any other address is refused the same way (`proxy_proto_missing` for an `https://` page, `https_required` for an `http://` one), and the log names the proxy. The sign-in page knows this before the password is sent: it compares Uptime Goblin's answer with its own address, and shows the `https_required` message without the form, or the `proxy_proto_missing` one above it. With `GOBLIN_INSECURE_HTTP_SESSIONS=1` such a sign-in is a plain-HTTP session, with the banner. Its requests cannot be told from the Uptime Goblin computer's own, whatever page address they carry, which matters for the sign-in lockout ([the ssh tunnel](#when-sign-in-is-refused)). The fix is the [reverse proxy](#the-reverse-proxy) recipe below.

Both cookies are `HttpOnly` and `SameSite=Strict`, and changes must come from Uptime Goblin's own page (the `Origin` must match the address, or be a name in `GOBLIN_ALLOWED_HOSTS`). The browser's `Origin` can make Uptime Goblin refuse a sign-in, never weaken a cookie: when the proxy says HTTPS but the page was opened with `http://`, Uptime Goblin refuses (`proxy_proto_mismatch`) instead of setting a cookie the browser would drop.

Browsers do not separate cookies by port: Uptime Goblin's cookie also goes to every other service at the same host name, whatever its port, and that service's server can read it and act as you until the session ends ([cookies](security.md#sign-in-sessions)). Give Uptime Goblin a host name of its own. At `http://localhost` (Docker Compose, the ssh tunnel), every local web app you open in the same browser receives Uptime Goblin's cookie: use a separate browser profile for Uptime Goblin, or sign out when you are done.

**`GOBLIN_INSECURE_HTTP_SESSIONS=1`** allows sign-in over plain HTTP on a network you trust. Over plain HTTP the password itself crosses the network in clear, not only the cookie: at every sign-in, every **Sign in again** and every password change (the current password and the new one). Use it only on a network where you would type the admin password unencrypted, and change the password once Uptime Goblin is served over HTTPS. The sign-in page says so above the form, before you type the password, when its address is not a loopback name: "This page uses plain HTTP, so your password crosses the network unencrypted when you sign in (GOBLIN_INSECURE_HTTP_SESSIONS allows it). Sign in only on a network you trust, and serve Uptime Goblin over HTTPS." A page at `localhost`, `127.x.x.x` or `[::1]` (Docker Compose's published port, the ssh tunnel) gets no such warning: its browser reaches Uptime Goblin on its own computer, or through ssh, which encrypts. Once you are signed in, every page shows: "This session uses plain HTTP, so anyone who can watch the traffic between your browser and Uptime Goblin can see its sign-in cookie, and your password each time you sign in or change it. Serve Uptime Goblin over HTTPS, then set GOBLIN_INSECURE_HTTP_SESSIONS=0 and restart Uptime Goblin (Docker: in .env, then docker compose up -d)." A page opened at an `https://` address is already served over HTTPS: there the session is plain HTTP only because the reverse proxy does not tell Uptime Goblin so, and the banner says that instead, with the fix: "Your browser uses HTTPS, but the reverse proxy in front of Uptime Goblin does not tell Uptime Goblin so, and with GOBLIN_INSECURE_HTTP_SESSIONS this session signed in as plain HTTP: its sign-in cookie is not marked Secure, so this browser would also send it to a plain http:// address of this host, where the network can see it. In nginx add `proxy_set_header X-Forwarded-Proto $scheme;` to Uptime Goblin’s location and reload nginx (GOBLIN_TRUST_PROXY must name the proxy), then set GOBLIN_INSECURE_HTTP_SESSIONS=0, restart Uptime Goblin (Docker: in .env, then docker compose up -d) and sign in again." The start line in the log says `plain-HTTP sessions: allowed`, and while Uptime Goblin listens on (or Docker Compose publishes it on) an address the network reaches, the log also warns at every start that the password at each sign-in and the cookie cross that network unencrypted (naming the password each script sends with legacy Basic too, while Basic is on). On loopback it warns at every start too while `GOBLIN_TRUST_PROXY` names a proxy or `GOBLIN_ALLOWED_HOSTS` a host that is not loopback: a proxy there that relays sign-ins over plain HTTP (one that sends `X-Forwarded-Proto: http`, one Uptime Goblin does not trust, or one that sends no forwarding headers and forwards the browser's host name) is accepted under the same opt-in. The same setting is the one opt-in for [legacy Basic](#scripts-and-legacy-basic) on plain HTTP. **A change needs a restart** (`sudo systemctl restart uptime-goblin.service`, or `docker compose up -d`; `docker compose restart` does not read `.env` again). `0` turns it off (so do `false`, `no`, `off` and an empty value), in every install mode. Removing the line is not enough everywhere: under Docker Compose an unset variable means `compose-default`, which is on while the port is published on loopback (below), and on a native install that listens on the network without a trusted proxy the next installer run stops until the file says `0` or `1` (it never adds the line itself). Turning it off ends the sessions that were signed in over plain HTTP: the next start deletes them and logs "Signed out N sessions that signed in over plain HTTP: GOBLIN_INSECURE_HTTP_SESSIONS is off.", and the start line says `plain-HTTP sessions: refused`. Every session is bound to the way it signed in, so a cookie that crossed the network over plain HTTP never works as the secure cookie through the HTTPS address, even while the setting is on; after fixing HTTPS, sign in again there.

- **Docker Compose** passes `compose-default` while `.env` does not set it (no line, or the line commented out, as `.env.example` ships it), and Uptime Goblin decides by where the port is published (`GOBLIN_BIND_ADDRESS`): on while that is a loopback address, as by default (`http://localhost:4317`, which only the Docker host reaches; inside the container the browser's connection comes from the Docker gateway, not from loopback); off on another address when `GOBLIN_TRUST_PROXY` names a proxy; otherwise Uptime Goblin refuses to start (exit status 78, "Docker Compose publishes Uptime Goblin on … (GOBLIN_BIND_ADDRESS), which is not a loopback address, …") until `.env` names your HTTPS proxy in `GOBLIN_TRUST_PROXY` or sets `GOBLIN_INSECURE_HTTP_SESSIONS=1` (plain HTTP on that network) or `0`. Then run `docker compose up -d`. `1` and `0` decide as written wherever the port is published. Check what Compose passes with `docker compose config | grep GOBLIN_INSECURE_HTTP_SESSIONS` (`compose-default` while `.env` does not set it, `"0"` or `""` is off, `"1"` is on), and after the start `docker compose logs uptime-goblin | grep 'plain-HTTP sessions'` says `allowed` or `refused`.
- **The native installer** never turns it on by itself. An install or upgrade whose `/etc/uptime-goblin.env` (or, for a new install, `--listen`) listens on the network (`HOST` not a loopback address) without a trusted proxy (`GOBLIN_TRUST_PROXY`, or `--trust-proxy`) stops before it changes anything, with "Uptime Goblin would listen on … with no reverse proxy it trusts …", unless systemd would already give Uptime Goblin a decision: a `GOBLIN_INSECURE_HTTP_SESSIONS` that Uptime Goblin reads as yes or no, in `/etc/uptime-goblin.env` or a drop-in (`=1` and `=0` in the file are kept as they are; a commented-out line, an empty value or another value decides nothing, and so does the `=1` that installers of earlier 1.5 pre-releases added by themselves under their comment "# Added by the Uptime Goblin 1.5 installer: keeps plain-HTTP sign-in working as in 1.4.x. …": [the installer](installation.md#native-debian-or-ubuntu-lxc) stops every install that holds that one, also on loopback or behind a trusted proxy, until you choose). The message gives the two ways on: serve Uptime Goblin over HTTPS through a reverse proxy (`HOST=127.0.0.1` and `--trust-proxy loopback` for nginx on the Uptime Goblin host, or `--trust-proxy <proxy address>` for one elsewhere), or, on a network you trust, run the installer again with `--allow-insecure-http`, which adds `GOBLIN_INSECURE_HTTP_SESSIONS=1` with a comment that says who chose it (the account that ran `sudo`) and that passwords cross the network in clear, and warns. Given where systemd would already give Uptime Goblin a `0` (in the file, a drop-in or its own environment), the option is not applied, and the installer says so, naming where a `0` that is not in the file comes from (a line added to the file would override a drop-in's `Environment=`); where it would give a `1`, nothing is added. A line you removed is never added again: the next run stops instead. It judges `HOST`, `GOBLIN_TRUST_PROXY` and this setting as systemd gives them to Uptime Goblin: by the last line in `/etc/uptime-goblin.env` that sets each, as systemd reads it, and by the drop-ins and systemd's own environment ([how the installer reads a line](installation.md#native-debian-or-ubuntu-lxc)). Once Uptime Goblin is served over HTTPS, set that line to `0` and restart Uptime Goblin, as its comment and warning say.

### The reverse proxy

nginx must forward the scheme the browser used and the `Host` it asked for. The complete recipe is in [installation](installation.md#https-trust-and-network-access); the two lines that matter for sign-in are:

```nginx
proxy_set_header X-Forwarded-Proto $scheme;
proxy_set_header Host $http_host;
```

Use `$scheme`, never a fixed `https`: should a request ever reach the location over plain HTTP, a fixed value tells Uptime Goblin it came over HTTPS, and 1.5 refuses that sign-in with `proxy_proto_mismatch`. Serve Uptime Goblin's host name over HTTPS only, and let plain HTTP only redirect to it ([the recipe](installation.md#https-trust-and-network-access) has the redirect and HSTS). `GOBLIN_TRUST_PROXY` must name the proxy (`loopback` when nginx runs on the Uptime Goblin host), or Uptime Goblin ignores what it says. Nginx Proxy Manager, Caddy and Traefik send both headers by default.

### Before upgrading from 1.4.x

1.4.3 records what its trusted proxy sends. After opening Uptime Goblin through nginx once, read the record; `"observed": {"forwardedProto": "https"}` is what 1.5 needs:

```sh
sudo cat /var/lib/uptime-goblin/run/status.json
```

- `"https"`: ready.
- `"http"`: the trusted proxy sends `X-Forwarded-Proto: http`, or sends `X-Forwarded-For` without a protocol. Add the `$scheme` line above.
- `null`: nothing was observed since Uptime Goblin last started. Nobody browsed through nginx since then, `GOBLIN_TRUST_PROXY` does not name the proxy, or the proxy sends no forwarding headers at all. So `null` is not only "add the header": also check `GOBLIN_TRUST_PROXY`, and browse once. Every start of 1.4.3 empties the record, including a reboot or a backup script that stops and starts Uptime Goblin: browse after the last start, then upgrade.
- 1.4.3 records the **first** element of `X-Forwarded-Proto`; 1.5 uses the **last** (the one the nearest, trusted proxy added). With one nginx they are the same.
- No file at all: 1.4.2 and earlier record nothing. Upgrade to 1.4.3 first and browse once, or check nginx yourself and upgrade with `--proxy-proto-checked` (below).

After changing nginx: `sudo nginx -t && sudo systemctl reload nginx`, browse to Uptime Goblin once, and check again. If you open Uptime Goblin at an `http://` address while `status.json` says `"https"`, the proxy hard-codes the header: use `$scheme`.

The Host header: in 1.4.3, through nginx, save any setting once. If it saves, the Host is forwarded (or the hostname is allowlisted) and 1.5's check passes. If it says "Cross-origin changes are not allowed", add `proxy_set_header Host $http_host;` (or add the hostname to `GOBLIN_ALLOWED_HOSTS`).

**The installer checks this for you.** Upgrading an install that 1.4.x serves behind a trusted proxy (`GOBLIN_TRUST_PROXY` set) is refused, changing nothing on the host, unless the running 1.4.3 recorded `"https"`. The message names what it saw and the fixes. Run the installer again after fixing nginx and browsing once, without restarting Uptime Goblin in between; add `GOBLIN_INSECURE_HTTP_SESSIONS=1` to `/etc/uptime-goblin.env` on a trusted network instead (or run it with `--allow-insecure-http`, which adds that line where neither the file nor anything else systemd would give Uptime Goblin says yes or no); or, if you checked the proxy yourself, run it with `--proxy-proto-checked`. A deploy script that stops Uptime Goblin for a backup must read the record before it stops Uptime Goblin and pass `--proxy-proto-checked` when it says `"https"`, because the restart empties it. Keep 1.4.3 running until the installer has read the record: it removes the record when it stops, and the installer then says Uptime Goblin is not running (start it, browse once, run the installer again) instead of naming nginx. An install of 1.4.2 or earlier is told to go to 1.4.3 first or to check by hand: it has no record to read. Upgrades from one 1.5 release to the next are not checked again: signing in already proves the proxy.

## When sign-in is refused

The sign-in page shows a message and the log has a line naming the fix. On an `http://` page that Uptime Goblin would refuse (`https_required`, `proxy_proto_mismatch`), the sign-in page shows the message without the form, and a page that was already open says the same at the top without **Sign in**: Uptime Goblin refuses such a sign-in only after it has read the password, which would by then have crossed the network unencrypted. This includes a page behind a proxy on the Uptime Goblin host that sends no forwarding headers ([the transports](#https-cookies-and-plain-http)). An action that finds the session gone, such as **Save**, shows the same message. A **Sign in again** dialog that was already open when Uptime Goblin started refusing (plain-HTTP sessions turned off while it waited) closes the next time you come back to the page, before its password is sent, and the page says the same. Once the fix is in place and Uptime Goblin restarted, a sign-in page that showed no form asks Uptime Goblin again the next time you come back to it (or reload it), and then offers the form, or the dashboard if you signed in from another tab meanwhile. In order of preference:

1. **Fix nginx** as [above](#the-reverse-proxy).
2. **`https_required`** ("Sign-in needs HTTPS, or a browser on the Uptime Goblin computer itself") or **`proxy_proto_missing`** ("Your browser uses HTTPS, but the reverse proxy in front of Uptime Goblin does not tell Uptime Goblin so"): until nginx is fixed, `sudoedit /etc/uptime-goblin.env`, add `GOBLIN_INSECURE_HTTP_SESSIONS=1`, and `sudo systemctl restart uptime-goblin.service` (a restart is needed; under Docker Compose set it in `.env`, then `docker compose up -d`). Sign in; the page shows the plain-HTTP banner. For `https_required` the password then crosses the network in clear, so do this only on a network you trust. Set the line to `0` and restart once nginx is fixed.
3. **`proxy_proto_mismatch`** ("This page uses plain HTTP (http://), but the reverse proxy in front of Uptime Goblin tells Uptime Goblin the connection is HTTPS"): fix nginx (`$scheme`) or open the `https://` address. As a temporary measure, remove `GOBLIN_TRUST_PROXY` and add `GOBLIN_INSECURE_HTTP_SESSIONS=1`, then restart: sign-in then works over plain HTTP, with the password in clear on the network, and every client behind the proxy shares one sign-in lockout until you restore `GOBLIN_TRUST_PROXY`.
4. **`cross_origin`** ("Uptime Goblin refused this sign-in because this page's address does not match what the reverse proxy tells Uptime Goblin"): add `proxy_set_header Host $http_host;` to nginx, or add the hostname to `GOBLIN_ALLOWED_HOSTS` and restart.
5. **The ssh tunnel, on a native install that listens on loopback.** From a computer that can reach the Uptime Goblin host with ssh:

   ```sh
   ssh -L 4317:127.0.0.1:4317 <uptime-goblin-host>
   ```

   and open <http://localhost:4317>. Use Uptime Goblin's own port on both sides (4317 unless `PORT` in `/etc/uptime-goblin.env` says otherwise): Uptime Goblin always accepts `localhost`, `127.0.0.1` and `[::1]` at the port it listens on, whatever `GOBLIN_ALLOWED_HOSTS` says. This is the `loopback` transport: it needs no HTTPS and no proxy setting, and it is not refused by the global sign-in lock (below). Its per-client lockout is its own (Uptime Goblin counts it as `loopback`, not as an address), so failed sign-ins through a reverse proxy that `GOBLIN_TRUST_PROXY` names and that sends forwarding headers never lock it, even when the proxy does not name its clients in `X-Forwarded-For`. **This holds only while `GOBLIN_TRUST_PROXY` names every proxy on the Uptime Goblin host (`loopback`) and each sends forwarding headers.** Unless `GOBLIN_TRUST_PROXY` names it, everything that connects to Uptime Goblin from a loopback address (127.0.0.0/8 or `::1`) counts against the tunnel's lockout, whatever its Host or forwarding headers say: failed sign-ins through a proxy on the Uptime Goblin host that connects to Uptime Goblin there and that `GOBLIN_TRUST_PROXY` does not name can lock the tunnel out. A client of such a proxy has that one lockout, never a second one, whatever Host it asks for and whatever forwarding header it adds. (A proxy there that connects to Uptime Goblin's own network address, with `HOST=0.0.0.0`, is counted by that address instead, like a proxy on another host.) A proxy there that sends no forwarding headers (nginx with a bare `proxy_pass`) and keeps a loopback Host (nginx's default `127.0.0.1:4317`, or a name the client chose, passed on with `$http_host`) also makes its requests look like the host's own, the `loopback` transport, trusted or not, whatever page address they carry: a remote client's Basic or `Bearer` header, a sign-in from a forged `http://127.0.0.1:4317` page, or, with `GOBLIN_INSECURE_HTTP_SESSIONS=1`, one from the proxy's own page counts against the tunnel's lockout and is not held by the global lock. With `GOBLIN_TRUST_PROXY=loopback` the lockout of such a proxy's other requests comes from the forwarding headers it passes on, as for any trusted proxy. The log names such a proxy once it relays a request under a Host that is not a loopback one, or one from a page at a `GOBLIN_ALLOWED_HOSTS` name ("A reverse proxy on this computer sends Uptime Goblin requests without any forwarding header…"); one that relays only requests that keep a loopback Host and come from no such page (a script's Basic or `Bearer` request, say) is never named; the fix is the [reverse proxy](#the-reverse-proxy) recipe. If the tunnel is locked out meanwhile, restart Uptime Goblin (the lockout is kept in memory) and sign in through the tunnel at once. Without `GOBLIN_TRUST_PROXY=loopback` the tunnel also shares 127.0.0.1's allowance of open connections (32 at once by default, `GOBLIN_MAX_CONNECTIONS_PER_CLIENT`) with every client of a proxy on the host that connects to Uptime Goblin at 127.0.0.1: name the proxy in `GOBLIN_TRUST_PROXY` (a trusted proxy has no such allowance), or raise the setting, if the tunnel's pages fail to load while the proxy is busy. This is for the native install, where Uptime Goblin runs on the host you reach with ssh, and only while Uptime Goblin listens on 127.0.0.1 (`HOST=127.0.0.1`, the installer's default, as with `--trust-proxy loopback`) or on every address (`HOST=0.0.0.0` or `::`). With `HOST=::1` or `HOST=localhost`, forward to that name instead: `ssh -L '4317:[::1]:4317' <uptime-goblin-host>` (quoted, or zsh takes the brackets for a file pattern) or `ssh -L 4317:localhost:4317 <uptime-goblin-host>`. An install made with `--listen <address>` listens only on that address: a tunnel to 127.0.0.1 reaches nothing there, and a tunnel to that address arrives from that address, so Uptime Goblin treats it as plain HTTP (`https_required`). There, add `GOBLIN_INSECURE_HTTP_SESSIONS=1` on a trusted network until the proxy is fixed (step 2).

   **Under Docker** there is no `loopback` way in: inside the container every browser, even one on the Docker host, connects from the Docker gateway, so the published port (<http://localhost:4317> on the Docker host, or an ssh tunnel to the Docker host) is the `http` transport. It signs in only while plain-HTTP sign-in is on: with `GOBLIN_INSECURE_HTTP_SESSIONS=1`, or with Docker Compose's default while `.env` does not set it and the port is published on loopback (with a plain `docker run`, after you set it to `0`, or on a port published on another address, set it to `1` and recreate the container), and it is not exempt from the global sign-in lock: during a guessing attack, wait for the lock to end or restart the container.

Other messages:

- **"Your browser sent two Uptime Goblin sign-in cookies"** (`multiple_credentials`): another site on a parent domain, or another port of the same host, may set a cookie with the same name. Remove this site's cookies in the browser, then sign in. Better: give Uptime Goblin a hostname of its own. When such a cookie appears while a page is open, Uptime Goblin refuses that page's requests too: the page says the same at the top, offers no **Sign in** (it would fail the same way) and stops refreshing. The next time you come back to the page after removing the cookies, it offers **Sign in**; if the other site removed its cookie instead, the page carries on by itself. After **Sign out** the sign-in page says "You are signed out, but this browser still has an Uptime Goblin sign-in cookie that another site set" for the same reason: this browser's session ended, and the other cookie must go before you sign in again.
- **"You signed in, but this browser did not keep Uptime Goblin's sign-in cookie"**: the page was opened at `http://` while Uptime Goblin issued a `Secure` cookie. Open the `https://` address.
- **"Uptime Goblin's disk is full, so it cannot save your sign-in or password change"** (`storage_full`): free some space on the Uptime Goblin host, then try again. Anyone already signed in stays signed in.
- **Too many attempts**: see [lockouts](#lockouts).

## Scripts and legacy Basic

Scripts (curl, wget, monitoring integrations) can keep sending HTTP Basic with `admin` and the password on **installs upgraded from 1.4.x**. It is **off on installs created by 1.5**. `GOBLIN_LEGACY_BASIC=1` turns it on, `0` off, whatever the install; a change needs a restart. On an install created by 1.5, `control.sqlite` names the release that created the data directory, and so does `created-by.json` beside it, which 1.4.x never writes. A new `control.sqlite` takes that release from `created-by.json`, so removing `control.sqlite` (see [a password is always required](#a-password-is-always-required)) leaves Basic off. A new `control.sqlite` in a data directory that holds 1.4.x files (`config.json`, `auth.json` or `history.sqlite`) but no `created-by.json` counts as upgraded. Basic answers carry `Deprecation: @1790812800` (deprecated since 1 October 2026) and `Link: </api/docs?doc=authentication>; rel="deprecation"`. From 1.6, Basic is off on upgraded installs too, unless `GOBLIN_LEGACY_BASIC=1`; it will be removed in a later release, when API tokens arrive. **Configure → Audit log**, kind **Scripts with a password**, lists the scripts still to move (below).

A request that carries `Sec-Fetch-Site` or `X-Goblin-Client` is a browser's, and never signs in with Basic in 1.5: its `Authorization` header is ignored, not checked and not counted as a failed sign-in. Browsers send `Sec-Fetch-Site` over HTTPS and to `localhost`, and Uptime Goblin's page sends `X-Goblin-Client` with each of its own requests. So there a browser that still remembers 1.4.x's Basic login does not lock anyone out, and **an nginx configuration that injects `Authorization: Basic` for browsers no longer signs browsers in**: sign in on the page instead.

To a plain-HTTP address on the network (not `localhost`, `127.x` or `[::1]`) browsers send no `Sec-Fetch-Site`, so a request the browser makes there on its own (a typed address, a bookmark, a link or an image, another site's included) carries neither header, and Uptime Goblin cannot tell it from a script. While legacy Basic is on, that matters wherever Uptime Goblin accepts Basic over plain HTTP: on the `http` transport with the plain-HTTP opt-in (`GOBLIN_INSECURE_HTTP_SESSIONS=1`, or Docker Compose's default while it publishes the port on loopback), and through a proxy on the Uptime Goblin computer that sends no forwarding headers and keeps a loopback `Host`, which Uptime Goblin takes for the computer itself (`loopback`, below), with no opt-in. There the browser's remembered 1.4.x Basic login is checked like a script's: a correct one counts as a script sign-in under **Scripts with a password** (below), and a wrong one as a failed sign-in (through such a proxy, against the ssh tunnel's lockout). Without a credential such a request gets 401 with the Basic challenge, as a script does (`wget` waits for it before it sends Basic), so the browser can show its own Basic prompt there. Clear the browser's saved login for Uptime Goblin, or reach Uptime Goblin over HTTPS. For the same reason the two exports, `GET /api/config/export` and `GET /api/audit/export`, need `X-Goblin-Request: 1` with Basic on every transport, as they do with a session cookie (below): another site's page cannot send that header, so it cannot make Uptime Goblin build them and write their audit entries, over plain HTTP, through such a proxy, or over HTTPS from a browser too old to send `Sec-Fetch-Site`. Make such a proxy send `X-Forwarded-For` and `X-Forwarded-Proto` and name it in `GOBLIN_TRUST_PROXY` all the same (the [recipe](installation.md#https-trust-and-network-access)): otherwise Uptime Goblin takes its clients for the Uptime Goblin computer itself (below).

With Basic off, a script gets 401 with `"code": "basic_disabled"`. Scripts must send `Content-Type: application/json` and `X-Goblin-Request: 1` with every change, as before. They send `X-Goblin-Request: 1` with the two exports too (`curl -H 'X-Goblin-Request: 1' …`) wherever they call Uptime Goblin from (over HTTPS, over plain HTTP, under Docker also from the Docker host, and from the Uptime Goblin computer itself, `loopback`), and an `Origin`, when they send one, naming the `Host`: otherwise 403 `cross_origin`, before the export is built or its audit entry written (the Basic sign-in itself is still checked and counted under **Scripts with a password**). 1.4.x needed no extra header on an export, so a 1.4.x script that downloads `GET /api/config/export` with Basic needs it added.

### Update export scripts from 1.4.x

An authenticated script that omits `X-Goblin-Request: 1` now receives **403 `cross_origin`** for `GET /api/config/export` and `GET /api/audit/export`. Add that one header to each export request. It is required with Basic and session cookies on every transport; it is not a credential and does not replace authentication or permissions. Other reads keep their existing behavior, and writes still need their existing request headers and JSON body rules.

Use Uptime Goblin's configured HTTPS address. If your client sends `Origin`, it must name the request's `Host`; a request marked `Sec-Fetch-Site: cross-site` is refused. The examples below omit `Origin`, as ordinary command-line clients may for these GET exports. Do not disable TLS verification, follow an unexpected redirect with credentials, or put a password in a URL or command argument.

These examples are for existing scripts on an install where legacy Basic is already enabled. They do not enable it on a new install or change its deprecation. With Basic disabled, use Uptime Goblin's signed-in page; adding the header cannot turn Basic on.

For an interactive configuration download, curl prompts for the admin password without placing it in the command line or shell history. A new private directory and restrictive umask protect the downloaded file:

```sh
(
  umask 077
  export_dir="$(mktemp -d)" || exit 1
  curl --disable --fail --silent --show-error --basic --user admin \
    --header 'X-Goblin-Request: 1' \
    --output "$export_dir/uptime-goblin-config-redacted.json" \
    'https://goblin.example/api/config/export' &&
  printf 'Export saved in %s\n' "$export_dir"
)
```

For an existing scheduled job, use its protected credential file instead of a password literal or an exported password variable. In this example, `$HOME/.config/uptime-goblin/exports.netrc` is an existing file owned by the job's account, mode600, in a private directory; it contains that account's Uptime Goblin Basic login for `goblin.example`. Create or update it privately, and keep it out of version control, shared logs and backups intended for sharing. Replace the example hostname with your Uptime Goblin hostname in both places.

```sh
(
  umask 077
  export_dir="$(mktemp -d)" || exit 1
  curl --disable --fail --silent --show-error --basic \
    --netrc-file "$HOME/.config/uptime-goblin/exports.netrc" \
    --header 'X-Goblin-Request: 1' \
    --output "$export_dir/uptime-goblin-audit-export" \
    'https://goblin.example/api/audit/export' &&
  printf 'Export saved in %s\n' "$export_dir"
)
```

The same header works for either endpoint; retain the job's existing supported filters and output handling. Treat both downloaded files as private: even redacted configuration and audit data can reveal internal names and addresses. A failed request is not a completed export.

Basic sends the password itself with every request, so it takes the sessions' rule for [plain HTTP](#https-cookies-and-plain-http): over HTTPS through a trusted proxy, and from the Uptime Goblin computer itself (`loopback`), as before; on the `http` transport only with `GOBLIN_INSECURE_HTTP_SESSIONS=1` (or Docker Compose's default while it publishes the port on loopback). Without it, a script there gets 403 with `"code": "https_required"`, the answer a sign-in gets there, before its password is checked: it is not counted as a failed sign-in, a 401 there carries no Basic challenge, the refusal is listed under **Scripts with a password** ("Script sign-in refused: plain HTTP is not allowed"), and the log says so once an hour ("A script's HTTP Basic sign-in from … over plain HTTP was refused (https_required): …"). Call Uptime Goblin through its HTTPS address instead, or from the Uptime Goblin computer itself.

A reverse proxy on the Uptime Goblin computer must send `X-Forwarded-For` and `X-Forwarded-Proto` (the [recipe](installation.md#https-trust-and-network-access) does). Basic through one that sends no forwarding headers and keeps a loopback `Host` (nginx's default, `Host: 127.0.0.1:4317`) is treated as coming from the Uptime Goblin computer itself (`loopback`) and accepted without `GOBLIN_INSECURE_HTTP_SESSIONS=1`, from wherever the proxy took it: Uptime Goblin cannot tell such requests from local scripts. That includes a browser's remembered 1.4.x Basic login on a load another site's page starts (an export still needs `X-Goblin-Request: 1` there, above). One that sends forwarding headers but that `GOBLIN_TRUST_PROXY` does not name is plain HTTP (`http`) to Uptime Goblin, whatever it says: with `GOBLIN_INSECURE_HTTP_SESSIONS=1` sign-ins and Basic through it are accepted from wherever the proxy took them, and the log says so once an hour ("A reverse proxy on this computer that GOBLIN_TRUST_PROXY does not name sends Uptime Goblin requests with forwarding headers…"). Name it in `GOBLIN_TRUST_PROXY` and serve Uptime Goblin through it over HTTPS.

`GOBLIN_LEGACY_BASIC` takes `1`, `true`, `yes` or `on`, and `0`, `false`, `no` or `off` (any case); empty or unset is the default above. Any other value (a typo such as `of`) refuses the start (exit status 78) before Uptime Goblin writes anything, with "GOBLIN_LEGACY_BASIC must be 1 or 0 (true, yes or on; false, no or off), or empty for the default; it is …": the default on an upgraded install is on, so a value meant as off must never leave it on. The native installer checks the value in `/etc/uptime-goblin.env` before an upgrade changes anything.

To see which scripts still use Basic before you turn it off, open **Configure → Audit log** and choose the kind **Scripts with a password** (the System page links there while Basic is on). The page opens at **Last 7 days**, also from that link: set **Period** to **Last 90 days** or **All kept entries** to see scripts that run less often. There, the first script sign-in of each day gets an entry with its address and user agent, and a summary at the end of the day says how many more there were, from how many addresses, with up to 10 of them. Refused script sign-ins are listed there too, counted by the hour instead: the first of each hour gets an entry at once, and the others of that hour one summary at its end. These days and hours are UTC ones.

## Lockouts

A client that keeps failing is locked out for up to 15 minutes, or until Uptime Goblin restarts. The global lock (50 failed sign-ins in 10 minutes from anywhere) lasts as long as failures keep arriving, and a restart only helps until the next 50. While it holds, browsers that are already signed in keep working (session requests are never throttle-checked), and sign-in from the Uptime Goblin computer itself (the `loopback` transport, [the ssh tunnel](#when-sign-in-is-refused) of a native install that listens on 127.0.0.1 or on every address; not under Docker) is not refused by it. A browser sign-in through a reverse proxy on the same host is never `loopback`: the documented proxy sends forwarding headers, and with `GOBLIN_TRUST_PROXY=loopback` Uptime Goblin counts its clients by their own addresses (the last `X-Forwarded-For` entry). A trusted proxy that does not send `X-Forwarded-For` makes all its clients share the proxy's address, so one client's failures lock out the others; the log says so once an hour ("Requests from the trusted proxy … do not name their client in X-Forwarded-For"), and the fix is `proxy_set_header X-Forwarded-For $remote_addr;`. Either way the Uptime Goblin computer's own lockout (the ssh tunnel) is separate from such a proxy's clients. It is not separate from the clients of a proxy on the Uptime Goblin host that connects to Uptime Goblin at a loopback address and that `GOBLIN_TRUST_PROXY` does not name: everything that connects from a loopback address and that no trusted proxy relays counts against the tunnel's lockout, whatever its Host or forwarding headers say, so they can lock out the ssh tunnel. The global lock holds them, whatever password any of them or the tunnel proved, except those that are the `loopback` transport: the requests of a proxy on the Uptime Goblin host that sends no forwarding headers at all and keeps a loopback Host, trusted or not. Uptime Goblin cannot tell those from the host's own, whatever page address (`Origin`) they carry, so they count against the tunnel's lockout even when the proxy is trusted, and the global lock does not hold them ([the ssh tunnel](#when-sign-in-is-refused) says what the log shows and how to get back in).

Only a correct password makes a client trusted for the global lock (a sign-in, a password change, or a script's Basic): a session cookie used from an address does not, so a stolen or lost device's cookie cannot exempt its addresses from the lock, before or after you sign it out.

An IPv6 client is counted by its /64 network, and on a home or office network every IPv6 device usually has an address in the router's one /64. Those devices are then one client: one lockout (one device's failures lock out the others), one place among the addresses trusted during the global lock (a correct password from one of them makes them all trusted), also through a trusted proxy, which forwards their addresses, and, when they connect to Uptime Goblin directly, one allowance of open connections. [Sign-in throttling](security.md#failed-sign-in-throttling) says how to keep them apart.

## Rollback, restore and recovery

- **Rolling back to 1.4.3 or 1.4.2** needs no preparation and uses the current password: `auth.json` holds it (see the mirror above), unless Uptime Goblin's pages show "Uptime Goblin saved the admin password but could not update auth.json". Until that banner has gone, `auth.json` still holds the previous password, and 1.4.x signs in with it. Fix the disk and wait for the banner to go (or restart 1.5, which tries again at once) before you roll back, above all when you changed the password because the old one may be known. 1.4.x ignores `control.sqlite`. Upgrading again signs in with the same password, and sessions from before the rollback still work, unless the password was changed under 1.4.x meanwhile (then it is imported and every session ends). The code rollback itself is in [rolling back 1.5 to 1.4.3](installation.md#rolling-back-15-to-143).
- **Restoring a snapshot** (`goblin-admin restore-snapshot`, with Uptime Goblin stopped: `sudo -u uptime-goblin env GOBLIN_SECRET_KEY_FILE=/etc/uptime-goblin/secret.key node /opt/uptime-goblin/lib/cli/goblin-admin.mjs restore-snapshot SNAPSHOT_ID --data-dir /var/lib/uptime-goblin` on the native install, with `SNAPSHOT_ID` replaced by an id that `goblin-admin snapshots` lists, see [goblin-admin](installation.md#goblin-admin)) restores the admin password of that time and signs every session out at the next start, including sessions that were revoked after the snapshot was taken. `goblin-admin snapshots` lists them, newest first. The pinned ones hold the data as it was when 1.5 first started on 1.4.x data (or started again after such a snapshot was restored): restoring one returns the data to 1.4.x with that time's password and settings, and removes the [audit log](security.md#audit-log) (export it first: the next start begins a new, empty one). **Restore it while the 1.5 code is still installed, then roll the code back**: `goblin-admin` is part of 1.5, and 1.4.x has none. After a code rollback, run the kept 1.5 copy instead: `sudo -u uptime-goblin env GOBLIN_SECRET_KEY_FILE=/etc/uptime-goblin/secret.key node /opt/uptime-goblin.previous/lib/cli/goblin-admin.mjs restore-snapshot SNAPSHOT_ID --data-dir /var/lib/uptime-goblin` (`/opt/uptime-goblin.failed/…` after the installer rolled an upgrade back by itself), or under Compose the kept 1.5 image ([goblin-admin](installation.md#goblin-admin)). A start takes a snapshot only when it migrates `control.sqlite`, so after a code-only rollback (which leaves `control.sqlite` in place) and an upgrade again, the changes made under 1.4.x in between (a password, settings) are in no snapshot: to keep them, roll the code back instead of restoring.
- **A restore that was interrupted** (a crash or power loss part way through `restore-snapshot`) leaves the data directory part restored: Uptime Goblin 1.5 then refuses to start (exit status 78) with "A restore of snapshot <id> was interrupted part way…" and the command to run. Run the same `restore-snapshot` again, with Uptime Goblin stopped; it finishes the restore, keeps what the data directory held before the first attempt as the pre-restore snapshot (restore that to undo both), and Uptime Goblin starts. If it says that an earlier restore was interrupted too, run that one again as well before you start Uptime Goblin. 1.4.x does not check for an interrupted restore, so after a code rollback keep it stopped (the documented commands disable the service) until the restore has finished; a password, settings or readings it wrote in between are kept in a snapshot of their own, which the re-run names, not deleted. A restore replaces `auth.json` in one step, so it is never missing part way and 1.4.x does not start without a password on a half-restored directory.
- **A damaged database** (a disk error: Uptime Goblin stops with "file is not a database") is no obstacle to restoring a snapshot: `restore-snapshot` moves the damaged `control.sqlite` or `history.sqlite` aside as it is, with its `-wal` and `-shm` files, and says so. The pre-restore snapshot that keeps it cannot be restored as a whole; copy its other files back by hand if you need them.
- **A forgotten password** is recovered as in 1.4.2: stop Uptime Goblin, move `auth.json` aside, set `GOBLIN_PASSWORD`, start. Uptime Goblin imports it and signs every session out. See [forgotten password](troubleshooting.md#forgotten-uptime-goblin-password).

## A password is always required

Uptime Goblin always requires the admin password. A start with neither `auth.json` nor `GOBLIN_PASSWORD` is refused (exit status 78) before anything is written: "Uptime Goblin needs an admin password, and none is set: the data directory has no auth.json, and GOBLIN_PASSWORD is not set or is empty. Set GOBLIN_PASSWORD (12 to 1024 characters) in Uptime Goblin's environment file (/etc/uptime-goblin.env for a native install, where the installer sets one; .env for npm start and Docker Compose), then start Uptime Goblin again. If Uptime Goblin had a password before, restore auth.json from a backup instead, or set GOBLIN_PASSWORD: it becomes the admin password and signs out every session." Uptime Goblin never makes a password up: the native installer writes one into `/etc/uptime-goblin.env` when it installs Uptime Goblin, and for `npm start` and Docker Compose you set it in `.env` (`.env.example` has the line).

Without a credential (a session cookie, or a script's [legacy Basic](#scripts-and-legacy-basic)) every request is answered 401 `signin_required`, from the Uptime Goblin computer itself too, whatever headers it sends. Only the sign-in page and its files, the sign-in itself and `/health` answer without one.

1.4.x, and earlier 1.5 pre-releases, started without a password as a _local preview_: on loopback only, with no sign-in, every request from the Uptime Goblin computer was the admin's. That is gone. Before you upgrade such an install, set `GOBLIN_PASSWORD`; the first start with it makes it the admin password. A data directory that had a password and lost its `auth.json` is refused the same way: restore `auth.json`, or set `GOBLIN_PASSWORD` (it becomes the admin password and signs out every session). Deleting `control.sqlite`, or restoring the newest pinned pre-1.5 snapshot (see [goblin-admin](installation.md#goblin-admin)), does not let Uptime Goblin start without a password either. Either way also removes the [audit log](security.md#audit-log): the next start begins a new, empty one, which lists no restore. It removes the sessions, the webhook signing key (with a webhook set, Uptime Goblin makes a new one, whose public key receivers need) and the notifications waiting and their history too. If you must start over with a new `control.sqlite`, do not delete the old one: with Uptime Goblin stopped, move it, with its `-wal` and `-shm` files, into a private folder outside the data directory and keep it. `goblin-admin verify-audit --data-dir <that folder>`, with the same key, still checks the old log there. A new `control.sqlite` does not turn [legacy Basic](#scripts-and-legacy-basic) on for an install created by 1.5: keep `created-by.json`, which says 1.5 created the data directory.

## Wall displays

A wall display signs in with a one-time **display code**, not the admin password. It then reads the dashboard and nothing else: no **Configure**, no Add source, pause or Refresh, no Account page, and no way to sign other sessions out or change the password. It stays signed in for up to 30 days, as long as it reads Uptime Goblin at least once every 7 days: a display that refreshes is in use, whether anyone looks at it or not. Each display's history charts may take at most 2 seconds of Uptime Goblin's work at once and then 100 ms for every second, so a stolen display cookie that keeps asking for 30-day charts cannot slow every other request: beyond that it is answered 429 `history_limited` with `Retry-After`, and the display keeps the chart it drew and asks again at its next refresh. A display asks for one chart at a time, at most every 15 seconds, well inside that limit.

1. On the Uptime Goblin host, create a code and name the display (the name shows in the sessions list and the audit log). It needs the key Uptime Goblin uses, as the [key commands](installation.md#goblin-admin) do:

   ```sh
   sudo -u uptime-goblin env GOBLIN_SECRET_KEY_FILE=/etc/uptime-goblin/secret.key node /opt/uptime-goblin/lib/cli/goblin-admin.mjs display code --name "Lobby TV" --data-dir /var/lib/uptime-goblin
   ```

   Under Docker Compose: `docker compose exec uptime-goblin node lib/cli/goblin-admin.mjs display code --name "Lobby TV"` (with `compose.secret.yaml`, give it that file as for the key commands). The code is printed once, in five groups of five letters and digits and a sixth of one, and works once, within 10 minutes. Uptime Goblin keeps only its hash, and refuses to print it into systemd's journal. Never use `docker compose run` to create a code: Docker retains that container's output. Creation requires a matching running Uptime Goblin server inside the container (`exec`); an unknown process state is refused. For a native systemd credential, use `systemd-run --pipe`, not journal-backed service output. After restoring or copying the data directory, start Uptime Goblin once before creating a code. Password imports cancel waiting codes, and detected restores remove all display records.

2. On the display, open Uptime Goblin's address with `?kiosk=1` added (its HTTPS address when it has one, for example `https://goblin.example.com/?kiosk=1`) and type the code under **Set up this wall display**. Letter case, spaces and hyphens do not matter, and `I`, `L` and `O` are read as `1`, `1` and `0`. The page checks the last character before sending the code, so any single mistyped character, and any two characters swapped, is caught there without counting as an attempt.

A display needs a keyboard for this: a USB or Bluetooth one, an on-screen keyboard, or its kiosk browser's remote input. It needs one again at least every 30 days. On `?kiosk=1` the sign-in page offers only the code form: to sign in with the admin password, open Uptime Goblin's address without `?kiosk=1`.

A code is accepted over HTTPS, from a browser on the Uptime Goblin host itself, or over plain HTTP where `GOBLIN_INSECURE_HTTP_SESSIONS=1` allows sign-in that way; there the page says the code crosses the network unencrypted. Sent over plain HTTP otherwise, it is refused and cancelled, since it crossed the network unencrypted: create a new one. A code that was used, has expired or was cancelled is refused without counting as a guess; a code Uptime Goblin never made counts toward the [lockout](#lockouts) like a wrong password.

Up to 10 codes can wait at once. `goblin-admin display list` shows the codes Uptime Goblin still keeps (waiting, used and the session each became, cancelled; never a code), `goblin-admin display cancel <id>` cancels one (the id is printed with the code), and `goblin-admin display cancel --all` every waiting code; none of them needs the key. A cancel without the key is written to the audit log by Uptime Goblin within the hour. Changing the admin password cancels every waiting code and signs every wall display out, like every other session.

`GOBLIN_DISPLAY_SESSION_DAYS` (1 to 30, default 30) and `GOBLIN_DISPLAY_IDLE_DAYS` (1 to 7, default 7) shorten a display's limits; empty is the default, and a longer value refuses the start ([configuration](configuration.md#environment-settings)). A display signs in again at least every 30 days: in its last 3 days it says by when. When its session ends, its page starts again at **Set up this wall display**: create a new code. Sign a display out under **Configure → Account** (it is listed as _Wall display "Lobby TV"_) when it is moved, lost or replaced; **Sign out other devices** signs every display out too.

A display still holds a session: whoever can use its browser can read the dashboard (source names, readings, alerts and events; never source addresses, credentials, error texts or the audit log), until it is signed out. Sources with **Show this source on the dashboard** unticked are left out of what it reads.

A `?kiosk=1` page signed in with the admin password, as wall displays were before display codes, shows a banner offering **Set up**: it signs the display out, and the page then asks for a code. Until then it keeps every right the admin has, and since a `?kiosk=1` page marks every read it makes as background, it is signed out after 12 hours without use, and after 30 days at most. Once signed out it shows the code form, never the password form. To move such displays over:

1. If people you do not fully trust could use a display, change the admin password first. It ends every session.
2. In each display browser, delete saved logins for Uptime Goblin's address and clear cached 1.4.x Basic authentication: clear the site's data, or close every window.
3. Create a code for each display and type it there.
4. Each display then needs a new code at least every 30 days.

After an upgrade, if wall displays are signed in, Uptime Goblin says how many at its start: an earlier release that ran in between could not show or sign them out, so check **Configure → Account → Sessions**.

## The audit log

Every sign-in and sign-out, every session you sign out or that a password change, a restore or a start ends, and every password change is recorded in the [audit log](security.md#audit-log) (**Configure → Audit log**), with the session, the address and the browser. A sign-in and its entry are saved together, so a disk that cannot take the entry refuses the sign-in as it would refuse the session; a sign-out that cannot be saved with its entry is made without it. Refused sign-ins and password changes are counted rather than listed one by one, and the login name typed at a refused sign-in is kept only as "admin" or "another name".

## Still to come

**Still to come before 1.5.0 is released:** failed-sign-in counts and trusted clients kept across restarts, device cookies, and a `goblin-admin` command that signs out every session. This build has none of them: a restart clears failed-sign-in counts and trusted clients, and no command on the Uptime Goblin host ends sessions. End them from a signed-in browser (**Configure → Account**) or a script (`DELETE /api/account/sessions`, which with legacy Basic ends every session: [the HTTP API](architecture.md#http-api)), by a password change, by an imported password or by a restore. Turning `GOBLIN_INSECURE_HTTP_SESSIONS` off ends the sessions signed in over plain HTTP at the next start.

Planned for later releases: named users and roles, multi-factor authentication, API tokens, single sign-on (OIDC and forward authentication), creating display codes from the web page, and `goblin-admin` password reset and unlock.
